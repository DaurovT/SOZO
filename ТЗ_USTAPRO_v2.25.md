# Техническое задание: платформа технического сервиса (Ташкент)
**Версия:** 2.25 (проект для оценки разработчиками; решения владельца продукта внесены — см. раздел 18 и «Историю версий»)
**Дата:** июль 2026
**Состав продукта:** мобильное приложение «Клиент» (Flutter, iOS/Android), мобильное приложение «Мастер» (Flutter, iOS/Android), веб-панель «Диспетчерская», веб-панель «Админ», бэкенд с API, биллингом и генератором отчётов.
---
## 1. Концепция и цели
Платформа автоматизирует полный цикл оказания услуг мелкого и среднего ремонта: от создания заявки до автоматически сформированного отчёта с фотофиксацией и финансовой разбивкой.
**Главные продуктовые принципы (нарушать нельзя):**
1. **Заявка — центральная сущность системы.** Биллинг, отчёты, техдолг, рейтинги, выплаты мастерам — всё это производные от жизненного цикла заявки. Ни одна цифра не вносится в систему дважды.
2. **Фотофиксация — условие перехода статуса, а не пожелание.** Мастер физически не может закрыть заявку без фото «после» и чеков на материалы.
3. **Ни одна платная работа не выполняется без санкции клиента.** Санкция даётся либо «оптом» (лимит точки в договоре), либо поштучно (кнопка «Утвердить» в приложении). Единственное исключение — аварийная локализация. Для B2C санкцией считается явное подтверждение сметы клиентом в приложении (или устно диспетчеру с записью в аудит — для заявок, созданных по телефону).
4. **Отчёт — побочный продукт правильно закрытой заявки.** Если цикл соблюдён, отчёт генерируется одной кнопкой без ручной сборки.
5. **Деньги мастера считаются от базового B2C-прайса**, а не от цены, по которой платит клиент. Скидки клиентам — коммерческое решение компании, мастер от них не страдает.
**Бизнес-модели, которые обслуживает платформа:**
- **B2C** — разовые вызовы физлицами, оплата Payme/Click/Uzum/карта/наличные.
- **B2B разовая** — заявки юрлиц без договора, цена = B2C + наценка (по умолчанию +30%), оплата по счёту.
- **B2B абонентка** — фиксированная сумма в договоре в месяц; работы списываются из неё по подписным ценам: **«B2B разовая» минус скидка подписки 10%** (эффективно ≈ B2C × 1.17 — решение владельца v2.23: скидка юрику считается от разовой цены юрика, не от розницы физика; подписчик платит дороже физика, но дешевле разового юрика); всё сверх абонентки закрывается отдельной счёт-фактурой в конце месяца по ценам «B2B разовая» без скидки; плановые осмотры входят.

## 2. Роли и участники
### 2.1. Стороны
| Сторона | Описание |
|---|---|
| Компания (мы) | Оператор платформы, бренд, получатель денег клиентов, плательщик мастерам |
| Организация (B2B-клиент) | Юрлицо с договором: сеть аптек, ресторан, БЦ, гостиница. Имеет 1..N точек |
| Точка | Физический объект организации (конкретная аптека, конкретный ресторан). Носитель лимитов и техдолга |
| Физлицо (B2C-клиент) | Частный заказчик без договора |
| Мастер | Исполнитель. Самозанятый/ГПХ, работает за долю |
### 2.2. Роли пользователей и приложения
| Роль | Приложение | Краткое описание прав |
|---|---|---|
| Клиент B2C | Клиент (моб.) | Создаёт свои заявки, оплачивает, видит свою историю |
| Сотрудник точки | Клиент (моб.) | Создаёт заявки от имени своей точки, следит за статусом. Денег и цен сверх лимита не видит (настраивается) |
| Руководитель точки | Клиент (моб.) | Всё по своей точке: заявки, утверждение в пределах своего порога, техдолг точки, отчёты точки |
| Руководитель организации (АХО/директор сети) | Клиент (моб.) | Все точки организации: утверждение сверхлимитных смет, пакетное утверждение дефектов с осмотров, лимиты точек, отчёты, счета |
| Владелец организации | Клиент (моб.) | Режим «только наблюдение»: дашборд по всем точкам, деньги, техдолг, без операционных кнопок (настраивается) |
| Мастер | Мастер (моб.) | Свои заявки, фиксация работ/фото/материалов, свой заработок |
| Диспетчер | Веб | Все заявки: назначение, контроль, проверка фото, споры, звонки |
| Бухгалтер компании | Веб | Биллинг: СФ, акты, сверки, выплаты мастерам, без операционки заявок |
| Админ (владелец платформы) | Веб | Всё: прайс, коэффициенты, организации, договоры, пользователи, балансы, настройки |
**Важно:** роль — свойство аккаунта, а не отдельное приложение. Один человек может иметь несколько ролей (руководитель точки + сотрудник другой точки); при входе выбирает контекст. Клиентское приложение одно, интерфейс собирается по роли.
### 2.3. Иерархия B2B и наследование прав
```
Организация (договор, абонентка, ЭДО-реквизиты)
 └── Точка 1 (лимиты, техдолг, адрес, график доступа)
      ├── Сотрудники точки (создание заявок)
      └── Руководитель точки (утверждение до порога)
 └── Точка 2 ...
 └── Руководитель организации (утверждение сверх порогов, управление лимитами)
 └── Владелец (наблюдение)
```
Пример из жизни: фармацевт сетевой аптеки видит поломку → создаёт заявку с фото → если оценка в пределах лимита точки, мастер выезжает автоматически → платит в итоге организация с абонентки → директор сети видит всё в своём дашборде и утверждает только то, что дороже лимита.

## 3. Модель данных (основные сущности)
Ниже — логическая модель. Детальную физическую схему БД проектирует бэкенд-архитектор, но состав полей обязателен.
### 3.1. Organization (Организация)
- id, название, ИНН, реквизиты, юр. адрес
- признак плательщика НДС и ставка НДС (для строк СФ; ставка — параметр системы)
- тип договора: `абонентка` / `разовые по счёту`
- абонентская сумма/мес, дата начала, день автосписания начисления (по умолч. 1-е)
- коэффициент подписки (наследует глобальный, можно переопределить в договоре)
- наценка B2B разовая (наследует глобальный, можно переопределить)
- перенос остатка: `нет` / `до N% на след. месяц` (параметр договора)
- статус: активна / приостановлена (неоплата) / расторгнута
- контакты для эскалаций (телефон директора — для аварий и молчания по сметам)
### 3.2. Location (Точка)
- id, organization_id, название, адрес, геокоордината, фото фасада, city_id (задел мультигорода, см. 17.4)
- тип объекта (аптека / ресторан / офис / БЦ / гостиница / склад…) — определяет шаблон чек-листа осмотра и базовые ставки калькулятора абонентки (17.2)
- график доступа (когда мастер может приехать), порядок доступа (ключ у охраны, пропуск), контактный телефон точки, контакты ТСЖ/УК здания и порядок доступа к общим зонам (стояки, подвал, крыша) — заполняется при первом осмотре, экономит холостые выезды
- флаг «фото запрещено» (режимный объект): вместо фото «до/после» — обязательный код приёмки + подпись представителя, отметка в акте (см. 4.1)
- предпочтительный мастер точки (закреплённый — знает объект, планировщик даёт ему мягкий приоритет) и чёрный список мастеров точки (после конфликта — не назначаются)
- **лимит на заявку** (авто-старт без утверждения), сум
- **месячный лимит точки**, сум (сумма авто-стартовавших заявок за месяц; при исчерпании все заявки идут на утверждение)
- счётчики месяца: израсходовано авто-стартом, всего работ за месяц
- паспорт объекта: площадь, число санузлов, кондиционеров (модель/год), щитков — заполняется при первом осмотре, нужен мастерам и для расчёта абонентки при продлении
### 3.3. User (Пользователь)
- id, телефон (логин, вход по OTP-SMS), ФИО, фото (мастера — обязательно), язык интерфейса (рус/узб)
- роли: список привязок {роль, organization_id?, location_id?}
- для мастера: skill-теги (сантехника, электрика, кондиционеры/фреон, сварка, малярка, слаботочка…), зоны выезда (районы Ташкента), статус (кандидат/на линии/выходной/отпуск/заблокирован), рейтинг, график работы и отпуска (17.3), статус онбординга (17.1), **дата активации (устройства) и стаж**, **договор: номер, тип, дата подписания, срок действия и дата окончания** — ГПХ-договор срочный: за N дней до истечения (параметр, по умолч. 14) — задача на перезаключение, работа по истёкшему договору — блокирующий флаг в ведомости выплат (юридический риск), **архив документов** (скан паспорта, подписанный договор, согласие на публикацию для страницы верификации — доступ только админу), налоговый режим (самозанятый / ГПХ — определяет удержания в ведомости, 8.6), транспорт (свой авто с инструментом / без авто — фильтр для заявок, требующих машину или крупное оборудование), предпочтительный напарник для парных работ (мягкий приоритет планировщика)
### 3.4. Order (Заявка) — центральная сущность
- id, номер (человекочитаемый: `Z-2026-000123`)
- тип: `B2C` / `B2B` / `гарантийная` (ссылка на исходную) / `из осмотра` (ссылка на дефект) / `осмотр плановый`
- срочность: `обычная` / `аварийная`
- источник: приложение / телефон (создал диспетчер) / Telegram-бот (фаза 3)
- клиент: user_id (B2C) или location_id (B2B), кто создал (user_id)
- категория услуги, позиции прайса [{price_item_id, qty, цена на момент заявки}] — цены **фиксируются копией**, чтобы изменение прайса не меняло старые заявки
- описание, фото клиента при создании (до 5)
- желаемое время, назначенное окно (двухчасовой слот)
- мастер: user_id, история переназначений
- связанные заявки (дробление крупной работы на нескольких специалистов, см. 4.5)
- скидка/промокод (поле закладывается в модель сразу, даже если маркетинг вне скоупа MVP — чтобы потом не ломать биллинг)
- статусы (см. раздел 4) + журнал переходов (кто, когда, откуда/куда)
- смета: оценка первичная, утверждённая, доп-сметы [{сумма, статус утверждения, кто утвердил, когда}]
- фото: «до» (мин. 1, обяз.), «в процессе» (опц.), «после» (мин. 1, обяз.) — каждое фото с серверным таймштампом и геометкой (гео может отсутствовать — подвал/техпомещение; тогда флаг «без гео»)
- материалы: [{название, кол-во, цена, фото чека}] — см. 8.4
- итог: стоимость работ, стоимость материалов, способ оплаты, канал списания (абонентка / сверхлимит-СФ / онлайн / наличные)
- гарантийный срок на момент закрытия (копия параметра, по умолчанию 30 дней)
- оценка клиента (1–5 + комментарий), отметка «спор»
### 3.5. Defect (Дефект / позиция техдолга)
- id, location_id, найден в заявке-осмотре (order_id), мастер
- описание, фото (обяз.), категория
- оценка устранения (позиции прайса + сумма), срок актуальности оценки (30 дней, потом требует переоценки)
- приоритет: `критичный` (угроза аварии/безопасности) / `высокий` / `средний` / `низкий`
- статус: `новый` → `на утверждении` → `утверждён` (порождает Order) / `отложен` (до даты) / `отклонён` / `устранён` (ссылка на закрывшую заявку)
### 3.6. Биллинговые сущности
- **SubscriptionAccount** — счёт абонентки организации: начисления, списания, остаток, перенос
- **Invoice (СФ)** — счёт-фактура: период, организация, строки (заявки сверх абонентки, материалы, разовые), суммы с выделением НДС (если организация — плательщик), статус (draft/отправлена/оплачена/просрочена), связь с ЭДО
- **MasterBalance** — баланс мастера: начисления долей, возмещения материалов, удержания (штрафы, гарантийные переделки), принятые наличные (долг мастера перед компанией), выплаты
- **Transaction** — универсальная проводка: дата, тип, сумма, дебет/кредит (счёт клиента/мастера/компании), ссылка на заявку/СФ. Всё движение денег — только проводками, никаких «правок цифр в полях»
- **Receivable (дебиторка)** — учётная запись долга контрагента (организация / B2C-клиент): источник (СФ, ложный вызов, неоплаченная заявка), сумма, погашено, возраст долга, этап взыскания (см. 8.9)
- **PartnerStore** — партнёрский магазин: реквизиты, категории товаров, кредитный лимит компании, период погашения реестра, условия скидки/ретро-бонуса; счёт кредиторки компании перед магазином (см. 8.4.4)
- **PurchaseCode** — одноразовый код закупки: заявка, лимит суммы, срок жизни (4 ч), статус (выдан/использован/просрочен), магазин, накладная (фото + позиции)
### 3.7. PriceList (Прайс)
- позиции: категория, название, ед. изм. (шт/точка/п.м/м²/час/выезд/объект/стык/створка/заявка/день/комплект), цена B2C от/до, **нормативная длительность (нормо-часы)** — основа расчёта слотов и загрузки мастеров (17.3), признак «требует skill-тег», признак «требует оборудование» (17.9), активность
- **этапные позиции** (малярка, стяжка, герметизация, монтаж с заливкой): план этапов — [{этап, нормо-часы, технологическая пауза после}]; цена за работу целиком, выезды сессий включены; планировщик бронирует все сессии при назначении (4.1)
- **парные позиции** (признак «требует 2 исполнителей»): демонтаж/монтаж тяжёлого оборудования, ванны, потолочные и крупногабаритные работы. Цена позиции уже включает второго человека; деление долей — по ролям (17.3)
- лицензируемые виды работ (газовое оборудование, лифты) в прайс не включаются до решения юридического вопроса (см. Открытые вопросы)
- глобальные коэффициенты: наценка B2B разовая, коэффициент подписки, наценка аварийности, доля мастера, минимальный чек, стоимость выезда/диагностики, стоимость планового осмотра, стоимость консервации (безопасное отключение/перекрытие при отказе от вынужденных работ, 4.6), коэффициент срочности тарифа «Срочно» (по умолч. +30%, снимается при неначале за 3 ч — 17.3)
- **порядок применения коэффициентов (единая формула):** цена клиента = базовая B2C × наценка (аварийная / ночная / срочная — одна наибольшая, 17.6a; только к работам, не к материалам) × канальный коэффициент (B2C = 1.0 / B2B разовая = 1.3 / подписка = 1.3 × (1 − скидка подписки 10%) ≈ 1.17) − скидка/промокод (применяется последней, к итогу работ клиента). Доля мастера — от базовой × наценки: скидки клиенту долю мастера не трогают (принцип 5), наценки — увеличивают (за аварию и ночь мастер получает больше, иначе никто не поедет)
- **минимальный чек:** если сумма работ ниже минимума, в смету добавляется позиция «Минимальный заказ» с добивкой до минимума — клиент видит её до утверждения
- **выезд:** при выполнении работ отдельно не тарифицируется (включён в стоимость), при отказе от работ после выезда — тарифицируется (параметр). Для заявок-диагностик: если после диагностики в ту же заявку добавляются работы, позиция «Выезд/диагностика» снимается — зачитывается в стоимость работ
- **диагностика с отложенным выполнением (объём большой, работа в другой день):** клиент на первом выезде платит только диагностику; при выполнении утверждённой на осмотре сметы (вторым выездом, в течение 30 дней — параметр) **диагностика зачитывается**: счёт за работу = смета − уплаченная диагностика, в акте отдельная строка «зачёт диагностики». Итог для клиента — та же цена, как если бы всё сделали сразу; дважды за выезд не платит никто. Отказался от работ — оплаченной остаётся только диагностика. Доля мастера — с фактически оплаченных сумм: с диагностики при первом выезде, с остатка при выполнении (если выезды делали разные мастера — каждому со своей части)
- **версионирование — релизы прайса (PriceListRelease).** Единица изменения цен — не отдельная позиция, а **релиз**: полный снапшот позиций **и глобальных коэффициентов** со статусами черновик → запланирован (дата активации, 00:00 Ташкента) → активен → архив; автор, комментарий («сезон кондиционеров лето-2027»), diff с текущим релизом перед активацией. Импорт из Excel создаёт черновик релиза, а не правит боевой прайс. Валидатор unit-экономики гоняется по всему релизу и блокирует активацию, если хоть одна позиция ниже порога маржи. **Откат** — новый релиз из снапшота предыдущего; история неизменяема, активные релизы не редактируются. Крупный релиз (изменено > 20% позиций или любая цена > 30% — параметры) требует **подтверждения второго админа** — как ручные проводки (8.6)
- **правила фиксации (решение владельца: изменение прайса никогда не пересчитывает действующее и прошлое):** какой релиз фиксирует заявка при создании — зависит от источника: **B2C и B2B-разовая — активный релиз на момент создания; заявка организации с договором — релиз договора** (включая сверхлимитные и тариф «Срочно» — иначе годовая заморозка цен ломалась бы первым же обновлением прайса); **заявка, порождённая дефектом** (осмотр, отклонённые вынужденные работы, отложенные апсейлы), наследует релиз оценки дефекта, пока оценка младше 30 дней (3.5) — утверждённая руководителем сумма и смета заявки не могут разойтись; **гарантийная заявка/переделка наследует релиз исходной заявки** (оплата мастеру-переделщику и удержания у виновного считаются в ценах исходной работы — консистентно с копией гарантийного срока). Все сметы, доп-сметы, консервации и переоценки внутри заявки считаются из её релиза, сколько бы заявка ни ждала в листе ожидания; созданные, но не начатые заявки при активации нового релиза **не переоцениваются никогда**. Исключения: оценка дефекта старше 30 дней — переоценка по текущему релизу (3.5); расходники «сумки» — по каталогу на момент списания (возмещение мастеру по текущим ценам, 8.4.3). Глобальные коэффициенты фиксируются копией в заявке при создании; доля конкретного мастера с учётом грейда — на момент назначения
- **B2B-договор и релизы (решение владельца):** два срока договора — **годовой** и **месячный** (параметр договора). Любой договор фиксирует релиз прайса **на дату подписания/продления**, пересмотра цен внутри срока нет никогда. Годовой: цены заморожены на весь год — торговый аргумент для сетей. Месячный (авто-продление): при каждом продлении договор переводится на текущий релиз — фактически ежемесячный пересмотр цен. Перевод на новый релиз происходит **только** событием продления, с авто-отчётом «что изменилось в ваших ценах»; если к дате продления действует новый релиз — организация уведомляется за N дней до продления (параметр, по умолч. 10). В уведомлении — **явная опция «не продлевать»** (отказ = расторжение с даты окончания срока по обычной механике; зачёт остатка абонентки работами в течение 60 дней, 18 п.5, — по релизу последнего действовавшего договора) и **рекомендация индексации** лимитов точек и абонентской суммы (при росте цен фиксированные сум-лимиты пробиваются чаще и абонентка выбирается быстрее — эрозию ловит и B2B-ритм 17.11; изменение сумм — только с согласия руководителя организации, в аудит). **Правило исполнимости уведомлений:** дата активации релиза — не раньше чем через M дней (7) после подтверждения (иначе уведомление мастерам невозможно); к продлению договора новый релиз применяется, только если организация была уведомлена за ≥ N дней — иначе продление проходит на прежнем релизе, перевод на новый — со следующего продления. Исключение — откат (возврат цен), применяется немедленно. **Релиз №1** (стартовая миграция, 17.6) имеет флаг «стартовый»: активируется без diff и второго подтверждения; импортируемые действующие договоры при миграции явно помечаются «переведён на релиз №1 по согласованию» — либо для договора создаётся снапшот его бумажного прайса
- **уведомления о релизе:** мастерам — за M дней (параметр, по умолч. 7) о смене цен по их skill-категориям (доля в сумах изменится — узнать из упавшей выплаты недопустимо); организациям — за N дней до продления, если цены изменятся; клиентские приложения инвалидируют кеш цен «от» по событию активации релиза
- **валидация unit-экономики:** при сохранении коэффициентов админка предупреждает, если маржа компании по подписке (коэффициент подписки − доля мастера − отчисление в резервный фонд ущербов 17.7 − норматив комиссий провайдеров) ниже настраиваемого порога — защита от конфигурации «работаем в минус»; для позиций со спецоборудованием — проверка покрытия амортизации (17.9)
### 3.8. Прочее
- **InspectionSchedule** — график плановых осмотров точек (порождает заявки-осмотры автоматически)
- **MasterStock («сумка мастера»)** — количественный учёт расходников у мастера: позиция, кол-во, себестоимость; нормативы min/max по skill-тегу (см. 8.4.2, фаза 2)
- **ToolChecklist** — справочник обязательного инструмента по skill-тегу + отметки проверок комплектности (онбординг и выборочные)
- **ConsumableCatalog / SparePartCatalog** — каталог расходников (фиксированная цена списания) и каталог типовых запчастей (ориентировочные цены эконом/стандарт/премиум)
- **Equipment** — парк оборудования компании: инвентарный учёт, выдача мастерам, амортизация, ТО (см. 17.9)
- **Complaint** — жалобы и обращения: типы, SLA, плейбук решений, корневые причины (см. 17.10)
- **AuditLog** — каждое значимое действие: кто, что, когда, с какого устройства/IP. Особенно: утверждения смет, изменения лимитов, изменения прайса, ручные проводки
- **NotificationLog** — все отправленные уведомления со статусом доставки
- **ContactLog** — голосовые контакты диспетчер↔клиент: триггер, задача-звонок, SLA, исход, следующий шаг (см. 17.11)
- **ClientAsset** — паспорт техники клиента: тип, бренд, модель, год, фото шильдика, история работ по единице (см. 17.12)
- **ServiceInterval** — справочник регламентных интервалов и сезонных окон по типам техники (см. 17.12)

## 4. Жизненный цикл заявки (статусная модель)
Это сердце системы. Переходы разрешены только по схеме, каждый переход пишется в журнал.
### 4.1. Статусы
| № | Статус | Кто переводит | Обязательные условия перехода |
|---|---|---|---|
| 1 | Новая | клиент/сотрудник точки/диспетчер | описание + категория; для B2B — фото желательно, для аварийной — не обязательно |
| 2 | Оценена | система/диспетчер | позиции прайса подобраны, сумма первичной сметы зафиксирована |
| 3 | На утверждении | система | B2B: смета > лимита точки, или заявка из осмотра, или доп-смета. B2C: подтверждение сметы клиентом на месте (пуш «Подтвердите стоимость», см. 6.1) — тоже фиксируется как утверждение в аудите |
| 4 | Утверждена | руководитель точки/организации (B2B) / клиент (B2C) | нажата кнопка «Утвердить»/«Согласен» (пишется в аудит) |
| 5 | Назначена | система (авто) / диспетчер | выбран мастер, подтверждено окно времени |
| 6 | Мастер выехал | мастер | кнопка «Выехал», клиенту уходит push с ETA и карточкой мастера |
| 7 | В работе | мастер | **загружено фото «до» (мин. 1)**; мастер на месте (гео-проверка ±300 м, мягкая — при несовпадении флаг диспетчеру, не блок) |
| 8 | Доп-согласование | мастер | вскрылись доп. работы: фото + позиции → push утверждающему; работа по согласованной части продолжается |
| 9 | Выполнена | мастер | **фото «после» (мин. 1)** + все материалы внесены с чеками + итоговая сумма = утверждённой (или утверждена доп-смета) |
| 10 | Проверена | диспетчер | просмотрены фото до/после, чеки; несоответствие → возврат в «В работе» с комментарием. Если оплата уже принята на месте — возврат её не отменяет: недочёты закрываются доработкой или спором |
| 11 | Ожидает оплаты | диспетчер | **исключение, а не норма:** B2C-оплата собирается на месте до ухода мастера (7.1, шаг 6); отпустить заявку без оплаты может только диспетчер (санкция с причиной). Таймер напоминаний (24 ч push, 72 ч SMS); при неоплате — долг аккаунта, новые заявки блокируются (параметр) |
| 12 | Закрыта | система | проведён биллинг: списание с абонентки / включение в СФ / онлайн-оплата получена / наличные зафиксированы за мастером. Начислена доля мастера |
| 13 | Оценена клиентом | клиент | опционально, окно 72 часа, влияет на рейтинг мастера |
Для B2B и наличных B2C статус «Ожидает оплаты» пропускается (канал списания известен на момент проверки).
**Особые ветки по типам заявок:**
- **«Не знаю, что сломалось» / диагностика:** первичная смета = позиция «Выезд/диагностика». Клиент утверждает только её; объём работ мастер оформляет на месте как доп-смету (механизм п. 8). Это штатный, а не исключительный сценарий — половина B2C-заявок будет такой.
- **Осмотр плановый:** без сметы и утверждения; ветка Новая → Назначена → Выехал → В работе → Выполнена → Проверена → Закрыта. Вместо фото «до/после» — заполненный чек-лист осмотра; результат — дефекты (3.5). Условие перехода в «Выполнена» — зафиксирован представитель точки (подтверждение кодом/подписью) либо явный fallback «представитель отсутствовал» с фото (9.3).
- **Гарантийная:** смета для клиента = 0, статусы «На утверждении»/«Утверждена» пропускаются, биллинг клиенту не начисляется (4.2).
- **Пауза «Ожидание материалов»:** для схемы «клиент покупает сам» (8.4) заявка из «В работе» ставится на паузу с датой повторного визита; при возобновлении конвейер продолжается без повторного фото «до».
- **Режимный объект (флаг «фото запрещено» на точке):** переходы «В работе» и «Выполнена» вместо фото требуют код приёмки сотрудника + подпись представителя на экране мастера; в акте — отметка «фотофиксация запрещена режимом объекта». Банки и режимные учреждения иначе не подключить.
- **Дубли:** при создании заявки система проверяет открытые заявки той же точки/адреса и категории за последние 24 ч — предупреждение «похожая заявка уже есть» с возможностью открыть её; диспетчер может слить дубли (причина отмены «дубль»).
- **Многодневная работа:** расчётная длительность больше смены → заявка разбивается на сессии в лентах нескольких дней (17.3); конец каждой сессии — фото «в процессе» + консервация объекта; статус остаётся «В работе» с индикатором числа дней, диспетчер видит возраст.
- **Этапная работа (технологические перерывы):** стяжка сохнет, герметик встаёт, штукатурка схватывается — работа идёт сессиями по несколько часов через день-два. Позиция прайса помечена как «этапная» (3.7): этапы с нормо-часами; у каждой паузы — не точная дата, а **допустимое окно** [минимум; максимум] (пример: стяжка — «не раньше 24 ч, не позже 7 дней») — чем шире окно, тем легче найти слот.
  **Когда бронируются сессии** — в момент, когда состав работ становится известен: (а) этапная позиция выбрана при создании заявки → все сессии бронируются при назначении; (б) работа выяснилась на месте (диагностика → смета) → в момент утверждения сметы система прямо на экране мастера предлагает клиенту слоты следующих сессий из реальной ленты, клиент подтверждает их вместе со сметой.
  **Инвариант: этап 1 не начинается, пока не подтверждены слоты всех следующих этапов в их допустимых окнах.** «Не начинай красить, если некому приехать домазать». Если слотов нет — планировщик до старта предлагает: перенести всю работу на даты, где цепочка складывается; выполнить продолжение сверхурочным слотом с согласия мастера; передать продолжение другому мастеру той же квалификации с разделом доли (параметр, по умолчанию выключено). Продолжения начатых работ стоят высоко в приоритетах очереди (см. ниже) — начатый объект важнее новых броней.
  Между сессиями заявка в паузе «Технологический перерыв» — **мастер в паузе свободен и берёт другие заявки** (пауза не занимает ленту). Конец каждой сессии — фото «в процессе» + отметка этапа. Цена — за работу целиком (за м², за узел), выезды на все сессии включены в позицию и отдельно не тарифицируются. Оплата B2C — на последней сессии (промежуточные сессии — единственное исключение из правила «мастер не завершает визит без оплаты», 7.1 шаг 6); отмена посередине — оплата фактически выполненных этапов (правило 4.4). Все сессии — один мастер; замена — через «раздел заявки» (4.5).
- **Заблокировано третьей стороной:** мастер на месте, но работать нельзя — нет доступа к подвалу/стояку/крыше/щитовой, нужно отключение стояка, ТСЖ/УК говорит «завтра в 10». Мастер жмёт «Нет доступа (третья сторона)»: причина из справочника + фото (закрытая дверь) + время следующей попытки, если оно известно. Заявка — в паузу «Заблокировано», при подтверждённом времени автоматически встаёт якорной в ленту на это время (клиенту и мастеру пуши). Без даты — задача диспетчеру «дозвониться до ТСЖ», эскалация через 48 ч, через 7 дней — решение с клиентом (перенос или закрытие с оплатой факта). Деньги — см. 4.4. **Профилактика (главное):** для категорий, требующих общих зон (стояк, подвал, крыша, щитовая), при создании заявки — чек-лист «нужно отключение стояка / доступ к общим зонам?» с подсказкой решить с ТСЖ заранее и полем «доступ подтверждён на {дата/время}» — заявка планируется на подтверждённое время, холостой выезд не случается.
- **Машины состояний по типам:** допустимые переходы зависят от типа заявки. B2C пропускает статусы 3–4: первичная смета B2C — вилка «от–до», обязательством становится сумма, подтверждённая клиентом на месте (событие «смета подтверждена» внутри «В работе», с аудит-записью). Полный граф переходов по каждому типу (B2C / B2B / аварийная / осмотр / гарантийная / из осмотра) — обязательное приложение к контракту разработки; переходы вне графа отклоняются на уровне API.
### 4.2. Терминальные и особые статусы
- **Отменена** — с обязательной причиной из справочника (клиент передумал / не дозвонились / клиент не пустил / нет мастера / не согласована смета / дубль). Финансовые последствия — см. 4.4.
- **Спор** — открывает клиент (кнопка «Оспорить», окно 72 ч после «Выполнена») или диспетчер. Блокирует начисление доли мастеру до резолюции. Резолюция диспетчера: `в пользу клиента` (переделка/возврат) / `в пользу мастера` / `компромисс` (частичный возврат). Возвраты по онлайн-оплатам проводятся через refund-API платёжного провайдера (Payme/Click/Uzum) со сторнирующей проводкой. Возврат по заявке, оплаченной наличными мастеру, выполняет компания переводом клиенту (не мастер из кармана) — проводка возврата + при вине мастера удержание с его баланса. Всё с комментарием в аудит. Споры на сумму выше порога (параметр) и споры по заявкам, которые вёл тот же диспетчер, эскалируются админу/старшему диспетчеру — диспетчер не судит собственные заявки. Отдельная причина спора: «приехал не тот мастер» (лицо не совпадает с фото в карточке) — разбирается как грубое нарушение, вплоть до блокировки.
- **Гарантийная переделка** — новая заявка типа «гарантийная» со ссылкой на исходную. Клиенту бесплатно в течение гарантийного срока (по умолчанию 30 дней; параметр, копия хранится в заявке). Если диспетчер квалифицирует вину мастера: переделка самим виновным — не оплачивается; переделка **другим** мастером — оплачивается исполнителю как обычная работа (расход компании), а у виновного — удержание из доли (настраиваемо: 0/50/100%). Если вина материала/эксплуатации — оплачивается как обычная. Материалы для гарантийной переделки при вине мастера — за счёт компании с удержанием у мастера 0/50/100% (тот же параметр, что и по работам).
### 4.3. Аварийная ветка
1. Заявка с флагом «аварийная» минует оценку: сразу «Назначена» ближайшему свободному мастеру с нужным skill-тегом (диспетчер видит и может перехватить).
2. Мастер выполняет **локализацию** (перекрыть/обесточить/остановить ущерб). Локализация — фиксированная позиция прайса «Аварийный выезд», списывается без утверждения всегда.
3. После локализации мастер на месте составляет **смету восстановления** (фото + позиции). Если смета ≤ лимита точки — авто-утверждение, продолжает. Если > — статус «На утверждении», push руководству **+ автозвонок диспетчера** контактному лицу для аварий.
4. В договоре: «аварийная локализация выполняется незамедлительно без согласования; восстановительные работы — по утверждённой смете».
### 4.4. Правила отмен и денег при отмене
| Момент отмены | Кто платит и что |
|---|---|
| До «Назначена» | бесплатно |
| После «Назначена», > 2 ч до окна | бесплатно, мастеру заявка снимается без штрафа рейтинга |
| < 2 ч до окна или «Мастер выехал» | клиенту начисляется «ложный вызов» = стоимость выезда из прайса (по умолч. 50 000); B2C — списание/долг на аккаунте, B2B — строка в СФ. Мастеру компенсация 50% выезда из этой суммы |
| После «В работе» (клиент останавливает работы) | оплачивается выезд + фактически выполненная часть по позициям (фиксирует мастер, подтверждает диспетчер); спорные случаи — резолюция диспетчера. Мастеру доля от оплаченной части |
| Клиент не открыл / не пустил | мастер жмёт «Клиент недоступен» → фото двери/фасада + гео → диспетчер прозванивает 15 мин → отмена с «ложным вызовом» |
| Нет доступа: зависимость всплыла на месте (никто не мог знать) | клиент повторный выезд НЕ оплачивает (выезд тарифицируется один раз); мастеру за холостой выезд — компенсация от компании (параметр, по умолч. 50% стоимости выезда) |
| Нет доступа: клиент подтверждал доступ, но не обеспечил (не договорился с ТСЖ) | «повторный выезд» = стоимость выезда в счёт клиента (B2C — к оплате, B2B — строка в СФ); мастеру — доля с него |
| B2B: мастер приехал в подтверждённое окно графика доступа, точка не пустила | строка «холостой выезд» в СФ (как ложный вызов B2B); мастеру компенсация 50% выезда |
| Мастер не вышел на связь / не приехал | автозапуск протокола быстрой замены (17.3): дежурный резерв + бродкаст-оффер, цель — новый мастер за 15 минут; клиенту push сразу. Санкции мастеру — по градации 17.3 |
Материалы, купленные до момента отмены, оплачиваются клиентом по чекам и передаются ему.
Непогашенный долг B2C (ложный вызов, неоплата): создание новых заявок блокируется до оплаты долга онлайн (параметр: блокировать/предупреждать). Исключение — аварийная заявка: принимается при одновременной онлайн-оплате долга либо по санкции диспетчера (потоп не ждёт погашения долга).
### 4.5. Переназначение мастера
Диспетчер может переназначить на статусах 5–8 (причина обязательна: заболел / не успевает / нет навыка / отказ клиента от мастера). История переназначений хранится. Если работа частично сделана первым мастером — диспетчер вручную делит долю (интерфейс «раздел заявки»: % первому, % второму, с аудитом).
По умолчанию одна заявка = один мастер. Работы, физически требующие двух человек (тяжёлый бойлер, чугунная ванна, потолочные работы, крупногабарит), — парные, с ролями «ведущий + помощник» (механика — 17.3, «Парные работы»); деньги делятся по ролям, не пополам. Разные специальности на одном объекте — диспетчер дробит на связанные заявки (поле «связанные заявки» в Order).
### 4.6. Доп-работы на месте: вынужденные и апсейл
Два принципиально разных случая — их нельзя смешивать ни в интерфейсе, ни в правилах.
**Вынужденная доп-работа** — исходную работу невозможно завершить без неё (открыли розетку — кабель сгорел, надо менять линию):
1. Мастер помечает доп-смету типом «вынужденная» → обязательные фото проблемы + позиции; где осмысленно — два варианта: минимальный (безопасная времянка / частичный ремонт) и полный (замена линии целиком)
2. **B2C:** пуш клиенту с фото и вариантами — клиент решает со своего телефона, даже стоя рядом с мастером (анти-подделка согласий); заявка, созданная по телефону, — устное согласие фиксирует диспетчер в аудит. **B2B:** красный флаг утверждающему, короткие таймеры 5.3 (30 мин повтор, 2 ч звонок диспетчера)
3. Согласие → доп-смета утверждена, работа продолжается по выбранному варианту
4. Отказ (или молчание B2B по таймерам): мастер выполняет **консервацию** — безопасное отключение/перекрытие (фиксированная позиция прайса, аналог аварийной локализации; в B2B списывается без утверждения как обязательная мера безопасности). Заявка завершается с флагом «выполнена частично»: оплата = выезд + фактически сделанное + консервация; в акте — фото проблемы и запись «клиент предупреждён об опасности, от работ отказался» (юридическая защита — та же логика, что с отклонёнными дефектами)
5. **B2B:** отклонённая или неутверждённая вынужденная работа автоматически становится **дефектом в техдолге точки** — с уже готовой оценкой и фото; руководитель утверждает позже из техдолга, ничего не пропадает
**Апсейл (рекомендация)** — исходная работа выполнима, но мастер видит полезное «заодно» (меняем смеситель — подводка на ладан дышит):
1. Отдельная кнопка «Рекомендовать» (это НЕ доп-смета): фото + позиции + комментарий. Не блокирует конвейер и не влияет на завершение исходной работы
2. **B2C:** предложение приходит клиенту в приложение — «Принять» (становится утверждённой доп-сметой, мастер делает сейчас) / «Отклонить» / «Отложить» (сохраняется в профиле клиента списком рекомендаций — сырьё для сервисных напоминаний фазы 3)
3. **B2B:** апсейл **никогда не автостартует**, даже в пределах лимита точки — он инициирован нашим мастером, действует принцип анти-навязывания (тот же, что для дефектов осмотра, 5.1). Уходит утверждающему по порогам; сотрудник точки принять его не может. «Отложить» → дефект в техдолг точки
4. Работа по непринятому апсейлу не оплачивается вообще — ни одна работа без санкции (принцип 3). Сделал «по устной договорённости» мимо приложения — сделал за свой счёт
5. **Анти-давление:** отказ от апсейла никак не влияет на завершение исходной работы; жалоба «мастер навязывал» — отдельная причина спора и сигнал диспетчеру; конверсия апсейлов и жалобы видны в профиле мастера. На рейтинг апсейл не влияет ни вверх, ни вниз — иначе мастера начнут продавать, а не чинить
**Экономика:** доля мастера с принятых вынужденных работ и апсейлов — обычная (от базовой цены). Апсейл — легальный способ мастера поднять свой чек; вынужденная ветка — защищённый способ не бросить клиента с опасной проблемой. Обе воронки (конверсия, средний чек доп-работ) — в дашборде бизнеса (13).

## 5. Матрица утверждений и лимитов (B2B)
### 5.1. Источники санкции
| Ситуация | Нужна кнопка «Утвердить»? |
|---|---|
| Обычная заявка, смета ≤ лимита заявки точки, месячный лимит не исчерпан | Нет — авто-старт |
| Смета > лимита заявки | Да — утверждающий по порогам (см. 5.2) |
| Месячный лимит точки исчерпан | Да — любая заявка точки до конца месяца |
| Заявка из планового осмотра (дефект) | **Да — всегда**, даже в пределах лимита. Дефект инициирован нашим мастером, а не клиентом; без явного согласия это выглядит навязыванием |
| Доп-смета в процессе работ | Да — на сумму превышения. Параметр организации: доп-сметы в пределах остатка лимита заявки — авто-утверждение или вручную (по умолч. вручную) |
| Вынужденная доп-работа (исходная блокирована) | Да — с красным флагом и короткими таймерами (4.6); при молчании — консервация без утверждения + дефект в техдолг |
| Апсейл мастера при работах | **Да — всегда**, даже в пределах лимита (инициирован мастером — принцип анти-навязывания); сотрудник точки принять не может; «отложить» → техдолг |
| Консервация (безопасное отключение при отказе) | Нет — как аварийная локализация: мера безопасности, фиксированная позиция прайса |
| Аварийная локализация | Нет — никогда |
| Восстановление после аварии | Как обычная смета (лимит/утверждение) |
| Критичный дефект с осмотра (угроза аварии) | Да, но с красным флагом, дублируется звонком диспетчера |

**Анти-дробление:** если с одной точки за 48 ч авто-стартует более N заявок (параметр, по умолч. 3) — следующие идут с флагом диспетчеру на ручную проверку. Защита от разбиения большой работы на куски ниже лимита заявки.
### 5.2. Пороги утверждения (задаются в договоре, хранятся в организации)
Пример конфигурации: руководитель точки утверждает до 1 000 000; руководитель организации — до 5 000 000; свыше — руководитель организации + владелец (двойное утверждение). Система поддерживает 1–3 уровня с настраиваемыми порогами. Утверждение всегда пишет в аудит: кто, когда, сумма, устройство. Утверждения на сумму выше порога (параметр, по умолч. 5 000 000) требуют повторной аутентификации в приложении (PIN/биометрия) — защита от SIM-swap и чужого телефона в руках.
### 5.3. Эскалация при молчании
Для смет и пакетов дефектов (утверждающий не на объекте):
- T+24 ч: повторный push + SMS утверждающему
- T+48 ч: эскалация на уровень выше (если есть) + задача диспетчеру «позвонить»
- T+72 ч: авто-отмена «не согласовано», уведомление всем сторонам. Для критичных дефектов — не отменяется, а остаётся висеть с ежедневным напоминанием
Для доп-смет в процессе работ (мастер стоит на объекте) — отдельные короткие таймеры: T+30 мин повторный push + SMS, T+2 ч звонок диспетчера утверждающему. Авто-отмена не применяется: мастер завершает согласованную часть, несогласованные позиции снимаются.
Все сроки — параметры системы.
### 5.4. Пакетное утверждение дефектов
После заявки-осмотра руководителю уходит push: «Осмотр {точка}: найдено N дефектов на {сумма}». Экран: список дефектов с фото, ценой, приоритетом; чекбоксы; кнопки «Утвердить выбранные» / «Отложить до даты» / «Отклонить». Утверждённые автоматически становятся заявками со статусом «Утверждена» и планируются диспетчером.

## 6. Приложение «Клиент» (Flutter)
Единое приложение, интерфейс собирается по роли. Языки: русский, узбекский. Вход по номеру телефона + OTP.
### 6.1. Режим B2C (физлицо)
- **Главный экран:** большая кнопка «Вызвать мастера», плитки категорий (сантехника, электрика, кондиционеры…), активная заявка со статус-баром, баннер «Аварийная ситуация?»
- **Создание заявки:** категория → типовые работы из прайса с ценами «от» (можно «не знаю, что сломалось» — тогда только описание) → фото (до 5) → адрес (карта + подъезд/этаж/домофон + наличие лифта — важно для тяжёлых/парных работ) → слот времени: показываются только реально доступные окна из планировщика (17.3) + вариант «Срочно» с наценкой (платный приоритет, 17.3) или бесплатный лист ожидания с честным прогнозным интервалом → поле промокода (решение владельца: в MVP; скидка — маркетинговый расход компании, доля мастера всегда от базовой цены) → для категорий с общими зонами — чек-лист «нужен доступ к стояку/подвалу/крыше?» с подсказкой договориться с ТСЖ заранее и полем «доступ подтверждён на {время}» (4.1) → итог с вилкой цены и правилом «точная цена до начала работ»; для этапных работ итог показывает план сессий («2 визита: среда и пятница»)
- **Экран активной заявки:** статус-трекер; после «Назначена» — карточка мастера (фото, имя, рейтинг, кол-во работ) и прогноз до выезда («мастер завершает предыдущий заказ, приедет ~16:40»); после «Выехал» — ETA по карте; при сдвиге прогноза за границу окна — проактивный push с извинением и новым временем; связь с диспетчером (MVP: звонок + быстрые шаблонные сообщения; полноценный чат — фаза 2); кнопки «Перенести» (бесплатно при > 2 ч до окна, не более 2 раз — дальше только отмена по правилам 4.4; при переносе мастер снимается, заявка возвращается в распределение), «Отменить» (с предупреждением о правилах 4.4)
- **Смета на месте:** если мастер уточнил смету до начала — клиенту пуш «Подтвердите стоимость {сумма}» → «Согласен» / «Отказываюсь» (отказ = ложный вызов не начисляется, оплачивается только выезд)
- **Завершение:** экран итога — фото до/после, работы, материалы с чеками, сумма; оплата (Payme/Click/Uzum/карта; наличные мастеру — фиксируются мастером, см. 8.5); оценка 1–5; кнопка «Оспорить» (72 ч); PDF-акт по кнопке
- **История, профиль, адреса, гарантийные обращения** («Проблема вернулась» → гарантийная заявка со ссылкой на исходную)
- **«Моя техника» (фаза 2):** паспорт техники квартиры с историей обслуживания каждой единицы и ближайшими рекомендациями по регламенту (17.12)
### 6.2. Режим «Сотрудник точки»
Максимально простой (фармацевт не должен думать): кнопка «Сообщить о поломке» → фото (обяз. предложено) → описание → категория (можно «не знаю») → срочность (обычная/аварийная с подсказкой, что такое авария) → отправить. Видит статусы своих заявок и ETA мастера. **Не видит** сметы и деньги (настройка организации: показывать/нет). Видит инструкцию «что делать при аварии до приезда» (перекрыть кран — с картинкой из паспорта объекта, где кран).
### 6.3. Режим «Руководитель точки»
Всё из 6.2 + лента всех заявок точки; экран утверждения сметы: фото, позиции, сумма, кнопки «Утвердить»/«Отклонить»/«Вопрос диспетчеру»; техдолг точки; месячный отчёт точки (PDF); индикатор лимитов («израсходовано 640 000 из 1 500 000 авто-лимита»).
### 6.4. Режим «Руководитель организации»
- **Дашборд:** плитки точек со светофором (зелёная — всё ок; жёлтая — заявки в работе; красная — авария или висит утверждение)
- **Центр утверждений:** единая лента всего, что ждёт решения (сметы, доп-сметы, пакеты дефектов), сортировка по срочности, бейдж на иконке приложения
- **Техдолг организации:** сумма по всем точкам, разбивка по приоритетам, тренд («в прошлом месяце 6,1 млн → сейчас 4,2 млн»)
- **Финансы:** остаток абонентки, прогноз «хватит до ~24 числа», сверхлимит текущего месяца, СФ (список, статусы, PDF), акт сверки за период по кнопке, помесячная динамика расходов по точкам
- **Управление:** лимиты точек, пользователи точек (пригласить по номеру телефона), график осмотров
- **Отчёты:** месячный сводный PDF по организации и по каждой точке
### 6.5. Режим «Владелец»
Дашборд руководителя организации без кнопок действий (read-only), настраивается в договоре: суммы, техдолг, светофор точек, отчёты. Единственное исключение из read-only: участие во втором утверждении сверхпороговых смет, если двойное утверждение включено в договоре (5.2) — иначе схема «руководитель + владелец» неисполнима.

## 7. Приложение «Мастер» (Flutter)
### 7.1. Экраны и сценарии
- **Смена:** тумблер «На линии / Не работаю». Пока «на линии» — участвует в авто-распределении
- **Кнопка «Не могу поехать»** на принятой заявке (причина обязательна): запускает протокол замены немедленно — честный ранний отказ караётся мягче тихого невыхода (17.3)
- **Дежурство:** индикатор «Ты дежурный сегодня» + гарантированный минимум смены в кошельке (17.3)
- **Входящая заявка:** пуш + экран: категория, адрес (расстояние), окно времени, состав работ, сумма **его доли** (не полная цена — настройка админа: показывать долю или полную цену; для B2C-вилки — расчёт от текущей оценки, финальная доля — от утверждённой на месте суммы), фото клиента. Кнопки «Принять» (60 сек на решение) / «Отказаться» (причина). Два отказа подряд без причины — понижение приоритета
- **Мои заявки:** лента дня — сегодняшний маршрут списком и на карте; завтрашняя лента видна с вечера (17.3); изменения ленты приходят пушем
- **Карточка заявки — рабочий конвейер строго по шагам:**
  1. «Выехал» → клиенту ETA. В любой момент работы доступна кнопка «Задерживаюсь +30/60 мин» — честный сдвиг плана с каскадным пересчётом очереди (17.3)
  2. На месте: «Приступить» → **обязательный экран фото «до»** (камера, без галереи — только живые снимки; серверный таймштамп + гео). Рядом — кнопка «Нет доступа (третья сторона)»: причина + фото + время следующей попытки (4.1); для этапных работ — отметка «Этап N завершён» с фото в конце каждой сессии
  3. Уточнение сметы: позиции прайса (поиск по названию), калькулятор итога; если > утверждённого — авто-запуск доп-согласования, экран «Ожидание подтверждения» (может делать согласованную часть). Доп-работы оформляются с типом: «Вынужденная — без неё не завершить» (фото проблемы обязательны, варианты минимум/полный) или «Рекомендация» — апсейл, отдельная кнопка, не блокирует работу (4.6)
  3a. Техника: фиксация обслуженной единицы — тип, бренд, модель + фото шильдика (паспорт техники клиента, 17.12); заполненность учитывается в качестве фиксации (7.4)
  4. Материалы: «+ Материал» → название, кол-во, цена, **фото чека обязательно**; купил из своих — помечается «возместить мастеру». Расходники «сумки» добавляются из каталога по фиксированной цене без чека (8.4.1). Кнопка «Код закупки» — одноразовый код для партнёрского магазина (8.4.4, фаза 2)
  5. «Завершить» → **обязательный экран фото «после»** (подсказка: тот же ракурс, что «до») → итоговый экран → подпись клиента пальцем (B2C, опционально) или код подтверждения сотруднику точки (B2B: сотрудник называет 4-значный код из своего приложения — подтверждение, что работа принята на месте). Fallback, если сотрудник с приложением недоступен (смена кончилась, телефон сел): мастер жмёт «Принято без кода» → обязательное фото результата с общим планом помещения → флаг диспетчеру на проверку
  6. Оплата (B2C): экран оплаты — QR провайдера на экране мастера / push клиенту со ссылкой на оплату / «Принял наличные». **Мастер не завершает визит без оплаты**; уход без оплаты — только с санкции диспетчера (заявка уходит в «Ожидает оплаты»). Мы не кредитуем незнакомых физлиц по умолчанию. После оплаты и оценки — опция чаевых (решение владельца: в MVP): целиком мастеру, мимо долей, отдельной проводкой
- **Наличные (B2C):** если клиент платит наличными — мастер жмёт «Принял наличные {сумма}» → сумма становится долгом мастера перед компанией (см. 8.5)
- **Кошелёк:** заработано за период, детализация по заявкам, возмещения материалов, удержания с причинами, принятые наличные, «к выплате», история выплат
- **Профиль:** рейтинг с разбивкой (пунктуальность, качество фото, оценки, переделки), skill-теги, зоны; апсейл-статистика (конверсия рекомендаций, выручка с них) — мотивационная метрика, на рейтинг не влияет
### 7.2. Оффлайн-режим (обязателен)
В подвалах и техпомещениях связи нет. Фото и все действия кешируются локально и синхронизируются при появлении сети. Требования:
- каждая офлайн-операция получает клиентский UUID — синхронизация идемпотентна, повторная отправка не создаёт дублей
- в офлайне фиксируется время устройства + монотонные часы; при синке сервер присваивает своё время получения, запись помечается флагом «зафиксировано офлайн» (обе метки хранятся — для споров)
- гео может отсутствовать (подвал) — фото принимается с флагом «без гео», не блокирует конвейер
- конфликт версий решается по серверному времени; индикатор «не синхронизировано» на карточке
### 7.3. Авто-распределение заявок
Алгоритм подбора: (1) фильтр по skill-тегам позиции прайса, (2) фильтр по зоне, (3) фильтр по загрузке (слоты), (4) ранжирование по рейтингу и близости. Первому — оффер на 60 сек, отказ/молчание — следующему. Диспетчер всегда может назначить вручную (ручное назначение имеет приоритет). Аварийные — ближайшему свободному, минуя очередь.
### 7.4. Рейтинг мастера (0–100, пересчёт еженедельно, скользящее окно 56 дней)
Компоненты и формулы (каждая нормируется в 0–100, итог — взвешенная сумма):
- **Пунктуальность, 25%** = доля заявок с отметкой «Приступить» внутри назначенного окна × 100
- **Оценки клиентов, 30%** = средняя оценка × 20; при < 10 оценок в окне — байесовское сглаживание к 4.5 (эквивалент 10 «виртуальных» оценок), чтобы одна злая оценка не убивала новичка
- **Качество фиксации, 15%** = доля пакетов фото/чеков, принятых диспетчером с первой попытки × 100
- **Отсутствие переделок, 20%** = 100 − 25 × (число гарантийных переделок по вине мастера в окне), минимум 0
- **Дисциплина офферов, 10%** = доля принятых офферов × 100; отказы с уважительной причиной, подтверждённой диспетчером (болезнь, форс-мажор), исключаются из знаменателя
**Новый мастер:** стартовый рейтинг 60, испытательный период — первые 20 заявок: нижние пороги не применяются, но 100% его фото-пакетов проходят модерацию диспетчером.
**Гигиена оценок:** оценка 1–2 автоматически открывает тикет диспетчеру (разбор ситуации); оценки по спорам, решённым в пользу мастера, исключаются из расчёта; мастер может подать апелляцию на оценку/санкцию — решение диспетчера пишется в аудит.
**Грейды:** Бронза (< 70) / Серебро (70–85) / Золото (> 85 и ≥ 100 закрытых заявок). Грейд влияет на приоритет в распределении; Золото получает долю 57% вместо 55% (**решение владельца — включено**, действует с запуска авто-рейтинга в фазе 2).
**Санкции:** ниже 40 — разбор с диспетчером, ниже 25 — блокировка. Никаких денежных штрафов за рейтинг — только приоритет; денежные удержания только за конкретные события (гарантийная переделка по вине, невыход с ущербом).
MVP: рейтинг выставляется диспетчером вручную; авто-расчёт по формулам — фаза 2 (формулы фиксируются сейчас, чтобы копить данные с первого дня).

## 8. Биллинг (до уровня проводок)
### 8.1. Счета
- Счёт абонентки каждой организации (SubscriptionAccount)
- Баланс каждого мастера (MasterBalance)
- Счёт компании (выручка, обязательства)
- Долговой счёт B2C-клиента (ложные вызовы, неоплаты)
Всё движение — только проводками (Transaction) с двойной записью, ссылкой на заявку/СФ и запретом редактирования задним числом (сторнирование отдельной проводкой).
**Округление:** все расчётные суммы (коэффициенты, доли, наценки) округляются до 100 сум; направление округления — в пользу клиента для списаний и в пользу мастера для начислений (параметр). Правило едино на всех слоях (бэкенд, отчёты, СФ), контрольные суммы обязаны сходиться копейка в копейку.
**Комиссии платёжных провайдеров** (Payme/Click/Uzum) учитываются отдельной проводкой расхода компании: клиент и мастер видят суммы брутто, сверка с выпиской провайдера сходится автоматически.
### 8.2. Проводки закрытия B2B-заявки на абонентке
Пример: работа по базовому B2C-прайсу 200 000; **эффективный подписной коэффициент = наценка B2B разовая 1.3 × (1 − скидка подписки 0.10) = 1.17** (v2.23); доля мастера 55%; материалы 120 000 (куплены мастером).
1. Списание с абонентки: 200 000 × 1.17 = **234 000** (дебет абонентки → выручка компании)
2. Начисление доли мастеру: 200 000 × 0.55 = **110 000** (расход компании → баланс мастера). **Доля считается от базовой B2C-цены**, а не от подписной — ценообразование каналов не бьёт по мастеру
3. Материалы: 120 000 → по умолчанию в СФ клиенту отдельной строкой (без наценки) + 120 000 на баланс мастера «возмещение». Параметр договора: материалы «отдельной СФ» (по умолч.) или «списывать с абонентки» — для клиентов, которым нужно «всё включено»
4. Если абонентки не хватает: остаток списывается до нуля, непокрытая часть пересчитывается через базовую цену в тариф B2B разовой. Формула: непокрытая база = (подписная цена − остаток) ÷ эффективный подписной коэффициент; в СФ = непокрытая база × наценка B2B. Пример: база 200 000, подписная 234 000, остаток абонентки 117 000 → списано 117 000; непокрытая база (234 000 − 117 000) ÷ 1.17 = 100 000 → в СФ 100 000 × 1.3 = 130 000. Формула едина для всех слоёв — иначе отчёт и СФ разойдутся
### 8.3. Месячный цикл организации
1-е число: начисление абонентки (обязательство клиента), автогенерация СФ на абонентку → ЭДО. Одновременно из абонентки **резервируется стоимость плановых осмотров месяца** (график × цена осмотра): осмотры списываются первоочерёдно и в сверхлимит не попадают никогда — это обязательство договора, а не опция.
В течение месяца: списания по заявкам.
Последний день: свод сверхлимита + материалов → вторая СФ с приложением — автоотчётом (см. 9).
Неоплата абонентки к 10-му: статус «приостановлена» — новые заявки только аварийные, руководству баннер. Плановые осмотры на время приостановки замораживаются (резерв не тратится); при расторжении договора резерв осмотров сторнируется. Параметры — настройки договора.
**B2B разовая (юрлицо без договора):** упрощённая карточка организации (реквизиты для СФ, одна точка по адресу заявки). Флоу: заявка (обычно по звонку) → смета → **счёт на предоплату** → бухгалтер отметил оплату → «Назначена» → работы → акт + СФ. Постоплата — только решением админа (лимит доверия, аудит). Без предоплаты работы не начинаются: у юрлица без договора нет аванса, риск неплатежа целиком наш.
Перенос остатка (если включён в договоре) оформляется проводкой переноса в новый период; сгорание — проводкой списания. Расторжение посреди месяца: судьба остатка абонентки — параметр договора (возврат по акту сверки / сгорание), закрывается ручной проводкой бухгалтера с двойным подтверждением.
### 8.4. Материалы, запчасти и инструмент
#### 8.4.1. Три категории того, что «в руках у мастера» — разные правила
| Категория | Что это | Кто платит | Как списывается |
|---|---|---|---|
| **Инструмент** | Собственность мастера: мультиметр и индикатор у электрика, паяльник ПП труб и разводные ключи у сантехника, манометрический коллектор у кондиционерщика — обязательный набор по skill-тегу (ToolChecklist) | Мастер | Никогда не тарифицируется клиенту и не списывается |
| **Расходники «сумки»** | Мелочь, всегда при себе: фум-лента, подмотка, герметик, изолента, клеммы, дюбели, саморезы, хомуты, прокладки | Клиент — по фиксированной цене из ConsumableCatalog | В заявку позициями каталога, **без фото чека** |
| **Запчасти под задачу** | Смесители, краны, картриджи, автоматы, сифоны, компрессоры — под конкретную заявку | Клиент — по документу | Всегда с документом (чек/накладная), см. 8.4.3 |
**Инструмент:** комплектность проверяется при онбординге и выборочно (фото набора); неполный набор — временное снятие skill-тега до устранения (мастер не получает заявки, требующие этого инструмента).
**Расходники:** требовать чек на фум-ленту за 3 000 сум — абсурд, который убьёт дисциплину фиксации, поэтому расходники списываются по фикс-прайсу каталога. Вся сумма расходников идёт мастеру (возмещение + микромаржа за запасливость) — компания на расходниках сумки не зарабатывает. Анти-приписки: нормативы расхода на категорию заявки (не более N единиц позиции на заявку категории X), превышение — флаг диспетчеру при модерации.
#### 8.4.2. Сумка мастера (MasterStock)
MVP: без количественного учёта — мастер добавляет расходники в заявку из каталога, точка. Фаза 2: количественный учёт — пополнение чеком (позиции зачисляются в сумку по себестоимости, мастеру возмещение) или со склада компании (фаза 3); списание в заявку уменьшает остаток; экран «Сумка» в приложении мастера: остатки, индикатор «ниже норматива», история пополнений.
#### 8.4.3. Источники запчастей (приоритет сверху вниз, выбирается в заявке)
1. **Партнёрский магазин в долг компании** (8.4.4) — целевой основной сценарий с фазы 2
2. **Мастер покупает за свои** (по умолчанию в MVP): чек обязателен, возмещение мастеру, клиенту без наценки. Лимит закупки без согласования — 500 000/заявка (параметр), выше — фото ценника → подтверждение диспетчера
3. **Клиент покупает сам:** мастер отправляет список закупки из заявки, заявка — в паузу «Ожидание материалов» (4.1)
4. **Склад компании** (фаза 3): себестоимость в СФ с настраиваемой наценкой 0–15%
**Выбор ценовой категории:** для запчастей дороже порога (параметр, по умолч. 200 000) мастер отправляет клиенту вилку «эконом / стандарт / премиум» (из SparePartCatalog или фото ценников в магазине) — выбор клиента фиксируется как часть доп-сметы, в аудит.
**Неиспользованные материалы:** купленное, но не израсходованное возвращается в магазин (по чеку; для партнёрского — сторно строки накладной) либо передаётся клиенту, если уже оплачено им; в акте отражается только фактический расход.
**Доказательство замены:** для запчастей дороже порога — фото старой детали, новой в упаковке и установленной; демонтированная деталь остаётся клиенту (защита от «замены исправного на исправное»). Гарантия на запчасть — по чеку/накладной магазина, её срок фиксируется в заявке отдельно от гарантии на работу. Если запчасть отказала в пределах гарантии магазина, но после гарантии на работу: запчасть меняется бесплатно (гарантия магазина), работа по замене — по прайсу (параметр: бесплатно/по прайсу).
#### 8.4.4. Партнёрские магазины: закупка в долг компании (фаза 2)
Главная боль текущей модели — мастер морозит свои деньги в чужих материалах. Решение: сеть партнёрских магазинов (сантехника, электрика) с договором отсрочки.
- **Договор с магазином:** кредитный лимит компании, период погашения (реестр раз в неделю/месяц), ретро-бонус от оборота (решение владельца: скидка магазина остаётся компании, клиент платит цену накладной). Категории — все профильные: сантехника, электрика, малярка/отделка, фурнитура и материалы корпусной и мягкой мебели; цель — 1–2 магазина каждой категории на крупный район
- **Сценарий:** мастеру нужны запчасти → в карточке заявки жмёт «Код закупки» → система генерирует одноразовый код (QR + цифры) с лимитом = согласованный бюджет материалов заявки + 10%, срок жизни 4 часа → магазин проверяет код на веб-странице проверки (без интеграции; личный кабинет магазина — фаза 3) → отпускает товар в долг компании → мастер фиксирует накладную в заявке (фото + позиции)
- **Деньги:** закупка = проводка «материалы по заявке / кредиторка магазину»; клиенту материалы транслируются по накладной **без наценки** (принцип сохраняется); выгода компании — скидка/ретро-бонус магазина (отдельная проводка); мастер свои деньги не тратит вообще
- **Погашение:** еженедельный реестр закупок по каждому магазину → оплата банком → отметка-проводка, акт сверки с магазином
- **Контроль злоупотреблений:** код привязан к заявке и лимиту суммы; накладная сверяется диспетчером с позициями сметы при модерации; расхождение — разбор с магазином и мастером; превышение лимита кода магазином — риск магазина (в договоре)
### 8.5. Наличные B2C
Мастер принял наличные → **вся** принятая сумма — долг мастера перед компанией. Взаимозачёт в ведомости: **к выплате = начисления (доли + возмещения) − удержания − принятые наличные**; отрицательный итог = мастер вносит разницу через Payme на счёт компании. Пример: заявка 300 000 наличными, доля мастера 99 000 + возмещение материалов 120 000 = 219 000 начислений − 300 000 наличных = −81 000 к внесению. Лимит наличного долга мастера — 2 000 000 (параметр): при превышении мастер обязан внести через Payme на счёт компании, иначе снимается с линии автоматически. Это убивает соблазн «работать мимо кассы» экономически: наличка прозрачна и неудобна, безнал — норма.
### 8.6. Выплаты мастерам
Период: раз в неделю (параметр). Ведомость: начисления − удержания − наличный взаимозачёт = к выплате. Ведомость разделяет **доход мастера** (доли за работы) и **возмещения** (материалы — не доход, налогами не облагаются). Для мастеров ГПХ компания — налоговый агент: ведомость считает удержания (НДФЛ, соцналог — ставки подтверждает бухгалтер); самозанятым выплачивается брутто, налог платят сами, действующий статус самозанятого проверяется при онбординге и периодически. Экспорт для банка, отметка «выплачено» — проводка. Мастер видит каждую копейку в кошельке с расшифровкой — прозрачность здесь = удержание мастеров.
**Гарантированный минимум дежурства** (17.3): начисляется проводкой за смену дежурства независимо от числа выездов; доли за фактические выезды — сверху.
**Возмещение ГСМ мастерам со своим авто (решение владельца, v2.21): нормативный километраж по маршруту ленты.** Без GPS-слежки за личной машиной: в конце смены система суммирует расстояния по карте **между адресами выполненных заявок ленты** (та же карт-матрица, что считает дорожные буферы планировщика) × ставка сум/км (параметр). Путь «дом → первая заявка» и «последняя → дом» **не считается** (личная дорога на работу; планировщик и так собирает ленту в зоне мастера). Начисляется в ведомость **как возмещение** (не доход, отдельная строка, налоговая квалификация — бухгалтеру); мастер видит в кошельке расшифровку «N км × ставка». Анти-абьюз встроен: считаются только переезды между реально выполненными заявками — накрутить можно только выполняя больше заявок. Только для мастеров с флагом «свой авто»; учитывается валидатором unit-экономики как средний транспортный расход.
**Офбординг мастера** (увольнение/блокировка): снятие с линии → заморозка выплат → взаимозачёт наличного долга и удержаний → акт сверки → финальная выплата или взыскание. Активные заявки переназначаются диспетчером.
**Налоги:** самозанятый платит налог сам; по договорам ГПХ компания — налоговый агент. Схему подтвердить с бухгалтером до запуска выплат (влияет на состав ведомости).
### 8.7. ЭДО, фискализация, возвраты (Узбекистан)
Интеграция со счёт-фактурным ЭДО-оператором (didox.uz / faktura.uz — выбрать на этапе разработки, заложить адаптерную архитектуру). Онлайн-платежи: Payme, Click, Uzum — через их мерчант-API; **возвраты по спорам — через refund-API провайдеров** (заложить в интеграционный слой сразу, ручные возвраты «мимо системы» запрещены). НДС: СФ формируются с выделением НДС для организаций-плательщиков (признак и ставка — в реквизитах организации). Фискальные чеки для B2C — по требованиям ОФД; уточнить у бухгалтера-консультанта на старте проекта, заложить в бэклог интеграцию с онлайн-ККМ (в т.ч. для наличных, принятых мастером).
### 8.8. План счетов, инварианты и учётный период
- **Минимальный план счетов:** денежные средства (расчётный счёт; клиринг провайдеров «деньги в пути»; наличные у мастеров), авансы полученные (абонентки), дебиторка клиентов, кредиторка мастерам (балансы), долги мастеров (наличные), кредиторка партнёрским магазинам, выручка, расходы (доли мастеров, комиссии провайдеров, возмещения)
- **Абонентка — аванс, а не выручка:** оплата абонентки зачисляется в «авансы полученные»; выручка признаётся в момент списания за закрытую заявку/осмотр. Невыбранный остаток — обязательство перед клиентом (принципиально для отчётности и для спора при расторжении)
- **Клиринг провайдеров:** Payme/Click/Uzum перечисляют возмещение пачкой T+1/T+2 минус комиссия → счёт «деньги в пути»; автоматическая сверка реестра провайдера с проводками платежей, расхождения — в очередь бухгалтеру
- **Инварианты:** сумма проводок каждой операции = 0 (двойная запись); ежедневный автоматический баланс-чекер по всем счетам, алерт админу при расхождении хоть на 1 сум
- **Закрытие периода:** месяц закрывается бухгалтером (lock) — проводки в закрытый период запрещены; корректировки — только текущим периодом со ссылкой на исходную проводку
- **Идемпотентность вебхуков:** повторный callback провайдера с тем же id платежа не создаёт вторую проводку
### 8.9. Дебиторская задолженность (АР)
- **Источники дебиторки:** неоплаченная абонентская СФ; сверхлимитная СФ; разовая B2B-СФ; долг B2C (неоплаченная работа, ложный вызов). Наличный долг мастера учитывается отдельно (8.5) и с клиентской дебиторкой не смешивается
- **Реестр АР:** по контрагентам, aging-корзины 0–30 / 31–60 / 61–90 / 90+ дней, начислено / погашено / остаток; дашборд бухгалтера: общая дебиторка, DSO, топ-10 должников, динамика по месяцам
- **Частичные оплаты:** разнесение по умолчанию FIFO (старейшие СФ первыми); бухгалтер может разнести вручную (с аудитом)
- **Дунинг B2B (сроки — параметры):** T+3 напоминание бухгалтерии клиента (email + push), T+7 руководству организации, T+10 приостановка обслуживания (8.3), T+30 претензионное письмо (PDF по шаблону, одной кнопкой), T+60 решение о пред-суде/списании (вручную)
- **Дунинг B2C:** «Ожидает оплаты» (4.1) → T+24 push, T+72 SMS + блок новых заявок; T+30 звонок диспетчера; T+90 списание в убыток (двойное подтверждение)
- **Пени:** опция договора (по умолчанию выключено): %/день от просроченной суммы с потолком N%; начисляются отдельной строкой следующей СФ, проводкой
- **Акт сверки взаиморасчётов:** PDF по контрагенту за период одной кнопкой, собирается из проводок без ручной сборки (документ, который бухгалтерии в Узбекистане просят постоянно)
- **Списание безнадёжного долга:** бухгалтер + админ (двойное подтверждение), проводка «убыток», причина в аудит; история заявок клиента сохраняется
- **Отметка оплат:** MVP — вручную бухгалтером по банковской выписке (поиск по ИНН/номеру СФ); фаза 2 — импорт выписки и авто-разнесение
### 8.10. Налоговый контур (карта для бухгалтера-консультанта)
Ставки и режимы подтверждает бухгалтер на старте проекта; задача системы — фиксировать каждое налоговое событие и строить регистры.
| Поток | Событие в системе | Налоговое событие |
|---|---|---|
| B2C оплата (онлайн/наличные) | «Закрыта» | фискальный чек ОФД на полную сумму (работы + материалы); НДС компании — по режиму |
| Транзит материалов клиенту | строка материалов в чеке/СФ | входит в оборот компании; облагается ли НДС передача «без наценки» — вопрос бухгалтеру |
| B2B абонентка | СФ 1-го числа + списания | авансовая СФ и признание выручки по факту работ — схему авансовых СФ в ЭДО уточнить |
| B2B сверхлимит и материалы | СФ конца месяца | СФ с НДС через ЭДО |
| Ложный вызов | начисление долга | чек/СФ: неустойка или услуга выезда? — квалификацию уточнить (влияет на НДС и ОФД) |
| Доля мастера ГПХ | ведомость выплат | НДФЛ + соцналог, компания — налоговый агент |
| Доля самозанятого | ведомость выплат | брутто; система контролирует действующий статус самозанятого |
| Возмещение материалов мастеру | ведомость выплат | не доход мастера, не облагается |
| Чаевые мастеру | проводка чаевых (мимо долей) | фискализация и налогообложение чаевых — квалификацию уточнить |
| Отчисление в резервный фонд ущербов (17.7) | проводка резерва | учёт резерва и выплат ущербов — схему уточнить |
| Ретро-бонус партнёрского магазина | проводка бонуса | доход компании |
| Сгорание остатка абонентки | проводка списания остатка | признание дохода без оказания работ — квалификацию и НДС уточнить |
**Налоговые регистры:** реестр фискальных чеков, реестр СФ, реестр выплат с удержаниями — экспорт бухгалтеру/в 1С. Налоговая отчётность должна собираться из системы, а не из головы бухгалтера.

## 9. Автоматические отчёты
### 9.1. Акт по заявке (PDF, 1–2 страницы, генерация одной кнопкой)
Шапка: логотип, номер заявки, точка/клиент, адрес, дата, мастер.
Тело: фото «до» и «после» рядом (сетка), при наличии — «в процессе»; таблица работ (позиция, ед., кол-во, цена, сумма); таблица материалов (название, кол-во, цена, сумма, № чека); итого работ / итого материалов / всего; канал оплаты (абонентка/СФ/онлайн); кто утвердил смету и когда (для B2B).
Подвал: гарантия (срок из заявки, по умолчанию 30 дней), контакты. QR-код на онлайн-версию акта.
### 9.2. Месячный отчёт по точке / организации (PDF)
Сводка: заявок всего / аварийных / плановых осмотров; сумма работ, сумма материалов; списано с абонентки, сверхлимит; динамика к прошлому месяцу. Реестр заявок таблицей со ссылками-QR на акты. Раздел «Техдолг»: устранено за месяц, добавлено, остаток по приоритетам. Этот PDF прикладывается к СФ автоматически — начальник АХО получает готовый пакет для своего руководства, ничего не собирая руками. **Это главная продающая ценность для B2B.**
### 9.3. Отчёт по осмотру
Чек-лист осмотра с отметками, найденные дефекты с фото и оценкой, рекомендации по приоритетам. Уходит руководству вместе с пакетом на утверждение. Шаблоны чек-листов — справочник в админке по типу объекта (аптека, ресторан, офис…): у ресторана — жироуловители и вытяжка, у аптеки — холодильники и кондиционеры.
**Представитель точки на месте (v2.22):** перед завершением осмотра мастер фиксирует, кто присутствовал: выбор из сотрудников точки или ручной ввод ФИО+должности; подтверждение присутствия — **код приёмки** (тот же механизм, что у обычных заявок, 7.1 шаг 5) либо **подпись пальцем на экране мастера** (механизм режимных объектов). Fallback «представитель отсутствовал»: осмотр действителен (доступ мог дать охранник/ключ), но фиксируется фото точки доступа + флаг диспетчеру на выборочную проверку, отчёт помечается «без представителя». ФИО, должность и способ подтверждения — **обязательные реквизиты PDF-акта осмотра**: при споре «мастер не приезжал, дефекты выдуманы» акт с подтверждением представителя — наша защита. **История осмотров точки** (карточка точки в админке и у руководителя организации): дата, мастер, представитель, акт PDF, найдено/утверждено/отклонено дефектов — весь след объездов в одном месте.

## 10. Техдолг объекта
Реестр дефектов точки (см. 3.5). Дашборд руководителя показывает: сумму техдолга, разбивку по приоритетам, старение (дефект висит 60+ дней — подсветка). Механика дожима: раз в месяц дайджест-push «Техдолг точки X: 4,2 млн, из них критичного 1,1 млн» с кнопкой в пакетное утверждение. Каждый утверждённый дефект = заявка = выручка. Воронку техдолга наполняют три источника: плановые осмотры, отклонённые/отложенные вынужденные доп-работы и отложенные апсейлы из обычных заявок (4.6) — техдолг её монетизирует. Отклонённые дефекты остаются в архиве с пометкой — при аварии по отклонённому дефекту компания защищена: «мы предупреждали {дата}, вы отклонили» (юридически значимый аудит-лог).

## 11. Уведомления (матрица)
Каналы: push (основной), SMS (критичные и OTP), звонок диспетчера (аварии, эскалации). Все — через очередь с ретраями, лог доставки. Push — через FCM; для Android-устройств без Google-сервисов критичные уведомления дублируются SMS (детект отсутствия FCM-токена). **Клиенты без приложения (телефонный канал, 12):** профиль доставки «SMS + веб-ссылка» — ключевые события (назначен, выехал+ETA, акт готов, напоминание оплаты) уходят SMS со ссылкой на веб-карточку заявки; набор SMS-событий — параметр (SMS платные, шлём только важное).
| Событие | Получатель | Канал |
|---|---|---|
| Заявка создана | диспетчер | панель + push |
| Мастер назначен / выехал (ETA) | клиент/сотрудник точки | push |
| Смета требует утверждения | утверждающий по порогу | push, T+24 SMS |
| Доп-смета в процессе работ (вынужденная — красный флаг) | утверждающий | push + SMS сразу; для вынужденной при молчании 2 ч — звонок диспетчера |
| Апсейл-рекомендация мастера | B2C — клиент; B2B — утверждающий | push |
| Авария на точке | руководство орг. + диспетчер | push + звонок |
| Заявка выполнена, акт готов | клиент + руководитель точки | push |
| Ожидает оплаты (B2C, напоминание) | клиент | push T+24, SMS T+72 |
| Пакет дефектов после осмотра | руководство орг. | push |
| СФ выставлена / абонентка к оплате | руководство + бухгалтерия орг. | push + email |
| Абонентка не оплачена (T+10) | руководство орг., админ | push + SMS |
| Этапы дунинга СФ (T+3 / T+7 / T+30) | бухгалтерия и руководство орг.; бухгалтер компании | email + push |
| Реестр закупок магазину к оплате | бухгалтер компании | панель + email |
| Выплата мастеру проведена | мастер | push |
| Жалоба зарегистрирована / решена | клиент | push |
| Жалоба от руководителя организации | старший диспетчер | push + панель, SLA-таймер |
| Лимит наличных у мастера превышен | мастер + админ | push + SMS |

## 12. Веб-панель «Диспетчерская»
- Доска заявок (kanban по статусам) + карта города с мастерами (последняя гео при активной заявке) и заявками
- Тепловая карта дня (17.3): загрузка мастеров по часам, риск срыва окон красным, очередь срочных и лист ожидания, предложения перебалансировки
- Ленты мастеров (17.3): маршрут дня каждого мастера, drag-and-drop правка с автоматическими пушами затронутым; зонный фильтр по умолчанию, старший смены видит все зоны; метрики здоровья сетки (churn, дыры, пробег)
- Карточка заявки: всё из 3.4 + звонок клиенту/мастеру (клик-ту-колл через телефонию, фаза 2 — запись звонков)
- Очередь проверки: фото до/после и чеки на модерацию, кнопки «Принять» / «Вернуть с комментарием»
- **Телефонный клиент — полный флоу (обязательный сценарий: половина B2C будет звонить, приложение им не нужно):**
  1. Входящий звонок → автопоиск клиента по номеру (существующий — карточка с историей и паспортом техники сразу на экране; новый — карточка создаётся за 30 секунд: имя, адрес)
  2. Диспетчер заполняет заявку голосом клиента: категория, описание, позиции прайса с озвучиванием вилки цены
  3. **Окно согласуется прямо в разговоре:** диспетчер видит живой планировщик (17.3) и предлагает реальные варианты — «могу сегодня 16:00–18:00 или завтра с утра»; клиент выбирает → бронь встаёт в ленту, мастер назначается сразу, не вешая трубку. Клиенту озвучивается: имя мастера и окно
  4. Все устные согласования (смета, доп-смета, перенос) диспетчер фиксирует от имени клиента с пометкой «озвучено по телефону» — в аудит
  5. **Жизнь заявки без приложения — через SMS и веб-ссылку:** клиенту уходит SMS со ссылкой на лёгкую веб-карточку заявки (без установки и регистрации; ссылка содержит одноразовый подписанный токен с ограниченным сроком жизни — действия по ней журналируются как подтверждения клиента, чужой заявку по перебору URL не откроет): статус, карточка мастера, ETA, смета с кнопкой «Согласен», акт с фото до/после, онлайн-оплата, оценка. Кто не открывает и ссылку — ключевые события дублируются SMS-текстом (назначен + окно; мастер выехал + ETA; акт готов), оплата — наличными или QR с экрана мастера, оценка и контроль качества — QC-звонком (17.11)
  6. Пропущенный входящий → задача «перезвонить за 10 минут» в очередь «Позвонить» (17.11) — пропущенный звонок это упущенная заявка
  7. Ненавязчивый перевод в приложение: в SMS после первой закрытой заявки — ссылка «в приложении удобнее: история, гарантия, запись в два тапа»; без спама (один раз, параметр)
  Телефония: MVP — обычные номера и ручной ввод; фаза 2 — клик-ту-колл, запись разговоров, автоподстановка звонящего
- Споры: карточка спора, материалы, резолюция; споры выше порога и споры по заявкам, которые вёл сам диспетчер, — эскалация админу/старшему диспетчеру
- Выборочные контрольные прозвоны отменённых заявок (анти-сговор «отменим и сделаем мимо кассы»): система ставит N% отмен в очередь диспетчеру (параметр)
- Расписание мастеров, переназначения, «раздел заявки»
- Очередь жалоб (17.10) со SLA-таймерами и плейбуком резолюций
- Очередь «Позвонить» (17.11): задачи-звонки по триггерам с приоритетами, SLA, скриптами и фиксацией исходов — включая QC-прозвоны и B2B-ритм клиентского успеха
- Передача смены (24/7): handover-журнал — незакрытые инциденты, ожидания утверждений, VIP-контроли переходят следующей смене с явной отметкой приёма; ничего не живёт «в голове ушедшего диспетчера»
## 13. Веб-панель «Админ»
- Прайс: позиции, версии, коэффициенты (все параметры из 3.7 и упомянутые «(параметр)»), валидация unit-экономики при сохранении

## 14. Нефункциональные требования
- **Языки:** русский + узбекский (латиница) во всех клиентских интерфейсах с первого релиза; админка — русский
- **Валюта:** сум, без копеек, разряды пробелами; единое правило округления (8.1)
- **Время:** интерфейсы и отчёты — Asia/Tashkent (UTC+5); хранение и логи — UTC
- **Производственный календарь Узбекистана** (Навруз, Курбан-байрам, переносы): справочник нерабочих дней в админке. Все деловые таймеры — эскалации утверждений (5.3), дунинг (8.9), авто-отмена «не согласовано», SLA жалоб и звонков — считаются с учётом нерабочих дней (параметр каждого таймера: календарные/рабочие часы). Иначе авто-отмена сработает посреди трёхдневного праздника, когда утверждающий физически не мог ответить. Планировщик в праздники — режим выходного дня (ёмкость по праздничному графику мастеров)
- **Язык коммуникаций:** SMS, push, веб-карточка заявки и документы клиенту — на языке из профиля (рус/узб); все шаблоны уведомлений двуязычные
- **Аутентификация:** телефон + OTP SMS; JWT с ротацией; роли на уровне API (каждый эндпоинт проверяет контекст организации/точки — сотрудник аптеки не должен получить чужие данные даже прямым запросом к API)
- **Смена номера / передача аккаунта:** смена телефона (= логина) — только через диспетчера/поддержку с верификацией личности; передача аккаунта мастера другому лицу запрещена — клиент видит фото мастера, причина спора «приехал не тот мастер». **Смена фото мастера — только через админа** (новое фото — только камерой при личной явке/видеоверификации, старое в истории, аудит): самостоятельная смена фото в профиле — это лазейка передачи аккаунта, поэтому в приложении мастера её нет
- **Фото:** сжатие на клиенте до ~1600px/500КБ, EXIF-очистка, серверный таймштамп (для офлайна — см. 7.2), гео в метаданных записи (не в EXIF, допускается null с флагом), хранение в объектном хранилище, доступ только по подписанным ссылкам (signed URL) участникам заявки, вечное для закрытых заявок (это юридический архив)
- **Персональные данные:** по закону РУз «О персональных данных» (ЗРУ-547) персданные граждан Узбекистана должны храниться на серверах на территории Узбекистана — выбор хостинга/ЦОД с учётом этого требования; подтвердить у юриста на старте проекта
- **Оффлайн:** приложение мастера полностью функционально без сети (7.2), синхронизация идемпотентна
- **Аудит:** append-only лог, без физического удаления записей
- **Резервирование:** ежедневные бэкапы БД + хранилища, восстановление ≤ 4 часов
- **Нагрузка (горизонт 2 года):** 200 мастеров, 5 000 заявок/мес, 500 организаций — обычный монолит + очередь задач справится; микросервисы не нужны, не усложнять
- **Стек (утверждён владельцем, v2.24):** Flutter (2 приложения), бэкенд — единый модульный монолит **NestJS (TypeScript)** (типизация — критична для статусных машин и биллинга), веб-панели — **React**, лендинги — **Next.js (SSR)**, ORM — **Prisma** (схема как код, дисциплинированные миграции), **монорепозиторий** с общими типами API, PostgreSQL, Redis (очереди/кеш, BullMQ), S3-совместимое хранилище, FCM для push. Логика выбора: один язык (TypeScript) на бэкенд, панели и лендинги — команда взаимозаменяема, пул JS-разработчиков в Ташкенте — второй по размеру; инфраструктура старта — без Kubernetes: два сервера в ЦОД РУз (приложение+воркеры / БД), Docker Compose, CI/CD, ежедневные бэкапы с копией во вторую площадку (DEV-04)
- **Мониторинг и эксплуатация:** сбор ошибок (Sentry или аналог), метрики и алерты (очередь синка мастеров, доставка push/SMS, вебхуки платёжек, баланс-чекер), лог-агрегация; ответственный за реагирование — в регламенте эксплуатации
- **Обновления приложений:** механизм force update (минимальная поддерживаемая версия — экран «обновите приложение»); версионирование API; feature flags для поэтапного включения функций
- **Документы:** шаблоны актов и СФ двуязычные (рус/узб) — выбор в настройках организации (гос- и нацкомпании часто требуют узбекский)
- **Интеграции:** Payme, Click, Uzum merchant API (включая refund); ЭДО (didox/faktura — адаптер); SMS-шлюз (Eskiz/PlayMobile); карты (Yandex Maps / Google — учесть стоимость лицензии); экспорт проводок и СФ в 1С (бухгалтерии УЗ живут в 1С — формат уточнить у бухгалтера, фаза 2–3)

## 15. Этапность разработки
### Фаза 1 — MVP (целевой срок 4–5 месяцев, команда: 2 Flutter, 2 backend, 1 дизайнер, 1 QA, ПМ)
Входит: роли и иерархия B2B; заявки со всей статусной моделью и фото-циклом; лимиты и утверждения (одноуровневые); аварийная ветка; авто-распределение (простое: зона+skill) + ручное назначение; биллинг: абонентка, доли мастеров, наличные B2C, СФ вручную-полуавтоматом (PDF без ЭДО); акт по заявке PDF; месячный отчёт PDF; push-уведомления; диспетчерская; админка (прайс, организации, балансы); оплата Payme + Click (включая refund-API); оффлайн-режим мастера; реестр дебиторки с aging и актом сверки (оплаты отмечаются вручную); расходники «сумки» по фиксированному прайсу; импорт прайса из Excel и инструмент начальных остатков (17.6); статусы онбординга мастеров в админке; нормо-часы позиций и базовый календарь мастера; промокоды B2C и чаевые (решения владельца); режим 24/7 с ночным коэффициентом; резервный фонд ущербов (проводка отчислений, 17.7); реестр оборудования с актами выдачи/возврата и фильтром распределения (17.9); жалобы: типы, статусы, очередь, плейбук (17.10); паспорт техники клиента + контрольное касание «как дела» через 7 дней (17.12 — база копится с первого дня); полный телефонный флоу с веб-карточкой заявки без приложения (12); программа баллов персонала точек с ваучерами из пула (17.14 — опция договора); лендинги B2C/B2B/мастерам с лид-контуром и UTM (17.15); рус/узб.
Уточнения скоупа MVP: плановые осмотры в MVP создаёт диспетчер вручную (тип «осмотр», чек-лист, дефекты простым списком) — авто-график InspectionSchedule в фазе 2; короткие напоминания по доп-сметам (30 мин / 2 ч, см. 5.3) входят в MVP, полная матрица эскалаций по сметам (24/48/72 ч) — фаза 2; чат с диспетчером в MVP заменён звонком и шаблонными сообщениями.
Не входит в MVP: техдолг как отдельный модуль (дефекты пишутся простым списком), пакетные утверждения, ЭДО-интеграция, многоуровневые пороги, рейтинг авто-расчётом (вручную диспетчером), склад, телефония, полноценный чат, Uzum, партнёрские магазины (в MVP мастер покупает за свои), автоматический дунинг и пени (напоминания вручную бухгалтером), количественный учёт «сумки».
### Фаза 2 (2–3 месяца после запуска)
Техдолг + пакетные утверждения + отчёт по осмотру; ЭДО; многоуровневые пороги и двойное утверждение; авто-рейтинг по формулам 7.4; эскалации по таймерам; партнёрские магазины (коды закупки, кредиторка, реестры погашения); количественный учёт «сумки» мастера; автоматический дунинг и пени; импорт банковской выписки; калькулятор абонентки и КП; графики/отпуска мастеров и слоты по нормо-часам; бейджи мастеров с QR; KPI диспетчерской; субподряд лицензиата — газ/лифты (17.8); отчёт SLA ≤ 60 мин по авариям; грейд Золото 57%; амортизационные проводки и ТО-график оборудования (17.9); паттерн-детект жалоб и корневые причины (17.10); регламентные напоминания, сезонные кампании и экран «Моя техника» (17.12); телефония с записью; Uzum; дашборд владельца.
### Фаза 3
Склад расходников; личные кабинеты партнёрских магазинов; proxy-номера для звонков; сервисные напоминания B2C по истории; Telegram-бот как лёгкий канал B2C; подписки для физлиц («домашний мастер» — абонентка для квартир); ИИ-оценка сметы по фото; интеграция с CRM-системами клиентов; английский язык.
### Критерии приёмки MVP (примеры, полный список — приложение при контрактовании)
1. Заявка не может перейти в «Выполнена» без фото «после» — проверяется на API-уровне, не только в UI
2. Смета выше лимита точки не запускается в работу ни при каком сценарии без записи об утверждении в аудите
3. Закрытие заявки порождает корректные проводки во всех четырёх схемах оплаты (абонентка/СФ/онлайн/наличные) — сверка тест-кейсами
4. Акт PDF собирается из данных заявки без ручного ввода
5. Мастер завершает заявку в подвале без сети; данные доезжают при появлении сети без потерь и дублей (повторная синхронизация тех же операций не меняет состояние)
6. Возврат по спору проводится через refund-API провайдера и порождает корректную сторнирующую проводку
7. Пять сквозных прогонов проходят без ручных правок данных: (а) B2C онлайн, (б) B2C наличные, (в) B2B абонентка, (г) B2B сверхлимит, (д) B2B разовая с предоплатой — от создания заявки до ведомости выплат и налоговых регистров; суммы сходятся на каждом шаге

|---|---|

| Мастер приписывает материалы | фото чека обязательно, лимит закупки, модерация диспетчером |
| Фейковые фото | только камера (без галереи), серверное время, гео |
| Простой из-за молчания утверждающего | таймеры эскалации, документированная авто-отмена; для доп-смет — короткие таймеры + звонок |

| Оборудование компании теряется/убивается | акты выдачи с фото, материальная ответственность, удержание остаточной стоимости по вине, ТО-график |
| Конфигурация «работаем в минус» | валидация unit-экономики коэффициентов в админке |
| Сговор «отменим и сделаем мимо кассы» | контрольные прозвоны отменённых заявок, экономика безнала, поток заявок по рейтингу |

| Приписки расходников | фикс-прайс каталога, нормативы расхода по категориям, флаг при превышении |

| Мастер копирует базу клиентов | телефон клиента только на время заявки, звонки кнопкой, минимум данных в приложении |

### 17.1. Онбординг мастера
Воронка: анкета (телефон, ФИО, skill-теги, опыт, фото) → проверка документов (паспорт, статус самозанятого/ГПХ) → собеседование + практическая проверка навыков по чек-листу категории → обучение стандартам платформы (фото-фиксация, общение с клиентом, работа в приложении) с мини-экзаменом прямо в приложении → подписание договора → активация с испытательным периодом (7.4).
Статусы кандидата: `анкета` → `проверка` → `обучение` → `активен` / `отклонён` — ведутся в админке, конверсия воронки видна на дашборде.
Реферальная программа «приведи мастера» — **включена (решение владельца)**: бонус рекомендателю после 20 закрытых заявок приведённого (размер бонуса — параметр); начисление на баланс мастера проводкой.
Форма и бейдж с QR-кодом (клиент сканирует — видит карточку мастера и подтверждение, что он от компании) — фаза 2.
**Комплект новичка:** форма, бейдж, стартовый набор расходников «сумки» — за счёт компании или удержанием из первых выплат (параметр). Стандарты сервиса в обучении: бахилы, коврик под инструмент, уборка после работ — нарушение фиксируется жалобами (17.10).
**Новые skill-теги** действующему мастеру — только через практический экзамен (запись в аудит); самопровозглашённых навыков нет.
### 17.2. Онбординг организации B2B и калькулятор абонентки
Воронка: лид → демо (демо-организация с сидированными данными — инструмент продавца) → **первичный аудит-осмотр объекта** (платный; при подписании договора зачитывается в первый месяц — параметр) → заполнение паспортов объектов → **калькулятор абонентки**: базовые ставки по типу объекта (сум/м²) + надбавки за санузлы, кондиционеры, щитки (коэффициенты в админке) × число точек → КП в PDF прямо из калькулятора → договор → создание структуры (организация, точки, пользователи) админом → SMS-приглашения пользователям.
Продление: за 30 дней до конца договора — авто-отчёт «выбрано работ за период vs заплачено абонентки» + рекомендация пересмотра суммы (статистика заявок + паспорт объекта). Это же — аргумент удержания: клиент видит, что абонентка окупается.
### 17.3. Ёмкость, слоты и график мастеров
- У каждой позиции прайса — нормативная длительность (3.7). Смета заявки → расчётная длительность → заявка занимает конкретные слоты в календаре мастера. Без этого «двухчасовые окна» — фикция
- График мастера: рабочие дни/часы, отпуска и больничные (мастер запрашивает в приложении, диспетчер подтверждает) — календарь доступности учитывается авто-распределением
- Перегрузка: нет свободных слотов сегодня — клиенту честно предлагаются ближайшие доступные окна (пусть и завтра); аварийные заявки вытесняют плановые — диспетчер видит конфликт и переносит плановую с извинением и push
- **Режим массового инцидента:** при > N заявок одной категории из одного района за час (авария сети, отключение) — диспетчер включает «инцидент»: заявки группируются по кластеру, клиентам шаблонное оповещение «в вашем районе массовое отключение, мастера направлены», приоритизация внутри кластера
- KPI диспетчерской (дашборд админа): время «Новая» → «Назначена», время модерации фото, доля заявок с нарушенным окном, время резолюции споров. Диспетчер — узкое горлышко системы, его метрики должны быть видны
**Планировщик окон — диспетчеризация в реальном времени.** Сценарий-камертон: 5 мастеров, все ушли на заявки, приходит шестая B2C-заявка — что обещать клиенту? Механика:
- **Календарь мастера — сетка 30-минутных слотов.** Заявка бронирует слоты = нормо-часы сметы + дорожный буфер (время до адреса по карте + запас, параметр по умолч. 20%). По каждой активной заявке система знает расчётное завершение: старт + нормо-часы. Этапные работы (4.1) бронируют все сессии сразу с учётом технологических пауз — в паузах мастер свободен для других заявок; заблокированные третьей стороной встают якорем на подтверждённое время доступа
- **Клиенту показываются только реально доступные окна.** При создании заявки система перебирает подходящих мастеров (skill + зона) и предлагает окна, под которые есть свободные слоты: «сегодня 16:00–18:00, 18:00–20:00, завтра с 10:00». Все заняты до вечера — честно показываем завтра. Никогда не обещаем то, под что нет ёмкости
- **Тариф «Срочно» (решение владельца: срочность — платная):** клиенту, которому не терпится, но это не авария, предлагается выбор: «в удобное окно — обычная цена» или «Срочно: ближайший освободившийся мастер, +{коэффициент срочности}% к работам» (параметр прайса, по умолч. +30%; применяется как аварийная наценка — только к работам; доля мастера считается с наценкой, поэтому мастерам выгодно хватать срочные). Срочная заявка идёт впереди обычных ожидающих в борьбе за свободную ёмкость и получает доступ к аварийному резерву (если аварий нет). Подтверждённые брони других клиентов ради срочной НЕ ломаются — обещания святы. **Правило честности:** если срочную не удалось начать за X часов (параметр, по умолч. 3 ч) — наценка снимается автоматически, клиент получает push «не успели — срочность не тарифицируем» и предложение ближайшего окна; доля мастера в этом случае — от базовой цены (наценки нет ни для кого). Тариф «Срочно» доступен и B2B вне аварий (списание с абонентки: базовая × срочность × подписной коэффициент; санкция — по обычной матрице лимитов 5.1)
- **Бесплатный лист ожидания:** не хочешь платить за срочность — заявка ждёт свободной ёмкости после броней (честный прогнозный интервал: «ориентировочно 15:30–17:30, уточним, когда мастер освободится»)
- **Кнопка мастера «Задерживаюсь +30/60 мин»:** доп-работы затянули — мастер честно сдвигает план одной кнопкой. Каскадный пересчёт его очереди; если сдвиг выбивает следующую заявку за обещанное окно — алерт диспетчеру с вариантами: переназначить другому свободному, предложить клиенту сдвиг (проактивный push с извинением и новым временем)
- **Проактивная коммуникация — главное лекарство от хаоса:** клиент узнаёт о задержке от нас в момент, когда прогноз вышел за границу окна, а не когда сам звонит злой. До выезда клиент видит «мастер завершает предыдущий заказ, приедет ~16:40», после выезда — ETA по карте
- **Аварийный резерв:** параметр «X% ёмкости часа не бронируется под плановые» — держим люфт под аварийные. Аварий нет — резерв отдаётся срочным (сразу) и листу ожидания (за 2 ч до начала)
- **Перегруз дня:** спрос > ёмкость → окна «сегодня» закрываются автоматически, клики клиентов по недоступным окнам считаются как **упущенный спрос** — метрика на дашборде бизнеса, прямой сигнал «пора нанимать мастеров»
- **Освободившийся слот не пропадает:** отмена брони или ранний финиш → слот немедленно предлагается по приоритетам: срочным → листу ожидания (авто-push «появилось окно сегодня 16:00, подтвердить?») → подтягивание гибких заявок из хвоста ленты
- **Тепловая карта дня у диспетчера:** загрузка мастеров по часам, красная подсветка заявок с риском срыва окна (прогноз завершения предыдущей работы позже начала следующей), предложения перебалансировки между мастерами. Диспетчер всегда может перекроить план вручную — планировщик советует, человек решает
- **Этапность:** MVP — окна из календарей по нормо-часам + фикс. буфер, очередь срочных и лист ожидания ведёт диспетчер с подсказкой «кто освободится раньше», сдвиги — алерт и ручное решение. Фаза 2 — авто-пересчёт ETA, тепловая карта, перебалансировка. Фаза 3 — прогноз длительности по накопленной истории (факт vs нормо-час по категориям и мастерам)
**Приоритеты очереди при постоянном перегрузе.** Спрос стабильно больше ёмкости — это норма жизни растущего сервиса, а не сбой. Порядок доступа к слотам (сверху вниз):
1. **Аварийные** — всегда первыми (+ аварийный резерв ёмкости)
2. **B2B в договорном окне** — срыв бьёт по продлению абонентки, это самые дорогие обещания
3. **Гарантийные** — наша вина; сорвать повторный визит — удвоить ущерб репутации
4. **Продолжения начатых этапных работ** (4.1) — объект вскрыт/не досох, бросить нельзя; слот ищется в допустимом окне этапа
5. **Срочные (платный тариф «Срочно»)** — впереди обычных ожидающих за свободную ёмкость + доступ к аварийному резерву; подтверждённые брони не ломают
6. **B2C с забронированным окном** — FIFO по времени брони
7. **Бесплатный лист ожидания** — FIFO
8. **Плановые осмотры** — фоновый демпфер и главный амортизатор перегруза: планируются на непиковые часы, автоматически уступают слоты и двигаются в пределах недели — клиент не ждёт осмотр с секундомером
Внутри уровня — строгий FIFO; ручной подъём приоритета диспетчером — только с причиной в аудит. **Денежных компенсаций за сдвиги нет** — валюта извинений: приоритетный слот на перенос, пометка «VIP-контроль» на следующую заявку клиента (личный контроль диспетчера), проактивная связь. Сурж-наценка в пиковые часы — параметр, по умолчанию выключен (Открытые вопросы).
**Дежурный резерв («скорая помощь»).** Каждый день один мастер — дежурный (ротация по недельному графику, составляет диспетчер; в идеале универсал сантехника+электрика — самые частые категории):
- Планировщик не бронирует дежурному плановые заявки; его работа — аварийные, экстренные замены и переполнение срочных
- **Оплата: гарантированный минимум за смену дежурства** (параметр) + обычная доля с фактических выездов. Без минималки дежурство — наказание, и все будут от него бегать; с минималкой — нормальная ротация
- Тихий день: с середины смены дежурному отдаются срочные и заявки листа ожидания рядом с его зоной (минимум простаивает, но остаётся ближним резервом)
**Протокол быстрой замены: мастер исчез или отказался. Цель — новый мастер за 15 минут.**
Детект (автоматический, диспетчер подключается вторым):
- Мастер не нажал «Выехал» за 30 мин до окна (параметр) → авто-пинг push+SMS → нет реакции 10 мин → алерт диспетчеру + автозапуск протокола
- Явный отказ после принятия — кнопка «Не могу поехать» с причиной → протокол сразу. Ранний честный отказ наказывается мягче тихого исчезновения: мастера должны говорить, а не прятаться
- После «Выехал» гео не приближается к адресу 15+ мин → мягкий флаг диспетчеру (звонок)
Замена:
1. Заявка получает флаг «Требуется замена» — красная, вверх доски диспетчера
2. Система собирает кандидатов по порядку: дежурный резерв → свободные рядом с нужным skill → те, у кого расчётное завершение в ближайшие 30 мин → снять мастера с гибкой заявки (планового осмотра) и перекинуть
3. Экспресс-оффер **бродкастом всем кандидатам сразу**: 120 сек, первый принявший забирает. Для замен оффер параллельный, не последовательный — скорость важнее вежливости очереди
4. Клиенту немедленно push: «Мастер заменён, к вам едет {имя}, будет к {время}» (или честный сдвиг окна). Молчание запрещено — клиент не должен узнать о проблеме сам
5. За 15 мин никто не взял → диспетчер звонит клиенту с двумя вариантами: сдвиг на сегодня позже или перенос на завтра с приоритетным первым окном и VIP-контролем
Последствия для исчезнувшего:
- Уважительная причина (болезнь, форс-мажор — подтверждает диспетчер) — без санкций, отметка в профиле
- Невыход без причины: удар по компоненте дисциплины рейтинга + счётчик невыходов: второй за 90 дней — снятие с линии и разбор, третий — блокировка; невыход с ущербом (сорванная авария, потерянный B2B-клиент) — денежное удержание (7.4)
- Градация жёсткости: явный отказ заранее — мягче; тихий невыход — максимальные санкции
**Парные работы: два человека там, где одному физически нельзя.**
Принцип: соло — по умолчанию, пара — по требованию позиции, экипаж — если статистика докажет. Никаких постоянных бригад с делёжкой пополам.
- **Роли, а не равные партнёры:** в парной заявке есть **ведущий** (нужный skill-тег, отвечает за работу, смету, фото-цикл, приёмку) и **помощник** (физическая помощь: поднять, подержать, подать). Деньги — по ролям: ведущий получает основную долю, помощник — меньшую или фиксированную ставку за сессию (параметры; пример: ведущий 40% + помощник 20% от суммы работ — парные позиции в прайсе дороже, так что суммарные 60% экономика выдерживает). «Прибыль пополам» — неправильно, и её здесь нет: ответственность и квалификация у ведущего
- **Планирование пары:** парная позиция в смете → планировщик ищет пересечение свободных слотов двух лент в одной зоне (ведущий по skill-тегу; помощник — любой свободный, включая младшие грейды и кандидатов на испытательном — для них это и подработка, и обучение). Каждый едет сам; сбор на объекте
- **«Нужен помощник» на месте:** мастер вскрыл работу и понял, что одному никак → кнопка «Нужен помощник» → мини-оффер бродкастом ближайшим свободным и дежурному: «подсобить ~2 ч, фикс + дорога» → первый принявший едет. Никого нет — работа переносится на ближайший парный слот (механика инварианта этапных работ). **Кто платит фикс помощника, если позиция не была парной:** клиент — никогда (цена для него не меняется); если объективно нельзя было предвидеть (скрытые условия) — расход компании; если ведущий недооценил очевидное — из доли ведущего (решает диспетчер, в аудит)
- **Карточка помощника — упрощённая:** адрес, время, ведущий, фикс — без конвейера, смет и фото-цикла (всё это на ведущем). На рейтинг помощь не влияет; исключение — невыход помощника на принятый оффер: обычные санкции невыхода (17.3)
- **Экипаж дня (фаза 2, включается статистикой):** если доля парных заявок в категории окажется высокой (метрика на дашборде бизнеса), диспетчер формирует на день экипаж — ведущий + помощник с одной общей лентой (едут вместе, машина одна): меньше логистики, выше пропускная способность по тяжёлым категориям. Экипаж — режим дня, не постоянная структура; роли и деление денег те же
- **Транспортный фильтр:** у мастера — признак «свой авто с инструментом»; заявки, требующие машину или крупное оборудование (17.9), планировщик отдаёт только автомобильным; «какой Дамас куда едет» решается на уровне сборки лент — заявка с оборудованием попадает в ленту того, у кого это оборудование и транспорт уже на руках
**Рабочая сетка при масштабе: 300 мастеров, 1500 заявок в день — как не сломаться.**
Принцип: три горизонта планирования + пространственная декомпозиция + запрет глобальной пересборки в течение дня. Каша начинается там, где всё планируется одновременно и всё можно двигать всегда.
- **Три горизонта:**
  - **Неделя:** графики смен и дежурств; пул плановых осмотров раскладывается по «низким» дням и часам
  - **День (сборка накануне вечером):** система собирает черновики лент на завтра
  - **Реальное время:** только локальные событийные операции — никакого перепланирования всего
- **Зонная декомпозиция — ключ к масштабу.** Город = зоны (районы). Мастер на день закрепляется за 1–2 смежными зонами; кросс-зонные переезды — только аварии и замены. Клиенту предлагаются окна тогда, когда в его зоне есть ёмкость. Задача «300 × 1500» глобально нерешаема и не нужна: зонирование режет её на независимые подзадачи «5–8 мастеров × 20–30 заявок», где хватает жадного алгоритма с локальными улучшениями. Никакой rocket science
- **Лента мастера — ячейка сетки (мастер × день):** упорядоченная последовательность заявок. Правила сборки: якорные заявки (жёсткие окна клиентов, графики доступа B2B-точек) ставятся первыми; гибкие (осмотры, лист ожидания) заполняют дыры между ними; между соседними заявками — дорожный буфер по матрице времени езды зона→зона; **план дня ≤ 80% смены** (параметр) — 20% люфта на сюрпризы. Забитая под завязку лента ломается от первого чиха
- **Волновая сборка:** вечером D−1 — авто-черновики; утром зонный диспетчер за 15 минут просматривает аномалии и подтверждает (правит, а не собирает руками); мастер видит завтрашний маршрут с вечера и утром сразу едет
- **Правило заморозки (анти-каша №1):** ближайшие 2 часа каждой ленты неприкосновенны для автоматики — трогать может только диспетчер вручную. Мастер уже едет по этому куску; автоматика играет только с хвостом дня
- **Интрадей — события, а не пересборка (анти-каша №2):** в течение дня глобальная переоптимизация запрещена. Разрешены четыре атомарные операции: вставить заявку в дыру ленты; сдвинуть хвост ленты; обменять две заявки между мастерами; заменить мастера (протокол выше). Каждая операция рассылает пуши всем затронутым. Полная пересборка — только вручную, старшим смены, при массовом инциденте
- **Зонная диспетчеризация:** диспетчерская шардируется по зонам — зонный диспетчер ведёт свои районы (норматив: 1 диспетчер на 50–70 мастеров), старший смены видит всю картину; панель по умолчанию фильтрована зоной диспетчера
- **Метрики здоровья сетки:** доля заявок, закрытых в окно; средний пробег на заявку; дыры в лентах; churn лент (сколько раз лента менялась за день — чем меньше, тем стабильнее); доля интрадей-вставок. Растущий churn — ранний симптом каши, виден на дашборде до того, как посыпались окна
- **Этапность:** MVP — сборка лент жадным алгоритмом по зонам + ручная правка (достаточно до ~100 мастеров); фаза 2 — зонное шардирование диспетчеров, авто-улучшатели лент, churn-метрики; фаза 3 — полноценный оптимизатор сборки D−1 с обучением на истории
### 17.4. Зоны покрытия и экспансия
Справочник зон (районы Ташкента) + city_id во всех геопривязанных сущностях с первого дня — задел на второй город, который дёшев сейчас и дорог потом. Адрес вне зоны покрытия: заявка не создаётся, телефон и адрес сохраняются в лид-лист «ждут покрытия» — данные для решения об экспансии.
### 17.5. Защита от увода клиентов и безопасность
- Телефон клиента доступен мастеру только со статуса «Назначена» до «Закрыта», затем маскируется; звонок — кнопкой из приложения (номер не отображается для копирования). Полная маскировка через proxy-номера — фаза 3
- В приложении мастера — минимум данных клиента: имя, адрес, подъезд; истории заявок клиента мастер не видит
- Чёрный список клиентов: после подтверждённого диспетчером неадеквата/угроз B2C-аккаунт блокируется; у мастера есть кнопка «Прервать: небезопасно» (фото/комментарий → диспетчер решает, отмена без штрафа мастеру)
### 17.6a. Режим 24/7 (решение владельца)
Платформа принимает заявки круглосуточно. Ночь (22:00–07:00, параметры): ночная смена диспетчерской (минимум 1 диспетчер), ночные зонные дежурные мастера (минималка ночной смены выше дневной), ночной коэффициент к работам (параметр прайса, применяется как аварийная наценка — только к работам, доля мастера считается с учётом коэффициента). Плановые заявки на ночные окна для B2C не бронируются: ночь — аварии и срочные по желанию клиента за ночной тариф. **Исключение — B2B-точки с ночным графиком доступа** (пекарни, клубы, склады, которые пускают мастеров только ночью): для них плановые ночные окна доступны; тариф — ночной коэффициент или особые условия договора (параметр организации). Иначе целый класс B2B-клиентов не смог бы получить плановое обслуживание вообще. **Ночью наценка «Срочно» не применяется** — действует только ночной коэффициент (он уже премиальный, двойное умножение запрещено); наценки аварийности, ночная и срочности взаимоисключающие, применяется одна — наибольшая из применимых.
### 17.7. Ответственность за ущерб: резервный фонд (страховых продуктов на рынке нет)
Мастер затопил соседей, сгорела проводка после ремонта — юридически отвечает компания. Готового страхования такого рода в Узбекистане нет, поэтому механизм свой:
- **Резервный фонд ущербов:** отчисление % от выручки работ (параметр, старт 1–2%) автоматической проводкой на счёт «резерв ущербов» в биллинге. Фонд виден админу: накоплено / выплачено / динамика
- **Ограничение ответственности в оферте B2C и договорах B2B:** компания возмещает прямой документально подтверждённый ущерб, причинённый работой мастера, в пределах потолка (параметр: фиксированная сумма или кратное стоимости работ — формулировки и потолок готовит юрист). Косвенные убытки (упущенная выгода) — исключены
- **Процедура разбора ущерба:** заявление клиента (фото, описание) → выезд старшего мастера/диспетчера → акт осмотра ущерба с фото → резолюция админа: выплата из фонда / частичная / отказ (всё в аудит) → выплата проводкой из резерва
- **Регресс к мастеру:** при доказанной грубой халатности (квалифицирует разбор) — удержание доли ущерба с баланса мастера частями, не более 30% каждой выплаты (параметр); при споре мастер может апеллировать админу
- **Мониторинг рынка:** раз в полгода проверять появление страховых продуктов ГО у страховщиков УЗ — при появлении фонд заменяется/дополняется полисом
Гарантийные переделки (брак работы без ущерба третьим лицам) — отдельный существующий механизм 4.2 и фондом не покрываются.
### 17.9. Парк оборудования компании и амортизация
Дорогая техника, которую мастеру покупать самому нерационально: прочистные машины («крот»), течеискатели, тепловизор, сварочные аппараты ПП больших диаметров, вакуумные станции и манометрические коллекторы для фреона, генератор, промышленный пылесос, леса/стремянки.
- **Учёт (сущность Equipment):** инвентарный номер, категория, стоимость покупки, дата, нормативный срок службы, остаточная стоимость, статус: `на складе` / `выдано мастеру` / `в ремонте (ТО)` / `списано`
- **Выдача под материальную ответственность:** акт выдачи прямо в приложении — фото состояния со всех сторон, мастер подтверждает кодом; возврат тем же актом с фото. Утеря или поломка по вине — разбор (как в 17.7), удержание 0/50/100% остаточной стоимости (параметр), частями не более 30% каждой выплаты
- **Амортизация:** ежемесячная автоматическая проводка «расход амортизации» по линейной норме (стоимость ÷ срок службы) — видна в P&L админа. Позиции прайса, требующие спецоборудование, ценятся с учётом амортизации — валидатор unit-экономики (3.7) это проверяет
- **Распределение заявок:** позиция прайса может требовать оборудование — аналог skill-тега («требует: прочистная машина»); планировщик предлагает такие заявки только мастерам с выданным оборудованием
- **ТО:** график обслуживания; статус «в ремонте» исключает оборудование (и зависящие от него заявки у этого мастера) из планирования; напоминания админу
- **MVP:** реестр + акты выдачи/возврата + фильтр распределения. Амортизационные проводки и ТО-график — фаза 2
### 17.10. Жалобы и обращения клиентов (support-контур)
Спор (4.2) — про деньги конкретной заявки. Жалоба — шире: хамство, грязь после работ, опоздание, курение на объекте, работа диспетчера, глюки приложения. Отдельный контур:
- **Сущность Complaint:** тип (`качество` / `поведение мастера` / `сроки` / `деньги` → конвертируется в спор / `сервис и диспетчер` / `приложение` / `другое`), связь с заявкой (опционально — жалоба может быть и без заявки), кто подал, статус: `новая` → `в работе` → `решена` → `закрыта` (подтверждение клиента или таймаут 72 ч), ответственный, резолюция, корневая причина из справочника
- **Каналы:** кнопка «Пожаловаться» в приложении у всех клиентских ролей; телефон диспетчера; жалоба руководителя организации автоматически эскалируется старшему диспетчеру сразу
- **SLA обработки:** первый ответ ≤ 2 ч в дневном окне 8:00–22:00 (жалоба ночью — таймер стартует с 8:00; аварийное ночью — это не жалоба, а авария), резолюция ≤ 24 ч, сложные ≤ 72 ч (параметры, с учётом производственного календаря); просрочка — эскалация админу; SLA жалоб входит в KPI диспетчерской (17.3)
- **Плейбук решений (справочник методов):** извинение + VIP-контроль следующей заявки; переделка (гарантийная механика 4.2); частичный/полный возврат (через спор с проводками); замена закреплённого мастера точки; для B2B — звонок руководству + официальный ответ письмом. Каждая резолюция обязана ссылаться на метод из справочника — так копится аналитика «что реально чинит проблему»
- **Паттерн-детект (фаза 2):** 3+ подтверждённых жалобы на одного мастера за 30 дней → авто-разбор; повторная жалоба того же клиента по той же причине → немедленная эскалация
- **Связь с рейтингом:** подтверждённая жалоба на поведение/качество = событие уровня «оценка 1» в компоненте оценок — после резолюции, не в момент подачи; неподтверждённые жалобы на рейтинг не влияют
- **Аналитика:** дашборд жалоб по типам, корневым причинам, мастерам, динамике. Цель контура — не гасить жалобы, а устранять причины
- **MVP:** типизация, статусы, очередь жалоб у диспетчера, плейбук. Паттерн-детект и корневые причины — фаза 2
### 17.11. Матрица контактов «диспетчер ↔ клиент» и контроль качества
Все голосовые контакты — из единой очереди «Позвонить» в панели диспетчера: каждый триггер создаёт задачу-звонок с приоритетом, SLA и скриптом; исход звонка фиксируется (дозвонился/нет, результат, следующий шаг) в ContactLog. Ничего не держится «в памяти диспетчера».
Приоритеты внутри очереди (когда звонков больше, чем диспетчеров): операционные по активным заявкам (аварии, замены, «клиент недоступен», доп-сметы) → эскалации утверждений и дунинг → QC-прозвоны → B2B-ритм. Несрочные категории (QC, B2B-ритм, дунинг) звонятся только в дневное окно 9:00–20:00 (параметр) — ночная смена делает только операционные звонки.
**До работ:**
| Триггер | SLA звонка | Суть |
|---|---|---|
| Заявка создана по телефону | входящий | диспетчер создаёт заявку, подбирает позиции, читает вилку цены |
| Заявка непонятна (нет фото, «не знаю, что сломалось», нельзя оценить) | 15 мин | уточнение, помощь с фото |
| Внешняя зависимость не подтверждена (доступ ТСЖ) | 2 ч | помочь клиенту решить вопрос доступа, зафиксировать время |
| Нет ёмкости в желаемое окно | 30 мин | предложить варианты голосом (продажа ожидания/срочного тарифа) |
| Накануне дорогой или этапной работы (сумма > порога, параметр) | до 20:00 D−1 | подтверждение готовности: доступ, материалы, оплата |
**Во время работ:**
| Триггер | SLA | Суть |
|---|---|---|
| Сдвиг окна > 1 ч или повторный сдвиг | сразу | извинение голосом поверх push, новое время |
| Замена мастера не решена за 15 мин (протокол 17.3) | сразу | варианты переноса |
| «Клиент недоступен» от мастера | 15 мин прозвона | дозвон до отмены с ложным вызовом |
| Вынужденная доп-смета без ответа 2 ч (4.6, 5.3) | по таймеру | голосом объяснить, что стоит работа |
| Авария на точке B2B | автозвонок | контактному лицу для аварий |
| Молчание утверждающего T+48 (5.3) | по таймеру | звонок руководству |
**После работ — контроль качества (ядро раздела):**
| Триггер | SLA | Суть |
|---|---|---|
| **QC-выборка: N% закрытых заявок** (параметр, старт 10%) | 24–48 ч после закрытия | скрипт: качество, чистота, поведение мастера, «порекомендуете?» |
| **Обязательный QC-прозвон** — первая заявка нового B2C-клиента; заявки мастеров на испытательном; чек > порога; доп-смета выросла > 50% от первичной | 24–48 ч | те же вопросы + особое внимание к доверию |
| Оценка 1–2 | 2 ч | живой разбор до того, как клиент понесёт негатив наружу; при подтверждении — жалоба/спор по процедуре |
| Отменённые заявки, выборка N% | 48 ч | анти-сговор «сделали мимо кассы» (16) |
| Гарантийное обращение | 4 ч | подтверждение и назначение с извинением |
| Просрочка оплаты B2C T+30 (8.9) | по дунингу | вежливое напоминание голосом |
**B2B-ритм (клиентский успех):**
| Триггер | Кому | Суть |
|---|---|---|
| Выборка абонентки < 50% два месяца подряд | руководителю орг. | «почему не пользуетесь?» — удержание: неиспользуемая абонентка = расторжение через полгода |
| Сверхлимит > 30% абонентки два месяца | руководителю орг. | предложение пересмотра абонентки вверх (апсейл договора) |
| За 30 дней до окончания договора | руководителю орг. | звонок к продлению вместе с авто-отчётом (17.2) |
| Ежемесячный контакт для топ-организаций (параметр: топ-N по выручке) | руководителю орг. | «всё ли устраивает» — до того, как проблемы станут жалобами |
**KPI по матрице:** доля выполненных QC-прозвонов из выборки, время реакции по каждому триггеру, конверсия «звонок к продлению → продление» — в KPI диспетчерской (17.3). MVP: очередь «Позвонить» с триггерами, скрипты текстом, исходы вручную; фаза 2 — клик-ту-колл с записью разговоров, авто-создание жалоб из исходов.
### 17.12. Постпродажное обслуживание: сервисный след техники
Каждая закрытая заявка оставляет след — мы знаем, ЧТО за техника у клиента и ЧТО с ней делали. Этот след превращается в повторную выручку.
**Паспорт техники клиента (ClientAsset):** при выполнении работ мастер фиксирует обслуженную единицу: тип (кондиционер / котёл / бойлер / стиральная машина / смеситель…), бренд, модель, год — фото шильдика обязательно (OCR-распознавание — фаза 3, пока поля руками). У B2C копится «паспорт квартиры», у B2B это уже часть паспорта объекта. История всех работ привязывается к конкретной единице техники: «этот кондиционер чистили в мае, меняли плату в августе».
**Справочник сервисных интервалов (админка):** {тип техники, тип работы, регламентный интервал, сезонное окно}. Примеры: кондиционер — чистка фильтров каждые 6 мес, полная профилактика ежегодно перед сезоном (апрель–май); котёл — ТО перед отопительным сезоном (сентябрь–октябрь); бойлер — чистка ТЭНа ежегодно. Интервалы задаёт компания, а не мастер — мастер не может спамить клиента «рекомендациями».
**Автоматические касания (генерируются при закрытии заявки):**
| Касание | Когда | Механика |
|---|---|---|
| Контрольное «как дела» | через 7–14 дней после ремонта | push «Кондиционер работает нормально?» → «Всё отлично» / «Есть проблема» (проблема = гарантийная заявка одной кнопкой — ловим брак внутри гарантии) |
| Регламентное напоминание | по интервалу справочника | push «Прошло 6 месяцев после чистки кондиционера Samsung — рекомендуем чистку фильтров, ~150 000» → кнопка «Записаться» создаёт заявку с предзаполненной позицией и закреплённым мастером |
| Сезонная кампания | сезонное окно справочника | сегмент «есть кондиционер в паспорте + не было чистки N мес»; **рассылка волнами с учётом свободной ёмкости планировщика** (дневной лимит записей по зонам, параметр) — иначе кампания сама себе устраивает массовый перегруз; кондиционеры — апрель, котлы — октябрь |
| Конец гарантии | за 7 дней до истечения | «Гарантия заканчивается — проверьте работу, если что-то не так, исправим бесплатно»: честность, которая строит лояльность и ловит проблемы в гарантийный срок |
**Гигиена коммуникаций:** маркетинговое согласие — отдельный чекбокс (закон о персданных); частотный потолок — не более 1 сервисного push в 2 недели на клиента (параметр); отписка в один тап; SMS для сервисных касаний не используется (только push) — SMS зарезервирован за операционкой.
**Экономика и мотивация:** конверсия напоминаний в заявки и выручка follow-up — метрики дашборда (13); повторная заявка по напоминанию уходит закреплённому мастеру (приоритет; если он заблокирован/уволен/в отпуске — обычное распределение) — мастеру выгодно качественно работать и аккуратно заполнять паспорт техники (его будущие заявки). B2C-клиент может «запомнить мастера» после хорошего опыта — любимый мастер получает мягкий приоритет на его заявки (аналог закреплённого мастера точки, 3.2). Заполненность паспорта техники — в метрику качества фиксации мастера (7.4).
**Этапность:** MVP — фиксация техники в заявке (паспорт копится с первого дня!) + контрольное касание «как дела»; фаза 2 — справочник интервалов, регламентные напоминания, сезонные кампании, экран «Моя техника» у клиента; фаза 3 — OCR шильдиков, предиктивные подсказки по истории отказов моделей.
### 17.8. Субподряд лицензиата (газ, лифты) — фаза 2
Заявки лицензируемых категорий принимаем и передаём партнёру-лицензиату: сущность «партнёр-подрядчик» (реквизиты, лицензия, категории, комиссия), передача заявки с контактами клиента, статусы исполнения ведёт диспетчер по данным партнёра, агентская комиссия — проводкой. Клиенту — единое окно и гарантия через нас. До подписания договора с лицензиатом категории в прайсе закрыты, при заявке — вежливый отказ с рекомендацией.

- **Инструмент начальных остатков:** импорт существующих организаций/точек/договоров, стартовые балансы абонентских счетов, открытая дебиторка, балансы мастеров — «входящими» проводками на дату запуска. Без этого биллинг никогда не сойдётся с реальностью, если у компании уже есть клиенты
- Импорт прайса из Excel («Каталог услуг и прайсы v3»): маппинг колонок, валидация, отчёт об ошибках
- Демо/стейджинг-среда с анонимизированными данными + демо-организация для продаж (17.2); данные с флагом «демо» исключаются из биллинга, отчётов и налоговых регистров
### 17.13. Архитектурный задел под B2B SaaS (направление отложено — требования к фундаменту обязательны)
**Контекст.** Владельцем рассматривается параллельная модель: продажа операционного контура системы как SaaS компаниям с собственным АХО и штатными мастерами (контроль ТО: заявки от точек, конвейер мастера с фотофиксацией, техдолг, осмотры, паспорта техники, KPI вместо рейтинга) — с возможным «переливом» заявок в маркетплейс, когда штатные силы клиента не справляются. **Решение о запуске SaaS отложено; функциональность SaaS в скоуп MVP/фазы 2 не входит и не оценивается.** Однако пять архитектурных решений стоят почти ноль на старте и экономят переписывание системы потом — они обязательны к исполнению с первого дня:
1. **tenant_id во всех сущностях** данных с первого дня; текущий оператор платформы — тенант №1. Изоляция данных по тенанту — на уровне запросов/схемы, а не UI.
2. **Биллинг-движок отделён от операционного контура событийно:** биллинг подписан на события жизненного цикла заявки (см. PRD-05), а не вплетён в переходы статусов. Заявка обязана уметь корректно жить с выключенным биллингом (нулевой денежный контур).
3. **Прайс-лист — опциональный атрибут заявки,** а не обязательное условие её существования: внутренняя заявка АХО (тенант с выключенным биллингом) не имеет цены, но имеет нормо-часы, материалы и фотофиксацию. Для заявок денежного контура (оператор, тенанты с биллингом) правило фиксации релиза 3.7 действует безусловно — опциональность не отменяет его.
4. **Справочники и шаблоны уведомлений имеют уровень «тенант»:** категории работ, чек-листы осмотров, SLA, тексты SMS/push — переопределяемы на тенанта (для оператора — значения по умолчанию).
5. **Фича-флаги на уровне тенанта** (механизм уже заложен в PRD-05): включение/выключение модулей (биллинг, офферы vs прямое назначение, партнёрские магазины) — конфигурацией, не форком кода.
**Явные не-цели сейчас:** панель тенант-админа, внутренний склад АХО, учёт себестоимости точки, white-label для ФМ-компаний — не проектировать и не строить до отдельного решения владельца.
### 17.14. Программа поощрения персонала точек: баллы и ваучеры (решение владельца, MVP)
**Зачем.** Человек на точке (продавец, фармацевт, завхоз) — тот, кто решает, вызвать нас или «своего знакомого мастера», и тот, кто может тихо дискредитировать сервис. Программа покупает его лояльность легально и дёшево: он получает баллы за заявки, пришедшие через него, и обменивает их на ваучеры супермаркета.
- **Легальность — обязательное условие:** программа — **опция B2B-договора, включается только с согласия руководства организации** (пункт договора «программа мотивации персонала точек»). Скрытое от работодателя вознаграждение его сотрудника трактуемо как коммерческий подкуп — так не делаем никогда. Продающий аргумент руководителю: его сотрудники сообщают о поломках сразу, а не «когда потекло на товар»; сметы всё равно утверждает он по матрице 5.1. Финальные формулировки пункта договора — юристу
- **Участники:** по умолчанию — сотрудники точек (заявители). Руководителей (точки/организации) админ может включить только точечно и только с ведома организации: они сами утверждают сметы — конфликт интересов
- **Механика начисления:** LoyaltyAccount на пользователя; баллы = % от **фактической суммы работ** заявки по ценам договора организации (без материалов — иначе выгодно требовать дорогие запчасти) по **закрытым и оплаченным** заявкам. Начисление привязано к **заявителю** — новое поле заявки applicant_user_id: при создании из приложения заявитель = создатель; **при телефонной заявке диспетчер привязывает сотрудника точки по номеру телефона** (иначе программа ломается ровно в том канале, которым пользуется целевая аудитория — завхоз без приложения). Авто-заявки (плановые осмотры, заявки из дефектов, сервисные касания, гарантийные) и заявки, созданные руководителями за сотрудников, баллов не порождают. Процент: глобальный параметр (по умолч. 1%) + **персональный override на человека** (гибкая настройка под каждого — решение владельца). 1 балл = 1 сум. Сторно баллов при споре/возврате/отмене заявки; **если баллы уже конвертированы в выданный ваучер — ваучер не отзывается**, баланс уходит в минус и гасится будущими начислениями (тот же паттерн, что наличный долг мастера). Месячный потолок начислений на человека (параметр). Анти-абьюз: раздувание заказов сдержано матрицей утверждений (сотрудник сам себе смету не согласует) и существующим флагом анти-дробления
- **Ваучеры:** при достижении порога конвертации (параметр) система автоматически выдаёт ваучер из **пула**: компания закупает электронные ваучеры партнёрской сети (стартовый партнёр — Корзинка; провайдер заменяем: Makro, Uzum и др.), коды загружаются в админку (код/QR, номинал, срок действия). Выдача из пула — **FEFO** (ближайший срок годности — первым). Сотрудник получает QR-код в приложении + SMS-дубль, гасит на кассе супермаркета при оплате. Истёкший неиспользованным **выданный** ваучер помечается, баллы не возвращаются (параметр: возвращать/нет); истёкшие коды **в пуле** списываются проводкой в маркетинговый расход; отчёт админа «истёкшие ваучеры» (выданные/в пуле). Алерт админу «пул заканчивается». **Отключение программы** (организация выключила опцию / договор расторгнут): начисления прекращаются немедленно, накопленные баллы конвертируемы ещё 60 дней (параметр), затем сгорают с уведомлением сотруднику за 7 дней. Прямая API-интеграция с сетью — фаза 3, при наличии API
- **Учёт и налоги:** начисленные баллы — обязательство программы (отдельный учёт); закупка пула — маркетинговый расход проводкой; выдача ваучера — списание из пула + списание баллов. **НДФЛ и оформление подарков физлицам — вопрос бухгалтеру (8.10)**
- **Экраны:** сотрудник точки — «Мои баллы» (баланс, история начислений по заявкам, прогресс до ваучера, ваучеры с QR); админ — настройка программы (проценты, порог, потолок), пул ваучеров, реестр выдач, отчёт эффективности (баллы vs динамика заявок точки)
- **Этапность:** MVP (решение владельца — часть оффера организациям с первого дня); API-интеграция с сетями — фаза 3
### 17.15. Лендинги и лид-контур (MVP)
Приложения не продают сами себя: для набора клиентуры, таргетированной рекламы и SEO нужны публичные веб-страницы. Три аудитории — **три лендинга** (общий домен, единый стиль, рус/узб):
- **Лендинг B2C:** УТП (мастер в согласованное окно, цена до начала работ, фотофиксация, гарантия), категории услуг с ценами «от» (по API из активного релиза прайса — кеш с инвалидацией по релизу), «как это работает» в 4 шага, отзывы, аварийная кнопка «позвонить сейчас». Конверсия — два пути: кнопки установки приложения (deep link) и **форма заявки без приложения** (телефон + категория + описание): лид падает задачей в очередь «Позвонить» диспетчерской с SLA перезвона 10 минут (та же механика, что пропущенный звонок, 12 п.6) — дальше телефонный флоу с веб-карточкой
- **Лендинг B2B:** боли (свой АХО дорог, подрядчики без контроля), оффер (один договор, SLA аварий, фотоотчёты по каждой работе, абонентка, программа мотивации персонала точек как опция), демо-скрины отчётов, **упрощённый калькулятор абонентки** (число точек × тип объекта → ориентировочная вилка по ставкам 17.2; точный расчёт — только в КП) и форма «Получить КП» (компания, число точек, контакт): лид создаётся в реестре B2B-лидов (сущность «лид» уже есть — калькулятор 17.2 работает с лидами; **экран реестра B2B-лидов со статусами воронки 17.2 и привязкой к организации — в MVP-админке**) + задача «позвонить лиду» с SLA (параметр). **Роли «менеджер продаж» в MVP нет — задачи B2B-лидов падают админу** (на старте продаёт владелец); выделенная роль — фаза 2. Ставки упрощённого калькулятора (тип объекта → ставка сум/м² + типовая площадь типа) — **справочник MVP-админки** (полный калькулятор КП фазы 2 переиспользует его)
- **Лендинг «Мастерам»:** набор исполнителей — такой же конвейер, как набор клиентов (масштабирование до 300 мастеров без потока кандидатов невозможно): условия (доля, график, оплата еженедельно, обучение), калькулятор «сколько заработаешь», анкета кандидата (имя, телефон, skill, опыт, транспорт) → воронка онбординга мастеров (17.1) **статусом «анкета» с меткой источника «лендинг»** (статусная модель воронки 17.1 не меняется); реферальный код мастера-рекомендателя подставляется из ссылки
- **Публичная страница верификации мастера** (переход по QR с бейджа, 13/A-11): фото, имя, skill-теги, статус «действует/недействителен», грейд — без телефона и адреса. **Согласие мастера на публикацию** (фото/имя/статус) — пункт договора при онбординге (ЗРУ-547), флаг в карточке мастера; страница отозванного бейджа показывает только «НЕДЕЙСТВИТЕЛЕН» — без фото и имени
- **Лид-контур и аналитика:** каждый лид хранит UTM-метки источника (кампания таргета видна до заявки и LTV — сквозная аналитика окупаемости рекламы); пиксели рекламных площадок; антиспам форм (honeypot + rate limit + SMS-подтверждение номера); чекбокс согласия на обработку персданных (ЗРУ-547) обязателен; события конверсии (лид создан / заявка создана / договор подписан) — в аналитику. Лид с формы вне зоны покрытия — в лид-лист «ждут покрытия» (17.4, наравне с телефонными обращениями). **Осознанное ограничение MVP:** звонки по tel:-ссылке с лендинга UTM не несут — атрибуция только через **выделенный номер лендингов** (заявка из D-08 по нему метится «источник: лендинг-звонок»); полный колл-трекинг с подменными номерами по кампаниям — фаза 2
- **Этапность:** MVP — все три лендинга со статическим контентом, формы, лид-задачи, UTM; фаза 2 — SEO-структура по категориям услуг и районам, A/B-тесты, блог/справочник цен
### 17.16. Внутренний склад компании (решение владельца)
До сих пор складской учёт существовал только для дорогой техники (Equipment, 17.9: статусы, акты выдачи/возврата, амортизация). Единый склад закрывает остальное: «что у компании есть, сколько осталось, кому и как отдали».
- **Номенклатура склада (StockItem):** категории — спецоборудование (= Equipment, интеграция без дублирования учёта), выдаваемый инструмент компании (если появится сверх собственного инструмента мастеров), расходники и запчасти (стартовые комплекты, страховой запас), форма/мерч/бейджи (комплект новичка), прочее (SIM-карты, наклейки «обслуживается SOZO»). Позиция: наименование, ед., себестоимость, остаток, min-остаток (алерт при снижении)
- **Движения (StockMovement) — только журналом, как проводки:** **приход** (закупка: накладная, поставщик, себестоимость → кредиторка/расход); **выдача во временное пользование** (только через акт Equipment 17.9 — с возвратом и матответственностью); **передача насовсем / продажа мастеру** (комплект новичка, форма, расходники: бесплатно за счёт компании ИЛИ с удержанием из выплат — параметр, удержание строкой в ведомости 8.6 частями ≤ 30%); **списание** (порча, утрата, истечение срока — причина обязательна, в аудит); **возврат на склад** (из временного пользования, при офбординге)
- **Инвентаризация:** периодический пересчёт с актом расхождений (факт vs система), расхождения — списанием/оприходованием с причиной; недостача по вине кладовщика/мастера — разбор по механике 17.7
- **Интеграция с биллингом:** приход — расход/кредиторка; продажа мастеру — удержание в ведомость; списание — расход проводкой; остатки склада видны в P&L-контуре админа
- **Этапность:** MVP — журнал движений, остатки, min-алерты, выдача/продажа/списание (лёгкий контур: Equipment уже в MVP, комплекты новичка учитываются с первого дня); фаза 2 — инвентаризация с актами; фаза 3 — выдача расходников в «сумку» со склада (8.4.2) и продажа запчастей со склада с наценкой (8.4.3 п.4) — как и планировалось
- **Не путать** с «внутренним складом АХО» из 17.13 — то не-цель про SaaS-тенантов; здесь — собственный склад оператора
### 17.17. UX-решения продакт-аудита (v2.25, обязательны — уточняют разделы 6, 7, 4.1, 14, 17.1, 17.3)
Аудит критических путей показал: создание заявки — 11 экранов против 3–4 действий у такси-паттернов, конвейер мастера — ~40 тапов с тремя узлами ввода, телеметрии нет. Принятые решения:
1. **Создание B2C-заявки — 3 шага** (уточняет 6.1): (1) «что сломалось» — категория+работы+фото+описание одним экраном; (2) «где и когда» — только улица/дом (гео-автоопределение) + слот; (3) итог. **Детали адреса (квартира, подъезд, этаж, домофон, лифт) запрашиваются после назначения мастера** пушем «уточните детали» — для планирования достаточно дома. Промокод — свёрнутая ссылка; чек-лист доступа — bottom-sheet шага слота; онбординг-слайды удалены (ценность показывают пустые состояния)
2. **Повтор заявки в 2–3 тапа** (6.1): карточка «Повторить: {работа}, {мастер}» на главном экране под кнопкой вызова → сразу выбор слота → отправить. MVP, не фаза 2
3. **Закрытие заявки — меньше просьб** (4.1 п.9, 7.1): **онлайн-оплата в приложении засчитывается как приёмка** (санкция клиента — платёж; код приёмки остаётся для наличных и телефонного канала); оценка и чаевые — один экран «Спасибо»
4. **Смета выше вилки — с доказательствами** (6.1): экран подтверждения дельты обязан показывать фото мастера и причину по каждой подорожавшей позиции (паттерн вынужденных доп-работ 4.6 — везде)
5. **Ускорители сметы мастера** (7.1 шаг 3): над поиском позиций — «частые по категории заявки» (топ-10 по статистике), «мои недавние», **пресеты-наборы** («замена смесителя» = 3 позиции одним тапом), «скопировать смету из прошлой заявки той же категории». Цель: 3 позиции ≤ 5 тапов без клавиатуры. Запчасти — выбор из SparePartCatalog с fallback «нет в каталоге», не свободный текст
6. **Паспорт техники — условный гейт** (17.12): обязательная фиксация техники — только для категорий с оборудованием (признак позиции прайса: котлы, кондиционеры, бойлеры, крупная техника); для остальных — чип «техники нет» одним тапом; бренд/модель необязательны при фото шильдика (дозаполняются модерацией/OCR). Мусорные записи «Смеситель, -, -» хуже отсутствия записи
7. **Офлайн-подтверждение сметы** (4.1, 7.2 — закрывает дедлок «подвал без сети у обоих»): при отсутствии сети клиент подтверждает смету **подписью пальцем на экране мастера + фото**; пакет уходит в очередь синка с флагом «согласовано офлайн» и попадает в выборочную модерацию — зеркало механизма «принято без кода». Работа не блокируется, санкционный контур сохраняется
8. **Оффер за рулём** (17.3): при детекте вождения — TTS-озвучка оффера и ответ кнопкой гарнитуры либо авто-отложение; молчание в режиме вождения **не считается** в дисциплине офферов; после восстановления сети — сводка «пока вы были офлайн: N офферов»
9. **Онбординг мастера без мёртвого времени** (17.1): учебные модули и тренажёр конвейера открываются сразу после отправки анкеты, не после собеседования — кандидат не остывает 1–2 дня
10. **Кошелёк: ответ «сколько сегодня» за 5 секунд** (7.3): чип «Сегодня» в кошельке + строка дня на главном экране мастера («Сегодня: +420 000 · 3 заявки»)
11. **Телеметрия обязательна** (14): оба приложения логируют события воронок (шаги визарда с отвалами, офферы с временем реакции, длительность шагов конвейера, источники создания заявки, платежи, оценки) — полный каталог событий в DEV-08/DEV-09; события мастера пишутся в офлайн-очередь. North Star: закрытые заявки с оценкой ≥ 4 на активного клиента/месяц. Квартальный in-app NPS мастеров в 2 тапа

## 18. Решения владельца продукта (приняты 19.07.2026) и остаточные вопросы
**Принятые решения (внесены в соответствующие разделы ТЗ):**
1. **Режим работы — полные 24/7:** круглосуточный приём любых заявок; ночная смена диспетчерской; ночной коэффициент к работам в ночные часы 22:00–07:00 (параметр прайса); ночные зонные дежурные
2. **SLA по авариям в договорах B2B — прибытие ≤ 60 минут днём** (параметр договора); **ночью — отдельный норматив ≤ 120 минут** (параметр): ночью на город 1–2 дежурных, часовой SLA по всем районам физически невыполним — обещать в договоре можно только исполнимое. Исполнимость обеспечивают зонные дежурные и приоритет аварий; отчёт о соблюдении SLA — фаза 2. Внимание: на старте с малым числом мастеров SLA держится только плотностью дежурств — подключать в договоры по мере покрытия зон
3. **Сурж-наценка:** заложена параметром, выключена; решение о включении — отдельно, по статистике пиков
4. **Минимум дежурной смены:** дневная ~200 000, ночная ~250 000 сум (параметры)
5. **Остаток абонентки при расторжении:** зачёт работами в течение 60 дней, затем сгорает
6. **Пени:** в типовом договоре 0.1%/день, потолок 10%; начисление — решением бухгалтера (гибко, для злостных)
7. **Скидка партнёрских магазинов — компании ретро-бонусом;** клиент платит цену накладной
8. **Первичный аудит — платный с зачётом** в первый месяц при подписании договора
9. **Грейд «Золото» — доля 57%** (вместо 55%); включено с запуска авто-рейтинга (фаза 2)
10. **Реферальная программа мастеров — включена:** бонус рекомендателю после 20 закрытых заявок приведённого (размер — параметр)
11. **Чаевые — в MVP:** опция на экране оплаты B2C после оценки; целиком мастеру, мимо долей, отдельной проводкой; фискализация чаевых — вопрос бухгалтеру (8.10)
12. **Лицензируемые работы — субподряд лицензиата:** заявки категорий «газ»/«лифты» принимаем и передаём партнёру-лицензиату за агентскую комиссию; механика партнёра-подрядчика — фаза 2, до подписания договора с лицензиатом категории в прайсе закрыты
13. **Промокоды и скидки B2C — в MVP:** поле промокода при создании заявки; скидка — маркетинговый расход компании, доля мастера всегда от базовой цены (принцип 5)
14. **Ответственность за ущерб — собственный механизм вместо страховки** (готовых страховых продуктов на рынке УЗ нет) — см. новый раздел 17.7: резервный фонд + ограничение ответственности в договоре + процедура разбора
15. **Компенсаций за сдвиги нет** (v1.9): приоритетный слот + VIP-контроль
16. **Партнёрские магазины — все категории сразу:** сантехника, электрика, малярка, фурнитура и материалы для корпусной и мягкой мебели и пр.; цель — 1–2 магазина каждой категории на крупный район
17. **Сроки B2B-договоров — годовые и месячные (v2.15):** годовой — цены заморожены на весь срок, пересмотра внутри года нет; месячный — авто-продление с переводом на текущий релиз прайса при каждом продлении (пересмотр цен — только в момент продления, для обоих типов)
18. **Программа баллов и ваучеров для персонала точек — в MVP (v2.16, раздел 17.14):** % от суммы работ закрытых заявок заявителя (глобально 1%, персональный override), ваучеры супермаркетов из закупленного пула (старт — Корзинка), QR на кассе; только как опция договора с согласия руководства организации; сотрудники точек по умолчанию, руководители — точечно
19. **Возмещение ГСМ мастерам с авто — нормативный километраж (v2.21, 8.6):** сумма расстояний по карте между выполненными заявками ленты × ставка сум/км (параметр); путь дом↔заявки не считается; начисление возмещением в ведомость, без GPS-слежки
20. **Внутренний склад компании — в MVP лёгким контуром (v2.21, 17.16):** номенклатура с остатками и min-алертами, журнал движений (приход / временное пользование через акты / продажа мастеру с удержанием / списание); инвентаризация — фаза 2, расходники в сумку со склада — фаза 3
21. **Подписной коэффициент пересмотрен (v2.23):** скидка подписчика считается от разовой цены юрика, а не от розницы физика — подписка = «B2B разовая» × (1 − 10%) ≈ B2C × 1.17. Подписчик платит дороже физика, но на 10% дешевле разового юрика; сверхлимит — по разовой без скидки. Прежний коэффициент 0.8 от B2C отменён
22. **Технологический стек утверждён (v2.24):** бэкенд — NestJS (TypeScript), веб-панели — React, лендинги — Next.js, ORM — Prisma, монорепозиторий; Flutter, PostgreSQL, Redis, S3 — без изменений; старт без Kubernetes (Docker Compose, два сервера в ЦОД РУз)
23. **UX-решения продакт-аудита приняты полностью (v2.25, раздел 17.17):** создание заявки в 3 шага с отложенными деталями адреса, повтор в 2–3 тапа, онлайн-оплата = приёмка, ускорители сметы, условный гейт паспорта техники, офлайн-подпись сметы, правила офферов за рулём, ранний доступ к обучению кандидатов, обязательная телеметрия обоих приложений с North Star «закрытые заявки с оценкой ≥4 на клиента/месяц»
**Остаётся открытым (не блокирует разработку):** выбор конкретного партнёра-лицензиата по газу/лифтам; размер реферального бонуса; потолок ответственности в договорах (юрист, 17.7); ставки налогов и НДС-режим (бухгалтер, 8.10); НДФЛ и оформление ваучеров-подарков физлицам по программе 17.14 (бухгалтер) и формулировки пункта договора о программе мотивации персонала (юрист); условия закупки ваучеров у Корзинки (бизнес); сервисные напоминания B2C — фаза 3 (решено ранее).
### Исходные формулировки вопросов (для истории)
1. **Режим работы:** платформа 24/7 или диспетчерская, например, до 22:00? Ночная наценка на аварийные выезды (отдельный коэффициент)?
2. **Ответственность за ущерб:** мастер затопил соседей / сжёг проводку — юридически отвечает компания как оператор. Страхование гражданской ответственности (полис компании или на мастеров) — решить до запуска; для B2B-продаж это сильный аргумент.
3. **SLA в договорах B2B:** обещаем ли время реакции на аварию (приезд ≤ 2 ч)? Если да — SLA как параметр договора + отчёт о его соблюдении (фаза 2).
4. **Маркетинг B2C:** промокоды, скидки, реферальная программа — сознательно вне скоупа MVP? Поле «скидка» в заявке уже заложено в модель (3.4), чтобы включение маркетинга потом не ломало биллинг.
5. **Расторжение договора:** возврат неиспользованной абонентки деньгами или зачётом? Влияет на текст договора; в системе — параметр (8.3).
6. **Чаевые мастеру** в B2C-оплате — разрешаем? Мотивация мастеров; кандидат в фазу 3.
7. **Скидка партнёрского магазина:** оставляем компании как ретро-бонус (клиенту — цена накладной; вариант по умолчанию) или транслируем клиенту как конкурентное преимущество?
8. **Пени за просрочку СФ** — включать в типовой договор? Ставка %/день и потолок.
9. **Бонус к доле за грейд «Золото»** (+2 п.п.) — включаем? Стимул качества против маржи.
10. **Стартовый список партнёрских магазинов:** с кем договариваемся в первую очередь (сантехника/электрика по районам) — от этого зависит, насколько рано фаза 2 окупится.
11. **Лицензируемые работы:** газовое оборудование, лифты — берём ли вообще (лицензия/субподряд лицензиата)? До решения юриста — исключены из прайса.
12. **Платный первичный аудит:** цена аудита-осмотра и правило зачёта при подписании договора.
13. **Реферальный бонус мастерам** «приведи мастера» — включаем? Размер и условие (N закрытых заявок приведённого).
14. **Сервисные напоминания B2C** (push «полгода не чистили кондиционер» по истории заявок) — growth-механика фазы 3; согласие на маркетинговые push — отдельный чекбокс при онбординге (требование закона о персданных).
15. ~~Компенсация за срыв окна~~ — **решено (v1.9): денежных компенсаций нет.** Валюта извинений — приоритетный слот, VIP-контроль, проактивная связь (17.3).
16. **Сурж-наценка пикового спроса** — включать ли когда-нибудь? Заложена параметром, по умолчанию выключена. Риск репутации против управления очередью.
17. **Размер гарантированного минимума дежурной смены** — ставка, при которой ротация дежурств не вызывает сопротивления мастеров.

**v1.9 (июль 2026) — девятая ревизия: перегруз как норма, дежурный резерв, протокол замены.**
95. **Приоритеты очереди при перегрузе** (17.3): шесть уровней (аварии → B2B SLA → гарантийные → брони B2C → ASAP → осмотры); плановые осмотры — демпфер, который двигается первым; строгий FIFO внутри уровня, ручной подъём только с аудитом.
96. **Решение: денежных компенсаций за сдвиги нет** (17.3, 18): валюта извинений — приоритетный слот, VIP-контроль диспетчера, проактивная связь; сурж-наценка заложена параметром (выкл.).
97. **Дежурный резерв** (17.3, 7.1, 8.6): один мастер в день без плановых броней — аварии, замены, переполнение ASAP; гарантированный минимум за смену + доля с выездов, иначе дежурство — наказание; тихий день — ASAP с середины смены.
98. **Протокол быстрой замены** (17.3, 4.4): автодетект «не нажал Выехал за 30 мин» → пинг → алерт; кандидаты дежурный → ближайшие свободные → освобождающиеся → снятие с осмотра; бродкаст-оффер 120 сек «первый забирает»; клиенту push немедленно; 15 мин безрезультатно → звонок диспетчера с вариантами переноса.
99. **Кнопка «Не могу поехать»** (7.1): явный ранний отказ запускает замену сразу и карается мягче тихого невыхода — стимул говорить, а не прятаться; счётчик невыходов: 2-й за 90 дней — снятие с линии, 3-й — блокировка.

114. **Парк оборудования компании** (17.9): инвентарный учёт Equipment, выдача под материальную ответственность актами с фото, линейная амортизация ежемесячной проводкой в P&L, «требует оборудование» как фильтр распределения (аналог skill-тега), ТО-график, удержание остаточной стоимости при утере по вине.
115. **Жалобный контур** (17.10): Complaint отдельно от споров — типы, SLA (ответ 2 ч / резолюция 24–72 ч), плейбук методов решения со справочником, паттерн-детект «3 жалобы за 30 дней», эскалация жалоб B2B-руководителей, связь с рейтингом только после подтверждения, дашборд корневых причин.
116. **Многодневные работы** (4.1): сессии в лентах нескольких дней, фото «в процессе» + консервация в конце каждой сессии.
117. **Закреплённые мастера** (3.2): предпочтительный мастер точки (знает объект — мягкий приоритет планировщика) и чёрный список мастеров точки.
118. **Неиспользованные материалы** (8.4.3): возврат в магазин / сторно накладной / передача клиенту; в акте — только фактический расход.
119. **Передача смены диспетчеров** (12): handover-журнал для 24/7 — ничего не живёт «в голове ушедшего».
120. **Комплект новичка и стандарты сервиса** (17.1): форма, бейдж, стартовая сумка; бахилы/коврик/уборка — в обучении, нарушения ловятся жалобами; новые skill-теги — только через экзамен.

**v2.3 (июль 2026) — тринадцатая ревизия: внешние блокировки и этапные работы.**
121. **Пауза «Заблокировано третьей стороной»** (4.1, 7.1): нет доступа к подвалу/стояку, ТСЖ «приходите завтра» — причина + фото + время следующей попытки; заявка автоматически встаёт якорем на подтверждённое время; без даты — задача диспетчеру, эскалация 48 ч, решение с клиентом через 7 дней.
122. **Матрица денег холостого выезда** (4.4): зависимость всплыла внезапно — клиент повторный выезд не платит, мастеру компенсация 50% выезда от компании; клиент подтверждал доступ и не обеспечил — повторный выезд в счёт клиента; B2B в подтверждённое окно не пустили — строка в СФ.
123. **Профилактика холостых выездов** (6.1, 3.2): чек-лист внешних зависимостей при создании заявки для категорий с общими зонами + контакты ТСЖ/УК в паспорте точки.
124. **Этапные работы** (4.1, 3.7, 17.3): позиции с планом этапов и технологическими паузами (стяжка, малярка, герметизация); в паузах мастер свободен; цена за работу целиком, выезды сессий включены; оплата на последней сессии; отмена посередине — по фактическим этапам.

**v2.4 (июль 2026) — уточнение этапных работ после разбора владельца.**
125. **Двухфазное бронирование сессий** (4.1): позиция известна при создании → сессии бронируются при назначении; работа выяснилась на месте → слоты следующих сессий предлагаются клиенту прямо на экране мастера и подтверждаются вместе со сметой.
126. **Допустимое окно этапа вместо точной даты** (3.7, 4.1): пауза задаётся диапазоном [минимум; максимум] («не раньше 24 ч, не позже 7 дней») — планировщик ищет слот в окне, а не в конкретный день.
127. **Инвариант старта** (4.1): этап 1 не начинается без подтверждённых слотов всех следующих этапов — «не начинай красить, если некому приехать домазать». Нет слотов → перенос всей цепочки / сверхурочный слот с согласия мастера / передача продолжения с разделом доли.
128. **Приоритет продолжений** (17.3): начатые этапные работы — уровень 4 очереди, выше новых броней: вскрытый объект бросить нельзя.

**v2.5 (июль 2026) — тариф «Срочно» (решение владельца: срочность платная).**
129. **ASAP переделан в платный тариф «Срочно»** (17.3, 6.1, 3.7): наценка срочности к работам (параметр, +30%), доля мастера с наценкой — мастерам выгодно хватать срочные; приоритет над обычными ожидающими и доступ к аварийному резерву; подтверждённые брони других клиентов не ломаются.
130. **Правило честности** (17.3): не начали срочную за 3 ч (параметр) — наценка снимается автоматически с push-уведомлением: за скорость берём деньги, только когда скорость случилась.
131. **Бесплатный лист ожидания** сохранён для нежелающих платить — после броней, с честным прогнозом; уровни очереди перенумерованы (теперь 8).
132. **Диагностика с отложенным выполнением** (3.7): большой объём выявлен на осмотре у физлица, работа в другой день — уплаченная диагностика зачитывается в счёт работы (строка «зачёт диагностики» в акте, окно 30 дней); клиент платит как за один визит, мастера получают доли со своих частей.

**v2.6 (июль 2026) — парные работы и транспортная логистика.**
133. **Парные позиции с ролями** (3.7, 4.5, 17.3): «требует 2 исполнителей» — ведущий (skill, ответственность, основная доля) + помощник (физпомощь, меньшая доля или фикс за сессию); деление по ролям, не пополам; цена парных позиций включает второго; помощниками работают младшие грейды и кандидаты — подработка + обучение.
134. **Кнопка «Нужен помощник»** (17.3): понял на месте, что одному никак — мини-оффер бродкастом ближайшим и дежурному («подсобить ~2 ч, фикс + дорога»); никого нет — перенос на парный слот.
135. **Экипаж дня** (17.3, фаза 2): включается статистикой — при высокой доле парных заявок в категории диспетчер собирает на день общую ленту «ведущий + помощник, одна машина»; режим дня, не постоянная бригада.
136. **Транспортный фильтр** (3.3, 17.3): признак «свой авто с инструментом»; заявки с машиной/оборудованием — только автомобильным; предпочтительный напарник — мягкий приоритет.
137. **Метрика доли парных заявок** (13): объективный триггер для запуска экипажей вместо ощущений.

**v2.7 (июль 2026) — перекрёстная проверка новых механик: логические нестыковки.**
138. **Терминология ASAP приведена к v2.5** (17.3, 12, 15, 16, 17.6a): «очередь срочных» и «лист ожидания» везде вместо устаревшего «ASAP» — разработчики не должны гадать, одно это или разное.
139. **Наценки не стакаются** (17.6a): аварийная, ночная и срочная — взаимоисключающие, применяется одна наибольшая; ночью «Срочно» не тарифицируется (ночной тариф уже премиальный).
140. **SLA дифференцирован день/ночь** (18): ≤ 60 мин днём, ≤ 120 мин ночью — часовой SLA на весь город с 1–2 ночными дежурными был невыполнимым обещанием в договоре.
141. **Снятая наценка срочности** (17.3): доля мастера — от базовой, наценки нет ни для кого; клиент получает предложение ближайшего окна.
142. **«Срочно» для B2B** (17.3): доступен вне аварий, базовая × срочность × подписной коэффициент, санкция по матрице 5.1.
143. **Сессии этапных работ** (4.1): промежуточные завершения без оплаты — явное исключение из правила «не завершай визит без оплаты».
144. **Карточка помощника** (17.3): упрощённая, без конвейера и фото; на рейтинг не влияет, кроме невыхода.

**v2.8 (июль 2026) — матрица контактов диспетчера и контроль качества.**
145. **Раздел 17.11**: все голосовые триггеры сведены в одну матрицу с SLA и скриптами — до работ (уточнения, доступ, подтверждение накануне дорогих), во время (сдвиги, замены, доп-сметы, аварии), после (QC-выборка 10% + обязательные прозвоны новых клиентов/мастеров/крупных чеков, оценка 1–2 за 2 часа, анти-сговор по отменам), B2B-ритм (недоиспользование абонентки, хронический сверхлимит → апсейл договора, звонок к продлению, ежемесячный контакт топ-организаций).
146. **Очередь «Позвонить»** (12, 3.8): задачи-звонки с исходами в ContactLog — ничего не живёт в памяти диспетчера; KPI по выполнению прозвонов и конверсии продлений.

**v2.9 (июль 2026) — постпродажное обслуживание: сервисный след техники.**
147. **Паспорт техники клиента** (17.12, 3.8, 7.1): мастер фиксирует обслуженную единицу (тип/бренд/модель + фото шильдика) — история работ копится по каждой единице; сбор — с первого дня MVP, иначе базы для напоминаний не будет; заполненность — в метрике качества фиксации мастера.
148. **Четыре автоматических касания** (17.12): контрольное «как дела» через 7–14 дней (проблема → гарантийная заявка одной кнопкой); регламентное напоминание по справочнику интервалов («полгода после чистки — пора»); сезонные кампании по сегментам (кондиционеры в апреле, котлы в октябре); предупреждение о конце гарантии за 7 дней.
149. **Интервалы задаёт компания, не мастер** (17.12): справочник в админке — мастер не может спамить рекомендациями; частотный потолок 1 push/2 недели, отписка в один тап, SMS в маркетинге не используется.
150. **Экономика follow-up** (17.12, 13): повторная заявка уходит закреплённому мастеру (мотивация качества); конверсия напоминаний и выручка follow-up — на дашборде; решение №14 из раздела 18 пересмотрено — сервисный контур начинается в MVP, а не в фазе 3.

**v2.10 (июль 2026) — полный флоу телефонного клиента.**
151. **Заявка по звонку от начала до конца** (12): автопоиск по номеру с историей и паспортом техники на экране; окно согласуется прямо в разговоре по живому планировщику, мастер назначается не вешая трубки; устные согласования — с пометкой «озвучено по телефону» в аудит.
152. **Веб-карточка заявки без приложения** (12, 11): SMS со ссылкой — статус, мастер, ETA, смета с кнопкой «Согласен», акт с фото, онлайн-оплата, оценка; без установки и регистрации. Кто не открывает — ключевые события SMS-текстом, оплата наличными/QR, качество — QC-звонком.
153. **Пропущенный звонок = упущенная заявка** (12, 17.11): авто-задача «перезвонить за 10 минут» в очередь «Позвонить».
154. **Ненавязчивый перевод в приложение** (12): одна ссылка после первой закрытой заявки, без спама.

**v2.11 (июль 2026) — перекрёстная проверка и забытое.**
155. **Производственный календарь Узбекистана** (14): все деловые таймеры (эскалации, дунинг, авто-отмена, SLA) учитывают нерабочие дни — иначе авто-отмена «не согласовано» срабатывает посреди Курбан-байрама; планировщик в праздники — режим выходного.
156. **Сезонные кампании дозируются ёмкостью** (17.12): рассылка волнами с дневным лимитом записей по зонам — кампания не должна сама себе устраивать массовый перегруз.
157. **Освободившийся слот не пропадает** (17.3): авто-предложение по приоритетам срочным → листу ожидания → подтягивание хвоста ленты.
158. **Приоритеты и рабочие окна очереди звонков** (17.11): операционные → эскалации → QC → B2B-ритм; несрочные звонки только 9:00–20:00; SLA жалоб — в дневном окне (17.10).
159. **Токен веб-ссылки** (12): одноразовый подписанный, с журналированием действий как подтверждений клиента.
160. **Язык коммуникаций** (14): SMS/push/веб-карточка/документы — на языке профиля клиента, шаблоны двуязычные.
161. **Мелкое забытое**: слияние дублей клиентов в админке (13); «наличие лифта» в адресе (6.1) для тяжёлых/парных работ; fallback закреплённого мастера при его недоступности и «любимый мастер» для B2C (17.12).

**v2.12 (июль 2026) — повторный прогон: четыре несостыковки.**
162. **Ночные плановые для B2B с ночным доступом** (17.6a): пекарни/клубы/склады, пускающие мастеров только ночью, не могли получить плановое обслуживание вообще — теперь исключение с тарифом по договору.
163. **Единая формула цены дополнена** (3.7): порядок «базовая × одна наибольшая наценка × канальный коэффициент − промокод»; скидка применяется последней и не трогает долю мастера; формула перестала противоречить взаимоисключению наценок из v2.7.
164. **Валидатор unit-экономики честнее** (3.7): учитывает отчисление в резервный фонд, комиссии провайдеров и амортизацию спецоборудования — раньше «маржа в плюсе» могла быть иллюзией.
165. **Фикс помощника на непарной позиции** (17.3): клиент не платит никогда; скрытые условия — расход компании, очевидная недооценка — из доли ведущего (решение диспетчера, аудит).

**v2.13 (июль 2026) — архитектурный задел под B2B SaaS.**
166. **Новый раздел 17.13:** направление B2B SaaS (продажа операционного контура компаниям с собственным АХО + возможный «перелив» заявок в маркетплейс) отложено решением владельца, но в фундамент внесены пять обязательных требований: tenant_id во всех сущностях с первого дня, событийное отделение биллинга от операционного контура, опциональность прайс-листа у заявки, тенантный уровень справочников и шаблонов уведомлений, фича-флаги на тенанта. Явные не-цели: панель тенант-админа, склад АХО, себестоимость точки, white-label — не строить до отдельного решения.

**v2.14 (июль 2026) — версионирование прайса: релизы.**
167. **Версионирование прайса переработано с уровня позиции на уровень релиза** (3.7): сущность PriceListRelease — снапшот позиций и глобальных коэффициентов, статусы черновик/запланирован/активен/архив, diff перед активацией, валидатор unit-экономики по всему релизу, откат новым релизом из снапшота (история неизменяема), импорт Excel создаёт черновик релиза; крупный релиз (>20% позиций или цена >30%) — подтверждение второго админа.
168. **Железное правило фиксации (решение владельца):** изменение прайса никогда не пересчитывает действующие заявки, действующие договоры и закрытое прошлое. Заявка фиксирует релиз при создании (все сметы и доп-сметы — из него); не начатые заявки не переоцениваются; коэффициенты фиксируются копией при создании, доля мастера с грейдом — при назначении. Исключения: переоценка дефекта старше 30 дней, расходники по каталогу на момент списания.
169. **B2B-договор фиксирует релиз на дату подписания** до продления; при продлении — перевод на текущий релиз с авто-отчётом изменений. Мастерам — уведомление за 7 дней о смене цен их категорий; клиентские приложения инвалидируют кеш цен по событию активации релиза.

**v2.15 (июль 2026) — сроки B2B-договоров (решение владельца).**
170. **Два срока договора — годовой и месячный** (3.7, 18 п.17): годовой — цены заморожены на весь год, пересмотра внутри срока нет; месячный — авто-продление с переводом на текущий релиз при каждом продлении. Пересмотр цен для любого договора — только в момент продления; опция «плавающий прайс» из v2.14 удалена как противоречащая этому правилу. Уведомление организации за 10 дней до продления, если цены изменятся.

**v2.16 (июль 2026) — программа поощрения персонала точек (решение владельца, MVP).**
171. **Новый раздел 17.14:** баллы за заявки заявителя точки (% от суммы работ закрытых и оплаченных заявок; глобально 1% + персональный override; сторно при спорах; месячный потолок) с конвертацией в ваучеры супермаркетов из закупленного пула (старт — Корзинка, QR на кассе; API-интеграция — фаза 3). Обязательное условие легальности: только как опция B2B-договора с согласия руководства организации — скрытое вознаграждение чужого сотрудника трактуемо как коммерческий подкуп. Участники по умолчанию — сотрудники точек; руководители — точечно (конфликт интересов с утверждением смет). НДФЛ по ваучерам и формулировки договора — в открытые вопросы (бухгалтер/юрист); включено в MVP-скоуп (15) и решения владельца (18 п.18).

**v2.17 (июль 2026) — адверсарная ревизия релизов и программы баллов: 11 дыр.**
172. **Правило фиксации релиза уточнено по источникам заявки** (3.7): B2C и B2B-разовая — активный релиз при создании; заявка организации с договором — **релиз договора** (буквальная реализация «активный при создании» молча ломала годовую заморозку цен); заявка из дефекта наследует релиз оценки дефекта (младше 30 дней); гарантийная заявка/переделка наследует релиз исходной (оплата переделщику и удержания у виновного — в ценах исходной работы). 173. **Продление месячного договора доработано** (3.7): в уведомлении за 10 дней — опция «не продлевать» (зачёт остатка абонентки — по релизу последнего договора) и рекомендация индексации лимитов/абонентки (эрозия фиксированных сум-лимитов при росте цен); правило исполнимости уведомлений (активация ≥ 7 дней от подтверждения; без уведомления за 10 дней продление проходит на прежнем релизе; откат — немедленно); релиз №1 — флаг «стартовый» без diff/второго подтверждения, импортируемые договоры помечаются о переводе.
174. **Программа баллов починена для телефонного канала** (17.14): новое поле заявки «заявитель» (applicant_user_id) — при телефонной заявке диспетчер привязывает сотрудника по номеру; авто-заявки и заявки руководителей за сотрудников баллов не порождают; база — фактическая сумма работ по ценам договора; сторно после конвертации не отзывает ваучер (минусовой баланс); правило 60 дней конвертации после отключения программы внесено в текст (раньше отсутствовало); FEFO-выдача из пула; учёт истёкших ваучеров (выданных и в пуле).

**v2.23 (июль 2026) — пересмотр подписного коэффициента (решение владельца).**
187. **Подписка = «B2B разовая» − 10%, а не B2C × 0.8** (2.2, 3.7, 8.2, 18 п.21): скидка юрику считается от разовой цены юрика, эффективный подписной коэффициент = 1.3 × 0.9 = 1.17 от B2C. Подписчик платит дороже розницы физика (+17%), но дешевле разового юрика (−10%); клин продаж «разовая vs подписка» = +11%. Числовой пример 8.2 пересчитан (списание 234 000 вместо 160 000; частичное покрытие: 117 000 остатка → 130 000 в СФ вместо 97 500). Прайс-файл v33 согласован с этой логикой.
