# DEV-19. Схема оставшихся разделов и изоляция арендаторов

Документ описывает проектирование девятнадцати разделов состояния, у которых
не было ни одной таблицы, и разбор того, что при этом обнаружилось в уже
существующей схеме. Миграции — `m25`…`m35`, модели — в `prisma/schema.prisma`.

Читать вместе с DEV-02 (исходная схема) и разделом README «Переезд на
PostgreSQL: где мы» (ход переноса).

## 2. Правила, по которым это сделано

Не изобретались заново: они уже сложились при переносе заявок, объектов и
наряда-допуска, здесь только применены последовательно.

**Человек опознаётся телефоном.** Не ссылкой на `User`. Учётной записи может
не быть вовсе: у жителя, у консьержа-согласующего, у кандидата в мастера до
приёма, у штатного работника оператора. Внешний ключ на пользователя отсёк бы
ровно те случаи, ради которых поля и заведены.

**Деньги — `BigInt` в тийинах с `CHECK`.** Ни одной суммы во float и ни одной
в jsonb: на jsonb не наложить проверку, а отрицательная цена в варианте
допработ всплыла бы не в базе, а в счёте клиенту.

**Снимок хранится рядом с идентификатором.** Имя мастера в предложении, имя
точки в акте, название позиции в накладной. Документ обязан читаться так, как
был напечатан, даже если справочник потом изменили. Это не денормализация
ради скорости — это требование к документу.

**jsonb — только для того, что читается целиком и никогда не ищется.** В
итоге таких полей четыре: `payload` развилки, `utm` лида и задачи обзвона,
`body_args` уведомления. Всё остальное разложено по колонкам.

**Дочерние коллекции — таблицы, если по ним считают.** Варианты запчастей,
строки смет, зоны чек-листа, документы кандидата: по каждой из них есть
вопрос, который задают («как часто выбирают дешёвый уровень», «у скольких
кандидатов паспорт загружен, но не проверен»), и ответ на него должен быть
запросом, а не разбором снимка в приложении.

**Сроки хранятся моментами, а не длительностями.** Дедлайн жалобы, срок
обзвона, три срока SLA. Они посчитаны один раз по политике, действовавшей в
момент события; правка политики не должна задним числом делать вчерашнюю
жалобу просроченной.

## 3. Решения, которые стоит объяснить отдельно

### 3.1. Два реестра оборудования сведены в один

В коде их было два: в `registry` — с инвентарным номером, стоимостью и датой
обслуживания; в `master-api/resources` — с категорией, требуемым навыком и
фотографией. Это одна и та же вещь: перфоратор с инвентарным номером, который
выдают мастеру под акт.

Два описания означали два ответа на вопрос «где сейчас этот перфоратор», и
разошлись бы они ровно в момент спора о пропаже. Таблица одна —
`equipment_unit`. Состояния тоже сведены: `repair` и `maintenance` — одно и
то же, а `lost` и `written_off` разное (утерянное ищут и взыскивают,
списанное закрыто).

### 3.2. Три набора коротких ссылок сведены в один

Веб-карточка заявки (W-01…W-05), согласование наряда-допуска (W-06) и ответ
жителя о доступе (C-56) жили тремя наборами с одинаковыми полями. Код для них
уже выдавался общей функцией общим алфавитом — человек диктует его по
телефону, и два разных алфавита означали бы, что он диктует то так, то этак.

Общими стали и правила, которые иначе пришлось бы писать трижды: срок, отзыв,
счётчик открытий. Отзыв — то, ради чего это вообще ссылка, а не подписанный
токен: токен нельзя отозвать, а ссылку на отменённый наряд открывать нельзя.

### 3.3. Профиль клиента ключуется телефоном

Не выданным идентификатором. Клиент входит по телефону, по нему же приходят
заявки из веб-карточки и по ссылке из SMS, где профиля ещё нет вовсе. Второй
способ назвать того же человека означал бы два профиля у одного клиента после
первого же импорта.

### 3.4. Развилки мастера — одна таблица на восемь видов

У всех одинаковый жизненный цикл: мастер сообщил, диспетчер разобрал.
Различаются только содержимым, которое читается целиком и не ищется. Восемь
таблиц означали бы восемь очередей, каждую из которых надо не забыть
посмотреть.

### 3.5. Правила, которые переехали из кода в базу

`CHECK`-ограничений стало 85. Не для красоты: каждое из них — правило, которое
раньше держалось только кодом и обходилось при записи из второго места.

- регресс к мастеру ≤ 30% ущерба (ТЗ 17.7) — это зарплата человека;
- скидка промокода 1–50% — сто процентов не должны получаться опечаткой;
- задолженность партнёрскому магазину ≤ кредитного лимита — закупка идёт
  тремя путями, и проверять в каждом значит однажды забыть;
- оплаченный счёт знает дату оплаты, отклонённая позиция акта — причину,
  закрытая задача обзвона — результат;
- один основной адрес у клиента, одно живое предложение мастеру на заявку,
  один открытый спор на заявку, одна открытая замена — частичные уникальные
  индексы.

## 4. Что обнаружилось в существующей схеме

Проектирование началось с вопроса «где ставить политики RLS у новых таблиц» и
закончилось тремя находками, каждая из которых важнее самих новых таблиц.

### 4.1. Политики стояли на пятнадцати таблицах из ста пятнадцати

RLS завела миграция `m7` — под контур «Дом». У заявки, пользователя, проводки,
организации, прайса и ещё трёх десятков таблиц политик не было вовсе, хотя и
README, и DEV-02 называют RLS механизмом изоляции арендаторов.

Практического вреда не было: арендатор один. Но это ровно тот случай, когда
«пока не вредило» — не аргумент: второй арендатор появляется одним `INSERT`, а
изоляции, которой нет, хватятся не при его появлении, а когда первый увидит
чужие заявки.

Закрыто в `m32`: политики на всех 115 таблицах. У дочерних таблиц своего
арендатора нет — политика проверяет арендатора родителя через `EXISTS`.
Дописывать им `tenant_id` значило бы хранить его дважды и однажды разойтись.

### 4.2. Приложение ходило в базу суперпользователем

Это главное. `ENABLE ROW LEVEL SECURITY` не действует на владельца таблицы, а
`FORCE ROW LEVEL SECURITY` не действует на суперпользователя. Приложение
подключалось ролью `sozo` — владельцем и суперпользователем одновременно.

То есть изоляция арендаторов была написана, объявлена в документации и **не
работала ни секунды**, включая те пятнадцать таблиц, что завела `m7`.

Обнаружить это можно было только попыткой прочитать чужую строку. Проверка
`db:check:rls` до сих пор проверяла лишь, что контекст живёт внутри
транзакции, — а это зелено и при полном отсутствии политик.

Закрыто в `m33`: роль `sozo_app` без суперпользователя и без `BYPASSRLS`,
права только на данные (DDL остаётся у владельца). Проверка расширена:
пишутся строки от двух арендаторов и проверяется, что каждый видит только
своё — на трёх уровнях вложенности, включая внучатую таблицу.

### 4.3. Политики требовали контекста, которого приложение не заполняет

Как только RLS заработала, посыпались отказы на записи. Причина: политики
`m7` требуют либо платформенной роли, либо совпадения оператора в контексте, а
контекст оператора приложение не заполняет никогда — в `main.ts` стоит
`operatorOrgId: null`.

Значит запрос жителя или мастера не удовлетворял ни одному из двух условий.

Закрыто в `m34`. Правило исправлено, а не отключено: изоляция арендаторов
держится всегда, а сужение до оператора применяется тогда, когда оператор в
контексте назван. У жителя и мастера оператора нет и быть не может — их доступ
ограничивает приложение по другому признаку: по помещению и по заявке.

**Что это не делает:** не даёт жителю читать чужие объекты через API — там свои
проверки. RLS стоит последней преградой на случай ошибки в них, и преграда
«чужой арендатор» остаётся абсолютной.

### 4.4. Побочное следствие, о котором надо знать

Запрос в `psql` под `sozo_app` без `SET app.tenant_id` теперь возвращает ноль
строк, а не всё подряд. Это правильно и это же неудобно: обслуживание базы
руками требует явно назвать арендатора. Под владельцем `sozo` видно всё —
именно поэтому приложение им больше не ходит.

## 5. Как это проверяется

```bash
npm run db:check:rls    # 10 проверок: контекст + настоящая изоляция
npm run db:check:pg     # 6 проверок: EXCLUDE на стояки
npm run schema:drift    # расхождение схемы с кодом
npm run test:e2e -w @sozo/api   # 566 сквозных проверок на PostgreSQL
```

Прогон e2e поднимает сервер ролью `sozo_app` — то есть проверяет систему с
работающей изоляцией, а не схему без неё.

## 6. Что осталось

Таблицы спроектированы и применяются, но **модули на них ещё не переведены**:
код продолжает писать в `state.json`. Это следующий шаг, и он механический —
форма переноса для каждого вида уже отработана на одиннадцати модулях
(рабочий набор с записью насквозь, только дописывание, полная перезапись).

Отдельно стоит заполнение контекста оператора: пока `operatorOrgId` всегда
пуст, сужение по оператору не действует ни на кого. Это не дыра в изоляции
арендаторов, но и не то, что описано в DEV-15.
