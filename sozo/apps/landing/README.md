# landing — публичные лендинги SOZO (PRD-06)

> **Исходное задание (сохранено):**
> landing — Next.js SSR (PRD-06: лендинги L-01…L-08 + веб-карточка W-01…W-05 + верификация /m/{code}).
> Каркас создаётся в M0-E1-S4 (`npx create-next-app@latest .`). LCP < 2.5 s на мобильном 4G, бюджет
> критического пути ≤ 500 КБ; цены — только из публичного API (PRD-05 §12.8) с деградацией
> «плитки без цен».

## Важно: это dev-каркас на Vite, а не финальный стек

Текущая реализация — **Vite + React 18 + TypeScript + react-router-dom**, SPA без SSR.
Так сделано сознательно, чтобы быстро получить рабочие лендинги для проверки контента и потоков.

**Прод-версия по DEV-07 должна быть на Next.js с SSR.** Причины, по которым SPA не годится в прод:

- SEO: контент лендингов рендерится на клиенте, поисковики видят пустой `<div id="root">`;
- LCP < 2.5 s на мобильном 4G достигается серверным рендерингом первого экрана;
- `/m/{code}` требует заголовка `X-Robots-Tag: noindex` и `<meta name="robots">` — в SPA их не выставить;
- кеширование цен с инвалидацией по `pricelist.release_activated` естественно ложится на ISR/revalidate.

Разметка, компоненты и логика форм переносятся в Next.js практически без изменений: страницы в
`src/pages/*.tsx` не завязаны на роутер, кроме `Link` и `useSearchParams`/`useParams`.

## Запуск

```bash
cd apps/landing
npm install
npm run dev      # http://localhost:5175
npm run build    # tsc --noEmit && vite build
npm run preview
```

Пакет называется `@sozo/landing` и намеренно **не** добавлен в `workspaces` корня — зависимости
ставятся локально в `apps/landing/node_modules`.

Базовый URL API настраивается через `VITE_API_URL` (см. `.env.example`), по умолчанию
`http://localhost:3000/v1`.

## Что подключено к реальному API

Все публичные эндпоинты работают без авторизации:

| Эндпоинт | Где используется |
| -------- | ---------------- |
| `GET /v1/public/prices` | плитки категорий и цены «от» на `/`, список категорий в форме `/order` |
| `GET /v1/public/object-type-rates` | ставки и типовые площади в калькуляторе `/calculator` (справочник A-29) |
| `GET /v1/public/master-verify/:code` | статус бейджа на `/m/:code` |
| `POST /v1/public/leads` | все три формы: `/order` (b2c), `/calculator` (b2b), `/apply` (master) |

Суммы приходят в **тийинах** (1 сум = 100 тийин) — конвертация в `src/lib/format.ts`.
Номер обращения (`ticket`) и SLA (`slaMinutes`) показываются на экранах успеха:
10 минут для B2C, 4 рабочих часа для B2B, 2 рабочих дня для кандидата.

### Деградация при недоступности API

- **Цены (`/`)** — плитки рендерятся из резервного списка названий категорий (`src/lib/catalog.ts`)
  **без цен**, с подписью «Цену уточнит диспетчер» (PRD-06 §3). Цены никогда не хардкодятся:
  единственный источник — публичный API.
- **Ставки (`/calculator`)** — сумма не считается, показывается объяснение и предложение оставить
  заявку; форма КП остаётся рабочей.
- **Верификация (`/m/:code`)** — при сетевой ошибке показывается «Не удалось проверить бейдж»,
  а **не** «НЕДЕЙСТВИТЕЛЕН»: недоступность сервиса не должна выглядеть как отрицательный вердикт.

## Защита форм

- **Honeypot** — скрытое поле `company_website` во всех трёх формах. Если заполнено, показывается
  обычный экран успеха, но запрос не отправляется (бэкенд дополнительно страхует это на своей стороне).
- **Двойной сабмит** — кнопка `disabled` на время запроса плюс `inFlight`-guard в `useLeadSubmit`.
- **Согласие ЗРУ-547** — обязательный чекбокс; без него кнопка неактивна, а бэкенд вернёт
  `CONSENT_REQUIRED`.
- **Телефон** — маска `+998`, кнопка неактивна, пока не введены 9 национальных цифр; на сервер уходит
  E.164 (`+998XXXXXXXXX`). Ошибка `PHONE_INVALID` показывается пользователю.
- **UTM** — метки первого касания снимаются из URL, живут в `sessionStorage` и подмешиваются в лид.

## Языки

Десять языков: `ru`, `uz`, `en`, `tr`, `tg`, `ar`, `fr`, `de`, `zh`, `ko`.

**Язык живёт в адресе, а не в localStorage.** Иначе не работает hreflang,
поисковик видит один русский сайт, а пересланная другу ссылка открывается не
на том языке, на котором её читали. Русский остался в корне: на `/order` и
`/b/:code` ведут визитки, наклейки в подъездах и QR-коды мастеров, и ломать
их ради единообразия нельзя.

```
/order        русский
/fr/order     французский
/ar/order     арабский, страница разворачивается справа налево
```

Префикс снимает `basename` роутера (`localeBasename()` в `src/i18n`), поэтому
в остальном коде ссылки пишутся как раньше — `<Link to="/order">`, и
react-router сам подставит язык. Из-за этого же смена языка — переход по
адресу с перезагрузкой, а не смена состояния: `basename` задаётся один раз
при старте. На лендинге это скорее плюс — свежий словарь, правильный
`<html lang>`, честное событие перехода для аналитики.

**Словари.** Русский подключён статически: он и язык большинства визитов, и
запасной вариант для пропущенного ключа. Остальные девять лежат в
`src/i18n/locales/` и уезжают отдельными чанками — иначе каждый посетитель
тянул бы девять чужих словарей, а PRD-06 §5.2 требует LCP меньше 2.5 s.

**Русский словарь собирается, а не пишется.** Строки вынимали из страниц по
одной странице за раз, поэтому источник — фрагменты `src/i18n/ru/*.ts`, по
файлу на страницу. Правят их, а потом:

```bash
node tools/build-ru-dict.mjs   # из корня sozo/ — пересобирает src/i18n/dict.ru.ts
node tools/check-dicts.mjs     # сверяет наборы ключей всех языков
```

Две проверки отвечают на разные вопросы, и нужны обе:

```bash
node tools/check-dicts.mjs         # все ли ключи на месте
node tools/check-translations.mjs  # а что в них написано
```

`check-dicts.mjs` ловит то, чем ломается механика: пропущенный ключ, лишний
ключ, потерянный плейсхолдер `{sla}`, пустое значение и вызов `t('...')` на
ключ, которого в словаре нет.

`check-translations.mjs` ловит то, чем ломается смысл: строку, оставшуюся
русской, символ `�` от потерянной кодировки, плейсхолдер, прилипший к слову,
и расхождение якорных понятий между лендингом и приложением (валюта, «точка»)
(«©2026SOZO» вместо «© 2026 SOZO» — верный признак машинного перевода, он
съедает пробел вокруг непонятной ему скобки). Прилипшие пробелы чинятся
скриптом `tools/fix-holder-spacing.mjs`: правка механическая, вычитки не
требует. Исключения обеих проверок лежат в `tools/locale-exceptions.mjs` —
с причинами, потому что молчаливое исключение через месяц выглядит как дыра.

Чего ни одна из них не ловит — верно ли выбрано слово. Первый проход
перевёл «точку» (объект бизнеса) как «балл» в восьми языках из девяти, а
«диспетчера» по-арабски — как «апостола». Это правится вычиткой, и
единственный надёжный эталон здесь — словарь приложения: лендинг и
приложение обязаны называть вещи одинаково.

**Множественное число** — через `Intl.PluralRules`, ключами
`.one/.two/.few/.many/.zero/.other` (`tn('calculator.points', 3)`). У русского
три формы, у арабского шесть, у китайского и корейского одна; своей функцией
это не выражается. `.other` обязателен — он же запасной вариант, и
`check-dicts.mjs` требует от каждого языка ровно те категории, которые
`Intl.PluralRules` для него называет: незаведённая категория не падает, а молча
уезжает на `.other`, и арабский посетитель видит форму для «многих» там, где
нужна двойственная.

Одна оговорка: данных о таджикских формах в ICU нет, и `Intl.PluralRules('tg')`
откатывается на `en-US` — то есть на пару `one/other`. Таджикскому этого хватает
(множественное там образуется суффиксом `-ҳо` независимо от числа), но если
понадобится точность, формы придётся считать самим. На разряды чисел это не
влияет: `Intl.NumberFormat('tg')` таджикский знает и ставит пробел, как в русском.

**Что переводится и что нет.** Категория прайса, район и навык уезжают в API
русской строкой из активного релиза: отправь клиент «Plumbing», сервер её не
узнает. Поэтому массивы в `src/lib/catalog.ts` остаются русскими, а
переводится только подпись — через ключ, найденный по этой же строке.
Незнакомая категория показывается по-русски: прайс ведёт админ, он может
завести позицию в любой день.

**Язык уходит с лидом** (`lang` в теле, `Accept-Language` в заголовке):
PRD-06 §5.3 требует, чтобы на нём же перезвонил диспетчер и пришла SMS.

## Дизайн

Лендинги оформлены по фирменному стилю из Figma (знак и надпись SOZO): **янтарь `#FEB70F`
на почти-чёрном `#141518`**. Панели (`admin-web`, `dispatcher-web`) на старой палитре — это
осознанное расхождение: лендинг продаёт, панели работают.

- **Токены** — `src/tokens.css`: тёмная и светлая шкалы, акцент, радиусы, тени, шрифты, кривые
  анимации. Hex допустим только здесь, в разметке и `styles.css` — только `var(--*)`.
- **Тёмный герой + светлое тело.** Герой, блок мастеров, аварийный блок, финальный CTA и подвал —
  на `--ink-900`; контентные секции — светлые. Шапка над тёмным героем прозрачная и «застекляется»
  при скролле (класс `is-over-dark` / `is-scrolled`).
- **Шрифты** — Inter (текст) и Manrope (заголовки) с Google Fonts, `display=swap`, оба с кириллицей.
- **Фотографии** — реальные снимки мастеров и работ вместо иконок: `public/photos/masters`
  и `public/photos/work`, WebP, ширина под макет (портреты 760×950, работы 1200×900). Фото героя
  идёт через `<link rel=preload>` и `fetchpriority=high` (LCP), остальные — `loading="lazy"`.
- **Анимации** — только CSS-переходы и один `IntersectionObserver` на страницу (`src/lib/reveal.ts`),
  никаких библиотек анимации. Всё выключается через `prefers-reduced-motion: reduce`.
- **Интерактив без зависимостей** — слайдер «до/после» (pointer events + clip-path), счётчики на
  `requestAnimationFrame`, табы приложений, FAQ на нативном `<details>`, ленты с `scroll-snap`.
- **Mobile-first**, проверено на 390px: две колонки плиток, липкая панель звонка, меню на весь
  экран по бургеру, горизонтальные ленты мастеров и отзывов.
- **Бюджет:** ~259 КБ JS (84 КБ gzip) + 38 КБ CSS (8 КБ gzip). Фотографии — 2,3 МБ на всё,
  на первый экран приходится ~200 КБ. Бюджет критического пути ≤ 500 КБ соблюдён.
