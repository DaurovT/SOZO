# DEV-01. Бэклог разработки USTAPRO (SOZO) — MVP

**Основание:** ТЗ USTAPRO v2.25 (раздел 15 «Этапность разработки») · пакет PRD-00…06 v1.1
**Назначение:** порядок сборки MVP по майлстоунам, эпикам и стори — так, чтобы разработчики просто делали и не думали. Любой конфликт с ТЗ трактуется в пользу ТЗ.
**Идентификаторы:** экраны C-xx (клиент), W-xx (веб-карточка), M-xx (мастер), D-xx (диспетчерская), A-xx (админка), L-xx (лендинги); стори — `Mx-Ey-Sz`.

---

## 1. Команда и роли

| Роль | Чел. | Зона ответственности |
|---|---|---|
| Flutter-разработчик | 2 | №1 — приложение «Клиент» (PRD-01), №2 — «Мастер» (PRD-02, офлайн) |
| Backend-разработчик | 2 | №1 — статусные машины, планировщик, интеграции; №2 — биллинг, документы, отчёты (PRD-05) |
| Web-frontend | 1 | Диспетчерская (PRD-03), админка (PRD-04), веб-карточка, лендинги (PRD-06) |
| QA | 1 | Тест-кейсы по критериям приёмки, сквозные трассы 8.2, регресс |
| PM / тимлид | 1 | Бэклог, демо владельцу, контроль соответствия ТЗ |

**Дизайн:** финальный дизайн заказчик делает сам позже. На время разработки — временный UI-кит (стандартные компоненты Material/Ant, единая палитра, никакой кастомной графики). Экраны собираются по блокам «Элементы и действия» из PRD; редизайн — отдельный этап после MVP, логика не меняется.

**Суммарный срок:** M0–M6 ≈ 21–24 недели с учётом параллельности (~5 мес, соответствует ТЗ 15).

### Не делаем сейчас (фазы 2–3 по ТЗ 15 — в MVP не входит)
- Техдолг как отдельный модуль с пакетными утверждениями (в MVP — дефекты простым списком, см. M3-E4) и отчёт по осмотру расширенный.
- ЭДО-интеграция (СФ — PDF полуавтоматом); импорт банковской выписки.
- Многоуровневые пороги и двойное утверждение владельцем.
- Авто-рейтинг мастеров по формулам 7.4 (в MVP рейтинг ставит диспетчер вручную).
- Полная матрица эскалаций по сметам 24/48/72 ч (в MVP — короткие напоминания 30 мин / 2 ч).
- Полноценный чат (в MVP — звонок и шаблонные сообщения), телефония с записью, Uzum.
- Автоматический дунинг и пени (напоминания вручную бухгалтером); количественный учёт «сумки».
- Авто-график осмотров InspectionSchedule (в MVP осмотры создаёт диспетчер вручную).
- Полный склад с инвентаризацией и количественным учётом (в MVP — лёгкий контур A-38, ТЗ 17.16: M5-E2-S5), бейджи с QR (страница L-07 — MVP, сами бейджи — фаза 2), калькулятор абонентки в админке A-08, тепловая карта D-04, KPI-виджет D-19, амортизация и ТО-график оборудования, паттерн-детект жалоб, дашборд-расширения владельца, вся фаза 3 (proxy-номера, Telegram-бот, ИИ-смета, англ. язык и пр.).
- **Примечания к скоупу бэклога:** партнёрские магазины «Код закупки» (M5-E3) и сезонные окна (M5-E4-S3) по ТЗ — фаза 2; включены в M5 решением по бэклогу как задел роста. При дефиците времени режутся первыми.

## 4. Критический путь и параллельность

**Критический путь (backend):**
M0-E2-S1 схема БД → M1-E1 статусная машина B2C → M2-E1 биллинг-движок → M3-E2/E3 (B2B-машина + абонентка) → M4-E1 планировщик → M4-E2 авто-распределение → M6-E1 офлайн-синк. Задержка любого из этих узлов сдвигает всё справа.

**Правила порядка:**
- Ни один экран не начинается раньше контракта API (OpenAPI-спека — до старта фронта; фронт работает на моках, бэкенд догоняет).
- Статусная машина (M1-E1) блокирует все клиентские экраны заявки; биллинг (M2-E1) блокирует всё в M2–M3, где есть деньги; планировщик (M4-E1) блокирует авто-распределение, «Срочно», этапные и парные.
- Веб-карточка и D-08 (M1) — раньше лендингов (M5): лид-контур опирается на очередь «Позвонить» (M4-E4-S1).

**Параллельность по командам:**
| Период | Backend №1 | Backend №2 | Flutter №1 (Клиент) | Flutter №2 (Мастер) | Web-frontend |
|---|---|---|---|---|---|
| M0 | ядро, auth, шина | схема БД, прайс | каркас + вход | каркас + вход | каркасы панелей |
| M1 | статусная машина | SMS/push, медиа-хранилище | C-01..C-19 | конвейер M-06..M-42 | D-01..D-08, W-01..05 |
| M2 | Payme/Click, refund | биллинг-движок, PDF | C-20, промокоды | M-34, M-35 | A-15..A-22, A-31 |
| M3 | B2B-машина, лимиты | абонентка, отчёты | B2B-контексты C-31..C-48 | режим осмотра | A-06..A-10, A-26 |
| M4 | планировщик, авто-распределение | наценки, споры/refund | C-12 окна, C-22/23/26 | офферы, дежурный, этапные | D-05, D-09..D-18, D-20 |

## 5. Definition of Done (общий для всех стори)

1. Код-ревью пройдено (минимум один аппрув, не автор).
2. Тесты написаны и зелёные (юнит на логику, интеграционный на API-переходы).
3. Критерий приёмки стори воспроизводится QA на стейдже.
4. Переходы статусов валидируются на API (проверка запросом мимо UI), не только в интерфейсе.
5. Все тексты рус/узб — через словарь локализации, хардкод строк запрещён.
6. Все настраиваемые значения — из таблицы 123 параметров (A-05, PRD-04 §5), магических чисел нет.
7. Значимые действия пишут события в append-only аудит-лог (кто, что, когда, устройство/IP).
8. Демо-записи (флаг «демо») исключены из биллинга, отчётов и регистров.

| SLA ответов | Владелец отвечает на вопросы команды в течение 24 ч; молчание > 24 ч — вопрос эскалируется PM, срок стори сдвигается на время ожидания |
| Изменения скоупа | Только через изменение ТЗ с новой версией; «на словах» ничего не меняем. PM оценивает влияние на сроки до принятия |

| Еженедельный статус | Раз в неделю письменный статус: сделано / план / блокеры / вопросы к владельцу с дедлайнами ответов |
| Открытые зависимости | Юрист (оферта, персданные ЗРУ-547, потолок ответственности), бухгалтер (налоговый контур, ОФД, ваучеры), бизнес (реферальный бонус, магазины-партнёры) — по списку PRD-00; блокируют соответствующие стори, отслеживаются в статусе |
