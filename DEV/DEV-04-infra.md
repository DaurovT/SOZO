# DEV-04. Инфраструктура и DevOps платформы USTAPRO (SOZO)

**Документ:** инженерный регламент инфраструктуры, эксплуатации и релизов.
**Источник истины:** ТЗ v2.25 (раздел 14 «Нефункциональные требования»), PRD-05 (архитектурная рамка, разделы 15.2–15.3).
**Архитектурная рамка:** единый модульный монолит **NestJS (TypeScript)**; веб-панели — React, лендинги — Next.js (SSR), ORM — Prisma, монорепозиторий (решение владельца, ТЗ v2.24); PostgreSQL, Redis (очереди/кеш), S3-совместимое хранилище, FCM. Горизонт нагрузки 2 года: ~200 мастеров, 5 000 заявок/мес, 500 организаций. Микросервисы не строим.

---

## 1. Среды

| Среда | Назначение | Данные | Доступ |
|---|---|---|---|
| **dev** | разработка, ветки feature | синтетика/сиды, без реальных персданных | вся команда; можно ломать |
| **stage** | приёмка, демо продавца, интеграционные прогоны | демо-данные (флаг «демо», ТЗ 17.6) + анонимизированные срезы prod (телефоны/ФИО/адреса замаскированы скриптом анонимизации, фото не копируются) | команда + ПМ + владелец; автодеплой из develop |
| **prod** | боевая | реальные персданные — только на серверах в Узбекистане (ЗРУ-547) | деплой через ручной gate; прямой доступ — см. раздел 6 |

Правила:
1. Копирование prod → stage только через скрипт анонимизации (обязательный шаг пайплайна, ручной дамп запрещён).
2. Внешние интеграции на dev/stage — sandbox-ключи провайдеров (Payme/Click test, SMS в лог вместо шлюза).
3. Конфигурация сред — только через переменные окружения/секрет-хранилище; в репозитории — `.env.example` без значений.

## 2. Хостинг (требование ЗРУ-547)

По закону РУз «О персональных данных» (ЗРУ-547) персданные граждан Узбекистана хранятся на серверах на территории Узбекистана. **Подтвердить трактовку у юриста на старте** (ТЗ 14).

Варианты размещения:

| Вариант | Что размещаем | Примечание |
|---|---|---|
| **Гособлако/коммерческое облако УЗ** (класс UZCLOUD — uzcloud.uz) | всё: БД, приложение, S3-хранилище | управляемые VM/K8s/S3-совместимое хранилище; тарифы и SLA — **уточнить у провайдера** |
| **Местные коммерческие ЦОД** (colocation/аренда VM в Ташкенте) | всё | цены/каналы — **уточнить у провайдера**; проверить наличие S3-совместимого хранилища, иначе MinIO на своих VM |
| **Гибрид** | персданные (PostgreSQL, фотоархив, бэкапы) — в УЗ; stateless-компоненты (CI-раннеры, мониторинг, Sentry-класс, CDN лендингов) — где угодно | юридически безопасен только если за пределы УЗ не уходят персданные (в т.ч. в логах и трейсах — фильтровать) |

Минимальная конфигурация старта (ориентир, не тариф):
- **app** ×2 (2 vCPU / 4 GB) за балансировщиком — API + воркеры очередей;
- **PostgreSQL** 4 vCPU / 8 GB / SSD 100+ GB, WAL-архивация на отдельный диск/бакет;
- **Redis** 1–2 GB (очереди, кеш, rate-limit);
- **S3-совместимое хранилище** — старт 100 GB, рост ~5 000 заявок × 6–10 фото × 0,5 МБ ≈ 15–25 GB/мес; хранение вечное → планировать ~0,5 ТБ к концу 2-го года;
- **bastion** (микро-VM) + VM мониторинга.

Рост: вертикально (БД до 8–16 vCPU), затем реплика чтения PostgreSQL и +app-ноды. На горизонте 2 лет шардирование не требуется.

## 3. CI/CD

**GitFlow-lite:** `main` (=prod), `develop` (=stage), `feature/*` от develop. Хотфиксы — `hotfix/*` от main с обратным мержем в develop.

| Правило | Как |
|---|---|
| Ревью | PR в develop/main — минимум 1 аппрув, merge без ревью запрещён настройками репозитория |
| Автотесты | пайплайн PR: линтер → юнит → интеграционные (статусные машины, проводки биллинга, идемпотентность синка) → сборка. Красный пайплайн блокирует merge |
| Деплой stage | автоматически при merge в develop (миграции → код → smoke-тест) |
| Деплой prod | вручную (gate: ПМ/техлид), только из main, тегированный релиз; откат = предыдущий тег + down-миграция или совместимая схема |
| Миграции БД | **только миграционными файлами** в репозитории, применяются пайплайном; ручные ALTER на prod запрещены; миграции обратно-совместимы минимум на 1 релиз (deploy без даунтайма) |
| Секреты | в CI — из секрет-хранилища раннера, не в логах |

## 4. Бэкапы (ТЗ 14: восстановление ≤ 4 часов)

| Объект | Схема | Хранение |
|---|---|---|
| PostgreSQL | **PITR** (непрерывная WAL-архивация) + ежедневный полный дамп ночью | полные — 30 дней; WAL — 7–14 дней; копия полного дампа в независимый бакет/ЦОД (в пределах УЗ) |
| Фотоархив S3 | **версионирование бакета** + запрет физического удаления (юридический архив закрытых заявок — **вечное хранение**, ТЗ 14) | вечно; lifecycle только в «холодный» класс, не удаление |
| Конфигурация/секреты | экспорт vault + IaC-репозиторий | по релизам |
| AuditLog | входит в бэкап БД; append-only, физическое удаление запрещено | вечно |

**Тест восстановления — раз в квартал:** восстановление полного бэкапа + накат WAL на отдельную VM, прогон smoke-тестов и баланс-чекера, замер времени (норматив ≤ 4 ч), протокол в журнал эксплуатации. Непроверенный бэкап считается отсутствующим.

## 5. Мониторинг и алертинг (ТЗ 14, PRD-05 §15.2)

| Метрика/алерт | Порог (старт) | Класс |
|---|---|---|
| Аптайм API (внешний healthcheck) | недоступность > 2 мин | критический |
| Глубина очередей воркеров + DLQ | рост очереди > 15 мин / любое сообщение в DLQ | критический |
| Лаг офлайн-синка мастеров | пакеты старше 30 мин не применены | высокий |
| Вебхуки платёжных провайдеров | вебхук в карантинной очереди (неизвестная заявка); нет вебхуков > 1 ч при активных оплатах | высокий |
| Доставка push/SMS | error rate шлюза > 5% | высокий |
| **Баланс-чекер** (PRD-05 §4.5) | любое расхождение проводок — **бизнес-алерт** бухгалтеру + техлиду, не «тихий лог» | критический |
| Диск/CPU/память БД, репликация | по стандартным порогам | средний |

- **Ошибки приложений:** Sentry-класс (self-hosted в УЗ или SaaS при условии фильтрации персданных из событий) — бэкенд + оба Flutter-приложения.
- **Логи:** структурированные (JSON), с `request_id`/`order_id`; агрегация (Loki/ELK-класс); персданные в логах маскируются; хранение логов — UTC (ТЗ 14).
- **Реагирование:** ответственный дежурный — в регламенте эксплуатации; критические алерты — в Telegram-канал эксплуатации.

## 6. Безопасность

| Мера | Реализация |
|---|---|
| Аутентификация | телефон + OTP; JWT с ротацией refresh-токенов; повторная аутентификация (PIN/биометрия) для крупных утверждений (анти SIM-swap, ТЗ 16) |
| Авторизация | проверка контекста организации/точки на каждом эндпоинте (ТЗ 14); переходы вне графов отклоняет API |
| Rate limit | на OTP (анти-SMS-флуд — это прямые деньги), на логин, на публичные эндпоинты веб-карточки; через Redis |
| Phone masking | телефон клиента открывается мастеру только на время заявки, звонки кнопкой; в логи/аналитику номера не пишутся в открытом виде |
| Фото | доступ **только по signed URL** с TTL, только участникам заявки; EXIF очищен на клиенте |
| Секреты | vault/секрет-хранилище (или шифрованные env через деплой-механизм); ключи провайдеров не хранятся в репозитории; ротация при уходе сотрудника |
| Доступ к prod-БД | **только через bastion** (SSH-ключи, MFA), персональные учётки, без общего root; прямой порт БД наружу закрыт |
| Аудит доступа | логирование сессий bastion и админских действий в append-only AuditLog; ежеквартальный пересмотр списка доступов |
| Сеть | TLS везде; внутренние сервисы в приватной сети; WAF/защита от ботов на публичных формах лендингов |

## 7. Мобильные релизы

| Канал | Что | Кто |
|---|---|---|
| internal | сборки из develop (Firebase App Distribution / TestFlight internal) | команда, QA |
| beta | закрытая бета из релиз-кандидата (Play closed testing / TestFlight external) | пилотные мастера и диспетчеры, M6 |
| prod | публикация в Google Play + App Store | по ручному gate, синхронно с бэкенд-релизом |

- **Force update** (уже в ТЗ 14): бэкенд отдаёт `min_supported_version` по каждому приложению; ниже — экран «обновите приложение» без входа. Версионирование API; feature flags для поэтапного включения.
- Подпись: Android keystore и iOS-сертификаты — в секрет-хранилище, не у одного разработчика на ноутбуке; сборка релизов только в CI.
- Учесть сроки ревью сторов (App Store до нескольких дней) в планировании релизов; критические бэкенд-фиксы не должны требовать релиза приложений.

## 8. Нагрузочные ориентиры и деградация

Ориентиры (горизонт 2 года): 5 000 заявок/мес ≈ 200–250/день; пик утро 8:00–10:00; ~200 мастеров онлайн; массовый инцидент (авария теплосети) — до 100 заявок/час кластерно.

| Узел | Ориентир | Деградация |
|---|---|---|
| API | p95 < 300 мс на CRUD, < 1 с на расчёт слотов | балансировщик, +app-ноды |
| Очередь офферов мастерам | оффер доставлен < 10 с; таймаут ответа — параметр | очередь переживает всплеск: офферы не теряются, обрабатываются по приоритетам (аварии → B2B SLA → …, ТЗ 16); при отказе FCM — SMS-fallback критических уведомлений |
| Push | FCM недоступен → ретраи с backoff, критические события дублируются SMS | деградация без потери событий (outbox) |
| Офлайн-синк | идемпотентен; шторм синка после восстановления сети у многих мастеров — очередь с ограничением конкуренции, не роняет БД | лаг растёт, данные не теряются |
| Вебхуки платёжек | приём всегда 200 + постановка в очередь; обработка асинхронно; неизвестные — карантин | оплата «доедет» после восстановления |
| Массовый инцидент | режим массового инцидента (кластеризация, шаблонные оповещения) — нагрузка на пуши/SMS пакетируется | rate-limit исходящих SMS, приоритет аварийным |

Перед запуском: нагрузочный прогон (k6/JMeter-класс) на stage — 3× дневного пика по созданию заявок, офферам и синку; фиксация базовых метрик как эталона для алертов.

## Требования БД для контура «Дом» (M7)

1. **Расширение `btree_gist`** — нужно для EXCLUDE-ограничения «один стояк — одно отключение в пересекающемся окне» (DEV-02 §4.4 п.9). Входит в `postgresql-contrib`; в образе `postgres:16-alpine` присутствует. Применяется миграцией `m7_shutdown_exclusion`.
2. **Пулер только в transaction mode.** Изоляция арендаторов построена на RLS с контекстом через `SET LOCAL`, который живёт исключительно внутри транзакции. В session mode контекст протекает между запросами разных операторов — это утечка персональных данных жителей, а не деградация производительности.
3. **Сервисной роли приложения не выдаётся `BYPASSRLS`** и она не владеет таблицами — иначе политики к ней не применяются. Роли платформы работают через `app.role = 'platform_*'` и отдельную политику.
4. **Проверка без сервера:** `npm run db:check` прогоняет миграции и инварианты на PGlite (PostgreSQL 18 в WASM). Не заменяет интеграционные тесты на боевой БД, но ловит расхождение схемы и кода до деплоя.
