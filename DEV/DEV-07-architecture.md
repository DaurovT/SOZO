## 3. Правила зависимостей (нарушение = отклонённый PR)

1. **Все модули могут зависеть от `kernel` и `platform`. Ни один — от `billing`.**
2. **`billing` не импортирует ничего доменного** — он подписан на события (`order.closed`, `contract.renewed`, `duty.shift_completed`, `stock.movement`, …) и читает свои таблицы + снапшоты цен из заявки. Выключенный `billing` не ломает ни один сценарий операционного контура — это SaaS-требование 17.13, проверяется интеграционным тестом «монолит стартует без billing-модуля».
3. `orders` не знает про `scheduling` напрямую: заявка публикует события, планировщик решает. Обратно — планировщик зовёт `orders` только через его публичный сервис переходов (единственная точка смены статуса, PRD-05 разд. 1).
4. `integrations` никого не импортирует и никем не импортируется напрямую — только адаптерные интерфейсы, объявленные в модулях-потребителях (порт/адаптер: `PaymentProviderPort` объявлен в `billing`, реализован в `integrations`).
5. Веб-приложения ходят только в HTTP API по `contracts`; никаких «дотянуться до БД».

## 4. Транзакционные границы (главное, ради чего документ)

**Правило А — одна бизнес-операция = одна транзакция БД.** В транзакцию входит: изменение агрегата + запись доменных событий в outbox-таблицу. Всё остальное — асинхронно воркерами.

**Правило Б — проводки только парами и только внутри транзакции.** `billing` пишет Дт/Кт одной записью Transaction; полупроводка невозможна на уровне кода (kernel/Money + репозиторий проводок не имеет метода «одна нога»).

**Правило В — переход статуса заявки:**
```
BEGIN;
  проверка графа + условий (фото, санкции, представитель осмотра);
  UPDATE order SET status; INSERT status_log;
  INSERT INTO outbox (order.status_changed{...});
COMMIT;  →  воркеры разбирают outbox: уведомления, биллинг, планировщик, генераторы задач
```
Сам биллинг по `order.closed` проводит **свою** транзакцию (проводки + балансы + outbox `billing.transaction_posted`). Итог: между «заявка закрыта» и «проводки есть» — миллисекунды асинхронности, но каждая половина атомарна, а outbox гарантирует доставку (at-least-once + идемпотентность обработчиков по event_id).

**Правило Г — что НИКОГДА не в одной транзакции:** вызовы внешних API (Payme, SMS, карты) — только до или после, с сагой через статусы (`pending → confirmed` по вебхуку); генерация PDF; пересчёт лент планировщика.

**Правило Д — деньги и идемпотентность:** вебхук провайдера обрабатывается с блокировкой по (provider, invoice_id); повторный вебхук — no-op. Офлайн-очередь мастера — идемпотентность по client_uuid операции (PRD-05 разд. 10).

**Правило Е — закрытие периода:** `period.locked` — сторно в закрытый период запрещено на уровне репозитория проводок (проверка даты), корректировки только текущим периодом.

## 5. Событийная шина

Outbox-таблица в PostgreSQL + воркеры BullMQ (Redis) — never Kafka (PRD-05). Каталог событий — PRD-05 разд. 4.6 и по модулям; имена `domain.event_name`. Каждый обработчик: идемпотентен, ретраится с backoff, после N падений — DLQ-таблица + алерт. Событ< 200 строк на обработчик; тяжёлое — дробить.

## 6. Данные (сжато, полное — DEV-02)

- `tenant_id NOT NULL` во всех доменных таблицах (оператор = тенант №1), составные индексы начинаются с него.
- Деньги — `BIGINT` в тийинах. Проценты/коэффициенты — `NUMERIC`, копией в заявке.
- Заявка хранит: `price_list_release_id`, снапшот строк цен, снапшот коэффициентов, `applicant_user_id`, `client_uuid`.
- Фото — только S3-ключи + подписанные URL; EXIF чистится на приёме (PRD-05 разд. 9).

## 7. Порядок сборки каркаса (первая неделя техлида)

1. Монорепо + CI + prisma schema из DEV-02 (день 1–2).
2. `kernel`: Money, EventBus/outbox + воркер, StateMachine-исполнитель (день 2–3).
3. `platform` (параметры, аудит) + `identity` (OTP-заглушка) (день 3–4).
4. `orders` со статусной машиной B2C по графу PRD-05 + первый сквозной тест «создать → закрыть» с событиями (день 4–5).
5. Демо владельцу: заявка проходит статусы, события падают в outbox, аудит пишется. Дальше — бэклог DEV-01 (M0).
