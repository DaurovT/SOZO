# DEV-07. Архитектурная декомпозиция: модули монолита, границы и транзакции

**Основание:** ТЗ v2.25 (стек утверждён решением v2.24: NestJS/TypeScript, React, Next.js, Prisma, PostgreSQL, Redis/BullMQ, монорепо — 18-п.22), PRD-05 (сервисы и события), DEV-02 (ER), DEV-03 (OpenAPI).
**Статус:** обязательная структура. Техлид может предлагать изменения — через правку этого документа до начала кодирования, не через «сложилось само».

## 1. Монорепозиторий

```
sozo/
├── apps/
│   ├── api/                # NestJS-монолит (единственный бэкенд)
│   ├── admin-web/          # React SPA: админ + бухгалтерия (PRD-04)
│   ├── dispatcher-web/     # React SPA: диспетчерская (PRD-03)
│   ├── operator-web/       # React SPA: кабинет эксплуатирующей организации, M7 (PRD-07, U-xx)
│   ├── landing/            # Next.js SSR: лендинги + веб-карточка заявки + страница верификации (PRD-06, PRD-01 W-xx)
│   ├── client-app/         # Flutter: приложение «Клиент» (PRD-01)
│   └── master-app/         # Flutter: приложение «Мастер» (PRD-02)
├── packages/
│   ├── contracts/          # ЕДИНСТВЕННЫЙ источник типов API: zod-схемы + генерация OpenAPI и Dart-моделей
│   ├── ui/                 # общие React-компоненты панелей (токены из DEV-06)
│   └── config/             # eslint/tsconfig/prettier — общие
├── prisma/                 # schema.prisma + миграции (одна схема на весь монолит)
└── infra/                  # docker-compose, CI, скрипты бэкапов (DEV-04)
```

**Почему кабинет — отдельное приложение (M7).** Сажать эксплуатирующую организацию в `dispatcher-web` нельзя — там все заявки всех клиентов; в `admin-web` тем более — она принадлежит владельцу платформы. Кабинет обслуживает **внешних по отношению к платформе людей** с собственной моделью прав и мультиобъектностью, поэтому это четвёртое веб-приложение, а не раздел существующего.

Правило: **веб-карточка заявки и страница верификации живут в `landing`** (Next.js, токенизированный доступ) — им нужны SSR и лёгкость, не SPA.
Flutter-приложения используют Dart-модели, **сгенерированные из `packages/contracts`** (openapi-generator) — руками модели не пишутся.

## 3. Правила зависимостей (нарушение = отклонённый PR)

1. **Все модули могут зависеть от `kernel` и `platform`. Ни один — от `billing`.**
2. **`billing` не импортирует ничего доменного** — он подписан на события (`order.closed`, `contract.renewed`, `duty.shift_completed`, `stock.movement`, …) и читает свои таблицы + снапшоты цен из заявки. Выключенный `billing` не ломает ни один сценарий операционного контура — это SaaS-требование 17.13, проверяется интеграционным тестом «монолит стартует без billing-модуля».
3. `orders` не знает про `scheduling` напрямую: заявка публикует события, планировщик решает. Обратно — планировщик зовёт `orders` только через его публичный сервис переходов (единственная точка смены статуса, PRD-05 разд. 1).
4. `integrations` никого не импортирует и никем не импортируется напрямую — только адаптерные интерфейсы, объявленные в модулях-потребителях (порт/адаптер: `PaymentProviderPort` объявлен в `billing`, реализован в `integrations`).
5. Веб-приложения ходят только в HTTP API по `contracts`; никаких «дотянуться до БД».
6. **`access` — единственная точка смены статуса наряда-допуска**, ровно как `orders` для заявки. Граф исполняется `StateMachine` из `kernel` по DEV-10 §7. `orders` спрашивает у `access` состояние наряда через публичный сервис, но сам его не меняет.
7. **`sla` не меняет статусы** — только считает дедлайны и публикует `sla.breached`. Реакция на нарушение — дело `orders` и движка уведомлений.
8. **`subscriptions` не импортируется `billing`** — правило 2 сохраняется без исключений: подписка публикует события (`subscription.charged`, `subscription.plan_changed`), `billing` на них подписан. Выключенный `billing` по-прежнему не ломает операционный контур, включая контур «Дом».

## 4. Транзакционные границы (главное, ради чего документ)

**Правило А — одна бизнес-операция = одна транзакция БД.** В транзакцию входит: изменение агрегата + запись доменных событий в outbox-таблицу. Всё остальное — асинхронно воркерами.

**Правило Б — проводки только парами и только внутри транзакции.** `billing` пишет Дт/Кт одной записью Transaction; полупроводка невозможна на уровне кода (kernel/Money + репозиторий проводок не имеет метода «одна нога»).

**Правило В — переход статуса заявки:**
```
BEGIN;
  проверка графа + условий (фото, санкции, представитель осмотра);
  UPDATE order SET status; INSERT status_log;
  INSERT INTO outbox (order.status_changed{...});
COMMIT;  →  воркеры разбирают outbox: уведомления, биллинг, планировщик, генераторы задач
```
Сам биллинг по `order.closed` проводит **свою** транзакцию (проводки + балансы + outbox `billing.transaction_posted`). Итог: между «заявка закрыта» и «проводки есть» — миллисекунды асинхронности, но каждая половина атомарна, а outbox гарантирует доставку (at-least-once + идемпотентность обработчиков по event_id).

**Правило Г — что НИКОГДА не в одной транзакции:** вызовы внешних API (Payme, SMS, карты) — только до или после, с сагой через статусы (`pending → confirmed` по вебхуку); генерация PDF; пересчёт лент планировщика.

**Правило Д — деньги и идемпотентность:** вебхук провайдера обрабатывается с блокировкой по (provider, invoice_id); повторный вебхук — no-op. Офлайн-очередь мастера — идемпотентность по client_uuid операции (PRD-05 разд. 10).

**Правило Е — закрытие периода:** `period.locked` — сторно в закрытый период запрещено на уровне репозитория проводок (проверка даты), корректировки только текущим периодом.

## 5. Событийная шина

Outbox-таблица в PostgreSQL + воркеры BullMQ (Redis) — never Kafka (PRD-05). Каталог событий — PRD-05 разд. 4.6 и по модулям; имена `domain.event_name`. Каждый обработчик: идемпотентен, ретраится с backoff, после N падений — DLQ-таблица + алерт. Событ< 200 строк на обработчик; тяжёлое — дробить.

## 6. Данные (сжато, полное — DEV-02)

- `tenant_id NOT NULL` во всех доменных таблицах, составные индексы начинаются с него.

> **Терминология — два разных «оператора», не путать.**
> **Тенант** (`tenant_id`) — экземпляр платформы: собственная операционная компания владельца, в перспективе город или лицензиат. Тенант №1 — сам владелец платформы.
> **Эксплуатирующая организация** (`operator_org_id`, DEV-15) — внешний клиент подписки: УК, ТСЖ, служба эксплуатации БЦ, техотдел сети, FM-подрядчик.
> Это **две независимые оси изоляции**. Внутри одного тенанта живут сотни эксплуатирующих организаций, и они не видят друг друга.
- Деньги — `BIGINT` в тийинах. Проценты/коэффициенты — `NUMERIC`, копией в заявке.
- Заявка хранит: `price_list_release_id`, снапшот строк цен, снапшот коэффициентов, `applicant_user_id`, `client_uuid`.
- Фото — только S3-ключи + подписанные URL; EXIF чистится на приёме (PRD-05 разд. 9).

1. Монорепо + CI + prisma schema из DEV-02 (день 1–2).

## 8. Изоляция арендаторов кабинета (M7-E0, DEV-15 §11.7)

**Решение: Row-Level Security в PostgreSQL как обязательный слой, скоупинг в коде — как первый слой и источник понятных ошибок.**

Почему не только код: 27 модулей и два бэкенд-разработчика означают, что рано или поздно в одном запросе забудут условие по организации. Для B2C это баг, для кабинета — утечка персональных данных жителей чужой управляющей компании. **RLS отказывает закрыто:** забыли — не увидели ничего, а не увидели чужое.

**Контракт реализации:**

1. Контекст запроса устанавливается `SET LOCAL app.tenant_id`, `app.operator_org_id`, `app.user_id`, `app.role` в начале транзакции — middleware поверх `prisma.$transaction`.
2. Политики включаются на всех таблицах контура (DEV-02 §4.2) и на таблицах, получивших арендаторское измерение (`Order`, `Shift`, `Defect`, `MasterAffiliation`).
3. `BYPASSRLS` **не выдаётся никому**, включая сервисную роль приложения. Роли платформы (админ, диспетчер) получают доступ отдельной, явной политикой.
4. Пулер — только в transaction mode: `SET LOCAL` живёт внутри транзакции, между запросами контекст не протекает.
5. **Тест-страж:** CI падает при появлении таблицы с арендаторским измерением и без политики. Без этого правило проживёт три спринта.
6. Диагностический режим для админов платформы: различает «нет прав» и «нет данных» — иначе пустая выдача вместо ошибки доступа станет постоянной ловушкой при отладке.

**Цена принята осознанно:** усложнение отладки, накладные расходы на транзакцию, требование к пулеру. Реализуется в **M7-E0** одновременно с миграцией на Prisma — переделка изоляции на живых данных недопустима.
