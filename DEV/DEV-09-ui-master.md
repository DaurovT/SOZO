# DEV-09. UI-спецификация мобильного приложения «Мастер» — USTAPRO / SOZO (Flutter)

**Статус:** рабочая спецификация для сборки MVP. · **Источники истины:** ТЗ USTAPRO v2.25 (вкл. UX-решения продакт-аудита 17.17), PRD-02 (экраны M-01…M-42, конвейер, офлайн, push) и DEV-06 (токены, компоненты, статус-цвета). · **Платформа:** Flutter, Android приоритет; языки рус/узб (латиница).

**Назначение документа:** Flutter-разработчик собирает любой экран без вопросов к дизайнеру и аналитику. Все визуальные значения — только имена токенов DEV-06; финальный редизайн владельца ляжет заменой значений токен-файла без правок экранов.

**Правило чтения:** бизнес-логика, гейты и крайние случаи — в PRD-02; здесь — что нарисовано, из каких компонентов, какие тексты и что происходит по тапу и офлайн. При расхождении логики верить PRD-02.

## 1. Общие принципы

Приложение — рабочий инструмент «на ногах»: мастер держит телефон одной рукой на лестнице, в подвале без сети, в перчатках, на солнце. Отсюда десять несущих правил:

1. **Крупные тап-зоны.** Главные кнопки конвейера — во всю ширину экрана, высота **56** (токен `pipelineButtonHeight: 56` — документированное расширение DEV-06 поверх стандартных 48), прижаты к низу в safe area с паддингом `s16`. Любая прочая интерактивная цель — не меньше 48×48.
2. **Одна главная кнопка на экран.** На каждом экране ровно одна primary-кнопка — ответ на вопрос «что делать дальше». Всё остальное — secondary, текстовые ссылки или пункты меню «⋮». Если главных действий кажется два — экран спроектирован неверно.
3. **Офлайн-индикация на каждом экране.** Общие элементы `OfflineBanner` и `SyncDot` (см. п. 3.0) присутствуют по умолчанию; экраны без офлайн-поддержки показывают заглушку с объяснением, а не спиннер.
4. **Камера в один тап.** Везде, где фото обязательно, кнопка [Снять] открывает камеру сразу — без промежуточных экранов и без выбора из галереи (галереи в приложении нет вообще, ТЗ 7.1).
5. **Минимум ввода текста.** Причины, типы, варианты — чипы и пресеты из справочников; количества — степперы «− 1 +»; свободный текст — только опциональные комментарии. Клавиатура — исключение, а не норма.
6. **Деньги — всегда одинаково.** Формат «1 250 000 сум»: неразрывные тонкие пробелы между разрядами, слово «сум» без сокращений, табличные цифры (`tabular-nums`). Доля мастера — `body` semibold цветом `text`; полная цена — `caption` цветом `textSecondary`. Копейки не показываем (тийины в UI не используются).
7. **Ноль строк в коде.** Все тексты — из i18n-словаря рус/узб (`intl`/ARB). В этом документе приведены финальные русские формулировки — они и есть содержимое словаря. Узбекские строки длиннее на 20–30 % — вёрстка обязана переносить и не обрезать.
8. **Только токены DEV-06.** `AppColors`, `AppRadius`, `AppSpacing`, `AppText`; хардкод `Color(0xFF…)` — блокер на ревью. Статусные цвета — только через `statusColor(status)`.
9. **Главное действие — под большим пальцем.** Кнопка конвейера внизу; разрушительные действия («Прервать», «Отказаться») — никогда не в зоне случайного тапа рядом с главной.
10. **Читаемость на солнце.** Основные тексты — `text` на `bg`/`surface` (контраст > 12:1); никакой информации только цветом — статус всегда дублируется словом в бейдже.

## 3. Поэкранная спецификация

### 3.0. Общие элементы (используются по всем экранам, описываются один раз)

- **`OfflineBanner`** — полоса под app bar во всю ширину: фон `warning` @ 12 %, иконка `cloud_off` 20 px `warning`, текст `caption` цветом `text`. Два варианта текста: для экранов действий — **«Офлайн — действия сохранятся и отправятся при сети»**; для read-only — **«Офлайн — данные на {чч:мм}»**. Появляется/исчезает без анимации сложнее fade.
- **`SyncDot`** — на карточках заявок и строках кошелька: иконка `sync_problem` 16 px `warning` + `caption` «не синхронизировано». Тап → M-42.
- **`PipelineButton`** — primary-кнопка конвейера: заливка `accent`, текст белый `body` semibold, радиус `radiusButton`, ширина экрана минус `s16`×2, высота 56, зафиксирована снизу.
- **`PausePlate`** — плашка паузы на M-11: фон `warning` @ 12 %, радиус `radiusCard`, иконка `schedule`, заголовок `body` semibold («Ожидание материалов», «Технологический перерыв», «Заблокировано третьей стороной», «Продолжение завтра»), под ним `caption` «Возобновление: {дата}».
- **`ModerationPlate`** — возврат с модерации: фон `error` @ 12 %, иконка `error` цветом `error`, текст «Возвращено диспетчером: {комментарий}» + кнопка secondary [Исправить].
- **`StatusBadge`** — чип по DEV-06 4.3, цвет строго из `statusColor(status)`.
- **`OrderCard`** — карточка заявки по DEV-06 4.2 (+ `SyncDot` при несинхронизированных операциях, полоса `error` слева у аварийных).
- Пустые состояния — только `EmptyState(icon, text, action)` по DEV-06 4.6. Тосты — DEV-06 4.7.

### 3.1. Вход и онбординг

#### M-01. Вход (телефон + OTP)
**Композиция:** логотип-словомарка (текст, без графики) → переключатель языка → поле телефона → PipelineButton → блок OTP (после отправки).
**Элементы:** чипы выбора языка «Русский / Oʻzbekcha» (radiusChip, активный — `accent` @ 12 %); поле телефона с маской «+998 __ ___ __ __» (DEV-06 4.4); PipelineButton **[Получить код]**; после отправки — 6 ячеек OTP (авто-подстановка из SMS), таймер `caption` **«Отправить снова через 0:59»**, по нулю — текстовая кнопка **[Отправить снова]**; PipelineButton **[Войти]**.
**Наполнение:** заголовок `h1` **«Вход для мастера»**; подпись `caption` «Код придёт по SMS». Ошибки под полем: **«Неверный код. Осталось попыток: 2»**, **«Слишком много запросов — попробуйте через минуту»**. Блокировка аккаунта — полноэкранно: иконка `lock`, **«Аккаунт заблокирован. Обратитесь к диспетчеру»**, кнопка [Позвонить диспетчеру]. Force update: **«Обновите приложение, чтобы продолжить работу»** + [Обновить].
**Поведение + офлайн:** отправка/проверка кода — состояние загрузки на кнопке (спиннер вместо текста). ОФЛАЙН: вход невозможен — EmptyState `wifi_off` **«Нет сети. Для входа нужен интернет»** без кнопки; при живой сессии в secure storage экран не показывается — приложение открывается офлайн сразу в M-06. Переходы: кандидат → M-02/M-05, мастер → M-06.

> **Состояние на 24.08.2026: M-02…M-05 в приложении не собраны.** Онбординг из
> приложения мастера убран целиком: мастера регистрирует и допускает к заявкам
> администратор (карточка мастера → «Открыть доступ» / «Закрыть доступ»,
> `POST /v1/admin/masters/:id/access`). Вошедший мастер, которому доступ ещё не
> открыт или закрыт, видит вместо воронки экран с причиной, кнопкой «Проверить
> доступ» и звонком диспетчеру. Серверные эндпоинты `/master/onboarding/*` и
> воронка A-12 в админке работают как прежде — по ним воронка вернётся в
> приложение, когда понадобится. Обучение перенесено в профиль («Как это
> работает») и доступно всегда, а не только кандидату.

#### M-02. Онбординг: анкета кандидата
**Композиция:** app bar с прогресс-баром шагов (тонкая полоса `accent` на `border`) → пошаговая форма (1 вопрос-блок на шаг) → PipelineButton [Далее] / [Отправить анкету].
**Элементы:** поля формы DEV-06 4.4 (ФИО, опыт лет — степпер, описание); skill-теги — сетка чипов мультивыбора (сантехника, электрика, кондиционеры/фреон, сварка, малярка, слаботочка…), выбранный — `accent` @ 12 % с текстом `accent`; фото лица — круглая плитка 96 px с иконкой `photo_camera` и подписью **«Сфотографироваться»** (только камера — это фото увидит клиент); зоны выезда — чипы районов Ташкента; транспорт — radio-чипы **«Свой авто с инструментом» / «Без авто»**; налоговый статус — **«Самозанятый» / «ГПХ»**; реферальный код — необязательное поле (предзаполняется из ссылки M-41).
**Наполнение:** заголовок `h1` **«Анкета мастера»**; подпись под skill-тегами `caption` **«Навыки подтверждаются экзаменом — отмечайте то, что умеете»**.
**Поведение + офлайн:** черновик сохраняется локально после каждого шага; валидация — по DEV-06 (граница `error` + текст под полем, без «прыжков»). ОФЛАЙН: заполнение полностью работает; отправка встаёт в очередь, баннер **«Анкета отправится при появлении сети»**. → M-03.

#### M-03. Онбординг: документы
**Композиция:** app bar «Документы» → список карточек документов → секция «Инструмент» по skill-тегам → PipelineButton [Отправить на проверку].
**Элементы:** карточка документа (`surface`, radiusCard): название (`body`), StatusBadge состояния — **«Не загружен»** (серый), **«На проверке»** (`accent`), **«Принят»** (`success`), **«Отклонён»** (`error`) с комментарием проверяющего `caption` цветом `error`; кнопка secondary **[Снять]** (камера). Документы: паспорт (разворот + прописка), статус самозанятого (справка Soliq) или данные ГПХ. Секция «Инструмент»: чек-лист ToolChecklist по каждому выбранному skill-тегу — строки позиций с чекбоксами + PhotoGrid фото набора.
**Наполнение:** подпись секции инструмента `caption` **«Без полного набора инструмента навык не активируется и заявки по нему не придут»**.
**Поведение + офлайн:** [Отправить на проверку] активна при полном комплекте; частичная загрузка сохраняется. ОФЛАЙН: съёмка и заполнение работают, файлы в очереди, отправка при сети. → M-05.

#### M-04. Онбординг: обучение + мини-экзамен
**Композиция:** список учебных модулей с прогрессом → PipelineButton [Начать экзамен] (активна при пройденных модулях **и после собеседования**) → экран экзамена → экран результата. Модули и тренажёр конвейера доступны **сразу после отправки анкеты** (ТЗ 17.17 п.9) — кандидат учится, пока идёт проверка.
**Элементы:** карточка модуля: иконка темы, название (`body`), прогресс `caption` («Просмотрено», «Осталось 10 мин»), стрелка. Темы: фото-фиксация, общение с клиентом, стандарты сервиса (бахилы, коврик, уборка), тренажёр конвейера. Экзамен: счётчик **«Вопрос 4 из 12»**, варианты — крупные карточки-кнопки (высота ≥ 56), [Ответить]. Результат: крупная цифра балла `h1`, **«Сдано»** (`success`) / **«Не сдано»** (`error`) + разбор ошибок по темам + secondary [Пересдать] (с остатком попыток).
**Наполнение:** экзамен до собеседования — кнопка неактивна с подписью `caption` **«Экзамен откроется после собеседования — пока изучайте модули»**.
**Поведение + офлайн:** скачанные модули читаются офлайн; экзамен только онлайн (анти-читинг) — баннер **«Экзамен доступен только при сети»**, кнопка неактивна. Сдан + договор → админ активирует → M-06 с бейджем испытательного.

#### M-05. Онбординг: статус кандидата
**Композиция:** статус-трекер воронки (вертикальный степпер: Анкета → Проверка → Обучение → Активация) → карточка «Следующий шаг» → secondary [Связаться с нами].
**Элементы:** шаг трекера: пройден — иконка `check_circle` `success`; текущий — точка `accent` + текст `body` semibold; будущий — `textSecondary`. Карточка следующего шага (`surface`): **«Ждём проверку документов — обычно 1–2 дня»** / **«Приходите на собеседование: {дата}, {адрес}»** / при доработке — комментарий и кнопка **[Исправить]** → M-02/M-03; secondary **[Учиться сейчас]** → M-04 (модули и тренажёр открыты с момента анкеты, ТЗ 17.17 п.9). Блок «Комплект новичка» (`caption`): форма, бейдж, стартовый набор.
**Наполнение:** отклонение — плашка `error` @ 12 %: **«Анкета отклонена: {причина}. Повторная подача — с {дата}»**.
**Поведение + офлайн:** статус обновляется пушем. ОФЛАЙН: последний закешированный статус + OfflineBanner read-only с меткой давности. Активация → M-06.

### 3.2. «Сегодня» и маршрут

#### M-06. «Сегодня» — лента дня (главный экран) ★
**Композиция (сверху вниз):** app bar: заголовок `h1` **«Сегодня»** + иконка синка `sync` с бейджем числа операций (тап → M-42) → OfflineBanner (при офлайне) → тумблер смены → плашка дежурства (если дежурный) → бейдж испытательного (если применимо) → сегменты «Сегодня / Завтра» → лента карточек заявок → нижняя навигация.
**Элементы:**
- **Тумблер смены** — крупная карточка `surface` во всю ширину: слева `body` semibold **«На линии»** / **«Не работаю»**, справа Switch (активный — `accent`); подпись `caption` **«На линии — офферы приходят автоматически»**; под тумблером — **строка дня** `caption` semibold: **«Сегодня: +420 000 сум · 3 заявки»** (tabular-nums; тап → M-34 с активным чипом «Сегодня»; ТЗ 17.17 п.10). Заблокирован по долгу: замок `lock`, текст `error` **«Сняты с линии: долг по наличным {сумма}»** + primary [Внести через Payme] → M-35 (в этом состоянии это единственная primary экрана).
- **Плашка дежурства** — `accent` @ 12 %: **«Ты дежурный сегодня. Минимум смены — 250 000 сум»** + **прогресс минималки**: полоса `accent` на `border` с подписью `caption` **«Набрано 140 000 из 250 000 сум»** (ТЗ 17.17 п.10); для дежурного с пустой лентой — EmptyState-текст **«Дежурство: аварийные и замены. С середины смены — срочные рядом с зоной»**.
- **Бейдж испытательного** — чип `warning`: **«Испытательный: 7 из 20 заявок»**.
- **Карточка заявки** — OrderCard: № + StatusBadge; категория и адрес; `caption`-строка «{окно} · {нормо-часы} ч · доля {сумма} сум»; метки-чипы: **«Сессия 2 из 5»**, **«Ведущий» / «Помощник»**, полоса `error` у аварийных; иконка `lock` 16 px на заявках ближайших 2 часов (лента заморожена для автоматики) — тултип **«Ближайшие 2 часа зафиксированы»**; SyncDot при несинхронизированном; изменённые диспетчером карточки — подсветка фоном `accent` @ 6 % до первого просмотра.
- Кнопка-иконка **[Карта]** (`map`) в строке сегментов → M-08.
**Наполнение (пустые состояния):** на линии — `EmptyState(bolt)`: **«Заявок пока нет»** + подпись **«Вы на линии — офферы придут пушем»**; не на линии — `EmptyState(bedtime)`: **«Вы не на линии»** + primary **[Выйти на линию]** (переключает тумблер).
**Поведение + офлайн:** pull-to-refresh; тап по карточке → M-11 (роль помощника → M-33). ОФЛАЙН: лента из локальной БД, OfflineBanner **«Офлайн — данные на {чч:мм}»** + вторая строка **«Маршрут мог измениться»**; тумблер показывает последнее известное положение с замком и подписью **«Смена переключается только при сети»** — авто-распределение живёт на сервере.
**Переходы:** M-07, M-08, M-09 (модально поверх), M-11, M-33, M-34, M-39, M-42.

#### M-07. Лента «Завтра»
**Композиция:** тот же каркас M-06, сегмент «Завтра» активен → плашка черновика → лента.
**Элементы:** плашка `border`-серая: **«Черновик — маршрут может измениться до утра»**; карточки заявок как в M-06, но тап → read-only превью (bottom-sheet: адрес, окно, состав работ, доля) с единственной кнопкой-веткой secondary-destructive **[Не могу поехать]** → M-32. Плашка дежурства завтра: **«Завтра вы дежурный ({смена}). Минимум {сумма} сум»**.
**Наполнение:** пустое состояние — `EmptyState(schedule)`: **«Лента на завтра собирается вечером»**, без кнопки.
**Поведение + офлайн:** лента появляется после вечерней сборки D−1 (push «Маршрут на завтра готов»); правки утром — пушем. ОФЛАЙН: кеш с меткой времени; [Не могу поехать] работает через очередь (см. M-32).

#### M-08. Маршрут дня на карте
**Композиция:** полноэкранная карта → нумерованные пины заявок → нижняя панель действий.
**Элементы:** пины с номерами по порядку ленты (фон `accent`, текст белый; аварийные — `error`); текущая геопозиция; линия маршрута; тап по пину → мини-карточка (bottom-sheet: №, адрес, окно, категория) с primary **[Открыть заявку]** → M-11; кнопка secondary **[Построить маршрут]** → внешний навигатор (Yandex/Google) к следующему адресу.
**Наполнение:** нет гео-разрешения — EmptyState `location_off`: **«Разрешите геолокацию, чтобы видеть маршрут»** + [Разрешить].
**Поведение + офлайн:** ОФЛАЙН: тайлы из кеша последнего региона; при пустом кеше — списочный fallback (лента M-06) с плашкой **«Карта недоступна без сети»**; точки — из локальной БД.

### 3.3. Офферы

#### M-09. Входящий оффер (60 секунд) ★
Полноэкранный модал поверх всего (heads-up push со звуком открывает его даже из фона). Таббар и app bar скрыты. Это витрина спец-паттерна П-1 (§4.1).
**Композиция (сверху вниз):** таймер-кольцо → бейджи → категория и состав работ → адрес и расстояние → окно времени → **доля мастера** (самый крупный текст экрана) → фото клиента при создании заявки (если есть) → две кнопки во всю ширину.
**Элементы:**
- **Таймер-кольцо** 96 px по центру верхней трети: цифры секунд `h1` внутри кольца; кольцо — `accent`, последние 10 сек — `error`; каждую секунду тик прогресса, на 50-й секунде — вибрация-предупреждение.
- **Бейджи** (чипы в строку, statusColor): **«Аварийная»** (`error`), **«Срочно +30 %»** (`accent`, подпись «доля выше»), **«Ночная»**, **«Парная: ведущий»**, **«Этапная: 5 сессий»**, **«Нужно оборудование: {название}»**.
- Категория — `h2`; состав работ — список `body`; адрес без подъезда/квартиры до принятия + **«{N} км от вас»**; окно `body` semibold.
- **Доля** — строка «Ваша доля» `caption` + сумма 32 px semibold `text` (по настройке админа — полная цена; для B2C-вилки подпись `caption` **«Финальная доля — от подтверждённой на месте суммы»**).
- Кнопки: **[Принять]** — PipelineButton высотой 64; под ней **[Отклонить]** — secondary во всю ширину высотой 56, отступ `s12` между ними (защита от промаха).
**Наполнение:** отказ обязан иметь причину — bottom-sheet с чипами: **«Занят» / «Далеко» / «Нет материала» / «Другое»** (+ поле комментария при «Другое»), кнопка [Подтвердить отказ]. Подпись под кнопками `caption`: **«Молчание = оффер уйдёт другому мастеру»**.
**Поведение + офлайн:** [Принять] → заявка в ленту, экран закрывается с тостом **«Заявка в ленте на {время}»**; таймер истёк — экран сам закрывается; оффер отозван (принял другой/отменён) — заглушка **«Заявка уже недоступна»** + [Закрыть]. **Режим вождения** (ТЗ 17.17 п.8): при детекте вождения оффер озвучивается TTS — «{категория}, {район}, доля {сумма}»; ответ — кнопкой гарнитуры (одно нажатие — принять, двойное — отклонить) либо авто-отложение оффера на 3 мин; экранная плашка `caption` **«Режим вождения — оффер озвучен, можно ответить гарнитурой»**; молчание за рулём **не учитывается** в дисциплине офферов. ОФЛАЙН: офферы не приходят вовсе; если сеть пропала при открытом оффере — [Принять] становится disabled с подписью **«Нет сети»**, таймер продолжает идти; после восстановления сети — тост-сводка **«Пока вы были офлайн: {N} офферов»** (информационно, без санкций). **Батарея < 10 %** — режим деградации: live-карта и расчёт ETA отключаются (плашка `warning` **«Экономия батареи: карта и ETA отключены»**), камера и офлайн-очередь работают. Аварийные офферы — кольцо и акценты `error` (единственное исключение «красной» кнопки принятия нет — [Принять] остаётся `accent`).
**Крайние случаи (UI):** два отказа подряд без причины понижают приоритет — после второго отказа тост **«Частые отказы снижают приоритет офферов»**.

#### M-10. Экспресс-оффер замены (120 секунд, бродкаст)
**Композиция:** как M-09 со следующими отличиями.
**Элементы:** таймер на 120 сек; сверху плашка `error` @ 12 %: **«Срочная замена — клиент ждёт с {чч:мм}»**; кнопка отказа заменена на secondary **[Пропустить]** — без причины и без штрафа (бродкаст ≠ персональный оффер), подпись `caption` **«Заявку получает первый принявший»**.
**Наполнение:** гонка проиграна — заглушка **«Заявку забрал другой мастер»** + [Закрыть]. Вариант мини-оффера «помощник» (`?type=helper`): заголовок **«Нужен помощник»**, описание **«Подсобить ~2 ч, фикс {сумма} сум + дорога»**, тот же механизм.
**Поведение + офлайн:** [Принять] → M-11 с флагом замены (плашка `accent` @ 12 % «Вы заменяете мастера — клиент уведомлён»); клиенту авто-push. ОФЛАЙН: не приходит.

### 3.4. Конвейер: карточка и шаги

#### M-11. Карточка заявки — рабочий конвейер ★
Центральный экран выполнения. Всегда отвечает на вопрос «что дальше» ровно одной активной кнопкой.
**Композиция (сверху вниз):** app bar: «№ Z-2026-…» + StatusBadge + меню «⋮» → OfflineBanner/SyncDot → ModerationPlate / PausePlate / **плашка-таймлайн доп-согласования** (если есть) → блок клиента и адреса → **блок «В пути»** (после «Выехал») → блок «Доступ на объект» (B2B) → состав работ и деньги → блок «Помощник» (если привлечён) → **степпер конвейера** → PipelineButton текущего шага.
**Элементы:**
- Блок адреса: адрес `body` semibold, строка `caption` «подъезд {n} · этаж {n} · домофон {код} · лифт: {есть/нет}»; **состояние «детали не указаны»** (клиент не заполнил C-50): вместо строки деталей — жёлтая пометка `warning` **«Детали не указаны — уточните у клиента/диспетчера»**, исчезает при заполнении клиентом или фиксации деталей диспетчером; имя клиента (только имя — минимум данных, ТЗ 17.5); кнопки-иконки в ряд: **[Позвонить клиенту]** (`call`; активна со статуса «Назначена» до «Закрыта», номер не отображается и не копируется), **[Позвонить диспетчеру]** (`support_agent`), **[Маршрут]** (`near_me`).
- Тип заявки — чипы: B2C / B2B / **«Гарантийная»** (+ ссылка «Исходная заявка Z-…», плашка **«Смета клиенту: 0 сум»**) / «Из осмотра» / «Осмотр».
- **Блок «Доступ на объект» (B2B)** — карточка `surface`: график доступа точки (дни/часы), контакт ТСЖ/охраны кнопкой, ограничения («пропускной режим», «шлагбаум», «техническое окно»); чек-лист общих зон: `caption` `success` **«Доступ подтверждён на {дата, время}»**.
- Состав работ: строки «название — qty × цена», итог и отдельно **«Ваша доля: {сумма} сум»** semibold; примечания диспетчера — плашка `border`.
- **Степпер**: вертикальный список шагов «Выехал → Приступить (фото „до“) → Работа / Смета → Материалы → Техника → Фото „после“ → Приёмка → Оплата». Пройденный — `check_circle` `success`; текущий — точка `accent` + строка semibold; будущий — `textSecondary` c иконкой `lock` и пояснением по тапу (тост: **«Сначала: {название текущего шага}»**). Для осмотра степпер заменён: «Выехал → Чек-лист осмотра → Представитель точки → Завершение».
- **Блок «В пути»** (объединён с M-12, v2.25 — отдельного экрана нет): после [Выехал] на карточке появляются ETA по карте `h2` **«В пути ~25 мин»**, строка `caption` `success` **«Клиенту отправлен ETA и ваша карточка»**, чипы во всю ширину высотой 56 **[Задерживаюсь +30 мин]** / **[Задерживаюсь +60 мин]** (диалог **«Сдвинуть план на +30 мин? Клиент получит новое время»**, после — тост **«План сдвинут. Очередь пересчитана»**); PipelineButton — **[На месте — приступить]**, тап сразу открывает камеру M-13 (без промежуточного экрана); при гео-приближении ±300 м к адресу — авто-подсказка (плашка `accent` @ 12 %) **«Вы на месте?»** с той же кнопкой.
- **Плашка-таймлайн доп-согласования** (объединён с M-18, v2.25 — отдельного экрана нет): после отправки доп-сметы — карточка `surface`: баннер `success` @ 12 % **«Можно выполнять согласованную часть»** + вертикальный таймлайн **«Отправлено {чч:мм}» → «Повтор через 30 мин» → «Звонок диспетчера через 2 ч»** (пройденные пункты `success`); результат пушем заменяет таймлайн: **«Утверждено: {вариант}»** (`success`) / **«Отклонено»** (`error`) + при вынужденной — кнопка **[Перейти к консервации]** → M-19; молчание не отменяет заявку — `caption` **«Без ответа: завершите согласованную часть — несогласованные позиции будут сняты»**; ОФЛАЙН: **«Результат появится при сети»**.
- **PipelineButton** текущего шага: **[Выехал]** / **[На месте — приступить]** / **[К смете]** / **[Завершить — фото „после“]** / **[Приёмка]** / **[Получить оплату]**.
- Блок «Помощник»: **«Помощник: {имя}»** + статус («выехал / на месте / работает») + кнопка secondary **[Подтвердить: помощь завершена]** (активна после отметки помощника «На месте»; без этого подтверждения приёмка M-28 заблокирована).
- Меню «⋮»: «Не могу поехать» (до «Выехал», → M-32) · «Клиент недоступен» (→ M-30) · «Нет доступа: третья сторона» (→ M-14) · «Прервать: небезопасно» (→ M-31) · «Нужен помощник» (→ M-26) · «Рекомендовать» (→ M-20) · «Продолжение завтра» (многодневная простая работа: обязательное фото «в процессе» + консервация рабочего места; завтра конвейер продолжается без повторного фото «до»).
**Наполнение:** заблокированная переназначенная заявка — полноэкранная заглушка **«Заявка передана другому мастеру»** + [В ленту]. Возврат с модерации — ModerationPlate: **«Возвращено диспетчером: {комментарий}»** + [Исправить] (ведёт к нужному шагу). Паузы — PausePlate с датой возобновления. Режимный объект — плашка `border`: **«Фото запрещено режимом объекта — приёмка кодом и подписью»**, шаги фото скрыты из степпера. Осмотр: чек-лист по шаблону типа объекта, дефекты — карточки «фото (обязательно) + категория + описание»; перед завершением — обязательный шаг **«Представитель точки»**: выбор сотрудника из списка или ФИО+должность, подтверждение кодом (механика M-28) или подписью пальцем; кнопка secondary **[Представитель отсутствовал]** → обязательное фото точки доступа, `caption` **«Отчёт будет помечен „без представителя“ и уйдёт на проверку»**.
**Поведение + офлайн:** весь конвейер работает офлайн: каждое действие — запись очереди с UUID; OfflineBanner «Офлайн — действия сохранятся…», SyncDot на карточке; гео-проверка ±300 м при «Приступить» — мягкая (несовпадение → флаг диспетчеру, ничего не блокируется и мастеру не показывается).
**Переходы:** M-12…M-32 по шагам и веткам.

#### M-12. В пути: «Выехал» + «Задерживаюсь +30/60» (объединён, v2.25)
Отдельного экрана нет — весь функционал живёт **блоком «В пути» на карточке M-11** (см. M-11): [Выехал], ETA `h2` **«В пути ~25 мин»**, строка `caption` `success` **«Клиенту отправлен ETA и ваша карточка»**, чипы **[Задерживаюсь +30 мин]** / **[+60 мин]** (доступны с момента «Выехал» и весь период работы; диалог подтверждения + тост **«План сдвинут. Очередь пересчитана»**), **[На месте — приступить]** → сразу камера M-13; гео ±300 м — авто-подсказка **«Вы на месте?»**. ID сохранён для ссылок и деп-линков.
**Поведение + офлайн:** «Задерживаюсь» каскадно пересчитывает очередь; если сдвиг выбивает следующую заявку за окно — алерт диспетчеру, мастеру ничего дополнительно не показывается. ОФЛАЙН: «Выехал» и «Задерживаюсь» пишутся в очередь с двойной меткой времени; предупреждение `caption` `warning` **«Нет сети: клиент увидит выезд с задержкой — при возможности позвоните»**.

#### M-13. Фото «до» (обязательный экран камеры) ★
Гейт перехода «В работе»: минимум 1 фото. Витрина паттерна П-2 (§4.2).
**Композиция:** полноэкранный видоискатель камеры → верхняя строка (счётчик + закрыть) → лента превью снятого → нижняя панель: кнопка спуска + [Готово].
**Элементы:**
- Видоискатель без доступа к галерее (кнопки галереи нет физически).
- Счётчик `caption` на подложке `text` @ 60 %: **«Фото: 2 из 10»**.
- Кнопка спуска — круг 72 px по центру снизу; лента превью-миниатюр 56 px над панелью, на каждой — крестик удаления (до отправки).
- **[Готово — приступить к работе]** — PipelineButton, активна при ≥ 1 фото; неактивная — с подписью `caption` **«Снимите хотя бы одно фото „до“»**.
- Текстовая ссылка внизу: **[Нет доступа — третья сторона]** → M-14.
**Наполнение:** каждому фото — клиентское время + монотонные часы, гео (или флаг «без гео»), клиентский UUID; в UI это не показывается, кроме бейджа `caption` **«Без гео»** на превью, если геолокация недоступна (подвал) — конвейер не блокируется.
**Поведение + офлайн:** нет разрешения камеры — блокирующий полноэкран: **«Без камеры работа невозможна»** + [Разрешить доступ]. [Готово] → статус «В работе», фиксируется отметка «Приступить» (по ней считается пунктуальность рейтинга). ОФЛАЙН: полный функционал; фото в локальной очереди (сжатие до ~1600 px / 500 КБ, EXIF-очистка), серверный таймштамп при синке, запись с флагом «зафиксировано офлайн».
**Переходы:** M-15 или продолжение работ на M-11. Повторное фото «до» после паузы «Ожидание материалов» не требуется.

#### M-14. «Нет доступа (третья сторона)»

#### M-15. Уточнение сметы ★
Превращение первичной оценки в точную смету на месте. Цены — строго из релиза заявки (`price_list_release_id`), не из текущего прайса. Целевая метрика (ТЗ 17.17 п.5): смета из 3 позиций — **≤ 5 тапов без клавиатуры**.
**Композиция (сверху вниз):** app bar «Смета» + меню «⋮» + бейдж релиза → список позиций → строка [+ Позиция] → калькулятор итога (закреплён снизу над кнопкой) → PipelineButton [Отправить на подтверждение].
**Элементы:**
- Позиция — строка `surface`: название `body`, «qty × цена» `caption`, сумма справа (tabular-nums); свайп/крестик — удаление, тап — правка (только своих позиций и только до утверждения); позиции первичной оценки помечены `caption` «из оценки».
- **[+ Позиция]** → полноэкранный поиск по прайсу: **над строкой поиска — три блока-ускорителя, работающие без клавиатуры** (ТЗ 17.17 п.5): **«Частые по категории заявки»** (топ-10 позиций релиза по статистике категории, чипы-карточки в один тап), **«Мои недавние»** (последние позиции мастера), **«Наборы»** (пресеты-бандлы: «Замена смесителя» = 3 позиции одним тапом; справочник наборов — админка); ниже — поле поиска + результаты из локального кеша релиза заявки; выбор → степпер qty «− 1 +», ед. изм. из позиции.
- Меню «⋮»: **«Скопировать смету из заявки той же категории»** — список прошлых заявок мастера этой категории, тап копирует позиции в текущую смету (по ценам релиза текущей заявки).
- **Калькулятор итога** — карточка `surface` с верхней границей: строки «Работы», «Материалы», «Наценка: {аварийная/ночная/срочная}» (применяется одна наибольшая), позиция **«Минимальный заказ»** (видна, пока итог ниже мин. чека), строка **«Итого для клиента»** `h2` и **«Ваша доля: {сумма} сум»** `body` semibold `accent`; при утверждённой смете — строка «Утверждено: {сумма}» и дельта цветом (`error` при превышении).
- Чипы типа доп-позиций при добавлении сверх утверждённого: **«Вынужденная — без неё не завершить»** → M-17 / **«Рекомендация»** → M-20; этапная позиция → переход к плану сессий M-25.
**Наполнение:** PipelineButton **[Отправить на подтверждение]**; подпись `caption`: B2C — **«Клиент подтвердит со своего телефона»** (анти-подделка согласий; телефонный клиент — фиксирует диспетчер); B2B — **«Итог выше утверждённого — уйдёт на доп-согласование»** (в пределах лимита организации работа продолжается без согласования). Отказ клиента после диагностики — итог сворачивается до «Выезд + диагностика»: плашка **«Клиент отказался от работ — к оплате только диагностика»**.
**Поведение + офлайн:** итог пересчитывается живо при каждом изменении; смета валидируется сервером против релиза заявки — позиция «не из релиза» отклоняется при синке (придёт как конфликт в M-42). Смета выше утверждённой не даёт пройти гейт завершения (M-27). ОФЛАЙН: составление полностью работает на кеше прайса (ускорители — тоже из кеша); отправка — в очередь, плашка **«Подтверждение уйдёт при появлении сети. Работать по неподтверждённой смете нельзя»** (таймер согласования стартует с серверной доставки); под плашкой — secondary **[Клиент подтвердит здесь — подписью]** (офлайн-подтверждение сметы, ТЗ 17.17 п.7): экран передаётся клиенту — итог сметы крупно + канвас подписи `SignaturePad` (П-3) + обязательное фото (камера, П-2); пакет в очередь с флагом **«согласовано офлайн»**, подпись `caption` **«Смета уйдёт на выборочную проверку диспетчером»** (зеркало «принято без кода»).
**Переходы:** M-16 (запчасть дороже порога), M-17, M-18 (плашка-таймлайн на M-11), M-20, M-25.

#### M-17. Вынужденная доп-работа ★

**Поведение + офлайн:** полностью работает офлайн. → M-27 (фото «после» по сделанной части) → приёмка/оплата.

**Поведение + офлайн:** полностью работает офлайн. → M-27.

#### M-25. Этапные сессии
Работы с технологическими перерывами (стяжка: «не раньше 24 ч, не позже 7 дней»). Не путать с простой многодневной работой — та закрывается на M-11 паузой «Продолжение завтра» без плана сессий.
**Композиция:** индикатор «Сессия i из N» → план этапов → блок брони слотов → PipelineButton.
**Элементы:** заголовок-чип **«Сессия 2 из 5»**; вертикальный план: этап, нормо-часы, окно паузы после («24 ч – 7 дней»), статус каждой сессии — StatusBadge «Забронирована {дата}» / «Выполнена» (`success`); блок брони (сценарий «работа выяснилась на месте»): система предлагает клиенту слоты следующих сессий из реальной ленты — статус **«Клиент подтверждает слоты вместе со сметой…»**; PipelineButton **[Этап {N} завершён]** → обязательное фото «в процессе» (камера, П-2) + отметка.
**Наполнение:** **инвариант брони** — при неподтверждённых слотах кнопка старта этапа 1 заблокирована с пояснением: **«Начать нельзя: не подтверждены слоты следующих этапов»** (`caption`: «не начинай красить, если некому приехать домазать»); нет слотов — карточка выбора: **«Перенести всю работу» / «Сверхурочный слот (с доплатой, по вашему согласию)» / «Передать этапы другому мастеру»** (последнее — параметр, по умолчанию выкл.). Завершение этапа → тост **«Этап закрыт. Перерыв до {дата} — заявка не занимает вашу ленту»**.
**Поведение + офлайн:** пауза «Технологический перерыв» — мастер свободен. ОФЛАЙН: завершение этапа с фото — офлайн; бронирование слотов требует сети (живая лента) — плашка **«Подтверждение слотов — при сети»**. Финальная сессия → M-27 → M-28 → M-29 (оплата B2C — на последней сессии; промежуточные — единственное исключение из «не уходить без оплаты»).

#### M-26. «Нужен помощник»
Вызов второго человека, когда вскрылось, что одному физически нельзя. Механика мини-оффера — как M-10.
**Композиция:** оценка времени → фикс → PipelineButton [Отправить мини-оффер] → статус поиска → результат.
**Элементы:** чипы оценки времени помощи: **«~1 ч» / «~2 ч» / «~3 ч» / «Полсмены»**; строка фикса помощника «{сумма} сум + дорога» (параметр, read-only); PipelineButton **[Отправить мини-оффер]**; статус поиска — спиннер-точки + **«Ищем помощника рядом…»**; результат — карточка **«Едет {имя}, будет через ~{N} мин»** + [Позвонить].
**Наполнение:** никого нет — карточка: **«Свободных помощников нет. Работа переносится на ближайший парный слот — перенос согласует диспетчер»** + [Позвонить диспетчеру]. Подпись `caption` **«Фикс помощника оплачивает не клиент»** (кто именно — решает диспетчер по правилам ТЗ 17.3).
**Поведение + офлайн:** ОФЛАЙН: недоступно (бродкаст требует сервера) — экран-заглушка `wifi_off`: **«Нужна сеть. Позвоните диспетчеру»** + [Позвонить диспетчеру]. → M-11 (блок «Помощник: {имя}»).

#### M-27. Фото «после» ★
Гейт «Выполнена»: минимум 1 фото «после» + чек-гейты. Контроль дублируется на API.
**Композиция:** список блокеров (если есть) → камера с подсказкой ракурса → превью → итоговый экран.
**Элементы:**
- **Чек-гейты перед камерой** — если не закрыты, вместо камеры список блокеров (карточки со ссылками): **«Материалы без чеков: 2»** → M-21; **«Итог выше утверждённой сметы»** → M-15/M-18 (плашка на M-11); **«Техника не зафиксирована»** → M-24 — блокер показывается **только для категорий с оборудованием**; для остальных гейт закрывается чипом «Техники нет» (ТЗ 17.17 п.6); **«Помощь не подтверждена»** → M-11. Каждая строка — иконка `error` + стрелка.
- Камера как M-13 (П-2), плюс **миниатюра фото «до»** в углу видоискателя с подписью `caption` **«Тот же ракурс, что „до“»** — тап разворачивает для сравнения.
- **[Готово]** → сразу M-28 (объединён, v2.25): отдельного итогового под-экрана нет — итог работ/материалов и **«Ваша доля: {сумма} сум»** показываются на экране приёмки M-28 (раскрывающийся блок).
**Наполнение:** пустой счётчик — кнопка неактивна с подписью **«Снимите хотя бы одно фото „после“»**.
**Поведение + офлайн:** полностью работает офлайн. Режимный объект — экран пропущен, приёмка кодом + подписью (M-28); осмотр — вместо фото «после» заполненный чек-лист + шаг «Представитель точки» (M-11). → M-28 (B2C с онлайн-оплатой в приложении — сразу M-29, экран кода пропускается, см. M-28).

#### M-28. Приёмка ★
Единый механизм для B2C и B2B: одноразовый 4-значный код подтверждения, который клиент (или сотрудник точки) получает пушем/SMS на **свой** телефон и называет мастеру.
**Композиция (сверху вниз):** итог работ и материалов (свёрнутый, раскрывается; сюда сведён итоговый под-экран из M-27 — объединён, v2.25) → поле кода → блок подписи (B2C) → fallback-ссылка → PipelineButton. **Ветка «онлайн-оплата» (B2C):** при выборе клиентом онлайн-оплаты в приложении экран кода пропускается — флоу M-27 → M-29, приёмка фиксируется вебхуком успешного платежа (ТЗ 17.17 п.3); на M-29 показывается плашка `success` **«Клиент оплатил онлайн — приёмка подтверждена платежом»**. Экран кода M-28 показывается только для наличных, телефонного канала и B2B (сотрудник точки).
**Элементы:**
- Заголовок `h2` **«Код подтверждения»**, подпись `caption` **«Клиент получил код на свой телефон — попросите назвать»** (B2B: «Сотрудник точки получил код…»).
- 4 крупные ячейки ввода кода (высота 64, `h1`, tabular-nums), цифровая клавиатура сразу открыта.
- **Подпись пальцем (B2C, опционально)** — secondary **[Добавить подпись клиента]** → полноэкранный канвас (паттерн П-3, §4.3). Не замена кода — усиление.
- Текстовая ссылка внизу: **[Клиент не может назвать код]** → fallback-флоу **«Принято без кода»**: обязательное фото результата с общим планом помещения (камера, П-2) + подпись `caption` **«Уйдёт диспетчеру на ручное подтверждение»** + PipelineButton **[Отправить без кода]**.
- **Режимный объект:** тот же код + обязательная подпись представителя на экране мастера; в акте отметка «фотофиксация запрещена режимом объекта».
- PipelineButton **[Подтвердить приёмку]** (активна при 4 введённых цифрах).
**Наполнение:** неверный код — тряска ячеек + текст `error` **«Неверный код. Осталось попыток: 2»**; после 3 попыток — предложение fallback: **«Код не подходит. Принять без кода?»**.
**Поведение + офлайн:** B2C → M-29 Оплата; B2B → статус «Выполнена» → M-06 (списание с абонентки/СФ без участия мастера — тост **«Работа сдана. Оплата — по договору организации»**). ОФЛАЙН: ввод кода и «Принято без кода» работают — запись в очередь; локальной валидации кода нет — код проверится при синке с пометкой «принят офлайн», конфликт уйдёт флагом диспетчеру; подпись — в очередь. Возврат с модерации возможен и после приёмки — заявка вернётся «В работе» с ModerationPlate; принятая оплата при этом не отменяется.

#### M-29. Оплата (B2C)
«Уйти без оплаты — исключение, а не норма».
**Композиция:** сумма к оплате `h1` по центру → три способа оплаты → статус платежа → ссылка «не могу получить».
**Элементы:** сумма **«К оплате: 1 250 000 сум»**; способы (карточки-кнопки высотой 64): **[Показать QR]** → QR-экран (П-4; Payme/Click, Uzum — ф.2); **[Отправить ссылку клиенту]** → push клиенту, статус **«Ждём оплату по ссылке…»**; **[Принял наличные 1 250 000 сум]** → диалог подтверждения: **«Вся сумма станет вашим долгом перед компанией. Продолжить?»** [Принял]/[Отмена] → индикатор долга обновляется. Статус платежа в реальном времени: спиннер → плашка `success` **«Оплата получена»**. Текстовая ссылка **[Не могу получить оплату]** → звонок диспетчеру (уход без оплаты — только с его санкции, заявка в «Ожидает оплаты»).
**Наполнение:** после оплаты и оценки у клиента появляется экран чаевых — мастеру придёт пуш **«Клиент оставил чаевые {сумма}»** (целиком мастеру, мимо долей, отдельной проводкой). Предупреждение при долге у лимита: плашка `warning` **«Долг по наличным {сумма} из 2 000 000. Внесите через Payme»**; превышение → автоснятие с линии (см. M-06) → M-35.
**Поведение + офлайн:** ОФЛАЙН: онлайн-оплата недоступна — карточки QR/ссылки задизейблены с подписью **«Нужна сеть»**; доступно **[Принял наличные]** (в очередь) и памятка `caption` **«QR у клиента может сработать по его сети — попробуйте показать»**. → «Выполнена» → M-06; кошелёк обновится после закрытия.

#### M-30. «Клиент недоступен»
**Композиция:** фото двери → время прибытия (авто) → PipelineButton [Отправить] → экран ожидания решения.
**Элементы:** кнопка камеры **[Снять фото двери]** (обязательно, П-2; гео пишется автоматически); строка «Прибытие: {чч:мм}» (read-only); secondary [Позвонить клиенту] (кнопкой, номер скрыт); PipelineButton **[Отправить]**.
**Наполнение:** после отправки — экран ожидания: **«Диспетчер прозванивает клиента — до 15 минут. Оставайтесь рядом»**; исходы пушем: **«Клиент откроет через 5 мин»** → продолжение → M-13; **«Отменено: ложный вызов. Вам начислена компенсация выезда»** → M-06.
**Поведение + офлайн:** ОФЛАЙН: фиксация в очередь, но прозвон не запустится до синка — настойчивая плашка `warning` **«Нет сети — позвоните диспетчеру голосом»** + [Позвонить диспетчеру].

#### M-31. «Прервать: небезопасно»
Защита мастера. Никаких блокировок конвейером — уйти можно всегда и сразу.
**Композиция:** короткое пояснение → опциональное фото/комментарий → PipelineButton.
**Элементы:** текст `body`: **«Если ситуация угрожает вам — уходите. Разберётся диспетчер»**; кнопка камеры [Снять фото] (опционально); поле комментария (опционально); PipelineButton (destructive-заливка `error`, единственное такое место в приложении) **[Прервать и уйти]** — работает без заполнения полей.
**Наполнение:** после — тост **«Отправлено диспетчеру. Санкций за прерывание нет»**.
**Поведение + офлайн:** ОФЛАЙН: работает полностью (безопасность не зависит от сети), синк потом. Материалы уходят диспетчеру: отмена без штрафа; подтверждённый неадекват → клиент в чёрный список. → M-06.

#### M-32. «Не могу поехать»
Честный ранний отказ — мягче тихого невыхода.
**Композиция:** чипы причины → комментарий → PipelineButton → предупреждение о последствиях.
**Элементы:** чипы причин (обязательно): **«Заболел» / «Форс-мажор» / «Не успеваю» / «Другое»** (+ комментарий при «Другое»); PipelineButton (destructive) **[Подтвердить отказ]**.
**Наполнение:** пояснение `caption`: **«Замена запустится немедленно. Уважительная причина (подтвердит диспетчер) — без санкций. Отказ без причины бьёт по рейтингу; 2-й невыход за 90 дней — снятие с линии»**. После — тост **«Заявка снята с вас. Спасибо, что предупредили заранее»**.
**Поведение + офлайн:** отказ должен дойти быстро: ОФЛАЙН — в очередь + крупная плашка `warning` **«Нет сети! Отказ отправится позже — позвоните диспетчеру сейчас»** + [Позвонить диспетчеру]. Заявка исчезает из ленты. → M-06.

### 3.5. Помощник

#### M-33. Карточка помощника (упрощённая)
Без конвейера, смет и фото-цикла — всё это на ведущем.
**Композиция:** адрес и время → описание задачи → фикс → блок ведущего → PipelineButton по статусу.
**Элементы:** адрес + окно `body` semibold; описание (`body`): «Поднять бойлер на 4 этаж, лифта нет»; строка **«Фикс за сессию: {сумма} сум»** (или меньшая доля — параметр); блок ведущего: **«Ведущий: {имя}»** + [Позвонить ведущему] (кнопкой); PipelineButton по шагам: **[Выехал]** → **[На месте]**; после «На месте» кнопка заменяется статусной плашкой **«Ожидает подтверждения ведущего»** (отметку «Помощь завершена» ставит только ведущий на M-11); меню «⋮»: [Не могу поехать] → M-32 (санкции невыхода обычные).
**Наполнение:** завершение — пуш **«Ведущий подтвердил помощь. Фикс придёт в кошелёк после закрытия заявки»**.
**Поведение + офлайн:** отметки — в очередь. Помощь на рейтинг не влияет (кроме невыхода). → M-06.

### 3.6. Деньги

#### M-34. Кошелёк ★
Полная прозрачность: мастер видит каждую копейку с расшифровкой — это удержание мастеров.
**Композиция (сверху вниз):** app bar «Кошелёк» + селектор периода → карточка итога «К выплате» → индикатор наличного долга → секции начислений/удержаний → история выплат.
**Элементы:**
- **Селектор периода** — чипы **«Сегодня»** / «Эта неделя / Прошлая / Месяц» (период ведомости — параметр). Чип **«Сегодня»** (ТЗ 17.17 п.10) — дневная лента проводок: каждая заявка/проводка дня строкой с суммой, итог дня сверху **«Сегодня: +420 000 сум · 3 заявки»**; сюда ведёт тап по строке дня на M-06.
- **Карточка итога** (`surface`, radiusCard): формула строками с табличными цифрами: **«Начисления + {сумма}» → «Удержания − {сумма}» → «Наличные у вас − {сумма}» → разделитель → «К выплате: {сумма} сум»** `h1`; отрицательный итог — `error` и подпись **«К внесению через Payme»** + primary [Внести] → M-35.
- **Индикатор долга** — прогресс-бар к лимиту: «Наличные: 1 400 000 из 2 000 000 сум»; ≥ 80 % — `warning`, при лимите — `error` + **«Внесите, иначе снятие с линии»**.
- **Секции-аккордеоны, каждая строка раскрывается до заявки/проводки:**
 — «Доля за работы» (по заявкам: «Z-2026-0417 · 380 000 сум»);
 — «Возмещения материалов» с подписью `caption` **«Возмещения — не доход, налогом не облагаются»**;
 — «Расходники сумки» (возмещение + микромаржа);
 — «Минимум дежурства» — отдельной строкой за смену;
 — **«Возмещение ГСМ»** (только со своим авто): «{N} км × {ставка} = {сумма}» с расшифровкой по сменам (переезды между заявками ленты; путь дом↔заявка не считается);
 — «Чаевые», «Реферальные бонусы»;
 — «Удержания» — каждая с причиной: «Гарантийная переделка по вине — 50 %», «Регресс ущерба, часть 2 из 4 (≤ 30 % выплаты)», «Невыход с ущербом»; на строке удержания — кнопка secondary **[Апелляция]** → тикет диспетчеру;
 — для ГПХ — строки «НДФЛ», «Соцналог»; самозанятые видят брутто.
- **История выплат** — список ведомостей: дата, сумма, StatusBadge («Отправлена» `success`).
**Наполнение:** пустое состояние (новый мастер) — `EmptyState(account_balance_wallet)`: **«Здесь появится каждая заработанная сумма — с расшифровкой до заявки»**. Спец-статусы: строка `error` **«Доля по Z-… заблокирована спором до резолюции»**; офбординг — плашка **«Выплаты заморожены: идёт сверка»**.
**Поведение + офлайн:** начисления считаются от релиза каждой заявки (старые заявки — старые цены). ОФЛАЙН: кеш с OfflineBanner «данные на {чч:мм}»; наличные, принятые офлайн, видны сразу со значком SyncDot. → M-35.

#### M-35. Внесение наличных через Payme
**Композиция:** текущий долг `h1` → поле суммы с пресетами → PipelineButton → статус зачисления.
**Элементы:** «Ваш долг: {сумма} сум»; поле суммы (по умолчанию — до нуля) + чипы-пресеты **«Весь долг» / «До безопасного уровня»**; PipelineButton **[Оплатить через Payme]** → deep-link в приложение/веб Payme; статус: «Платёж в обработке…» → плашка `success` **«Зачислено. {Вы снова на линии}»** (вторая фраза — если снятие было по лимиту: возврат на линию автоматический).
**Наполнение:** платёж не прошёл — плашка `error` **«Платёж не прошёл — попробуйте ещё раз»** + [Повторить].
**Поведение + офлайн:** зачисление — по вебхуку провайдера, идемпотентно. ОФЛАЙН: недоступно — заглушка `wifi_off` **«Внесение работает только при сети»**. → M-34; → M-06.

### 3.7. Профиль, склад, оборудование

#### M-36. Сумка / MasterStock (фаза 2)
**Композиция:** список остатков → индикаторы нормативов → [Пополнить чеком] → история.
**Элементы:** строка позиции: название, остаток «шт/м», себестоимость; чип `warning` **«Ниже норматива»** при остатке < min по skill-тегу; primary **[Пополнить чеком]** — фото чека (камера) + позиции → зачисление по себестоимости, мастеру возмещение; история пополнений списком. Списание в заявку (из M-21) уменьшает остаток автоматически.
**Наполнение:** пустое состояние — **«Сумка пуста. Пополните чеком — расходники в заявках будут списываться отсюда»**. В MVP экрана нет (расходники добавляются из каталога без учёта остатков).
**Поведение + офлайн:** остатки из кеша; пополнения — в очередь. → M-21.

#### M-37. Оборудование компании («Моё оборудование»)
**Композиция:** список выданных единиц → карточка единицы → действия актов.
**Элементы:** карточка единицы (`surface`): фото состояния, название и категория, инвентарный № `caption`, дата выдачи, StatusBadge: **«Выдано вам»** (`accent`) / **«В ремонте»** (`warning`); тап → карточка с архивом актов (PDF); кнопки secondary **[Принять выдачу]** / **[Оформить возврат]** → M-38; плашка-пояснение `border`: **«Заявки, требующие оборудование, приходят только мастерам с выданным оборудованием и транспортом»**.
**Наполнение:** пустое состояние — `EmptyState(build)`: **«Оборудование не выдано»**. Статус «в ремонте» — подпись **«Зависящие заявки временно не приходят»**. Утеря/поломка по вине — отражается удержанием в кошельке (M-34).
**Поведение + офлайн:** кеш; акты — офлайн через очередь (кроме подтверждения кодом, см. M-38).

#### M-38. Акт выдачи/возврата оборудования
Материальная ответственность прямо в приложении. Пошаговый мастер-флоу.
**Композиция:** шаг 1: фото со всех сторон → шаг 2: сверка комплектности → шаг 3: подтверждение кодом.
**Элементы:** шаг 1 — PhotoGrid с обязательными слотами ракурсов (мин. N, камера, П-2), счётчик **«Ракурс 2 из 4»**; шаг 2 — чек-лист комплектности (чекбоксы позиций); шаг 3 — ввод одноразового кода (ячейки как M-28) — аналог подписи; PipelineButton **[Подтвердить кодом]**; итог — **«Акт оформлен. PDF в архиве»**.
**Наполнение:** расхождение состояния при возврате — обязательное поле комментария + подпись **«Будет разбор с кладовщиком»**.
**Поведение + офлайн:** съёмка и заполнение — офлайн; подтверждение кодом — только при сети (код одноразовый серверный) — плашка **«Код подтверждения требует сети»**. → M-37.

#### M-39. Профиль
**Композиция (сверху вниз):** шапка: фото, имя, грейд-чип → карточка рейтинга → испытательный/апсейл-статистика → skill-теги → зоны и транспорт → настройки → список переходов.
**Элементы:**
- Грейд-чип: **«Бронза» / «Серебро» / «Золото»** (цвет — `border`-серый / `textSecondary` / `warning` @ 12 % с текстом `text` — без введения новых цветов).
- **Карточка рейтинга**: число 0–100 `h1` + разбивка компонент с формулами (`caption`): пунктуальность 25 %, оценки клиентов 30 %, качество фиксации 15 %, отсутствие переделок 20 %, дисциплина офферов 10 %; в MVP — подпись **«Рейтинг устанавливается диспетчером; авто-расчёт — скоро»**. Рейтинг < 40 — плашка `warning` **«Назначен разбор с диспетчером»**; < 25 — блокировка при входе.
- Апсейл-статистика: «Конверсия рекомендаций 34 % · выручка {сумма}» + `caption` «на рейтинг не влияет».
- Skill-теги — чипы; снятый — `warning` c текстом **«Снят временно: неполный инструмент»**; кнопка secondary **[Запросить новый навык]** → экзаменационный флоу M-04.
- **Проверка инструмента** (по пушу или вручную): чек-лист ToolChecklist по каждому активному тегу → PipelineButton **[Подтверждаю: всё на месте]** / ссылка **[Не хватает: {позиция}]** (снимает тег до восстановления).
- Прочее: зоны выезда, транспорт, предпочтительный напарник, счётчик невыходов, язык интерфейса (Русский / Oʻzbekcha), [Выйти].
- **Квартальный NPS** (ТЗ 17.17 п.11): раз в квартал при открытии профиля (или пушем) — bottom-sheet **в 2 тапа**: шкала 0–10 чипами (тап 1) → [Отправить] (тап 2); комментарий опционален; закрытие без ответа — повтор через 7 дней, не чаще; событие `nps_submitted` в аналитику (§6).
- Переходы-строки: **График и отпуска** → M-40 · **Реферальная программа** → M-41 · **Оборудование** → M-37 · **Сумка** → M-36 (ф.2) · **Синк-центр** → M-42 · **Изменения прайса** (по deep-link `profile/price-changes` — список изменённых позиций с датой активации).
- [Апелляция] на оценку/санкцию — из соответствующей строки → тикет диспетчеру.
**Поведение + офлайн:** кеш; изменения настроек — в очередь.

#### M-40. График и отпуска
**Композиция:** календарь месяца → легенда → PipelineButton [Запросить отпуск] → список запросов.
**Элементы:** календарь: смены (точка `accent`), дежурства (точка `warning` + «Д»), одобренный отпуск (заливка `success` @ 12 %), на рассмотрении (`warning` @ 12 %), праздники производственного календаря УЗ (`textSecondary`); PipelineButton **[Запросить отпуск]** → bottom-sheet: диапазон дат, чипы типа **«Отпуск» / «Больничный»**, комментарий → [Отправить диспетчеру]; список запросов со StatusBadge: «На рассмотрении» / «Одобрен» / **«Отклонён: {причина}»**.
**Наполнение:** подпись `caption` **«Одобренный отпуск исключает вас из распределения заявок»**.
**Поведение + офлайн:** просмотр из кеша; запрос — в очередь. MVP — базовый календарь; полные графики — фаза 2.

#### M-41. Реферальная программа «Приведи мастера»
**Композиция:** карточка с кодом/ссылкой → PipelineButton [Поделиться ссылкой] → список приведённых.
**Элементы:** персональный код `h1` + ссылка; PipelineButton **[Поделиться ссылкой]** → системный share sheet; карточка приведённого: имя, статус онбординга (StatusBadge), прогресс-бар **«{N} из 20 закрытых заявок»**, статус бонуса: «Ожидает» / **«Начислен {сумма} сум»** (`success`, проводкой на баланс → видно в M-34).
**Наполнение:** пустое состояние — `EmptyState(group_add)`: **«Приведите мастера — получите бонус после его 20 закрытых заявок»** + [Поделиться ссылкой].
**Поведение + офлайн:** кеш; шаринг работает офлайн (ссылка известна локально).

### 3.8. Синхронизация

#### M-42. Синк-центр офлайна
Видимость очереди — основа доверия к офлайн-режиму. Витрина паттерна П-5 (§4.5).
**Композиция:** статус-шапка → сводка объёма → список операций очереди → PipelineButton.
**Элементы:**
- **Статус-шапка**: всё чисто — иконка `cloud_done` `success` + **«Всё синхронизировано»** + `caption` «Последний синк: {чч:мм}»; идёт отправка — прогресс + **«Отправляем: {i} из {N}»**; есть ошибки — `error`.
- Строка операции: иконка типа (статус/фото/материал/подпись/наличные), «Z-2026-… · {тип}», клиентское время фиксации, размер (для фото), StatusBadge: **«В очереди»** (серый) / **«Отправляется»** (`accent`) / **«Ошибка»** (`error`) / **«Конфликт»** (`warning`). Тап → соответствующая заявка; тап по конфликту → деталь: «На сервере: {итог}» против «У вас было: {локально}» (разрешение — по серверному времени; спорные — флаг диспетчеру).
- Сводка: **«К отправке: 14 операций · 36 МБ»**.
- PipelineButton **[Синхронизировать сейчас]**; на упавших — secondary [Повторить].
**Наполнение:** порядок передачи — подпись `caption` **«Сначала статусы и данные, затем фото»** (операции заявки строго в порядке фиксации; медиа — фоном с докачкой с места обрыва).
**Поведение + офлайн:** ретраи с экспоненциальным backoff; повторная отправка не создаёт дублей (client_uuid — ключ идемпотентности); очередь и медиа переживают перезапуск и перезагрузку, хранилище шифруется, очистка — только после подтверждения сервера. ОФЛАЙН: экран и есть офлайн-состояние — шапка **«Ждём сеть»**, очередь видна полностью.

## 4. Спец-паттерны

Пять фирменных паттернов приложения. Каждый реализуется одним общим виджетом в shared-пакете — дублирование в экранах запрещено (как со `statusColor`).

### 4.1. П-1. 60-секундный оффер (полноэкранный)
- **Виджет `OfferScreen`** — используется M-09, M-10, мини-оффером M-26. Полноэкранный, поверх всего (в т.ч. с заблокированного экрана по heads-up push), таббар скрыт, системный «назад» = «свернуть» без отказа.
- **Режим вождения** (ТЗ 17.17 п.8): при детекте вождения виджет озвучивает оффер TTS (категория, район, доля) и слушает кнопку гарнитуры (принять/отклонить) либо авто-откладывает оффер на 3 мин; молчание за рулём не пишется в дисциплину офферов (флаг `driving_mode` в событии аналитики).
- **Таймер-кольцо**: круглый прогресс 96 px, цифры секунд `h1` внутри; цвет `accent`, последние 10 сек — `error`; тик прогресса раз в секунду — единственная разрешённая «анимация» сложнее стандартной (укладывается в дефолтный progress-индикатор платформы).
- **Вибрация**: при появлении — двойная; за 10 сек до конца — одиночная-длинная. Звук — из push-канала, отдельного звука в приложении нет.
- **Кнопки**: [Принять] — 64 высотой, во всю ширину; [Отклонить]/[Пропустить] — secondary 56; между ними `s12`. Никаких свайпов «принять» — только тап (перчатки).
- **Истечение**: экран закрывается сам; никакого состояния «просрочен» не остаётся. TTL push = таймеру.
- Читаемость на бегу: категория, доля и адрес видны с расстояния вытянутой руки — доля 32 px semibold.

### 4.2. П-2. Фото-обязательность (камера-only)
- **Виджет `MandatoryCamera(minPhotos, maxPhotos, hint)`** — используется M-13, M-14, M-16 (ценники), M-17, M-19, M-21 (чеки, доказательство замены), M-24, M-25 (этап), M-27 (+ миниатюра «до»), M-28 (fallback), M-30, M-38.
- Открывается **в один тап** из кнопки [Снять…]; кнопки галереи не существует нигде в приложении.
- Счётчик «Фото: {n} из {max}»; превью-лента с удалением до отправки; кнопка завершения неактивна до `minPhotos` — с текстовой причиной, а не молча.
- Пропустить нельзя: единственные выходы — снять фото или уйти в явную ветку («Нет доступа», системный «назад» в M-11 без продвижения шага).
- Технически: сжатие ~1600 px / 500 КБ, EXIF-очистка, клиентский UUID, двойные метки времени, гео или флаг «без гео» — всё внутри виджета, экраны об этом не знают.

### 4.3. П-3. Подпись пальцем
- **Виджет `SignaturePad`** — M-28 (B2C-усиление, режимные объекты), «Представитель точки» в осмотрах (M-11), **офлайн-подтверждение сметы в M-15** (подпись клиента + фото, флаг «согласовано офлайн» — ТЗ 17.17 п.7).
- Полноэкранный канвас в **альбомной ориентации** (авто-поворот): белое поле `surface` с рамкой `border`, штрих — `text`, толщина фикс.; подпись — данные, не украшение.
- Подсказка до первого штриха по центру: `textSecondary` **«Распишитесь пальцем»** — исчезает при касании.
- Кнопки: secondary [Очистить] и primary [Готово] (активна после первого штриха) — в углах, вне поля подписи.
- Сохраняется как изображение в очередь синка (офлайн — как любая операция), привязка к заявке и роли подписанта.

### 4.4. П-4. QR-показ
- **Виджет `QrDisplay(payload, title, caption)`** — M-29 (оплата), M-22 (код закупки).
- По DEV-06 4.10: фон `bg`, белая карточка `radiusCard`, QR чёрный на белом без стилизации и логотипа (надёжность сканирования важнее бренда — единственное разрешённое исключение из токенов).
- **Яркость экрана программно поднимается до максимума** при показе и возвращается при уходе с экрана.
- Под QR — `h2`-назначение («Оплата», «Код закупки») и `caption`-пояснение; для кодов закупки — дублирующий цифровой код `h1` (продиктовать, если сканер магазина не читает) и таймер срока жизни.
- Снизу — [Поделиться] (где применимо) / [Закрыть].

### 4.5. П-5. Офлайн-очередь (индикация синка)
- Три уровня индикации, все — из одного источника состояния очереди:
 1. **OfflineBanner** на каждом экране (§3.0) — факт офлайна;
 2. **SyncDot** на карточках и строках — несинхронизированные операции конкретной сущности;
 3. **Бейдж числа операций** на иконке синка (app bar M-06) → M-42.
- Статусы операции в M-42: «В очереди» → «Отправляется» → готово (исчезает) / «Ошибка» (ретрай) / «Конфликт» (разбор).
- Тексты фиксированные: **«Офлайн — действия сохранятся и отправятся при сети»**, **«Офлайн — данные на {чч:мм}»**, **«не синхронизировано»**, **«Всё синхронизировано»** — одинаковые во всех экранах, из словаря.
- Не-офлайновые действия никогда не показывают спиннер в ожидании сети — сразу заглушка/disabled с причиной: **«Нужна сеть»** (+ где критично — [Позвонить диспетчеру]).

## 5. Чек-лист приёмки UI

Проверяется на каждом экране перед мержем; пункты 1–4 — руками на устройстве, 5–10 — ревью кода.

1. **Перчатки и большие пальцы:** все тап-зоны ≥ 48×48; главная кнопка конвейера — во всю ширину, высота ≥ 56, внизу экрана; никаких обязательных свайпов и long-press.
2. **Яркое солнце:** основной текст только `text` на `bg`/`surface`; ни одно состояние не передаётся только цветом — всегда есть слово (бейдж, подпись).
3. **Одна primary на экран:** вторая primary-кнопка на экране — блокер ревью.
4. **Конвейер офлайн:** каждое действие шагов M-11…M-32 из офлайн-матрицы PRD-02 §6.1 выполняется в авиарежиме и появляется в M-42; проверка «мастер завершает заявку в подвале без сети» проходит целиком.
5. **Офлайн-индикация:** на экране присутствуют OfflineBanner и (для списков) SyncDot; не-офлайновые действия показывают «Нужна сеть», а не вечный спиннер.
6. **Строки из словаря:** ни одной русской/узбекской строки в коде виджетов; все тексты — ключи i18n; формулировки соответствуют этому документу.
7. **Узбекская вёрстка:** экран проверен с узбекской локалью (строки длиннее на 20–30 %) — без обрезаний, наложений и фикс-ширин под русский текст.
8. **Токены без хардкода:** нет `Color(0x…)`, `Colors.*`, числовых радиусов и отступов вне шкалы; статус-цвета — только `statusColor(status)`; линт на `Color(0x` включён.
9. **Деньги и камера:** все суммы в формате «1 250 000 сум» с `tabular-nums`; каждая фото-точка открывает камеру в один тап через `MandatoryCamera`, кнопок галереи нет.
10. **Пустые, ошибочные и заблокированные состояния:** у каждого экрана реализованы EmptyState по DEV-06 4.6, состояние ошибки и задизейбленные кнопки с текстовой причиной («Снимите хотя бы одно фото», «Сначала: {шаг}») — молчаливых disabled нет.

## 6. Аналитические события (телеметрия, ТЗ 17.17 п.11 — обязательна)

Каталог событий приложения мастера. Каждый экран/виджет пишет свои события через общий трекер; **события пишутся в ту же офлайн-очередь**, что и операции (низший приоритет — после статусов и медиа), и уходят при синке. North Star продукта: закрытые заявки с оценкой ≥ 4 на активного клиента/месяц.

| Событие | Параметры | Где пишется |
|---|---|---|
| `offer_shown` | `offer_id, type (regular/swap/helper), driving_mode` | M-09/M-10 при показе |
| `offer_accepted` | `offer_id, reaction_ms, driving_mode` | тап [Принять] / кнопка гарнитуры |
| `offer_declined` | `offer_id, reaction_ms, reason, driving_mode` | подтверждение отказа |
| `offer_expired` | `offer_id, driving_mode` | истечение таймера (за рулём — не в дисциплину) |
| `step_started` | `order_id, step, offline` | открытие шага конвейера (M-11…M-29) |
| `step_completed` | `order_id, step, duration, offline` | завершение шага — длительности узлов ~40-тапного конвейера |
| `estimate_search` | `order_id, query_len, time_to_pick` | поиск позиции в M-15 (query_len=0 — выбор из ускорителя) |
| `estimate_preset_used` | `order_id, preset_type (frequent/recent/bundle/copy), positions` | тап по ускорителю/набору/копии сметы |
| `moderation_returned` | `order_id, step, reason` | ModerationPlate на M-11 |
| `cash_accepted` | `order_id, amount` | [Принял наличные] в M-29 |
| `wallet_opened` | `tab (today/week/month/payouts)` | открытие M-34 |
| `shift_on` / `shift_off` | `duty (bool)` | тумблер смены M-06 |
| `sync_queue_flushed` | `ops, age` (возраст старейшей операции) | успешный синк очереди (M-42/фон) |
| `nps_submitted` | `score, has_comment` | квартальный NPS в профиле (M-39) |

Правила: события не блокируют UI и не показываются мастеру; идентификаторы — те же `client_uuid`/`order_id`, что в очереди операций; PII в параметрах запрещён. Клиентское приложение — зеркальный каталог в DEV-08.

## N. Экраны контура «Дом» (M-43…M-50, M7/M8)

**Общее правило раздела.** Каждый экран ниже обязан иметь офлайн-состояние по правилу §17 — заглушка «нужна сеть» допустима только там, где это явно указано в PRD-02 §6.1. Все действия идут через ту же очередь операций, что конвейер, с двойными метками времени.

### M-43. Наряд-допуск
**Композиция (сверху вниз):** app bar «Допуск» + `SyncDot` → OfflineBanner (при офлайне) → `PermitCard` (компонент DEV-06 §4.N) → блок «Кто встречает» (имя эскорта, кнопка звонка дежурному) → блок «Зона влияния»: «Затронет {N} помещений» → две primary-кнопки по состоянию: **[Открыл зону]** / **[Закрыл зону]**.
**Элементы:** метка критичной зоны — иконка `warning_amber` + текст, **не цвет** (цвет занят статусами). Требуемая квалификация — строка `caption` с отметкой соответствия.
**Наполнение:** окно — «Сегодня 14:00–16:00», не ISO. Обратный отсчёт до конца окна.
**Поведение + офлайн: ОФЛАЙН — да.** Данные из локальной БД. «Открыл» открывает камеру (camera-only), фото и отметка — в очередь. **Блокировка старта:** если закешированный статус наряда `requested` или `rescheduled` — кнопка disabled, под ней текст **«Допуск не согласован — нужна сеть»**, а не спиннер и не молчаливое ничего.

### M-44. Пропуск в здание
**Композиция:** QR по центру, минимум 240×240 → числовой резервный код `h1` моноширинно с разбивкой по 3 знака → блок правил объекта (вход, грузовой лифт, парковка, часы шумных работ) → срок действия.
**Поведение + офлайн: ОФЛАЙН — да**, QR рендерится из закешированного токена. Яркость экрана поднимается автоматически на время показа QR (иначе сканер на посту не считает). Аннулированный пропуск — полноэкранный `error`: «Пропуск отозван», без QR.

### M-45. Отключение ресурса
**Композиция:** карточка отключения (`ShutdownBanner`) → «Затронет {N} помещений» → **[Отключил]** / **[Включил]** с обязательным фото → таймлайн отметок.
**Поведение + офлайн: ОФЛАЙН — да (очередь).** Плашка при офлайне: **«Соседей уведомим, когда появится сеть; о плановом окне они предупреждены заранее»** — мастер должен понимать, что уведомление не ушло. При превышении планового окна — напоминание и кнопка «Отправить новый прогноз».

### M-46. Моя выработка
**Композиция:** период → часы в смене → закрытые заявки → SLA-показатели → выполнение регламентов. **Ни одной денежной суммы.**
**Поведение:** экран показывается вместо M-34 «Кошелёк» **только в сменах оператора**. Мастер, работающий и на платформу, видит оба: M-34 по своим свободным сменам, M-46 по сменам оператора. Переключение — не ручное, а по владельцу текущей смены.

### M-47. Плановое ТО на объекте
**Композиция:** карточка оборудования (модель, серийник, дата ввода, история) → чек-лист регламента с отметками и фото по пунктам → «Зафиксировать замечание» → завершение.
**Поведение + офлайн: ОФЛАЙН — да.** Чек-лист кешируется целиком. Завершение блокируется при незакрытых обязательных пунктах — с перечнем, а не общим «заполните всё».

### M-48. Обход: маршрут и чек-лист
**Композиция:** прогресс-бар зон → список зон чек-листа с отметками → на каждой зоне кнопка «Замечание» → «Завершить обход» с итогом.
**Поведение + офлайн: ОФЛАЙН — да, полностью.** Кешируются чек-лист и открытые замечания по объекту (нужны для дедупликации).

### M-49. Замечание — быстрая фиксация
**Композиция:** полноэкранная камера → плитка категорий 3 колонки → отправлено. **Три тапа, целевое время — 15 секунд.**
**Элементы:** плитка — иконка A-44 + подпись максимум в две строки. Кнопка микрофона для голосового комментария — необязательный четвёртый тап, не блокирующий отправку.
**Наполнение:** зона подставляется по гео и текущему пункту чек-листа и показывается строкой с возможностью исправить; серьёзность по умолчанию «содержание».
**Поведение:** дубль по зоне за 14 дней → bottom-sheet «Здесь уже есть замечание от {автор}, {дата}» с кнопками «Присоединиться» / «Всё равно создать». **Никаких обязательных полей, кроме фото и категории** — форма на десять полей означает, что через неделю руководитель вернётся в WhatsApp.

### M-50. Мои замечания
**Композиция:** сегменты «Открытые / Просроченные / Устранённые» → список карточек с фото-превью и статусом. **ОФЛАЙН — да (кеш).**
