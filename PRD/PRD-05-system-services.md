# PRD-05. Системные сервисы и серверная часть платформы USTAPRO

**Документ:** Product Requirements Document для бэкенд-команды.
**Источник истины:** ТЗ «Платформа технического сервиса (Ташкент)» v2.25 (далее — ТЗ; ссылки вида «ТЗ N.M»).
**Скоуп:** движки, автоматы, фоновые процессы и интеграции. Экраны и UX — в PRD клиентских приложений; здесь только серверная логика.
**Архитектурная рамка (ТЗ 14):** единый модульный монолит **NestJS (TypeScript)**; веб-панели — React, лендинги — Next.js (SSR), ORM — Prisma, монорепозиторий с общими типами API (решение владельца, ТЗ v2.25); PostgreSQL, Redis (очереди/кеш), S3-совместимое хранилище, FCM. Микросервисы не строим — нагрузка горизонта 2 лет: 200 мастеров, 5 000 заявок/мес, 500 организаций. Все сервисы ниже — модули монолита + воркеры очереди, общающиеся доменными событиями через внутреннюю шину (outbox-таблица + воркеры; никакого Kafka).
**Общие правила для всех сервисов:** время хранится в UTC, отображение Asia/Tashkent (ТЗ 14); суммы — в сумах без копеек, округление до 100 сум (ТЗ 8.1); все значимые действия — в append-only AuditLog (ТЗ 3.8, 14); все «параметры (по умолч. X)» — конфигурируемые настройки админки; записи с флагом «демо» исключаются из биллинга, отчётов и налоговых регистров (ТЗ 17.6).

## 1. Сервис статусных машин заявок (Order State Machine)

### 1.1. Назначение
Единственная точка изменения статуса заявки. Валидирует переход по графу типа заявки, проверяет обязательные условия (фото, чек-лист, оплата, санкции), исполняет side-effects (события, проводки, таймеры), пишет журнал переходов. Переходы вне графа отклоняются на уровне API (ТЗ 4.1 «Машины состояний по типам», критерий приёмки №1–2).

### 1.2. Входы/выходы
- **Вход:** команда `transition(order_id, target_status, actor, payload)` от API-слоя (мобильные приложения, панели), от системных сервисов (планировщик, биллинг, таймеры) и от офлайн-синка (раздел 10).
- **Выход:** обновлённый статус; запись в журнал переходов (кто, когда, откуда/куда — ТЗ 3.4); доменное событие `order.status_changed{type, from, to, actor, reason}`; ошибка 409 с машиночитаемым кодом при недопустимом переходе или невыполненных условиях.

### 1.3. Общие правила (все типы)
1. Базовый словарь статусов — ТЗ 4.1: 1 Новая, 2 Оценена, 3 На утверждении, 4 Утверждена, 5 Назначена, 6 Мастер выехал, 7 В работе, 8 Доп-согласование, 9 Выполнена, 10 Проверена, 11 Ожидает оплаты, 12 Закрыта, 13 Оценена клиентом. Терминальные/особые: Отменена (причина из справочника обязательна), Спор (ТЗ 4.2). Паузы (суб-состояния «В работе», не отдельные статусы, но блокируют конвейер): «Ожидание материалов», «Технологический перерыв», «Заблокировано третьей стороной» (ТЗ 4.1).
2. Условия-инварианты переходов проверяются на API, не в UI: «В работе» требует фото «до» (мин. 1, камера-only) + мягкую гео-проверку ±300 м (несовпадение → флаг диспетчеру, не блок); «Выполнена» требует фото «после» (мин. 1) + все материалы с чеками + итог = утверждённой сумме или утверждена доп-смета (ТЗ 4.1 п. 7, 9).
3. Режимный объект (флаг точки «фото запрещено»): вместо фото — код приёмки сотрудника + подпись представителя; отметка в акт (ТЗ 4.1). Fallback приёмки B2B: «Принято без кода» → фото общего плана → флаг диспетчеру (ТЗ 7.1 шаг 5).
4. «Проверена» → возврат в «В работе» с комментарием при браке фото/чеков; если оплата уже принята — возврат её не отменяет, недочёты закрываются доработкой или спором (ТЗ 4.1 п. 10).
5. Отмена возможна из любого нетерминального статуса; финансовые последствия считает биллинг по матрице ТЗ 4.4 (см. 4.6 настоящего PRD). Дубль-детект при создании: открытые заявки той же точки/адреса и категории за 24 ч → предупреждение; слияние дублей — диспетчер (ТЗ 4.1). При создании фиксируется заявитель — поле `applicant_user_id` (создатель заявки; для телефонных заявок — привязка диспетчером в карточке, D-08; у авто-заявок пусто) — используется программой баллов (раздел 4.4 п.21).
6. Спор: окно 72 ч после «Выполнена», блокирует начисление доли мастеру до резолюции; резолюции: в пользу клиента / мастера / компромисс; возвраты — только refund-API + сторно-проводка; споры выше порога и «свои» заявки диспетчера — эскалация админу (ТЗ 4.2).
7. Переназначение мастера — статусы 5–8, причина обязательна, история хранится; частичное выполнение — «раздел заявки» (% первому/второму, аудит) (ТЗ 4.5).
8. Каждый переход публикует событие; подписчики: движок уведомлений (раздел 6), биллинг (раздел 4), планировщик (раздел 2), генераторы задач (раздел 7), сервисные касания (раздел 7.2).

### 1.4. Графы переходов по типам (обязательное приложение к контракту — формализовано в DEV-10-status-graphs.md: словари статусов/действий, диаграммы, машиночитаемый YAML; менять синхронно с этим разделом)

Формат: «из → в | кто | условия | side-effects».

#### 1.4.1. B2C (обычная)
B2C пропускает статусы 3–4: первичная смета — вилка «от–до», обязательством становится сумма, подтверждённая клиентом на месте — событие «смета подтверждена» внутри «В работе» с аудит-записью (ТЗ 4.1).

| Из → В | Кто | Условия | Side-effects |
|---|---|---|---|
| — → Новая | клиент / диспетчер (телефон) | описание + категория; адрес в зоне покрытия (иначе лид-лист «ждут покрытия», ТЗ 17.4); долг B2C не блокирует (блокировка — на этапе создания, ТЗ 4.4) | событие `order.created`; дубль-детект; уведомление диспетчеру |
| Новая → Оценена | система / диспетчер | позиции прайса подобраны (или «Выезд/диагностика» при «не знаю, что сломалось»); вилка «от–до» зафиксирована копией цен | расчёт нормо-часов → запрос слотов планировщику |
| Оценена → Назначена | планировщик (авто) / диспетчер | мастер принял оффер или назначен вручную; окно подтверждено; бронь слотов создана | push клиенту (карточка мастера); телефон клиента открывается мастеру (ТЗ 17.5) |
| Назначена → Мастер выехал | мастер | кнопка «Выехал» | push клиенту с ETA; старт гео-мониторинга замены (ТЗ 17.3) |
| Мастер выехал → В работе | мастер | фото «до» ≥1 (камера-only); гео ±300 м мягко | серверные метки фото; событие для модерации |
| В работе: событие «смета подтверждена» | клиент (пуш «Подтвердите стоимость») / диспетчер («озвучено по телефону») | сумма ≤/= уточнённой смете; отказ клиента = оплачивается только выезд, ложный вызов не начисляется (ТЗ 6.1) | аудит-запись санкции; фиксация обязательства |
| В работе → Доп-согласование | мастер | вынужденная доп-работа (фото проблемы + позиции, варианты минимум/полный) или итог > подтверждённого | push клиенту (решение только с телефона клиента — анти-подделка, ТЗ 4.6); работа по согласованной части продолжается |
| Доп-согласование → В работе | клиент / система | доп-смета утверждена или отклонена (отказ → консервация, флаг «выполнена частично», ТЗ 4.6 п. 4) | аудит; при отказе — позиция «Консервация» в смету |
| В работе → пауза «Ожидание материалов» | мастер | схема «клиент покупает сам»; дата повторного визита | слоты освобождаются; при возобновлении фото «до» повторно не требуется (ТЗ 4.1) |
| В работе → пауза «Заблокировано третьей стороной» | мастер | причина из справочника + фото + время следующей попытки | якорная бронь на подтверждённое время / задача диспетчеру «дозвониться до ТСЖ»; таймеры 48 ч / 7 дней (ТЗ 4.1) |
| В работе → Выполнена | мастер | фото «после» ≥1; материалы с чеками; итог = санкционированному; **оплата собрана** (QR/ссылка/наличные) — уход без оплаты только с санкции диспетчера; **онлайн-оплата в приложении = санкция приёмки**: вебхук успешного платежа фиксирует приёмку автоматически (аудит-запись «приёмка подтверждена платежом», код не требуется); код приёмки запрашивается для наличных / телефонного канала / B2B (ТЗ 17.17 п.3) | событие «оплата принята» или маршрут в «Ожидает оплаты»; фиксация ClientAsset (17.12) |
| Выполнена → Проверена | диспетчер | модерация фото/чеков ок; иначе возврат в «В работе» с комментарием | — |
| Проверена → Ожидает оплаты | диспетчер | **исключение**: санкция с причиной (ТЗ 4.1 п. 11) | таймеры напоминаний 24 ч push / 72 ч SMS; при неоплате — долг аккаунта, блок новых заявок (параметр) |
| Проверена → Закрыта (наличные/онлайн получены) | система | биллинг провёл проводки (онлайн-оплата подтверждена вебхуком / наличные зафиксированы за мастером) | проводки закрытия; начисление доли; гарантийный срок фиксируется копией; акт доступен; таймер оценки 72 ч; генерация QC-задач и сервисных касаний |
| Ожидает оплаты → Закрыта | система | оплата поступила (вебхук / отметка) | те же side-effects |
| Закрыта → Оценена клиентом | клиент | окно 72 ч | пересчёт рейтинга; оценка 1–2 → тикет диспетчеру |
| Выполнена/Закрыта → Спор | клиент (72 ч) / диспетчер | причина | блок доли мастера; маршрутизация по порогам |
| любой ≤ 8 → Отменена | клиент / диспетчер / система (эскалация) | причина из справочника | финансовая матрица отмен (4.6 PRD); слоты освобождаются → событие `slot.freed` |

#### 1.4.2. B2B (абонентка и разовая по договору)
Полный конвейер 1–13 с утверждениями; «Ожидает оплаты» пропускается — канал списания известен (ТЗ 4.1).

| Из → В | Кто | Условия | Side-effects |
|---|---|---|---|
| — → Новая | сотрудник/руководитель точки / диспетчер | описание + категория, фото желательно | событие; дубль-детект; анти-дробление (счётчик авто-стартов точки за 48 ч, ТЗ 5.1) |
| Новая → Оценена | система / диспетчер | позиции + сумма первичной сметы | — |
| Оценена → Назначена (авто-старт) | система | смета ≤ лимита заявки точки И месячный лимит не исчерпан И это не заявка из осмотра/апсейл | счётчик месячного лимита +=; при > N авто-стартов за 48 ч — флаг диспетчеру |
| Оценена → На утверждении | система | смета > лимита заявки, ИЛИ месячный лимит исчерпан, ИЛИ заявка из осмотра, ИЛИ доп-смета (матрица ТЗ 5.1) | push утверждающему по порогам (ТЗ 5.2); таймеры эскалации 24/48/72 ч (ТЗ 5.3) |
| На утверждении → Утверждена | руководитель точки / организации / +владелец (двойное) | кнопка «Утвердить»; сумма в пределах порога роли; > порога повторной аутентификации — PIN/биометрия (ТЗ 5.2) | аудит (кто, когда, сумма, устройство); отмена таймеров |
| На утверждении → Отменена | система | молчание T+72 ч (не для критичных дефектов) | «не согласовано», уведомления всем |
| Утверждена → Назначена | планировщик / диспетчер | как B2C; учитывается график доступа точки, закреплённый мастер (мягкий приоритет), чёрный список точки (ТЗ 3.2) | как B2C, получатель push — сотрудник точки |
| Назначена → … → В работе | мастер | как B2C; на режимном объекте — код приёмки вместо фото | — |
| В работе → Доп-согласование | мастер | доп-смета: вынужденная (красный флаг, таймеры 30 мин / 2 ч) или превышение; апсейл — **всегда** через утверждающего, никогда не автостартует, сотрудник точки принять не может (ТЗ 4.6) | push+SMS утверждающему; при молчании по вынужденной — консервация без утверждения (фикс-позиция) + дефект в техдолг |
| В работе → Выполнена | мастер | фото «после» + материалы + код подтверждения сотрудника точки (4-значный) или «Принято без кода» + фото + флаг | — |
| Выполнена → Проверена | диспетчер | модерация | — |
| Проверена → Закрыта | система | биллинг: списание с абонентки / включение в сверхлимит-СФ (проводки раздела 4) | доля мастера; отчётные данные |
| Закрыта → Оценена клиентом | руководитель/сотрудник | 72 ч | — |

**B2B разовая без договора (ТЗ 8.3):** Новая → Оценена → **Счёт на предоплату** (суб-статус «Ожидает предоплаты») → бухгалтер отметил оплату → Назначена → далее по B2B-графу; закрытие — акт + СФ. Постоплата — только решением админа с аудитом. Переход «Назначена» без отметки оплаты — запрещён на API.

#### 1.4.4. Осмотр плановый (ТЗ 4.1)
Без сметы и утверждения; вместо фото «до/после» — заполненный чек-лист по типу объекта; результат — дефекты.

| Из → В | Кто | Условия | Side-effects |
|---|---|---|---|
| — → Новая | InspectionSchedule (авто, фаза 2) / диспетчер (MVP) | график осмотров организации | стоимость осмотра уже зарезервирована из абонентки 1-го числа (ТЗ 8.3) |
| Новая → Назначена | планировщик | приоритет 8 (фоновый демпфер): непиковые часы, авто-уступает слоты, двигается в пределах недели (ТЗ 17.3) | — |
| Назначена → Выехал → В работе | мастер | стандартно | — |
| В работе → Выполнена | мастер | **чек-лист осмотра заполнен**; дефекты внесены (фото обяз., категория, оценка позициями прайса, приоритет); **зафиксирован представитель точки** (подтверждение кодом приёмки или подписью на экране) либо fallback «представитель отсутствовал» + фото точки доступа (ТЗ 4.1, 9.3) | создание Defect-записей; заполнение паспорта объекта; при «отсутствовал» — флаг диспетчеру на выборочную проверку, отчёт помечается «без представителя» |
| Выполнена → Проверена → Закрыта | диспетчер / система | модерация чек-листа | списание резерва осмотра с абонентки (первоочерёдное, никогда не сверхлимит); отчёт по осмотру (раздел 13); пакет дефектов → push руководству (ТЗ 5.4) |

Приостановка организации замораживает осмотры (резерв не тратится); расторжение — сторно резерва (ТЗ 8.3).

#### 1.4.5. Гарантийная (ТЗ 4.1, 4.2)
Смета клиенту = 0; статусы 3–4 пропускаются; биллинг клиенту не начисляется.

| Из → В | Кто | Условия | Side-effects |
|---|---|---|---|
| — → Новая | клиент («Проблема вернулась») / диспетчер | ссылка на исходную заявку; текущая дата ≤ дата закрытия исходной + гарантийный срок (копия в заявке) | QC-триггер: звонок 4 ч (ТЗ 17.11) |
| Новая → Назначена | планировщик | приоритет 3 очереди (наша вина); по умолчанию — виновный мастер, диспетчер может назначить другого | — |
| Назначена → … → Проверена | мастер / диспетчер | стандартный фото-цикл | — |
| Проверена → Закрыта | система | квалификация вины диспетчером: вина мастера + переделал сам → доля 0; переделал **другой** → ему обычная доля (расход компании), у виновного удержание 0/50/100% (параметр); вина материала/эксплуатации → обычная оплата (ТЗ 4.2) | проводки удержаний; материалы при вине мастера — за счёт компании с тем же параметром удержания; рейтинг: компонент «переделки» |

#### 1.4.6. Из осмотра / из дефекта (ТЗ 3.5, 5.1, 5.4, 4.6)
Источники дефектов: плановые осмотры, отклонённые/отложенные вынужденные доп-работы, отложенные апсейлы (ТЗ 10).

Статусная машина дефекта: `новый → на утверждении → утверждён | отложен(до даты) | отклонён`; `утверждён → устранён` (ссылка на закрывшую заявку). Оценка дефекта актуальна 30 дней, затем требует переоценки (ТЗ 3.5). Отклонённые — в архив с юридически значимой пометкой «предупреждали {дата}» (ТЗ 10).

| Из → В | Кто | Условия | Side-effects |
|---|---|---|---|
| Defect(утверждён) → Order: сразу «Утверждена» | система | утверждение **всегда явное** — даже в пределах лимита точки (анти-навязывание, ТЗ 5.1); пакетное утверждение чекбоксами (ТЗ 5.4) | заявка создаётся со статусом «Утверждена», смета = оценка дефекта; ссылка defect_id |
| Утверждена → Назначена → … → Закрыта | планировщик и далее | стандартный B2B-хвост | закрытие → Defect.status = устранён; техдолг точки −= сумма |

#### 1.4.7. Этапная (ТЗ 4.1, 3.7, 17.3)
Позиция прайса с планом этапов [{этап, нормо-часы, пауза [мин; макс]}]. Цена за работу целиком; выезды сессий включены.

| Из → В | Кто | Условия | Side-effects |
|---|---|---|---|
| Оценена/смета на месте → бронирование цепочки | планировщик | **Инвариант старта: этап 1 не начинается, пока не подтверждены слоты ВСЕХ следующих этапов в их допустимых окнах.** Вариант (а): позиция известна при создании — все сессии бронируются при назначении. Вариант (б): работа вскрылась на месте — слоты следующих сессий предлагаются клиенту на экране мастера и подтверждаются вместе со сметой | брони всех сессий; при невозможности собрать цепочку — предложения: перенос всей работы / сверхурочный слот с согласия мастера / передача продолжения другому мастеру той же квалификации с разделом доли (параметр, по умолч. выкл.) |
| В работе → «Этап N завершён» | мастер | фото «в процессе» + отметка этапа; **промежуточные сессии завершаются без оплаты** — единственное исключение из «не уходи без оплаты» (ТЗ 17.3/v2.7) | — |
| «Этап N завершён» → пауза «Технологический перерыв» | система | есть следующий этап | мастер свободен, пауза не занимает ленту; следующая сессия — приоритет 4 очереди (продолжения выше новых броней) |
| Технологический перерыв → В работе (сессия N+1) | мастер | наступил слот сессии; окно паузы [мин; макс] соблюдено | — |
| последняя сессия → Выполнена | мастер | фото «после»; оплата B2C — на последней сессии | стандартный хвост |
| отмена посередине | клиент/диспетчер | — | оплата фактически выполненных этапов (правило ТЗ 4.4); все сессии — один мастер; замена — только через «раздел заявки» (ТЗ 4.5) |

#### 1.4.8. Парная (ТЗ 3.7, 4.5, 17.3)
Парная позиция («требует 2 исполнителей»): роли **ведущий** (skill, смета, фото-цикл, приёмка) и **помощник** (упрощённая карточка: адрес, время, ведущий, фикс — без конвейера, смет и фото).

| Из → В | Кто | Условия | Side-effects |
|---|---|---|---|
| Утверждена/Оценена → Назначена | планировщик | найдено пересечение свободных слотов двух лент в одной зоне: ведущий по skill-тегу, помощник — любой свободный (включая младшие грейды/кандидатов); мягкий приоритет «предпочтительный напарник» (ТЗ 3.3) | две брони; помощнику — упрощённый оффер |
| В работе: «Нужен помощник» | ведущий (на непарной позиции) | одному физически нельзя | мини-оффер бродкастом ближайшим свободным + дежурному («подсобить ~2 ч, фикс + дорога»); никого нет → перенос на ближайший парный слот (механика инварианта этапных). Фикс помощника: клиент — никогда; скрытые условия → расход компании; очевидная недооценка → из доли ведущего (решает диспетчер, аудит) (ТЗ 17.3/165) |
| основной конвейер | ведущий | статусы ведёт только ведущий | закрытие: деление по ролям, напр. ведущий 40% + помощник 20% (параметры) — раздел 4.4 |
| невыход помощника | система | принятый оффер не исполнен | санкции невыхода 17.3 (единственное влияние помощи на рейтинг) |

### 1.5. События
**Порождает:** `order.created/estimated/approval_requested/approved/assigned/master_departed/started/addwork_requested/addwork_approved|rejected/paused{type}/resumed/stage_completed/completed/verified/awaiting_payment/closed/rated/cancelled{reason}/dispute_opened|resolved`, `defect.created/approved/…`, `order.replacement_required`.
**Слушает:** `payment.confirmed` (→ Закрыта), `offer.accepted` (→ Назначена), `timer.expired` (эскалации/авто-отмена), `sync.operation_applied` (офлайн).

### 1.6. Крайние случаи
Двойное нажатие/ретрай — идемпотентность по `(order_id, from, to, client_op_uuid)`. Конкурирующие переходы (диспетчер и мастер одновременно) — оптимистичная блокировка по версии заявки, проигравший получает 409. Отмена во время «Доп-согласование» — таймеры доп-сметы гасятся. Многодневная работа — статус «В работе» с индикатором числа дней (ТЗ 4.1). Перенос клиентом: бесплатно при > 2 ч до окна, максимум 2 раза, мастер снимается, заявка в редистрибуцию (ТЗ 6.1).

### 1.7. Инварианты
- Переход вне графа типа — невозможен ни для одной роли, включая админа (только цепочка допустимых переходов).
- «Выполнена» без фото «после» — невозможна на API (критерий приёмки №1).
- Смета выше лимита не в работе без записи утверждения в аудите (критерий №2).
- Ни одна платная работа без санкции; работа мимо приложения не оплачивается (ТЗ 4.6 п. 4).
- Этапная: этап 1 не стартует без подтверждённой цепочки; все сессии — один мастер.

### 1.8. Ссылки на ТЗ: 3.4, 3.5, 4.1–4.6, 5.1–5.4, 7.1, 17.3. **Фаза:** MVP полностью (все 8 графов; пакетные утверждения дефектов и авто-осмотры — фаза 2, но граф «из осмотра» в MVP работает от ручных осмотров диспетчера).

## 2. Планировщик (Capacity & Scheduling Engine)

### 2.1. Назначение
Управляет ёмкостью: сетка 30-минутных слотов на мастера, брони заявок, предложение клиентам только реально доступных окон, сборка лент D−1, интрадей-операции, приоритетная очередь при перегрузе. «Никогда не обещаем то, под что нет ёмкости» (ТЗ 17.3).

### 2.2. Входы/выходы
- **Входы:** графики мастеров (дни/часы, отпуска/больничные с подтверждением диспетчера), нормо-часы позиций прайса, матрица времени езды зона→зона, справочник зон и city_id, производственный календарь, события заявок, тумблер «на линии», признак транспорта и выданное оборудование, графики доступа B2B-точек, дежурства.
- **Выходы:** список доступных окон для клиента/диспетчера (живой планировщик в телефонном флоу, ТЗ 12); брони слотов; ленты мастеров (черновики D−1 и актуальные); события `slot.freed`, `lane.changed`, `window.at_risk`; метрики (упущенный спрос, churn лент, дыры, пробег).

### 2.3. Алгоритм/правила
1. **Слоты и брони.** Календарь мастера — сетка 30-мин слотов. Бронь заявки = ceil((нормо-часы сметы + дорожный буфер) / 0.5 ч) слотов. Дорожный буфер = время до адреса по карте × (1 + запас, параметр по умолч. 20%). По каждой активной заявке известно расчётное завершение = старт + нормо-часы (ТЗ 17.3).
2. **Выдача окон.** По заявке: фильтр мастеров (skill-теги позиций ∧ зона адреса ∧ транспорт/оборудование, если требуется ∧ не в чёрном списке точки) → перебор свободных последовательностей слотов с учётом плана ≤ 80% смены и аварийного резерва → двухчасовые окна кандидатов. Все заняты — честно показываем завтра. Клики по недоступным окнам логируются как **упущенный спрос** (метрика найма).
3. **Якорные и гибкие.** Якорные (жёсткие окна клиентов, графики доступа B2B, подтверждённое время «Заблокировано») ставятся в ленты первыми; гибкие (осмотры, лист ожидания) заполняют дыры. Между соседними заявками — буфер по матрице зон.
4. **Лимит 80%:** план дня ленты ≤ 80% смены (параметр); 20% — люфт на сюрпризы.
5. **Заморозка 2 ч:** ближайшие 2 часа каждой ленты неприкосновенны для автоматики; трогает только диспетчер вручную.
6. **Четыре атомарные интрадей-операции** (глобальная переоптимизация запрещена): (а) вставить заявку в дыру ленты; (б) сдвинуть хвост ленты; (в) обменять две заявки между мастерами; (г) заменить мастера (протокол — раздел 3). Каждая операция рассылает пуши всем затронутым. Полная пересборка — только вручную старшим смены при массовом инциденте.
7. **Приоритеты очереди — 8 уровней** (доступ к слотам сверху вниз, внутри уровня строгий FIFO; ручной подъём — только с причиной в аудит):
   1. Аварийные (+ аварийный резерв ёмкости);
   2. B2B в договорном окне;
   3. Гарантийные;
   4. Продолжения начатых этапных работ (слот в допустимом окне этапа);
   5. Срочные (тариф «Срочно»): впереди обычных за свободную ёмкость + доступ к резерву при отсутствии аварий; подтверждённые брони не ломают;
   6. B2C с забронированным окном (FIFO по времени брони);
   7. Бесплатный лист ожидания (FIFO, честный прогнозный интервал);
   8. Плановые осмотры — демпфер: непиковые часы, авто-уступают слоты, двигаются в пределах недели.
   Денежных компенсаций за сдвиги нет; валюта извинений — приоритетный слот, VIP-контроль, проактивная связь (ТЗ 17.3, 18.15).
8. **Тариф «Срочно»:** +коэффициент срочности к работам (по умолч. +30%; как аварийная наценка — только к работам, доля мастера с наценкой). Правило честности: не начали за X ч (по умолч. 3) — наценка снимается автоматически, push клиенту, доля мастера от базовой. Доступен B2B вне аварий: базовая × срочность × подписной коэффициент, санкция по матрице 5.1. Ночью «Срочно» не применяется — действует ночной коэффициент; наценки аварийная/ночная/срочная взаимоисключающие, применяется одна наибольшая (ТЗ 17.6a).
9. **Аварийный резерв:** X% ёмкости часа не бронируется под плановые; аварий нет — резерв отдаётся срочным (сразу) и листу ожидания (за 2 ч до начала).
10. **Освободившийся слот не пропадает:** отмена/ранний финиш → `slot.freed` → предложение по приоритетам: срочные → лист ожидания (авто-push «появилось окно сегодня 16:00, подтвердить?») → подтягивание гибких из хвоста ленты.
11. **Сборка D−1 (волновая):** вечером — авто-черновики лент жадным алгоритмом по зонам (якорные → гибкие в дыры → буферы → лимит 80%); утром зонный диспетчер за 15 мин правит аномалии и подтверждает; мастер видит завтрашний маршрут с вечера. Три горизонта: неделя (смены, дежурства, пул осмотров по «низким» дням) / день (D−1) / реальное время (только 4 операции).
12. **Зоны:** мастер на день закреплён за 1–2 смежными зонами; кросс-зонные переезды — только аварии и замены; окна клиенту — из ёмкости его зоны. Декомпозиция «5–8 мастеров × 20–30 заявок» на зону — жадный алгоритм с локальными улучшениями, без глобальной оптимизации.
13. **Этапные цепочки:** бронируются все сессии сразу с учётом пауз-окон [мин; макс]; в паузах мастер свободен; инвариант старта — раздел 1.4.7.
14. **Парные:** поиск пересечения свободных слотов двух лент в одной зоне (ведущий по skill; помощник любой свободный); «экипаж дня» (фаза 2) — общая лента двух мастеров.
15. **Кнопка «Задерживаюсь +30/60»:** каскадный пересчёт очереди мастера; вылет следующей заявки за окно → алерт диспетчеру с вариантами (переназначить / предложить клиенту сдвиг с проактивным push).
16. **Инцидент-режим:** > N заявок одной категории из одного района за час → диспетчер включает «инцидент»: кластеризация заявок, шаблонное оповещение района, приоритизация внутри кластера, разрешена ручная пересборка.
17. **Дежурный резерв:** один мастер в день на ротации; плановые ему не бронируются; работа — аварии, замены, переполнение срочных; с середины тихого дня — срочные и лист ожидания рядом с зоной. Оплата — минималка смены (день ~200 000, ночь ~250 000, параметры) + доли с выездов (проводки — раздел 4).
18. **Праздники:** режим выходного дня по производственному календарю (ёмкость по праздничному графику).
19. **Ночь (22:00–07:00):** плановые B2C ночью не бронируются; исключение — B2B-точки с ночным графиком доступа (тариф — ночной коэффициент или условия договора) (ТЗ 17.6a).

### 2.4. События
**Порождает:** `windows.offered`, `booking.created/moved/released`, `lane.draft_ready`, `lane.changed` (push затронутым), `window.at_risk`, `slot.freed`, `demand.lost`, `incident.started/ended`.
**Слушает:** `order.*` (создание/утверждение/отмена/задержка/этапы), `offer.accepted`, `master.shift_changed`, `equipment.issued/returned`, `calendar.updated`.

### 2.5. Крайние случаи
Аварийная вытесняет плановую — конфликт виден диспетчеру, перенос с извинением и push. Отпуск/больничный после сборки лент — переброска броней как серия атомарных операций. Мастер ушёл с линии с бронями — алерт + протокол замены. Цепочка этапной ломается интрадей (мастер выбыл) — варианты инварианта старта (перенос цепочки / сверхурочный / передача). Слот освободился внутри замороженных 2 ч — предлагается только диспетчеру.

### 2.6. Инварианты
- Клиент не видит окно, под которое нет свободных слотов подходящего мастера.
- Подтверждённая бронь не ломается автоматикой ради более приоритетной (кроме аварий с ручным решением диспетчера).
- Заявка «требует оборудование/машину» не попадает в ленту мастера без оборудования/транспорта.
- Сумма броней ленты ≤ 80% смены при авто-сборке.
- Первые 2 ч ленты автоматика не модифицирует.

### 2.7. Ссылки на ТЗ: 3.7 (нормо-часы), 6.1, 12, 17.3, 17.4, 17.6a, 14 (календарь). **Фаза:** MVP — слоты по нормо-часам + фикс. буфер, жадная сборка лент по зонам, ручная очередь срочных/листа ожидания с подсказками, дежурный, протокол замены; фаза 2 — авто-пересчёт ETA, тепловая карта, перебалансировка, зонное шардирование, churn-метрики, экипажи; фаза 3 — оптимизатор D−1 с обучением, прогноз длительности по истории.

## 3. Авто-распределение, офферы и протокол замены

### 3.1. Назначение
Подбор исполнителя на заявку: фильтрация, ранжирование, последовательные офферы; бродкаст-режим для замен и помощников; автодетект исчезновения мастера и замена за 15 минут.

### 3.2. Входы/выходы
**Входы:** заявка (позиции → skill-теги, требования оборудования/транспорта, зона, окно), состояние мастеров (на линии, слоты, рейтинг/грейд, гео), закреплённый/любимый мастер, чёрные списки. **Выходы:** оффер мастеру (push + экран: категория, адрес/расстояние, окно, состав, **его доля** — от текущей оценки при вилке B2C, финальная — от утверждённой суммы; фото клиента); назначение; событие `order.replacement_required`; санкции невыходов.

### 3.3. Алгоритм/правила
1. **Стандартный подбор (ТЗ 7.3):** (1) фильтр skill-теги позиций; (2) фильтр зона; (3) фильтр загрузка (свободные слоты под окно); (4) фильтр оборудование/транспорт (ТЗ 17.9, 17.3); (5) исключить чёрный список точки/клиента; (6) ранжирование: закреплённый мастер точки / любимый мастер B2C — мягкий приоритет, затем грейд/рейтинг и близость. Первому — оффер **60 сек**; отказ/молчание — следующему. Два отказа подряд без причины — понижение приоритета (ТЗ 7.1). Ручное назначение диспетчера всегда приоритетнее автомата.
2. **Аварийные:** ближайшему свободному с нужным skill, минуя очередь.
3. **Повторная заявка по сервисному напоминанию:** закреплённому мастеру (приоритет); если заблокирован/уволен/в отпуске — обычное распределение (ТЗ 17.12).
4. **Протокол быстрой замены (цель — новый мастер за 15 минут; ТЗ 17.3).** Детект: (а) не нажал «Выехал» за 30 мин до окна (параметр) → авто-пинг push+SMS → нет реакции 10 мин → алерт диспетчеру + автозапуск; (б) кнопка «Не могу поехать» с причиной → протокол сразу; (в) после «Выехал» гео не приближается 15+ мин → мягкий флаг (звонок диспетчера). Замена: флаг «Требуется замена» (красная, вверх доски) → сбор кандидатов по порядку: дежурный → свободные рядом с нужным skill → расчётное завершение в ближайшие 30 мин → снять с гибкой заявки (осмотра) → **экспресс-оффер бродкастом всем сразу, 120 сек, первый принявший забирает** → клиенту немедленно push «Мастер заменён, едет {имя}» или честный сдвиг → 15 мин никто не взял → задача-звонок диспетчеру: сдвиг сегодня или перенос на завтра с приоритетным окном и VIP-контролем.
5. **Санкции исчезнувшему:** уважительная причина (подтверждает диспетчер) — без санкций; невыход без причины — удар по компоненте дисциплины + счётчик: 2-й за 90 дней — снятие с линии и разбор, 3-й — блокировка; невыход с ущербом — денежное удержание. Ранний явный отказ мягче тихого невыхода.
6. **Бродкаст помощника:** «Нужен помощник» → ближайшие свободные + дежурный, фикс + дорога, первый принявший (раздел 1.4.8).

### 3.4. События
**Порождает:** `offer.sent/accepted/declined/expired`, `order.assigned`, `replacement.started/resolved/failed`, `master.no_show{count}`. **Слушает:** `order.approved/created(аварийная)`, `timer.expired` (детекты), `master.declined`, `slot.freed`.

### 3.5. Крайние случаи
Никого после фильтров — заявка в очередь диспетчера + лист ожидания клиенту с честным прогнозом. Оффер принят одновременно двумя (бродкаст) — атомарный CAS на заявке, второму «уже забрали». Мастер принял и сразу «Не могу» — протокол замены без двойной санкции. Заявка с вилкой — доля в оффере от текущей оценки (дисклеймер).

### 3.6. Инварианты
Оффер живёт ровно 60 сек (бродкаст 120 сек), просроченный — не принимается. Заявка не может быть назначена мастеру без нужного skill/оборудования/транспорта даже вручную без явного override с аудитом. Клиент узнаёт о замене от нас (push), а не сам.

### 3.7. Ссылки на ТЗ: 7.1, 7.3, 17.3, 17.9, 17.12. **Фаза:** MVP — фильтры зона+skill, последовательный оффер, протокол замены, дежурный; фаза 2 — ранжирование по авто-рейтингу, грейды.

## 4. Биллинг-движок

### 4.1. Назначение
Единственный источник финансовой истины: двойная запись, план счетов, автоматические проводки всех сценариев жизненного цикла, ведомости выплат, закрытие периода, баланс-чекер. «Всё движение денег — только проводками, никаких правок цифр в полях» (ТЗ 3.6).

### 4.2. Входы/выходы
**Входы:** события статусной машины (Закрыта, Спор, Отменена, локализация, консервация, этапы), вебхуки провайдеров, отметки бухгалтера (оплаты СФ, выписка), действия админа (ручная проводка с двойным подтверждением), календарные триггеры (1-е число, последний день, неделя выплат, месяц амортизации). **Выходы:** Transaction-проводки; обновлённые балансы (SubscriptionAccount, MasterBalance, Receivable, счета компании); СФ; ведомости; алерты баланс-чекера; налоговые регистры.

### 4.3. План счетов (минимальный, ТЗ 8.8)
Денежные средства: расчётный счёт; клиринг провайдеров «деньги в пути»; наличные у мастеров. Авансы полученные (абонентки). Дебиторка клиентов. Кредиторка мастерам (балансы). Долги мастеров (наличные). Кредиторка партнёрским магазинам. Обязательства программы баллов персонала точек; пул подарочных ваучеров (ТЗ 17.14). Выручка. Расходы: доли мастеров, комиссии провайдеров, возмещения, амортизация, резервный фонд ущербов, маркетинговый расход (закупка пула ваучеров).

### 4.4. Проводки по сценариям (формулы и числовые примеры — из ТЗ, обязательны к побитовому воспроизведению)
1. **Единая формула цены (ТЗ 3.7):** цена клиента = базовая B2C × наценка (одна наибольшая из аварийной/ночной/срочной; только к работам) × канальный коэффициент (B2C 1.0 / B2B разовая 1.3 / подписка = 1.3 × (1 − скидка 10%) ≈ 1.17 — ТЗ 18-п.21) − скидка/промокод (последней, к итогу работ клиента). Доля мастера = базовая × наценка × доля (55%, Золото 57%): скидки долю не трогают, наценки увеличивают. Минимальный чек — позиция «Минимальный заказ» добивкой. Выезд: включён при выполнении работ; тарифицируется при отказе после выезда; «Выезд/диагностика» снимается при добавлении работ в ту же заявку; отложенное выполнение — «зачёт диагностики»: счёт = смета − уплаченная диагностика (окно 30 дней), доли мастеров — с фактически оплаченных частей.
2. **Закрытие B2B на абонентке (ТЗ 8.2), пример: база 200 000, эффективный подписной коэффициент k = 1.3 × 0.9 = 1.17, доля 55%, материалы 120 000:**
   (а) Дт Абонентка (авансы) — Кт Выручка: 200 000 × 1.17 = **234 000**;
   (б) Дт Расход «доли мастеров» — Кт MasterBalance: 200 000 × 0.55 = **110 000** (от базовой!);
   (в) Материалы: 120 000 → строка СФ клиенту без наценки (или списание с абонентки — параметр договора) + Кт MasterBalance «возмещение» 120 000.
3. **Частичное покрытие абонентки (ТЗ 8.2 п. 4):** остаток списывается до нуля; непокрытая база = (подписная цена − остаток) ÷ k; в СФ = непокрытая база × наценка B2B. **Пример:** база 200 000, подписная 234 000, остаток 117 000 → списано 117 000; непокрытая база (234 000 − 117 000) ÷ 1.17 = 100 000 → в СФ 100 000 × 1.3 = **130 000**. Формула едина для всех слоёв (биллинг, отчёт, СФ).
4. **B2C онлайн:** вебхук провайдера → Дт «деньги в пути» — Кт Выручка (брутто); комиссия провайдера — отдельная проводка расхода; клиринг T+1/T+2 → перенос на расчётный счёт по реестру со сверкой.
5. **B2C наличные (ТЗ 8.5):** «Принял наличные {сумма}» → Дт «наличные у мастеров» (долг мастера) — Кт Выручка на **всю** сумму. Взаимозачёт в ведомости: к выплате = начисления (доли + возмещения) − удержания − принятые наличные. **Пример:** заявка 300 000 наличными; доля 99 000 + возмещение 120 000 = 219 000 − 300 000 = **−81 000** — мастер вносит разницу через Payme. Лимит наличного долга 2 000 000 (параметр): превышение → обязан внести, иначе автоснятие с линии.
6. **Парные (ТЗ 17.3):** деление по ролям, пример: ведущий 40% + помощник 20% от суммы работ (параметры) — две проводки начисления. Фикс помощника вне парной позиции: расход компании или удержание из доли ведущего (решение диспетчера, аудит); клиенту — никогда.
7. **Минималка дежурства (ТЗ 8.6, 17.3):** проводка за смену дежурства независимо от выездов (день ~200 000 / ночь ~250 000, параметры); доли за выезды — сверху.
8. **Чаевые (ТЗ 7.1, 18.11):** отдельная проводка целиком мастеру, мимо долей; фискализация — вопрос бухгалтеру (8.10).
9. **Резервный фонд ущербов (ТЗ 17.7):** автоматическая проводка % от выручки работ (старт 1–2%, параметр) на счёт «резерв ущербов»; выплаты ущерба — из резерва по резолюции админа; регресс к мастеру — удержание частями ≤ 30% каждой выплаты.
10. **Амортизация (ТЗ 17.9):** ежемесячная проводка «расход амортизации» линейно (стоимость ÷ срок службы) по каждой единице Equipment; удержание остаточной стоимости при утере по вине — 0/50/100% (параметр), частями ≤ 30% выплаты. Фаза 2.
11. **Партнёрские магазины (ТЗ 8.4.4, фаза 2):** закупка по коду → Дт «материалы по заявке» — Кт «кредиторка магазину»; клиенту — по накладной без наценки; ретро-бонус — доход компании отдельной проводкой; еженедельный реестр → оплата → проводка погашения + акт сверки.
12. **Отмены (ТЗ 4.4):** матрица — до «Назначена» и > 2 ч до окна: бесплатно; < 2 ч/после «Выехал»: «ложный вызов» = стоимость выезда (параметр прайса, по умолч. 50 000) → долг B2C / строка СФ B2B; мастеру компенсация 50% выезда из этой суммы; после «В работе»: выезд + фактическая часть (фиксирует мастер, подтверждает диспетчер); скрытая зависимость: клиент повторный выезд не платит, мастеру компенсация от компании (по умолч. 50% выезда); клиент не обеспечил подтверждённый доступ: повторный выезд в счёт клиента, мастеру доля; B2B не пустила в окно: «холостой выезд» в СФ + 50% мастеру. Материалы до отмены — клиент оплачивает по чекам, передаются ему.
13. **Гарантийные (раздел 1.4.5):** доля/удержания по квалификации вины.
14. **Споры/возвраты (ТЗ 4.2):** только refund-API провайдера + сторнирующая проводка; наличный возврат — переводом компании + при вине удержание с мастера.
15. **Месячный цикл (ТЗ 8.3):** 1-е — начисление абонентки (обязательство), авто-СФ → ЭДО, резерв осмотров (график × цена; первоочерёдное списание, никогда не сверхлимит); последний день — свод сверхлимита + материалов → вторая СФ с приложением-автоотчётом; неоплата к 10-му → «приостановлена» (только аварийные, осмотры заморожены); перенос остатка/сгорание — проводками; расторжение: зачёт работами 60 дней, затем сгорает (ТЗ 18.5), ручная проводка с двойным подтверждением.
16. **Ведомость выплат (ТЗ 8.6):** раз в неделю (параметр); разделяет доход (доли) и возмещения (не облагаются); ГПХ — компания налоговый агент (НДФЛ, соцналог — ставки от бухгалтера), самозанятым — брутто с контролем статуса; статус самозанятого перепроверяется периодически (таймер #48, раздел 8.2) — не подтверждён → выплата блокируется до переподтверждения или перевода на ГПХ с удержаниями; экспорт для банка; «выплачено» — проводка. Офбординг: снятие с линии → заморозка выплат → взаимозачёт → акт сверки → финальная выплата/взыскание.
17. **Округление (ТЗ 8.1):** до 100 сум; списания — в пользу клиента, начисления — в пользу мастера (параметр); правило едино на всех слоях, контрольные суммы сходятся копейка в копейку.
18. **Начальные остатки (ТЗ 17.6):** «входящие» проводки на дату запуска (организации, абонентки, дебиторка, балансы мастеров).
19. **Реферальная программа мастеров (ТЗ 17.1, 18 п.10):** триггер — приведённый мастер закрывает свою **20-ю оплаченную заявку** (счётчик по `order.closed` заявок мастера с `referred_by = master_id`); по достижении — проводка бонуса рекомендателю на MasterBalance (сумма — параметр, размер не зафиксирован до решения владельца); идемпотентность — один бонус на одного приведённого, повторное достижение счётчика бонус не порождает; событие `referral.bonus_accrued{referrer_id, referee_id}`.
20. **Релизы прайса и фиксация цен (ТЗ 3.7):** все расчёты биллинга по заявке ведутся из копий цен и коэффициентов, зафиксированных в заявке (`price_list_release_id` + снапшот строк). Какой релиз фиксирует заявка: B2C и B2B-разовая — релиз, активный на момент создания; заявка организации с договором — релиз договора (даты подписания/последнего продления); заявка из дефекта — релиз оценки дефекта (оценка младше 30 дней, иначе переоценка — таймер #26); гарантийная — релиз исходной заявки (смета клиенту = 0, релиз нужен для квалификации вины и долей). Активация нового релиза (`pricelist.release_activated{release_id, activated_at}`) **не порождает ни одной проводки и ни одного пересчёта** по существующим заявкам, договорам и закрытым периодам — железное правило владельца. Доля конкретного мастера с грейдом фиксируется при назначении; расходники «сумки» — по каталогу на момент списания. Срок договора — годовой (цены заморожены весь год) или месячный с авто-продлением (фактически ежемесячный пересмотр; таймер #53); перевод договора на новый релиз — **только** событием продления (`contract.renewed`) с генерацией отчёта «что изменилось в ценах» (ТЗ 18-п.17). Валидатор unit-экономики выполняется по всему релизу до активации (блокирующий); откат — новым релизом из снапшота, без мутации истории.
21. **Программа баллов персонала точек (ТЗ 17.14, MVP):** LoyaltyAccount на сотрудника B2B-организации с включённой опцией договора (руководители — только включённые админом). Начисление по `order.closed`: баллы = % от суммы **работ** (без материалов) заявки, где пользователь — **заявитель** (`applicant_user_id`; телефонные заявки — привязка сотрудника диспетчером в карточке, D-08); авто-заявки (осмотры, из дефектов) и заявки, созданные руководителем за сотрудника, баллов не порождают (процент — персональный override, иначе глобальный, по умолч. 1%; 1 балл = 1 сум) → проводка Дт «маркетинговый расход» — Кт «обязательства программы баллов»; месячный потолок начислений (параметр) — сверх потолка не начисляется; идемпотентность — одно начисление на заявку. Сторно по `order.cancelled` / `dispute_resolved` (в пользу клиента) / refund — обратная проводка на ранее начисленную сумму заявки (баланс может уйти в минус, гасится будущими начислениями). Конвертация при достижении порога (параметр): авто-выдача ваучера из пула (свободный код нужного номинала, FIFO по сроку годности) → списание баллов (Дт «обязательства программы») + списание номинала со счёта «пул ваучеров»; пул кончился/нет номинала — задача админу, конвертация откладывается (баллы копятся). Закупка пула — маркетинговый расход (Дт «маркетинговый расход» — Кт денежные средства) с постановкой номиналов на счёт «пул ваучеров». Реестр выдач — выгрузка бухгалтеру (НДФЛ — открытый вопрос, ТЗ 8.10). Отключение опции организацией: начисления прекращаются немедленно, конвертация доступна ещё 60 дней (параметр), затем остаток сгорает списанием обязательства (таймер #49, раздел 8.2).
22. **Возмещение ГСМ (ТЗ 8.6):** по событию закрытия смены — расчёт нормативного километража: карт-матрица расстояний между адресами выполненных заявок ленты (та же, что считает дорожные буферы планировщика; путь дом↔заявки не считается) × ставка сум/км (параметр) → проводка возмещения в ведомость (**не доход**, отдельная строка, расшифровка по сменам в кошельке мастера); только мастера с флагом «свой авто»; учитывается валидатором unit-экономики как средний транспортный расход. Событие `fuel.reimbursement_accrued`.
23. **Склад (ТЗ 17.16):** проводки прихода (кредиторка поставщику/расход), продажи мастеру (удержание строкой в ведомость частями ≤ 30% выплаты), списания (расход, причина в аудит); остатки склада видны в P&L-контуре админа. Событие `stock.movement`.

### 4.5. Закрытие периода, баланс-чекер, идемпотентность (ТЗ 8.8)
- **Абонентка — аванс, не выручка:** признание выручки в момент списания за закрытую заявку/осмотр; невыбранный остаток — обязательство.
- **Закрытие периода:** lock бухгалтером; проводки в закрытый период запрещены; корректировки — текущим периодом со ссылкой на исходную проводку.
- **Баланс-чекер:** ежедневный автопрогон: сумма проводок каждой операции = 0; сходимость всех счетов; алерт админу при расхождении хоть на 1 сум.
- **Идемпотентность вебхуков:** повторный callback с тем же id платежа не создаёт вторую проводку (уникальный индекс по `(provider, payment_id)`).
- **Налоговые регистры (ТЗ 8.10):** реестр фискальных чеков, реестр СФ, реестр выплат с удержаниями; экспорт бухгалтеру/1С; карта налоговых событий по таблице 8.10 — каждый поток порождает запись регистра.

### 4.6. События
**Порождает:** `billing.transaction_posted`, `invoice.issued/paid/overdue`, `payout.registry_ready/paid`, `subscription.charged/low/exhausted/suspended`, `master.cash_limit_exceeded`, `balance.check_failed`, `period.locked`, `referral.bonus_accrued`, `loyalty.points_accrued/points_reversed/voucher_issued` (п. 4.4-21; новых слушателей не требуется — программа баллов работает от уже перечисленных `order.closed/cancelled/dispute_resolved` и refund-сторно), `fuel.reimbursement_accrued` (п. 4.4-22, по закрытию смены), `stock.movement` (п. 4.4-23). **Слушает:** `order.closed/cancelled/dispute_resolved`, `payment.webhook`, `duty.shift_completed`, `equipment.month_tick`, `damage.resolution`, `store.purchase_recorded`, `contract.renewed`. Событие `pricelist.release_activated` биллинг игнорирует по существующим заявкам (фиксация релиза по правилу п. 4.4-20); его слушают движок уведомлений (мастерам — за 7 дней до активации; организациям — за 10 дней до даты продления их договора, если цены изменятся), приложения (инвалидация кеша цен «от») и кеш публичного API цен лендингов (раздел 12.8).

### 4.7. Крайние случаи
Закрытие заявки при нулевом остатке абонентки — весь объём через формулу частичного покрытия. Сторно в закрытый период — запрещено, корректировка текущим. Вебхук по неизвестной заявке — карантинная очередь бухгалтеру. Отрицательный итог ведомости — задолженность мастера, контроль внесения. Демо-данные не порождают проводок.

### 4.8. Инварианты
Σ дебетов = Σ кредитов каждой операции (двойная запись). Редактирование проводок задним числом запрещено — только сторно. Доля мастера всегда от базовой B2C × наценки, никогда от цены клиента. Критерий приёмки №3: корректные проводки всех четырёх схем оплаты; №7: пять сквозных прогонов сходятся на каждом шаге.

### 4.9. Ссылки на ТЗ: 3.6, 3.7, 4.4, 8.1–8.10, 17.3, 17.6, 17.7, 17.9, 18. **Фаза:** MVP — всё ядро (абонентка, доли, наличные, СФ полуавтоматом, дежурства, чаевые, промокоды, резервный фонд, начальные остатки); фаза 2 — партнёрские магазины, амортизация, пени, импорт выписки, ЭДО.

## 5. Дебиторка и дунинг (AR Engine)

### 5.1. Назначение
Учёт долгов контрагентов, aging, автоматические этапы взыскания, пени, списание. Наличный долг мастера ведётся отдельно и с клиентской дебиторкой не смешивается (ТЗ 8.9).

### 5.2. Входы/выходы
**Входы:** `invoice.issued`, неоплаченные заявки B2C, ложные вызовы, отметки оплат (вручную по выписке — MVP; импорт выписки — фаза 2), производственный календарь. **Выходы:** Receivable-записи; aging-корзины 0–30/31–60/61–90/90+; дашборд (общая АР, DSO, топ-10 должников, динамика); задачи дунинга; претензионные письма PDF; акты сверки; проводки пеней и списаний.

### 5.3. Алгоритм/правила
1. **Источники:** абонентская СФ; сверхлимитная СФ; разовая B2B-СФ; долг B2C (неоплаченная работа, ложный вызов). Каждая — Receivable{источник, сумма, погашено, возраст, этап}.
2. **Частичные оплаты:** FIFO (старейшие СФ первыми); ручное разнесение бухгалтером — с аудитом.
3. **Дунинг B2B (сроки — параметры, считаются по производственному календарю):** T+3 — напоминание бухгалтерии клиента (email + push); T+7 — руководству организации; T+10 — приостановка обслуживания (8.3: только аварийные); T+30 — претензионное письмо (PDF по шаблону одной кнопкой); T+60 — решение о пред-суде/списании (вручную).
4. **Дунинг B2C:** «Ожидает оплаты» → T+24 ч push; T+72 ч SMS + блок новых заявок (параметр: блокировать/предупреждать; аварийная — исключение: оплата долга одновременно или санкция диспетчера); T+30 дн — задача-звонок диспетчера; T+90 — списание в убыток (двойное подтверждение бухгалтер + админ).
5. **Пени (ТЗ 8.9, 18.6):** опция договора, по умолчанию выкл.; типовой договор 0.1%/день, потолок 10%; начисление — решением бухгалтера («гибко, для злостных»), отдельной строкой следующей СФ, проводкой.
6. **Списание безнадёжного:** двойное подтверждение, проводка «убыток», причина в аудит; история клиента сохраняется.
7. **Акт сверки:** PDF по контрагенту за период одной кнопкой, из проводок без ручной сборки.

### 5.4. События
**Порождает:** `ar.stage_changed{T3|T7|T10|T30|T60}`, `ar.org_suspended`, `ar.writeoff`, `ar.penalty_accrued`, задачи в очередь «Позвонить». **Слушает:** `invoice.issued/paid`, `order.awaiting_payment/closed`, `payment.confirmed`, `calendar.day_tick`.

### 5.5. Крайние случаи
Таймер выпадает на праздник — переносится по календарю (иначе авто-действие посреди Курбан-байрама, ТЗ 14). Частичная оплата гасит старейшую СФ, этап дунинга пересчитывается по остатку. Оплата в день приостановки — авто-снятие приостановки. Долг закрыт после претензионного письма — этап сбрасывается, письмо в архиве.

### 5.6. Инварианты
Receivable изменяется только проводками. Приостановка организации не трогает аварийные заявки. Списание невозможно одним человеком. DSO и корзины пересчитываются идемпотентным ночным джобом.

### 5.7. Ссылки на ТЗ: 8.3, 8.9, 4.4, 14. **Фаза:** MVP — реестр АР с aging, акт сверки, ручные отметки оплат, напоминания вручную; фаза 2 — автоматический дунинг, пени, импорт выписки.

## 6. Движок уведомлений

### 6.1. Назначение
Единая точка исходящих коммуникаций: push/SMS/email/автозвонок-задача, очередь с ретраями, лог доставки, двуязычные шаблоны, профили доставки, частотные потолки.

### 6.2. Входы/выходы
**Входы:** доменные события всех сервисов; матрица «событие → получатель → канал» (ТЗ 11, конфигурируемая); язык профиля получателя; наличие FCM-токена; маркетинговое согласие. **Выходы:** отправленные сообщения; NotificationLog со статусом доставки; задачи-звонки в очередь «Позвонить» (для канала «звонок диспетчера»); метрики доставки.

### 6.3. Алгоритм/правила
1. **Каналы:** push (основной, FCM), SMS (критичные + OTP, шлюз Eskiz/PlayMobile), email (СФ, дунинг), «звонок диспетчера» = задача в очередь 17.11 (аварии, эскалации).
2. **Профили доставки:** (а) стандартный — push, критичное дублируется SMS по матрице; (б) **FCM-fallback**: детект отсутствия FCM-токена (Android без Google-сервисов) → критичные уведомления дублируются SMS; (в) **«SMS + веб-ссылка»** для клиентов без приложения (телефонный канал): ключевые события (назначен + окно; выехал + ETA; акт готов; напоминание оплаты) — SMS со ссылкой на веб-карточку (раздел 11); набор SMS-событий — параметр (SMS платные, шлём только важное).
3. **Матрица событий — ТЗ 11 полностью** (заявка создана → диспетчер; назначен/выехал → клиент; смета на утверждение → push, T+24 SMS; вынужденная доп-смета → push+SMS сразу, молчание 2 ч → звонок; авария → push+звонок; акт готов; ожидает оплаты T+24/T+72; пакет дефектов; СФ/абонентка; дунинг; реестр магазинам; выплата мастеру; жалобы; лимит наличных; **баллы персонала (ТЗ 17.14)**: `loyalty.points_accrued` → «Начислены баллы» — push сотруднику точки, низкий приоритет; `loyalty.voucher_issued` → «Ваучер ждёт вас» — push + SMS-дубль с QR-кодом, deep-link на экран баллов; **релизы прайса (ТЗ 3.7)**: за 7 дней до активации релиза → «Смена прайса по вашим категориям» — push мастерам по skill-категориям изменённых позиций (таймер #51); за 10 дней до даты продления договора, если релиз изменится → «При продлении изменятся цены» — push + email руководству организации с авто-отчётом «что изменилось» (таймер #52)). Матрица — конфигурация, не хардкод.
4. **Очередь с ретраями:** экспоненциальный backoff, DLQ с алертом; статусы доставки от FCM/шлюза записываются в NotificationLog.
5. **Локализация:** все шаблоны двуязычные (рус/узб латиница); язык — из профиля получателя; документы — тоже (ТЗ 14).
6. **Частотные потолки:** сервисные (маркетинговые) push — не более 1 в 2 недели на клиента (параметр), отписка в один тап, SMS в маркетинге не используется; операционные — без потолка (ТЗ 17.12).
7. **Волны кампаний:** рассылка сезонных кампаний дозируется ёмкостью планировщика (раздел 7.2).

### 6.4. События
**Порождает:** `notification.sent/delivered/failed`, `calltask.created`. **Слушает:** практически все доменные события по матрице.

### 6.5. Крайние случаи
Нет FCM-токена — fallback SMS для критичных. Нет телефона получателя роли (не заполнен контакт эскалации) — алерт диспетчеру. Дубли событий — дедупликация по `(event_id, recipient, channel)`. Шлюз SMS лёг — ретраи + алерт мониторинга (метрика доставки — ТЗ 14).

### 6.6. Инварианты
Каждое исходящее — запись в NotificationLog. Маркетинговое касание невозможно без согласия и вне потолка. OTP — только SMS. Критичное уведомление не может быть «только push» для получателя без FCM.

### 6.7. Ссылки на ТЗ: 11, 12, 14, 17.11, 17.12. **Фаза:** MVP — push + SMS + профили + лог; фаза 2 — email-дунинг, расширенная матрица эскалаций.

### 7.1. Генератор задач-звонков (очередь «Позвонить», ТЗ 17.11)

### 7.2. Генератор сервисных касаний (ТЗ 17.12)
**Назначение:** превращение сервисного следа техники (ClientAsset + ServiceInterval) в повторную выручку — 4 типа автоматических касаний.
**Входы:** закрытие заявок с зафиксированной техникой; справочник интервалов {тип техники, тип работы, интервал, сезонное окно} (задаёт компания, не мастер); свободная ёмкость планировщика по зонам; маркетинговые согласия. **Выходы:** push-касания; предзаполненные заявки по кнопке «Записаться» (закреплённый мастер — приоритет); гарантийные заявки одной кнопкой; метрики конверсии follow-up.
**Четыре типа:**
1. **Контрольное «как дела»** — через 7–14 дней после ремонта: «Работает нормально?» → «Всё отлично» / «Есть проблема» (→ гарантийная заявка одной кнопкой).
2. **Регламентное напоминание** — по интервалу справочника («6 мес после чистки кондиционера — рекомендуем, ~150 000») → «Записаться» создаёт заявку с предзаполненной позицией и закреплённым мастером.
3. **Сезонная кампания** — сегмент по паспорту («есть кондиционер + не было чистки N мес»); **рассылка волнами с учётом свободной ёмкости планировщика — дневной лимит записей по зонам (параметр)**, иначе кампания сама устраивает перегруз; кондиционеры — апрель, котлы — октябрь.
4. **Конец гарантии** — за 7 дней до истечения: «проверьте работу, исправим бесплатно».
**Гигиена:** согласие — отдельный чекбокс; потолок 1 сервисный push / 2 недели; отписка в один тап; SMS не используется.
**Крайние случаи:** закреплённый мастер недоступен → обычное распределение; клиент отписался → только контрольное «как дела» (операционное, не маркетинг — уточнить с юристом) и конец гарантии. **Инвариант:** волна кампании не создаёт записей сверх дневного лимита зоны. **Фаза:** MVP — фиксация техники + контрольное касание; фаза 2 — интервалы, регламентные, кампании; фаза 3 — OCR шильдиков, предиктив.

### 7.3. Лид-контур лендингов (ТЗ 17.15)
**Назначение:** приём форм трёх лендингов (PRD-06) → лиды и задачи; ни один сабмит не теряется.
**Три формы:** (1) заявка B2C (телефон + категория + описание) → лид + задача в очередь «Позвонить» (7.1) с SLA перезвона 10 мин — та же механика, что пропущенный звонок; дальше телефонный флоу с веб-карточкой (раздел 11); (2) B2B «Получить КП» → лид в реестре B2B-лидов (A-37) + задача «позвонить лиду» админу с SLA (параметр); (3) анкета мастера → кандидат воронки онбординга со статусом «анкета», меткой источника «лендинг» и реф-кодом рекомендателя из ссылки.
**Правила:** идемпотентность сабмита (повторная отправка не плодит лиды); антиспам — honeypot, rate limit N/IP/час и M/номер/сутки (параметры), SMS-код подтверждения номера; UTM: first-touch (cookie 90 дней) + last-touch хранятся в лиде и наследуются созданными из него заявкой/организацией/кандидатом (сквозная аналитика окупаемости рекламы); лид вне зоны покрытия → лид-лист «ждут покрытия» (ТЗ 17.4). **Выделенный телефонный номер лендингов:** заявка из D-08 по нему метится «источник: лендинг-звонок» (tel:-звонки UTM не несут; полный колл-трекинг — фаза 2).
**События:** `lead.created{type: b2c|b2b|master_candidate, utm}`, `order.created_from_lead`, `contract.signed_from_lead`, `master.candidate_created` — слушают аналитика и дашборд. **Фаза:** MVP.

|---|---|---|---|---|---|

## 9. Фото-пайплайн

### 9.1. Назначение
Приём, обработка, хранение и выдача фото/чеков — юридического архива платформы.

### 9.2. Входы/выходы
**Вход:** снимки из приложений (камера-only, без галереи), тип (до/в процессе/после/чек/шильдик/дефект/акт выдачи оборудования/фасад), контекст (заявка/дефект/actor), клиентские метаданные (время устройства, монотонные часы, гео nullable). **Выход:** объект в S3-хранилище; запись метаданных; signed URL по запросу авторизованного участника.

### 9.3. Алгоритм/правила
1. **Клиентская часть (контракт для мобильных):** только камера — живые снимки; сжатие до ~1600px / ~500КБ; **EXIF-очистка**; гео пишется в метаданные записи (не в EXIF), допускается null с флагом «без гео» (подвал — не блокирует конвейер).
2. **Серверная часть:** присвоение серверного таймштампа при получении; для офлайн-загрузок — хранение **обеих** меток (устройство + сервер) и флага «зафиксировано офлайн» (для споров); валидация лимитов (фото клиента при создании — до 5; «до» ≥ 1; «после» ≥ 1); привязка к сущности; идемпотентность по клиентскому UUID.
3. **Хранение:** объектное S3-совместимое; фото закрытых заявок — **вечно** (юридический архив, ТЗ 14); физическое удаление запрещено.
4. **Доступ:** только по signed URL с коротким TTL, только участникам заявки (клиент, мастер, диспетчер, утверждающие, бухгалтер в рамках роли); проверка контекста на каждом запросе выдачи.
5. **Гео-проверка «Приступить»:** ±300 м мягко — несовпадение → флаг диспетчеру.
6. **Режимные объекты:** фото не требуются, вместо них код приёмки + подпись (раздел 1.3).

### 9.4. События
**Порождает:** `photo.uploaded{type}`, `photo.no_geo_flag`, `photo.geo_mismatch`. **Слушает:** `order.closed` (перевод в вечное хранение/архивный класс), `sync.batch` (офлайн-загрузки).

### 9.5. Крайние случаи
Повторная загрузка того же UUID — no-op. Загрузка к чужой/закрытой заявке — 403/409. Битый файл — reject с кодом, конвейер не пропускает статус. Часы устройства врут — серверная метка первична в конфликтах (ТЗ 7.2).

### 9.6. Инварианты
Ни одно фото не принимается из галереи (подпись клиента приложения + признак источника). EXIF отсутствует в хранимом объекте. Фото закрытой заявки неудаляемо. Прямых публичных URL не существует.

### 9.7. Ссылки: ТЗ 3.4, 4.1, 7.1, 7.2, 14. **Фаза:** MVP полностью.

## 10. Офлайн-синк приложения мастера

### 10.1. Назначение
Полная работоспособность приложения мастера без сети (подвалы); гарантированная идемпотентная доставка операций при появлении связи (критерий приёмки №5).

### 10.2. Входы/выходы
**Вход:** батч офлайн-операций: `{client_op_uuid, тип операции (переход статуса/фото/материал/отметка этапа/фиксация техники/наличные), payload, device_time, monotonic_time}`. **Выход:** акты применения per-operation (applied / duplicate / conflict / rejected{code}); серверные времена; обновлённое состояние для клиента.

### 10.3. Алгоритм/правила
1. Каждая офлайн-операция получает **клиентский UUID**; сервер хранит реестр применённых UUID — повторная отправка не создаёт дублей и **не меняет состояние** (строгая идемпотентность).
2. **Двойные метки:** в офлайне фиксируется время устройства + монотонные часы; при синке сервер присваивает время получения; запись помечается «зафиксировано офлайн»; обе метки хранятся для споров.
3. Операции применяются в порядке монотонных часов устройства внутри батча; каждая проходит полную валидацию статусной машины (раздел 1) — офлайн не обходит инварианты.
4. **Конфликты** (состояние на сервере ушло вперёд — диспетчер переназначил, клиент отменил): решение по серверному времени; конфликтная операция отклоняется с кодом, клиенту — актуальное состояние; спорные случаи (работа выполнена по отменённой заявке) — флаг диспетчеру, деньги по матрице 4.4.
5. Индикатор «не синхронизировано» на карточке — по ack-протоколу.
6. Мониторинг очереди синка — метрика с алертом (ТЗ 14).

### 10.4. События
**Порождает:** `sync.batch_received`, `sync.operation_applied/conflicted`, далее — обычные доменные события применённых операций. **Слушает:** —.

### 10.5. Крайние случаи
Батч пришёл дважды (обрыв на ответе) — все операции duplicate, состояние не меняется. Фото догоняют операции — переходы, требующие фото, применяются после догрузки (батч атомарен по зависимостям). Устройство с уехавшими часами — серверное время первично. Оффер в офлайне не принимается (60 сек — только онлайн).

### 10.6. Инварианты
Повторная синхронизация тех же операций не меняет состояние (критерий №5 дословно). Ни одна офлайн-операция не может нарушить граф переходов. Обе временные метки неизменяемы после записи.

### 10.7. Ссылки: ТЗ 7.2, 14, критерий приёмки №5. **Фаза:** MVP полностью.

## 11. Веб-карточка заявки (токенизированный доступ без приложения)

### 11.1. Назначение
Лёгкая веб-страница жизни заявки для телефонных клиентов: статус, карточка мастера, ETA, смета с кнопкой «Согласен», акт с фото, онлайн-оплата, оценка — без установки и регистрации (ТЗ 12 п. 5).

### 11.2. Входы/выходы
**Вход:** переход по ссылке из SMS с токеном. **Выход:** данные карточки; действия клиента (согласие со сметой, оплата, оценка), журналируемые **как санкции клиента**.

### 11.3. Алгоритм/правила
1. **Токен:** одноразовый подписанный (HMAC/JWT c jti), привязан к заявке и телефону, ограниченный срок жизни; каждая SMS несёт свежий токен. Перебор URL не открывает чужую заявку; повторное использование одноразового action-токена — отказ. Просмотровый и action-токены разделены (просмотр может быть многоразовым в TTL — решение реализации; действия — строго одноразовые).
2. **Действия по токену** («Согласен со сметой», оплата, оценка) журналируются в аудит как подтверждения клиента — юридический эквивалент кнопки в приложении.
3. Оплата — редирект на провайдера; подтверждение — вебхуком (раздел 12).
4. Кто не открывает ссылку — ключевые события дублируются SMS-текстом; оплата наличными/QR с экрана мастера; качество — QC-звонком.
5. Языки: рус/узб по профилю. Перевод в приложение — одна ссылка после первой закрытой заявки (параметр, без спама).

### 11.4. События
**Порождает:** `webcard.viewed`, `webcard.estimate_approved` (→ статусная машина как «смета подтверждена»), `webcard.rated`, `payment.initiated`. **Слушает:** `order.*` для рендера актуального состояния.

### 11.5. Крайние случаи
Истёкший токен — страница «ссылка устарела, запросите новую» (звонок/SMS диспетчеру). Заявка закрыта/отменена — карточка в архивном режиме без действий. Двойной клик «Согласен» — идемпотентность по jti.

### 11.6. Инварианты
Ни одно действие по веб-карточке без валидного одноразового токена. Токен одной заявки не даёт доступ к другой. Все действия — в аудите с пометкой канала «веб-карточка».

### 11.7. Ссылки: ТЗ 12 п. 5, 11, 14. **Фаза:** MVP.

## 12. Интеграции

### 12.1. Платёжные провайдеры Payme / Click / Uzum (merchant API)
**Назначение:** онлайн-оплата B2C, погашение долгов, внесение наличных мастером, возвраты.
**Входы/выходы:** создание инвойса/ссылки/QR (QR на экране мастера, push-ссылка клиенту, веб-карточка); вебхуки статусов; refund-запросы; клиринговые реестры.
**Правила:** (1) все возвраты по спорам — **только через refund-API** со сторнирующей проводкой (критерий №6), ручные возвраты запрещены; (2) идемпотентность вебхуков по `(provider, payment_id)` (ТЗ 8.8); (3) комиссия — отдельной проводкой расхода, клиент/мастер видят брутто; (4) клиринг T+1/T+2 через счёт «деньги в пути», автоматическая сверка реестра провайдера с проводками, расхождения — в очередь бухгалтеру; (5) адаптерный слой: единый интерфейс `PaymentProvider{createInvoice, refund, parseWebhook, fetchClearingRegistry}`.
**События:** `payment.confirmed/failed/refunded`, `clearing.matched/discrepancy`. **Крайние случаи:** вебхук раньше редиректа; двойной вебхук; refund по частично оплаченной — компромисс-резолюция суммы. **Фаза:** Payme + Click (с refund) — MVP; Uzum — фаза 2.

### 12.2. ЭДО (didox.uz / faktura.uz)
Адаптерная архитектура (`EdoProvider{sendInvoice, getStatus, sendAct}`), выбор оператора на этапе разработки. СФ с выделением НДС для плательщиков (признак и ставка — в организации); авансовые СФ абонентки — схему уточнить у бухгалтера (ТЗ 8.10). MVP — СФ PDF полуавтоматом без ЭДО; интеграция — фаза 2.

### 12.3. SMS-шлюз (Eskiz / PlayMobile)
Адаптер `SmsProvider{send, deliveryStatus}`; OTP, критичные события, дубли для без-FCM, веб-ссылки. Статусы доставки — в NotificationLog; мониторинг доставки — алерт. Фаза: MVP.

### 12.4. Карты и геокодинг (Yandex Maps / Google)
Геокодирование адресов, матрица времени езды зона→зона (дорожные буферы планировщика), ETA мастера, карта диспетчера. Учесть стоимость лицензии (ТЗ 14). Кеширование матрицы зон. Фаза: MVP (базово), ETA-прогнозы — фаза 2.

### 12.5. Экспорт в 1С
Экспорт проводок, СФ и реестров (фискальные чеки, выплаты с удержаниями) в формате, согласованном с бухгалтером (ТЗ 8.10, 14). Формат уточняется у бухгалтера; фаза 2–3.

### 12.6. ОФД-фискализация (онлайн-ККМ) — заглушка с интерфейсом
Фискальные чеки B2C на полную сумму (работы + материалы) при «Закрыта», включая наличные, принятые мастером (ТЗ 8.10). До подключения — интерфейс `FiscalProvider{registerReceipt(order), registerRefund(order)}` с реализацией-заглушкой, пишущей событие в налоговый регистр как «требует фискализации»; квалификации (ложный вызов — неустойка или услуга? чаевые?) — от бухгалтера. Фаза: интерфейс — MVP, интеграция — бэклог по требованиям ОФД.

### 12.7. Телефония
MVP — обычные номера, ручной ввод; фаза 2 — клик-ту-колл, запись разговоров, автоподстановка звонящего; фаза 3 — proxy-номера. Пропущенный входящий → задача «перезвонить за 10 минут».

### 12.8. Публичный API лендингов (ТЗ 17.15)
Read-only API без аутентификации, только публичные поля: цены «от» по категориям услуг и ставки типов объектов для упрощённого калькулятора B2B — из активного релиза прайса. Кеш с TTL (параметр) + инвалидация по `pricelist.release_activated`; rate limit. Фаза: MVP.

**Общий инвариант интеграций:** внешние вызовы — через очередь с ретраями и circuit breaker; все адаптеры заменяемы конфигурацией; секреты — вне кода.

## 13. Генератор отчётов PDF

### 13.1. Назначение
Все документы собираются из данных системы одной кнопкой, без ручного ввода (критерий №4). Шаблоны двуязычные (рус/узб — выбор в настройках организации/профиле).

### 13.2. Состав документов
1. **Акт по заявке (ТЗ 9.1), 1–2 стр.:** шапка — логотип, номер, точка/клиент, адрес, дата, мастер; тело — фото «до»/«после» сеткой (+«в процессе»), таблица работ (позиция, ед., кол-во, цена, сумма), таблица материалов (название, кол-во, цена, сумма, № чека), итого работ/материалов/всего, канал оплаты, кто и когда утвердил (B2B); строки «зачёт диагностики», «Минимальный заказ», «Консервация» при наличии; отметки «фотофиксация запрещена режимом объекта», «выполнена частично, клиент предупреждён об опасности, от работ отказался» (+фото проблемы); подвал — гарантия (копия срока из заявки), контакты, QR на онлайн-версию.
2. **Месячный отчёт по точке/организации (ТЗ 9.2):** сводка (заявок всего/аварийных/осмотров; суммы работ и материалов; списано с абонентки, сверхлимит; динамика к прошлому месяцу); реестр заявок с QR-ссылками на акты; раздел «Техдолг» (устранено/добавлено/остаток по приоритетам). Автоматически прикладывается к СФ конца месяца — главная продающая ценность B2B.
3. **Отчёт по осмотру (ТЗ 9.3):** чек-лист с отметками, дефекты с фото и оценкой, рекомендации по приоритетам; уходит с пакетом на утверждение; акт включает **обязательные реквизиты представителя точки** — ФИО, должность, способ подтверждения (код/подпись), либо отметку «без представителя».
4. **Претензионное письмо (ТЗ 8.9):** по шаблону, из данных Receivable, одной кнопкой (дунинг T+30).
5. **Акт сверки взаиморасчётов (ТЗ 8.9):** по контрагенту за период, собирается из проводок.
6. **КП калькулятора абонентки (ТЗ 17.2, фаза 2):** расчёт от паспорта объекта (ставки по типу × м² + надбавки за санузлы/кондиционеры/щитки × число точек), прямо из калькулятора; сам калькулятор — инструмент отдела продаж в админке (см. F-025/F-026 PRD-04), вне MVP-скоупа.
7. **Счёт на предоплату B2B разовой (ТЗ 8.3);** СФ (PDF-форма до ЭДО); ведомость выплат (экспорт банку); авто-отчёт к продлению «выбрано vs заплачено» (ТЗ 17.2).

### 13.3. Правила/инварианты
Генерация идемпотентна и воспроизводима (акт закрытой заявки всегда одинаков — данные заморожены копиями цен). Хранение сгенерированных PDF — в объектном хранилище с доступом по signed URL. Демо-данные в документы не попадают. **События:** `report.generated{type}`. **Фаза:** акт, месячный, акт сверки, счёт — MVP; отчёт по осмотру, претензионные, КП калькулятора абонентки — фаза 2 (осмотры MVP — упрощённо).

## 14. Безопасность и доступ

### 14.1. Назначение
Аутентификация, авторизация, контекст-проверки, защита данных.

### 14.2. Правила
1. **Аутентификация:** телефон + OTP SMS; JWT с ротацией (ТЗ 14). Смена номера — только через поддержку с верификацией личности; передача аккаунта мастера запрещена.
2. **Контекст-проверки на каждом эндпоинте:** роль + organization_id + location_id из привязок пользователя; сотрудник аптеки не получит чужие данные даже прямым запросом к API (ТЗ 14). Мульти-роли: активный контекст выбирается при входе.

## 16. Рейтинговый движок мастеров (Rating Engine)

### 16.1. Назначение
Единая точка расчёта рейтинга 0–100 и грейда каждого мастера: агрегирует пять взвешенных компонент по скользящему окну, применяет байесовское сглаживание оценок клиентов для защиты новичков от единичных плохих оценок, присваивает грейд и передаёт его в приоритет ранжирования распределения (раздел 3.3 п.1) и в долю мастера в проводках биллинга (раздел 4.4 п.1, п.8). MVP — рейтинг и грейд выставляются вручную диспетчером/админом с обязательным комментарием; формулы уже фиксируются и считаются в фоне на реальных событиях, чтобы копить историю с первого дня; официальная публикация авто-расчёта — фаза 2 (ТЗ 7.4).

### 16.2. Входы/выходы
- **Входы:** события статусной машины за скользящее окно 56 дней (отметка «Приступить» относительно назначенного окна — раздел 1; оценки клиентов 1–5 — раздел 1.4.1 «Оценена клиентом»; модерация фото/чек-пакетов диспетчером с первой попытки — раздел 9; гарантийные переделки по вине мастера — раздел 1.4.5; исходы офферов — раздел 3); ручная установка рейтинга и комментарий (MVP); апелляции мастера на оценку/санкцию; резолюции споров (оценки по спорам, выигранным мастером, исключаются из расчёта).
- **Выходы:** MasterRating{score 0–100, компоненты, грейд, дата пересчёта}; событие `rating.recalculated`; флаги санкций (разбор/блокировка); значение доли для биллинга и приоритет для планировщика/авто-распределения.

### 16.3. Алгоритм/правила (формулы и числовой пример — из ТЗ 7.4, обязательны к побитовому воспроизведению)
1. **Частота и окно:** пересчёт еженедельно (таймер #44, раздел 8.2), скользящее окно последних 56 дней; каждая из пяти компонент нормируется в шкалу 0–100, итог — взвешенная сумма компонент.
2. **Пунктуальность, 25%** = (число заявок с отметкой «Приступить» внутри назначенного окна ÷ всего заявок окна) × 100.
3. **Оценки клиентов, 30%, с байесовским сглаживанием** = средняя оценка окна × 20; при **< 10 оценок** в окне — сглаживание к 4.5 (эквивалент 10 «виртуальных» оценок): `R_bayes = (Σ реальных оценок + 10 × 4.5) / (n + 10)`, компонента = `R_bayes × 20`. **Пример:** у мастера 4 оценки за окно: 5, 4, 5, 3 (Σ = 17) → `R_bayes = (17 + 45) / (4 + 10) = 62 / 14 ≈ 4.43` → компонента ≈ **88,6**; без сглаживания при одной случайной оценке «2» компонента рухнула бы до 40, со сглаживанием `(2 + 45) / 11 ≈ 4.27 → 85,4` — одна злая оценка не убивает новичка.
4. **Качество фотофиксации, 15%** = (число фото/чек-пакетов, принятых диспетчером с первой попытки ÷ всего пакетов окна) × 100.
5. **Отсутствие переделок, 20%** = `100 − 25 × (число гарантийных переделок по вине мастера в окне)`, минимум 0 (4-я и последующие переделки за окно обнуляют компоненту).
6. **Дисциплина офферов, 10%** = (число принятых офферов ÷ всего офферов окна) × 100; отказы с уважительной причиной, подтверждённой диспетчером, исключаются из знаменателя (не считаются ни принятым, ни отказом).
7. **Итоговая формула:** `score = 0,25×Пунктуальность + 0,30×Оценки + 0,15×Фото + 0,20×Переделки + 0,10×Офферы`. **Числовой пример:** пунктуальность 96, оценки (сглаж.) 96, фото 100, переделки 90, офферы 80 → `score = 0,25×96 + 0,30×96 + 0,15×100 + 0,20×90 + 0,10×80 = 24 + 28,8 + 15 + 18 + 8 = 93,8` → грейд Золото.
8. **Грейды и доля (ТЗ 7.4, 18 п.9; см. раздел 4.4 п.1):** Бронза `< 70` (доля 55%); Серебро `70–85` (доля 55%); Золото `> 85 И ≥ 100 закрытых заявок за всё время` (доля **57%** вместо 55%, включено решением владельца, действует с запуска авто-рейтинга — фаза 2). Порог по числу заявок защищает от «Золота» на статистически малой выборке. Грейд также даёт мягкий приоритет в ранжировании распределения (раздел 3.3 п.1).
9. **Испытательный период:** новый мастер стартует с рейтингом **60** без грейда; первые **20 заявок** — нижние пороги санкций (п.11) не применяются, но **100% его фото-пакетов** идут на модерацию диспетчера (не выборочно, раздел 7.1 «обязательный QC»); грейд не присваивается до завершения испытательного периода. Окно 56 дней не сбрасывается при выходе из испытательного периода — просто пороги санкций начинают применяться.
10. **Гигиена оценок:** оценка клиента 1–2 автоматически открывает тикет диспетчеру (раздел 7.1) — сама оценка в расчёт входит, тикет не меняет формулу; оценки по спорам, разрешённым в пользу мастера (раздел 1.3 п.6), исключаются из расчёта; апелляция мастера на оценку/санкцию — решение диспетчера пишется в аудит, при удовлетворении оценка исключается со следующего пересчёта (не задним числом текущего).
11. **Санкции по рейтингу (не денежные):** `score < 40` → разбор с диспетчером (флаг в карточке мастера); `score < 25` → блокировка (мастер не получает офферы, экран блокировки при входе). Денежных штрафов за рейтинг нет — только приоритет; денежные удержания — только за конкретные события (гарантийная переделка по вине, невыход с ущербом — раздел 4.4).
12. **MVP-режим:** рейтинг и грейд выставляются вручную диспетчером/админом с обязательным комментарием (аудит); формулы считаются в фоне на реальных событиях для накопления истории, но не публикуются как «официальный» рейтинг до включения feature flag авто-рейтинга (раздел 15.5).

### 16.4. События
**Порождает:** `rating.recalculated{master_id, score, grade, components}`, `rating.probation_ended`, `rating.sanction_triggered{level}`, `rating.appeal_resolved`. **Слушает:** `order.started` (пунктуальность), `order.rated` (оценки), `photo.uploaded`/события модерации (фото), `order.dispute_resolved` (переделки и исключение оценок по спорам), `offer.accepted/declined/expired` (дисциплина), `timer.expired` (таймер #44).

### 16.5. Крайние случаи
Мастер без заявок в окне — компоненты не пересчитываются, рейтинг сохраняется предыдущим значением (простой не обнуляет рейтинг). Ровно 10 оценок в окне — сглаживание не применяется (граница строгая: `< 10`, не `≤`). Спор разрешён в пользу мастера после уже прошедшего пересчёта — исключение оценки применяется на следующем цикле, а не задним числом. Выход из испытательного периода в середине окна 56 дней — окно не сбрасывается, пороги санкций начинают действовать с момента выхода.

### 16.6. Инварианты
Доля мастера в проводках закрытия (раздел 4.4 п.1) берётся из грейда, зафиксированного на момент закрытия заявки копией — последующий пересчёт рейтинга не меняет уже проведённые проводки. Пересчёт всегда обрабатывает все пять компонент вместе — частичный пересчёт запрещён. Санкция блокировки применяется только по результату планового пересчёта, не «на лету» посреди окна.

### 16.7. Ссылки на ТЗ: 7.1 (гигиена оценок, обязательный QC испытательных), 7.4 (формулы, грейды, испытательный период), 18 п.9 (Золото 57%). **Фаза:** MVP — ручной рейтинг с комментарием, формулы фиксируются и считаются в фоне; фаза 2 — автоматический расчёт и публикация, влияние на ранжирование распределения (раздел 3.7).

## 17. Критерии приёмки системы (ТЗ 15)

1. Заявка не переходит в «Выполнена» без фото «после» — **на уровне API**, не только UI.
2. Смета выше лимита точки не запускается в работу ни при каком сценарии без записи об утверждении в аудите.
3. Закрытие заявки порождает корректные проводки во всех четырёх схемах оплаты (абонентка / СФ / онлайн / наличные) — сверка тест-кейсами с числовыми примерами разделов 8.2, 8.5 ТЗ.
4. Акт PDF собирается из данных заявки без ручного ввода.
5. Мастер завершает заявку в подвале без сети; данные доезжают без потерь и дублей; повторная синхронизация тех же операций не меняет состояние.
6. Возврат по спору проводится через refund-API провайдера и порождает корректную сторнирующую проводку.
7. **Пять сквозных прогонов без ручных правок данных:** (а) B2C онлайн; (б) B2C наличные (включая взаимозачёт в ведомости); (в) B2B абонентка; (г) B2B сверхлимит (формула частичного покрытия: 117 000 списано, 130 000 в СФ на примере ТЗ 8.2); (д) B2B разовая с предоплатой — от создания заявки до ведомости выплат и налоговых регистров; суммы сходятся на каждом шаге.
Дополнительно (выводится из инвариантов ТЗ, рекомендуется в контракт): ежедневный баланс-чекер зелёный на всех прогонах; переходы вне графов всех 8 типов отклоняются API; этапная заявка не стартует без подтверждённой цепочки; чужая заявка недоступна ни по одному эндпоинту и ни по одному веб-токену; таймер эскалации не срабатывает в нерабочий день справочника.
