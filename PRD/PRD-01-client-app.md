# PRD-01. Мобильное приложение «Клиент» + веб-карточка заявки

**Продукт:** платформа технического сервиса USTAPRO (Ташкент, Узбекистан)
**Документ:** Product Requirements Document приложения «Клиент» (Flutter, iOS/Android) и лёгкой веб-карточки заявки для телефонных клиентов
**Основание:** ТЗ USTAPRO v2.25 (единственный источник истины; ссылки на разделы ТЗ приведены в каждом экране)
**Дата:** июль 2026

---

## 1. Обзор

### 1.1. Назначение
Приложение «Клиент» — единая точка входа для всех заказчиков платформы: от физлица, вызывающего сантехника, до директора сети аптек, утверждающего сметы по 12 точкам. Приложение закрывает полный клиентский цикл: создание заявки → отслеживание мастера → санкционирование работ (сметы, доп-работы, апсейлы) → оплата → оценка → гарантия → постпродажные касания. Для B2B добавляются контуры утверждений, лимитов, техдолга, финансов и отчётов (ТЗ §6).

Веб-карточка заявки — лёгкий веб-интерфейс без установки и регистрации для клиентов телефонного канала (ожидается, что половина B2C будет звонить, а не ставить приложение — ТЗ §12): SMS со ссылкой, содержащей одноразовый подписанный токен, даёт статус, ETA, подтверждение сметы, акт, онлайн-оплату и оценку.

### 1.2. Роли пользователей (ТЗ §2.2)
| Роль | Что делает в приложении |
|---|---|
| B2C-клиент (физлицо) | Создаёт свои заявки, подтверждает сметы и доп-работы, платит, оценивает, спорит, гарантийные обращения, «Моя техника» |
| Сотрудник точки | Создаёт заявки от имени своей точки («Сообщить о поломке»), следит за статусом и ETA, называет мастеру одноразовый код приёмки (или подтверждает приёмку в приложении без кода — единый механизм, см. C-34). Денег и цен сверх лимита **не видит** (настройка организации) |
| Руководитель точки | Всё как сотрудник + лента всех заявок точки, утверждение смет в пределах своего порога, техдолг точки, лимиты, месячные отчёты точки |
| Руководитель организации (АХО/директор сети) | Все точки: дашборд-светофор, центр утверждений (сметы, доп-сметы, пакеты дефектов), техдолг организации, финансы (абонентка/СФ/акт сверки), лимиты и пользователи точек, график осмотров, отчёты |
| Владелец организации | Режим «только наблюдение»: дашборд, деньги, техдолг — без операционных кнопок. Единственное исключение — участие во **втором утверждении** сверхпороговых смет при включённом двойном утверждении (ТЗ §5.2, §6.5) |

### 1.3. Принцип «одно приложение, интерфейс собирается по роли» (ТЗ §2.2)
Роль — свойство аккаунта, не отдельное приложение. Пользователь входит по телефону + OTP; сервер возвращает список привязок `{роль, organization_id?, location_id?}`. Клиент рендерит навигацию, экраны и права из активного контекста. Все проверки прав дублируются на API (каждый эндпоинт проверяет контекст организации/точки — ТЗ §14): скрытие кнопки в UI не является защитой.

### 1.4. Выбор контекста при нескольких ролях
Один человек может быть руководителем точки А и сотрудником точки Б. При входе (и в любой момент через профиль) он выбирает активный контекст (экран C-05). Push-уведомления приходят по всем контекстам аккаунта; тап по пушу автоматически переключает контекст на нужный и открывает целевой экран (deep-link). Если контекст один — экран выбора пропускается.

### 1.5. Ключевые продуктовые принципы, влияющие на UI (ТЗ §1)
1. Ни одна платная работа без санкции клиента: каждая кнопка «Утвердить»/«Согласен» пишется в аудит (кто, когда, сумма, устройство).
2. B2C-смета до выезда — вилка «от–до»; обязательством становится сумма, подтверждённая клиентом на месте (§4.1).
3. Вынужденные доп-работы и апсейл — два разных механизма, не смешиваются ни в интерфейсе, ни в правилах (§4.6).
4. Апсейл никогда не давит: отказ не влияет на завершение исходной работы (§4.6).
5. Оплата B2C собирается на месте до ухода мастера; «Ожидает оплаты» — исключение по санкции диспетчера (§4.1, §7.1 шаг 6).

## 3. Спецификации экранов

### 3.1. Онбординг и вход

#### C-01. Splash / выбор языка (онбординг-слайды удалены, v2.25)
- **Назначение:** запуск, выбор языка; проверка минимальной версии (force update). Онбординг-слайды удалены (ТЗ §17.17 п.1): ценность сервиса показывают пустые состояния, после выбора языка — сразу вход по телефону.
- **Кто видит:** все, первый запуск.
- **Точки входа:** запуск приложения; deep-link из SMS/push (после проверки сессии).
- **Данные:** логотип, версия.
- **Элементы и действия:** переключатель «Русский / Oʻzbekcha» (сохраняется в профиль после входа — язык всех коммуникаций, ТЗ §14); кнопка «Начать» → C-02.
- **Состояния:** загрузка (проверка токена сессии и минимальной версии); ошибка сети — retry; версия ниже минимальной — блокирующий экран «Обновите приложение» с кнопкой в стор (ТЗ §14 force update).
- **Переходы:** активная сессия → C-05/главный экран контекста; нет сессии → C-02.
- **Крайние случаи:** deep-link при отсутствии сессии — сохранить цель, открыть после входа.
- **ТЗ:** §6, §14, §17.17.

#### C-02. Вход по телефону
- **Назначение:** идентификация по номеру телефона (логин).
- **Кто видит:** все неавторизованные.
- **Точки входа:** C-01; выход из аккаунта; протухший refresh-токен.
- **Данные:** поле номера с маской +998 XX XXX-XX-XX.
- **Элементы и действия:** поле телефона; кнопка «Получить код» (активна при валидном номере); ссылка «Не могу войти» → телефон поддержки/диспетчера (смена номера — только через поддержку с верификацией личности, ТЗ §14).
- **Состояния:** загрузка (отправка SMS); ошибка шлюза — «Не удалось отправить код, попробуйте позже»; нет сети — баннер офлайна, кнопка неактивна; троттлинг повторных запросов.
- **Переходы:** успех → C-03.
- **Крайние случаи:** заблокированный аккаунт (чёрный список клиентов, ТЗ §17.5) — сообщение «Аккаунт заблокирован, обратитесь в поддержку»; ввод номера, ранее известного только по телефонному каналу, — история и паспорт техники подтягиваются в тот же аккаунт.
- **ТЗ:** §6, §14, §17.5.

#### C-03. Ввод OTP + согласия (объединён с C-04, v2.25)
- **Назначение:** подтверждение владения номером; для новых пользователей здесь же — сбор согласий чекбоксами (отдельный экран согласий убран, ТЗ §17.17 п.1).
- **Кто видит:** все на входе.
- **Точки входа:** C-02.
- **Данные:** маскированный номер, поле 4–6 цифр, таймер повтора; для новых пользователей — тексты согласий (ссылки на полные версии).
- **Элементы и действия:** авточтение SMS-кода (Android SMS Retriever); «Отправить код повторно» (после таймера 60 с); «Изменить номер» → C-02; для новых пользователей — чекбокс 1 «Согласен на обработку персональных данных» (**обязательный**, ЗРУ-547) и чекбокс 2 «Согласен получать сервисные и маркетинговые уведомления» (**отдельный, необязательный** — отписка в один тап в C-30, ТЗ §17.12); вход завершается только при отмеченном чекбоксе 1.
- **Состояния:** загрузка (проверка кода); неверный код — inline-ошибка, счётчик попыток; исчерпаны попытки — временная блокировка входа; нет сети — retry.
- **Переходы:** → C-05 (или сразу главный, если контекст один).
- **Крайние случаи:** SIM-swap-риск закрывается не здесь, а повторной аутентификацией PIN/биометрией на крупных утверждениях (C-36, ТЗ §5.2); существующий пользователь при изменении текста согласий — пересмотр на C-04.
- **ТЗ:** §6, §14, §17.17.

#### C-04. Согласия (объединён с C-03, v2.25)
- **Назначение:** юридически корректный сбор согласий по закону РУз «О персональных данных» (ЗРУ-547). В онбординге отдельного экрана нет — чекбоксы собираются на экране OTP (C-03, ТЗ §17.17 п.1); экран остаётся для пересмотра согласий из профиля и при изменении текста согласий.
- **Кто видит:** существующие пользователи — при изменении текста согласий; все — из профиля (пересмотр).
- **Точки входа:** C-30 (пересмотр); принудительно после входа при изменении текста согласий.
- **Данные:** текст оферты и политики персданных (ссылки на полные версии).
- **Элементы и действия:** чекбокс 1 «Согласен на обработку персональных данных» — **обязательный**; чекбокс 2 «Согласен получать сервисные и маркетинговые уведомления» — **отдельный, необязательный** (ТЗ §17.12: маркетинговое согласие — отдельный чекбокс; отписка в один тап в C-30); кнопка «Продолжить» (активна при чекбоксе 1).
- **Состояния:** загрузка текстов; ошибка сети — кешированные тексты либо retry.
- **Переходы:** → возврат в C-30 либо главный экран контекста.
- **Крайние случаи:** отказ от обязательного согласия — работа невозможна, экран не пропускается; отказ от маркетинга не блокирует ничего и отключает только сервисные push-кампании (операционные push идут всегда).
- **ТЗ:** §14, §17.12, §18 (решение №14 исходного списка).

#### C-05. Выбор роли/контекста
- **Назначение:** выбор активного контекста при нескольких ролях.
- **Кто видит:** пользователи с 2+ привязками ролей; с одной — экран пропускается.
- **Точки входа:** после входа; переключатель контекста в C-30; автоматически при тапе по push другого контекста.
- **Данные:** карточки контекстов: «Личный (B2C)», «{Организация} — {Точка} — Сотрудник», «{Организация} — Руководитель» и т.д.; бейджи непрочитанного (ожидающие утверждения, активные заявки).
- **Элементы и действия:** тап по карточке — вход в контекст; чекбокс «Запомнить выбор» (входить сразу в этот контекст).
- **Состояния:** загрузка списка привязок; ошибка — retry; пустой список ролей (аккаунт есть, привязки удалены) — экран «Нет доступных ролей, обратитесь в поддержку».
- **Переходы:** B2C → C-06; сотрудник → C-31; рук. точки → C-31/C-35; рук. орг. → C-40; владелец → C-48.
- **Крайние случаи:** роль отозвана админом, пока пользователь в контексте, — при первом же запросе API вернёт 403, приложение выбрасывает на C-05 с тостом «Доступ изменён».
- **ТЗ:** §2.2, §14.

### 3.2. B2C: главный экран и создание заявки

#### C-06. Главный экран B2C
- **Назначение:** хаб физлица: создать заявку, увидеть активную, попасть в аварийный сценарий.
- **Кто видит:** B2C.
- **Точки входа:** вход/выбор контекста; таббар.
- **Данные:** активная заявка (мини-статус-бар: статус, окно, имя мастера); последняя закрытая заявка (для карточки «Повторить»: работа, мастер, адрес); список категорий; последний адрес.
- **Элементы и действия:** большая кнопка **«Вызвать мастера»** → C-07; карточка **«Повторить: {последняя закрытая работа}, {мастер}»** (v2.25, ТЗ §17.17 п.2; MVP) — тап → сразу выбор слота → «Отправить»: повтор заявки в 2–3 тапа с тем же адресом, работами и (при доступности) тем же мастером; плитки категорий (сантехника, электрика, кондиционеры…) → C-07 с предвыбором; баннер **«Аварийная ситуация?»** → C-07 с флагом «аварийная» (заявка минует оценку, идёт ближайшему свободному мастеру — ТЗ §4.3); карточка активной заявки → C-14; таббар: Главная / История (C-24) / Техника (C-28, фаза 2) / Профиль (C-30).
- **Состояния:** загрузка — скелетоны; пусто (нет активных заявок) — акцент на кнопке вызова; ошибка/нет сети — кеш последнего состояния + баннер «Нет соединения», создание заявки недоступно офлайн.
- **Переходы:** см. выше.
- **Крайние случаи:** непогашенный долг (ложный вызов, неоплата) — блокирующий баннер «Оплатите задолженность {сумма}» с кнопкой онлайн-оплаты; создание новых заявок заблокировано (параметр: блокировать/предупреждать), **кроме аварийной** — она принимается при одновременной онлайн-оплате долга либо по санкции диспетчера (ТЗ §4.4); рекомендация-апсейл в статусе «отложено» — ненавязчивая карточка «Отложенные рекомендации».
- **ТЗ:** §6.1, §4.3, §4.4.

#### C-07. Шаг 1 «Что сломалось» (объединён с C-08, C-09, v2.25)
- **Назначение:** первый из трёх шагов визарда (ТЗ §17.17 п.1): категория + типовые работы + фото (до 5) + описание — один экран, поиск работ сверху.
- **Кто видит:** B2C.
- **Точки входа:** C-06 (кнопка, плитка, аварийный баннер).
- **Данные:** активные категории прайса; лицензируемые категории (газ, лифты) до подписания договора с лицензиатом в прайсе закрыты — не показываются или показываются с вежливым отказом и рекомендацией (ТЗ §17.8); позиции прайса выбранной категории: название, ед. изм., цена «от» (вилка B2C), признаки «этапная» и «парная» (цена уже включает второго исполнителя, ТЗ §3.7); миниатюры добавленных фото; поле описания.
- **Элементы и действия:** строка поиска по названию работы — сверху экрана (результат сразу выбирает категорию и работу); сетка категорий; после выбора категории — список работ с чекбоксами и степперами количества, растущий подытог «от {сумма}»; блок фото «Добавить фото» до 5 (камера или галерея — для клиента, в отличие от мастера, галерея разрешена), удаление фото; поле описания (обязательное при «не знаю, что сломалось»); тумблер «Аварийная ситуация» (с подсказкой, что считается аварией); «Не знаю, что сломалось» — пропуск выбора работ: смета = позиция «Выезд/диагностика», объём оформит мастер на месте доп-сметой — штатный сценарий (ТЗ §4.1); ссылка «Не нашли работу? Опишите словами» (заявка-диагностика); кнопка «Далее».
- **Состояния:** загрузка прайса; ошибка — retry с кешем последней версии прайса; кеш цен «от» инвалидируется по событию активации релиза прайса; при расхождении кеша с сервером на сабмите — пересчёт с уведомлением клиента (ТЗ §3.7); пусто по поиску — «Ничего не нашли, опишите проблему словами»; сжатие/загрузка фото (клиентское сжатие до ~1600px/500КБ, EXIF-очистка — ТЗ §14) с прогрессом, ошибка загрузки фото — повтор поштучно; нет сети — создание недоступно.
- **Переходы:** → C-10 (шаг 2 «Где и когда»); аварийная → сокращённый флоу (фото не обязательны, слот не выбирается) → C-10 → подтверждение.
- **Крайние случаи:** категория закрыта после кеширования — валидация на сабмите; сумма ниже минимального чека — предупреждение о позиции «Минимальный заказ» с добивкой, клиент видит её до утверждения (ТЗ §3.7); выбрана этапная позиция — бейдж «Работа в несколько визитов», детали на итоге (C-13/C-18); отказ в доступе к камере — предложить галерею; 5 фото — кнопка добавления неактивна.
- **ТЗ:** §6.1, §3.4, §3.7, §4.1, §4.3, §14, §17.8, §17.17.

#### C-08. Создание заявки: работы — объединён с C-07 (v2.25)
Секция «Работы» шага 1 «Что сломалось». Спецификация — в C-07; ID сохранён для преемственности ссылок (перенумерация не проводилась).

#### C-09. Создание заявки: фото и описание — объединён с C-07 (v2.25)
Секция «Фото и описание» шага 1 «Что сломалось». Спецификация — в C-07; ID сохранён для преемственности ссылок.

#### C-10. Шаг 2 «Где и когда» (объединён с C-12, v2.25)
- **Назначение:** второй шаг визарда (ТЗ §17.17 п.1): адрес и время — один экран. Адрес — **только улица/дом** с гео-автоопределением и пином: для планирования выезда этого достаточно; детали (квартира, подъезд, этаж, домофон, лифт) запрашиваются после назначения мастера на C-50. **Исключение:** для категорий/позиций с признаком «парная» или «требует оборудование» на шаге 2 дополнительно спрашиваются **этаж и наличие лифта** — они нужны планировщику **до** назначения (транспортный фильтр и подбор пары, ТЗ §17.3); для остальных категорий эти поля остаются в C-50 после назначения.
- **Кто видит:** B2C.
- **Точки входа:** C-07.
- **Данные:** карта (пин) с автоопределением по гео; сохранённые адреса клиента; поле «Улица, дом»; только реально доступные двухчасовые окна из планировщика (skill + зона + свободные слоты, ТЗ §17.3): «сегодня 16:00–18:00, 18:00–20:00, завтра с 10:00» — никогда не показывается то, под что нет ёмкости.
- **Элементы и действия:** выбор из «Моих адресов» (C-29) — для сохранённого адреса детали доступа подставляются в заявку автоматически; пин на карте + гео-автоопределение; чекбокс «Сохранить адрес»; чипы доступных окон; карточка **«Срочно»**: «ближайший освободившийся мастер, +{коэффициент}% к работам» (по умолч. +30%; только к работам, не к материалам) с правилом честности: «не начнём за {X=3} ч — наценку снимем автоматически» (ТЗ §17.3); карточка **«Бесплатный лист ожидания»**: честный прогнозный интервал «ориентировочно 15:30–17:30, уточним, когда мастер освободится»; для категорий с признаком «требует общих зон» — **чек-лист внешних зависимостей bottom-sheet'ом этого шага** (C-11); для категорий/позиций с признаком «парная» или «требует оборудование» — поля **«Этаж»** и **«Есть лифт?»** (да/нет) прямо на шаге 2 (нужны планировщику до назначения, ТЗ §17.3); «Далее».
- **Состояния:** загрузка карты и расчёта окон; нет гео-разрешения — ручной ввод; ошибка геокодера — ввод адреса текстом; нет окон сегодня — честно показываются завтрашние; ошибка — retry.
- **Переходы:** → C-13 (шаг 3 «Итог»); аварийная → экран подтверждения (слот не выбирается — мастер едет сейчас).
- **Крайние случаи:** **адрес вне зоны покрытия** — заявка не создаётся; экран «Мы пока не работаем в этом районе», телефон и адрес сохраняются в лид-лист «ждут покрытия», кнопка «Сообщить, когда появитесь» (ТЗ §17.4); клики по недоступным/отсутствующим окнам логируются как **упущенный спрос** (метрика бизнеса, ТЗ §17.3); ночные окна (22:00–07:00) для плановых B2C не бронируются — ночь только аварии/срочные за ночной тариф (ТЗ §17.6a); наценки не стакаются: ночью «Срочно» не предлагается (действует ночной коэффициент, применяется одна наибольшая наценка); выбрана этапная позиция — вместо одного окна подбирается цепочка сессий с допустимыми окнами пауз (превью в C-13/C-18); слот, занятый за время раздумий, — валидация на сабмите, пересчёт окон; запись на визит-ремонт после ранее оплаченного выезда-осмотра — баннер «Стоимость осмотра будет зачтена в итоговую стоимость работ» (правило зачёта диагностики, ТЗ §3.7).
- **ТЗ:** §6.1, §17.3, §17.4, §17.6a, §17.17.

#### C-11. Чек-лист доступа (общие зоны / ТСЖ) — bottom-sheet шага 2 (v2.25)
- **Назначение:** профилактика холостых выездов для категорий, требующих доступа к стояку/подвалу/крыше/щитовой (ТЗ §4.1 «Заблокировано третьей стороной»). С v2.25 — не отдельный экран, а bottom-sheet шага C-10 (ТЗ §17.17 п.1); ID сохранён.
- **Кто видит:** B2C, только для категорий с признаком «требует общих зон».
- **Точки входа:** открывается автоматически на шаге C-10.
- **Данные:** вопросы чек-листа: «Нужно ли отключение стояка?», «Нужен ли доступ к подвалу/крыше/щитовой?».
- **Элементы и действия (объект НЕ подключён — прежнее поведение v2.25):** переключатели да/нет; при «да» — подсказка «Договоритесь с ТСЖ/УК заранее — иначе мастер приедет впустую» и поле **«Доступ подтверждён на {дата/время}»** (дата-пикер) — заявка планируется на подтверждённое время; вариант «Доступ ещё не подтверждён» — предупреждение о правилах повторного выезда (если клиент подтверждал доступ и не обеспечил — повторный выезд платный, ТЗ §4.4); «Готово» — возврат к слотам C-10.
- **Состояния:** статический sheet; валидация: при «да» выбран один из вариантов.
- **Переходы:** закрытие sheet → C-10 (при подтверждённом времени доступа слоты предлагаются вокруг него).
- **Элементы и действия (объект ПОДКЛЮЧЁН, `connection_status = active` — M7, DEV-15 §10.3):** смысл переворачивается. Вместо просьбы договориться — плашка **«Доступ запросим за вас»**: «{Название УК} обычно отвечает за {N} часов». Клиент выбирает **предпочтительное окно**, а не подтверждённое время; система создаёт наряд-допуск (DEV-10 §7) и ставит **мягкий холд** слота. Чек-лист сокращается до одного информационного блока: какие зоны потребуются и потребуется ли отключение ресурса — с предупреждением «на время работ будет отключена холодная вода в вашем стояке, соседей мы предупредим».
- **Состояния:** статический sheet; валидация: при «да» выбран один из вариантов. Для подключённого объекта — состояние «УК не отвечает дольше обычного» при приближении SLA.
- **Переходы:** закрытие sheet → C-10 (при подтверждённом времени доступа слоты предлагаются вокруг него); для подключённого объекта → C-13, статус согласования виден в C-14.
- **Крайние случаи:** зависимость всплыла на месте, хотя чек-лист пройден «нет», — повторный выезд клиент не оплачивает (ТЗ §4.4). **Подключённый объект:** отказ УК в допуске — заявка не отменяется, клиенту предлагается перенос или отмена без штрафа; отзыв согласованного допуска после выезда мастера — клиент не платит холостой выезд ни при каких условиях (расчёт идёт между платформой и оператором, DEV-15 §11.5); **критичные зоны** (газ, щитовая, лифт) — авто-согласия не бывает, честный текст «ждём решения управляющей компании».
- **ТЗ:** §4.1, §4.4, §6.1, §17.17 · DEV-15 §4, §10.3.

#### C-12. Слот времени / «Срочно» / лист ожидания — объединён с C-10 (v2.25)
Секция выбора времени шага 2 «Где и когда». Спецификация — в C-10; ID сохранён для преемственности ссылок.

#### C-13. Шаг 3 «Итог» (v2.25)
- **Назначение:** третий шаг визарда (ТЗ §17.17 п.1): финальная проверка (вилка цены) и отправка заявки.
- **Кто видит:** B2C.
- **Точки входа:** C-10.
- **Данные:** сводка: категория, работы, фото, адрес (улица/дом), окно/срочно/лист ожидания; вилка цены «от–до» с правилом **«точная цена фиксируется до начала работ»**; позиция «Минимальный заказ», если применима; наценка «Срочно», если выбрана; для этапных работ — план сессий («2 визита: среда и пятница», ТЗ §6.1).
- **Элементы и действия:** **промокод — свёрнутая ссылка** «У меня есть промокод» (v2.25): разворачивается в поле с кнопкой «Применить» (MVP — решение владельца №13; скидка применяется последней к итогу работ, долю мастера не трогает); редактирование любого шага (возврат назад); кнопка «Отправить заявку».
- **Состояния:** проверка промокода (валиден/истёк/не найден — inline); отправка — прогресс; ошибка отправки — данные не теряются, retry.
- **Переходы:** успех → C-14 (статус «Новая»).
- **Крайние случаи:** **детект дублей**: открытая заявка того же адреса и категории за 24 ч → диалог «Похожая заявка уже есть» с кнопками «Открыть её» / «Всё равно создать» (ТЗ §4.1); долг аккаунта — блок по правилам C-06.
- **ТЗ:** §6.1, §3.4, §3.7, §4.1, §18 (решение №13), §17.17.

### 3.3. B2C: жизнь заявки

#### C-14. Активная заявка
- **Назначение:** центр отслеживания: статус, мастер, ETA, управление.
- **Кто видит:** B2C (полностью); сотрудник точки — усечённая версия (без денег, см. C-31).
- **Точки входа:** C-06; push-события заявки (deep-link); C-24.
- **Данные:** статус-трекер по статусной модели (Новая → Оценена → Назначена → Выехал → В работе → Выполнена → …, ТЗ §4.1; B2C пропускает «На утверждении/Утверждена» — смета подтверждается на месте); после «Назначена» — **карточка мастера**: фото, имя, рейтинг, количество работ + **прогноз до выезда** («мастер завершает предыдущий заказ, приедет ~16:40», ТЗ §17.3); после «Выехал» — **ETA по карте**; состав работ, вилка суммы; фото заявки; для этапных — индикатор сессий («Сессия 2 из 3, следующая — пятница 10:00»); паузы: «Ожидание материалов», «Технологический перерыв», «Заблокировано третьей стороной» (с временем следующей попытки).
- **Элементы и действия:** кнопка «Позвонить диспетчеру»; быстрые шаблонные сообщения (MVP; полноценный чат — фаза 2, ТЗ §6.1); кнопка **«Перенести»** — бесплатно при > 2 ч до окна, максимум 2 раза, дальше только отмена; при переносе мастер снимается и заявка возвращается в распределение (предупреждение в диалоге); кнопка **«Отменить»** — диалог с правилами денег при отмене (ТЗ §4.4: < 2 ч до окна или после выезда — ложный вызов = стоимость выезда; после начала работ — выезд + фактически сделанное); кнопка «Пожаловаться» → C-23.
- **Состояния:** загрузка; ошибка/нет сети — последнее кешированное состояние + баннер, поллинг при восстановлении; сдвиг прогноза за границу окна — карточка «Приносим извинения, новое время ~{T}» (проактивный push, ТЗ §17.3).
- **Переходы:** push «Мастер назначен — уточните детали для мастера» / баннер «Уточните детали адреса» → C-50 (v2.25); push «Подтвердите стоимость» → C-15; вынужденная доп-работа → C-16; апсейл → C-17; этапные слоты → C-18; «Выполнена» → C-19.
- **Крайние случаи:** замена мастера (протокол 17.3) — карточка мастера обновляется, баннер «Мастер заменён, к вам едет {имя}, будет к {время}»; лист ожидания — карточка «появилось окно сегодня 16:00» с кнопкой «Подтвердить» (слот не пропадает, ТЗ §17.3); снятие наценки «Срочно» — баннер «Не успели за 3 часа — срочность не тарифицируем» + предложение ближайшего окна; «Клиент недоступен» от мастера — прозвон диспетчера, при недозвоне отмена с ложным вызовом (ТЗ §4.4).
- **ТЗ:** §6.1, §4.1, §4.4, §17.3.

#### C-50. Детали адреса для мастера (новый, v2.25)
- **Назначение:** мини-экран уточнения деталей адреса (квартира, подъезд, этаж, домофон, лифт) **после назначения мастера** — для планирования выезда достаточно улицы/дома, детали нужны только назначенному мастеру (ТЗ §17.17 п.1).
- **Кто видит:** B2C.
- **Точки входа:** push «Мастер назначен — уточните детали для мастера» (deep-link); баннер в C-14.
- **Данные:** адрес заявки (улица/дом — read-only); поля: квартира, подъезд, этаж, домофон, **наличие лифта** (важно для тяжёлых/парных работ — ТЗ §6.1); комментарий для мастера. Если этаж и лифт уже собраны на шаге 2 визарда (категории «парная» / «требует оборудование», C-10) — эти поля предзаполнены (read-only с возможностью исправить).
- **Элементы и действия:** поля деталей; чекбокс «Сохранить в моих адресах» (обновляет C-29); кнопка «Готово».
- **Состояния:** для повторного/сохранённого адреса детали подставляются из сохранённого — экран предзаполнен, остаётся подтвердить; отправка/ошибка — retry.
- **Переходы:** → C-14.
- **Крайние случаи:** клиент не заполнил детали — ничего не блокируется: диспетчер уточнит их при звонке-подтверждении, мастер видит пометку «детали не указаны»; баннер в C-14 остаётся до заполнения или фиксации деталей диспетчером.
- **ТЗ:** §6.1, §17.17.

#### C-15. Подтверждение сметы на месте
- **Назначение:** превращение вилки «от–до» в обязательство: клиент подтверждает точную смету, составленную мастером до начала работ.
- **Кто видит:** B2C.
- **Точки входа:** push «Подтвердите стоимость {сумма}»; баннер в C-14.
- **Данные:** позиции с ценами и количеством, «Минимальный заказ» при добивке, итог работ; примечание о материалах (по чекам/каталогу, будут добавлены по факту); по позициям с запчастями — выбранный мастером ценовой уровень («эконом»/«стандарт»/«премиум») и цена конкретной запчасти, чтобы клиент видел, что именно утверждает (ТЗ §8.4.1); для диагностики с отложенным выполнением — правило зачёта диагностики (ТЗ §3.7); **при итоге выше первично показанной вилки — обязательный блок доказательств: фото мастера и причина по каждой позиции, подорожавшей относительно вилки** (перенесён паттерн вынужденных доп-работ C-16 — v2.25, ТЗ §17.17 п.4).
- **Элементы и действия:** кнопка **«Согласен»** — фиксируется как утверждение в аудите (кто, когда, сумма, устройство — ТЗ §4.1, §1 принцип 3); кнопка **«Отказываюсь»** — диалог: «Работы не начнутся. Оплачивается только выезд/диагностика» (отказ ≠ ложный вызов — ТЗ §6.1); кнопка «Позвонить диспетчеру».
- **Состояния:** загрузка; ошибка отправки решения — retry (мастер ждёт на объекте); нет сети у клиента — мастер может показать QR/экран, но решение принимается только с телефона клиента (анти-подделка согласий, ТЗ §4.6) либо устно диспетчеру с записью в аудит (телефонные заявки).
- **Переходы:** «Согласен» → C-14 (работа продолжается); для этапной работы, выявленной на месте, — вместе со сметой подтверждаются слоты сессий → C-18; «Отказываюсь» → завершение с оплатой выезда → C-19/C-20.
- **Крайние случаи:** смета выше первично показанной вилки — визуальный акцент на дельте + обязательные фото и причины по подорожавшим позициям (без них мастер не может отправить смету на подтверждение — v2.25); клиент молчит — мастер связывается голосом/через диспетчера, авто-отмена не применяется.
- **ТЗ:** §4.1, §6.1, §3.7, §4.6, §17.17.

#### C-16. Вынужденная доп-работа
- **Назначение:** санкция клиента на доп-работу, без которой исходную работу невозможно завершить (кабель сгорел — надо менять линию); анти-подделка: решение только с телефона клиента.
- **Кто видит:** B2C — сам клиент; для B2B аналогичное решение принимает утверждающий в C-36 (красный флаг, короткие таймеры).
- **Точки входа:** push с фото и вариантами; баннер «Требуется ваше решение» в C-14.
- **Данные:** обязательные фото проблемы; описание; **варианты, где осмысленно**: «Минимальный» (безопасная времянка/частичный ремонт, цена) и «Полный» (полное устранение, цена); последствия отказа — «мастер выполнит консервацию (безопасное отключение), позиция {цена}».
- **Элементы и действия:** радио-выбор варианта; кнопка **«Согласен с вариантом {минимальный|полный}»** (доп-смета утверждена, работа продолжается по выбранному варианту, аудит); кнопка **«Отказаться от доп-работ»** — диалог-предупреждение об опасности и консервации: заявка завершится с флагом «выполнена частично», оплата = выезд + фактически сделанное + консервация; в акте — фото проблемы и запись «клиент предупреждён об опасности, от работ отказался» (юридическая защита, ТЗ §4.6 п.4); «Позвонить диспетчеру».
- **Состояния:** загрузка фото; ошибка — retry; решение не отправилось — мастер видит «ожидание», работа по согласованной части продолжается (ТЗ §4.1 статус 8).
- **Переходы:** согласие → C-14; отказ → консервация → C-19.
- **Крайние случаи:** заявка создана по телефону — устное согласие фиксирует диспетчер в аудит с пометкой «озвучено по телефону» (ТЗ §4.6, §12); интерфейс никогда не смешивает вынужденную работу с апсейлом (разные экраны, разные цвета/тексты — ТЗ §4.6).
- **ТЗ:** §4.6, §4.1 (статус 8), §5.1.

#### C-17. Апсейл (рекомендация мастера)
- **Назначение:** необязательное «заодно» (меняем смеситель — подводка на ладан дышит); никогда не блокирует исходную работу.
- **Кто видит:** B2C; для B2B рекомендация уходит утверждающему (C-36/C-41), сотрудник точки принять не может (ТЗ §4.6 п.3).
- **Точки входа:** push «Мастер рекомендует»; карточка в C-14; список отложенных рекомендаций в C-06/C-28.
- **Данные:** фото, позиции с ценами, комментарий мастера; пометка «Это рекомендация — отказ не влияет на текущую работу» (анти-давление, ТЗ §4.6 п.5).
- **Элементы и действия:** **«Принять»** — становится утверждённой доп-сметой, мастер делает сейчас; **«Отклонить»**; **«Отложить»** — сохраняется в профиле списком рекомендаций (сырьё для сервисных напоминаний, ТЗ §4.6 п.2); «Пожаловаться на навязывание» — отдельная причина спора/жалобы, сигнал диспетчеру.
- **Состояния:** стандартные; решение офлайн не принимается.
- **Переходы:** любое решение → C-14.
- **Крайние случаи:** работа по непринятому апсейлу не оплачивается вообще («сделал по устной договорённости — сделал за свой счёт», ТЗ §4.6 п.4); на рейтинг мастера апсейл не влияет ни вверх, ни вниз.
- **ТЗ:** §4.6, §10, §17.12.

#### C-18. План сессий этапной работы
- **Назначение:** просмотр и подтверждение цепочки сессий (стяжка, малярка, герметизация — работа с технологическими паузами).
- **Кто видит:** B2C.
- **Точки входа:** C-13 (этапная позиция выбрана при создании — сессии бронируются при назначении); C-15 (работа выяснилась на месте — слоты следующих сессий предлагаются прямо при утверждении сметы, ТЗ §4.1); карточка сессий в C-14.
- **Данные:** этапы с датами/окнами: «Сессия 1 — среда 10:00; пауза 24 ч–7 дней; Сессия 2 — пятница 10:00»; правило: цена за работу целиком, выезды всех сессий включены; оплата — на последней сессии (ТЗ §4.1).
- **Элементы и действия:** выбор слотов следующих сессий из реально доступных окон ленты мастера; кнопка «Подтвердить план» (инвариант: этап 1 не начнётся, пока не подтверждены слоты всех следующих этапов — «не начинай красить, если некому приехать домазать»); «Перенести сессию» — в пределах допустимого окна паузы; «Позвонить диспетчеру».
- **Состояния:** расчёт слотов; нет слотов в допустимом окне — варианты планировщика: перенос всей работы на даты, где цепочка складывается / сверхурочный слот с согласия мастера / (параметр, по умолч. выкл.) передача продолжения другому мастеру.
- **Переходы:** подтверждение → C-14; между сессиями заявка в паузе «Технологический перерыв».
- **Крайние случаи:** отмена посередине — оплата фактически выполненных этапов (ТЗ §4.4, §4.1); промежуточные сессии завершаются без оплаты — единственное исключение из «мастер не уходит без оплаты» (ТЗ §4.1); все сессии ведёт один мастер (замена — «раздел заявки» диспетчером).
- **ТЗ:** §4.1, §3.7, §17.3.

#### C-19. Итог выполненной заявки
- **Назначение:** приёмка результата клиентом: фото до/после, работы, материалы, сумма.
- **Кто видит:** B2C.
- **Точки входа:** push «Заявка выполнена»; C-14.
- **Данные:** фото «до»/«после» (сравнительная сетка), «в процессе» при наличии; таблица работ (позиция, кол-во, цена, сумма); материалы: запчасти с фото чеков/накладных, расходники «сумки» по фикс-каталогу без чеков (ТЗ §8.4.1); при покупке материалов по «Коду закупки» в партнёрском магазине — раздел **«Список покупки»**: позиции, количество и сумма по чеку мастера (ТЗ §8.4.2); если ранее была оплачена диагностика/выезд-осмотр, зачитываемая в стоимость работ, — отдельная строка **«Осмотр зачтён в стоимость работ: −{сумма}»** (ТЗ §3.7); скидка/промокод; итог; для «выполнена частично» — отметка и запись о консервации; гарантийный срок.
- **Элементы и действия:** просмотр фото на весь экран; разворачиваемый блок «Список покупки» (если использовался Код закупки); подтверждение приёмки: **успешная онлайн-оплата в приложении засчитывается как приёмка — отдельный тап «Подтверждаю приёмку» при онлайн-оплате не требуется** (санкция клиента — платёж, v2.25, ТЗ §17.17 п.3); **одноразовый код приёмки — для наличных и телефонного канала**: клиент называет его мастеру устно или подтверждает приёмку в приложении без озвучивания кода кнопкой «Подтверждаю приёмку» (единый механизм, тот же, что и в C-34, ТЗ §7.1 шаг 5); при недоступности клиента или сбое доставки кода — диспетчер подтверждает приёмку вручную по фото мастера (fallback «без кода»); кнопка «Оплатить» → C-20 (если оплата на месте ещё не проведена); кнопка «PDF-акт» (после закрытия — с QR на онлайн-версию, ТЗ §9.1); «Оспорить» → C-22 (окно 72 ч); «Пожаловаться» → C-23.
- **Состояния:** загрузка фото по signed URL; ошибка — retry; нет сети — недоступно.
- **Переходы:** → C-20 (оплата) → C-21 «Спасибо» (оценка + чаевые, v2.25).
- **Крайние случаи:** диспетчер вернул заявку мастеру на доработку — статус откатывается на «Выполнена» (не «Проверена», которая соответствует уже пройденной проверке), клиент видит «дорабатывается»; если оплата уже принята — возврат её не отменяет, недочёты закрываются доработкой или спором (ТЗ §4.1 статус 10).
- **ТЗ:** §6.1, §9.1, §4.1, §8.4, §17.17.

#### C-20. Оплата (чаевые перенесены в C-21, v2.25)
- **Назначение:** оплата B2C на месте до ухода мастера; успешная онлайн-оплата одновременно фиксирует приёмку (ТЗ §17.17 п.3).
- **Кто видит:** B2C.
- **Точки входа:** C-19; push-ссылка на оплату от мастера (§7.1 шаг 6); напоминания «Ожидает оплаты» (T+24 push, T+72 SMS).
- **Данные:** сумма к оплате (работы + материалы − скидка), способы оплаты.
- **Элементы и действия:** кнопки **Payme**, **Click**, **Uzum** (Uzum — фаза 2), банковская карта — через мерчант-SDK/redirect; вариант «Отсканировать QR с экрана мастера»; пометка «Наличные — передайте мастеру, он зафиксирует» (фиксирует мастер кнопкой «Принял наличные», ТЗ §8.5; при наличных приёмка подтверждается кодом приёмки — C-19); чаевые — на экране «Спасибо» после оценки (C-21, v2.25).
- **Состояния:** ожидание callback провайдера (спиннер + «не закрывайте экран»); неуспех платежа — повтор/другой способ; нет сети — QR/наличные как fallback.
- **Переходы:** успех → C-21 «Спасибо» (оценка + чаевые); заявка закрывается биллингом.
- **Крайние случаи:** уход мастера без оплаты — только с санкции диспетчера, заявка в «Ожидает оплаты»: напоминания, при неоплате — долг аккаунта и блок новых заявок (ТЗ §4.1 статус 11, §8.9); двойной клик по оплате — идемпотентность на бэкенде (ТЗ §8.8); возвраты при спорах — только через refund-API провайдера, в UI показывается статус возврата (ТЗ §4.2).
- **ТЗ:** §6.1, §7.1 шаг 6, §8.5, §8.7, §18 (решение №11), §17.17.

#### C-21. Оценка + чаевые — экран «Спасибо» (объединён с блоком чаевых C-20, v2.25)
- **Назначение:** один экран «Спасибо» вместо цепочки «оценка → чаевые»: звёзды + чипы сумм чаевых + одна кнопка (ТЗ §17.17 п.3).
- **Кто видит:** B2C.
- **Точки входа:** после оплаты; push «Оцените работу» (окно 72 ч после «Выполнена»); C-25.
- **Данные:** карточка мастера, заявка.
- **Элементы и действия:** 5 звёзд; чипы сумм чаевых + «своя сумма» (при онлайн-оплате; целиком мастеру, мимо долей, отдельной проводкой — решение владельца №11); поле комментария; одна кнопка «Отправить» (оценка и чаевые уходят вместе; чип не выбран — чаевых нет, отдельная кнопка «Без чаевых» не нужна); «Позже»; после хорошей оценки — предложение **«Запомнить мастера»** (любимый мастер — мягкий приоритет на будущие заявки, ТЗ §17.12).
- **Состояния:** отправка; ошибка — retry; окно 72 ч истекло — оценка недоступна.
- **Переходы:** → C-06.
- **Крайние случаи:** оценка 1–2 автоматически открывает тикет диспетчеру (разбор, звонок в течение 2 ч — ТЗ §7.4, §17.11); оценки по спорам, решённым в пользу мастера, исключаются из рейтинга (на UI не влияет).
- **ТЗ:** §6.1, §4.1 (статус 13), §7.4, §17.11, §17.12, §18 (решение №11), §17.17.

#### C-22. Спор («Оспорить»)
- **Назначение:** оспаривание результата/суммы в окно 72 ч после «Выполнена».
- **Кто видит:** B2C; руководитель точки (по заявкам точки).
- **Точки входа:** C-19, C-25.
- **Данные:** заявка, сумма; причины из справочника (качество, сумма, «приехал не тот мастер» — разбирается как грубое нарушение, ТЗ §4.2).
- **Элементы и действия:** выбор причины; описание; фото (опц.); «Отправить спор» — блокирует начисление доли мастеру до резолюции; статус спора и резолюция (в пользу клиента / мастера / компромисс) отображаются в карточке.
- **Состояния:** отправка/ошибка; окно 72 ч истекло — кнопка скрыта, остаётся «Пожаловаться».
- **Переходы:** → C-25 (карточка со статусом «Спор»).
- **Крайние случаи:** возврат по онлайн-оплате — через refund-API провайдера; по наличным — возврат переводом от компании, не мастером из кармана (ТЗ §4.2).
- **ТЗ:** §4.2, §6.1.

#### C-23. Жалоба
- **Назначение:** обращения шире денег заявки: хамство, грязь, опоздание, работа диспетчера, глюки приложения (ТЗ §17.10).
- **Кто видит:** все клиентские роли (кнопка «Пожаловаться» у всех).
- **Точки входа:** C-14, C-19, C-25, C-30; для B2B — из карточек заявок.
- **Данные:** типы: качество / поведение мастера / сроки / деньги (конвертируется в спор) / сервис и диспетчер / приложение / другое; связь с заявкой опциональна.
- **Элементы и действия:** выбор типа; описание; фото; «Отправить»; список моих жалоб со статусами (новая → в работе → решена → закрыта) и резолюциями.
- **Состояния:** отправка/ошибка/пусто («жалоб нет»).
- **Переходы:** тип «деньги» — подсказка «это спор» → C-22.
- **Крайние случаи:** жалоба руководителя организации автоматически эскалируется старшему диспетчеру; SLA первого ответа ≤ 2 ч в окне 8:00–22:00; закрытие — подтверждение клиента или таймаут 72 ч; push «жалоба зарегистрирована/решена».
- **ТЗ:** §17.10, §11.

#### C-24. История заявок
- **Назначение:** список всех заявок клиента.
- **Кто видит:** B2C.
- **Точки входа:** таббар.
- **Данные:** карточки: номер (Z-2026-000123), дата, категория, статус, сумма, мастер; фильтры: активные/закрытые/споры/гарантийные.
- **Элементы и действия:** тап → C-14 (активная) или C-25 (закрытая); pull-to-refresh; пагинация.
- **Состояния:** скелетоны; пусто — «Пока нет заявок» + кнопка «Вызвать мастера»; ошибка/офлайн — кеш + баннер.
- **Переходы:** см. выше.
- **Крайние случаи:** заявки, созданные по телефону, отображаются в той же истории (единый аккаунт по номеру).
- **ТЗ:** §6.1.

#### C-25. Карточка закрытой заявки / акт
- **Назначение:** архив: полный итог, PDF-акт, гарантия, вход в гарантийное обращение.
- **Кто видит:** B2C.
- **Точки входа:** C-24; QR на бумажном акте.
- **Данные:** всё из C-19 + канал оплаты, гарантийный срок и его окончание (копия параметра на момент закрытия, по умолч. 30 дней), обслуженная техника (ссылка в C-28), оценка.
- **Элементы и действия:** «Скачать PDF-акт» (§9.1); **«Проблема вернулась»** → C-26 (в пределах гарантии); «Оспорить» (если в окне 72 ч); «Пожаловаться»; «Повторить заявку» (предзаполненное создание — сразу к выбору слота, 2–3 тапа, v2.25).
- **Состояния:** загрузка PDF; ошибка; фото по signed URL.
- **Переходы:** → C-26, C-22, C-23.
- **Крайние случаи:** гарантия истекла — кнопка «Проблема вернулась» заменяется «Создать новую заявку»; за 7 дней до конца гарантии приходит push «Гарантия заканчивается — проверьте работу» (ТЗ §17.12); «Повторить заявку» по итогам платной диагностики — предзаполненная заявка на ремонт, на шаге слота (C-10) показывается напоминание о зачёте стоимости осмотра (ТЗ §3.7).
- **ТЗ:** §6.1, §9.1, §4.2, §17.12.

#### C-26. Гарантийное обращение
- **Назначение:** создание гарантийной заявки со ссылкой на исходную; клиенту бесплатно в пределах гарантийного срока.
- **Кто видит:** B2C.
- **Точки входа:** C-25 («Проблема вернулась»); C-27 («Есть проблема»).
- **Данные:** исходная заявка, срок гарантии, описание проблемы, фото.
- **Элементы и действия:** описание + фото; «Отправить» — создаётся заявка типа «гарантийная»: смета 0, статусы утверждения пропускаются, биллинг клиенту не начисляется (ТЗ §4.1, §4.2); выбор удобного окна.
- **Состояния:** отправка/ошибка.
- **Переходы:** → C-14 (гарантийная заявка активна; приоритет очереди — уровень 3, выше обычных броней, ТЗ §17.3).
- **Крайние случаи:** запчасть отказала после гарантии на работу, но в пределах гарантии магазина — запчасть бесплатно, работа по замене — параметр (ТЗ §8.4.3); QC-звонок диспетчера в течение 4 ч (ТЗ §17.11).
- **ТЗ:** §4.2, §6.1, §8.4.3, §17.11.

#### C-27. Контрольное касание «Как дела»
- **Назначение:** проверка результата через 7–14 дней после ремонта — ловим брак внутри гарантии.
- **Кто видит:** B2C.
- **Точки входа:** push «Кондиционер работает нормально?» → диалог/экран.
- **Данные:** заявка, обслуженная техника.
- **Элементы и действия:** кнопка **«Всё отлично»** (закрывает касание); кнопка **«Есть проблема»** — гарантийная заявка одной кнопкой → C-26.
- **Состояния:** стандартные; молчание — без последствий.
- **Переходы:** → C-26 или закрытие.
- **Крайние случаи:** частотный потолок сервисных push — не более 1 в 2 недели (ТЗ §17.12); операционные касания идут независимо от маркетингового согласия, маркетинговые — только при согласии.
- **ТЗ:** §17.12, §15 (MVP).

#### C-28. Моя техника (фаза 2)
- **Назначение:** паспорт техники квартиры: каждая единица с историей обслуживания и рекомендациями по регламенту.
- **Кто видит:** B2C.
- **Точки входа:** таббар; C-25 (ссылка на единицу).
- **Данные:** единицы (тип, бренд, модель, год, фото шильдика — заполняет мастер при работах, ТЗ §17.12); история работ по единице («этот кондиционер чистили в мае, меняли плату в августе»); ближайшие регламентные рекомендации из справочника интервалов («прошло 6 мес после чистки — рекомендуем, ~150 000»); отложенные апсейл-рекомендации.
- **Элементы и действия:** кнопка **«Записаться»** у рекомендации — создаёт заявку с предзаполненной позицией и закреплённым/любимым мастером (приоритет; если недоступен — обычное распределение); редактирование данных единицы; «Отписаться от напоминаний» (в один тап).
- **Состояния:** пусто — «Здесь появится техника после первого визита мастера»; загрузка/ошибка.
- **Переходы:** → создание заявки (сразу к шагу слота, C-10), C-25.
- **Крайние случаи:** интервалы задаёт компания, не мастер — спам «рекомендациями» невозможен (ТЗ §17.12); сезонные кампании дозируются ёмкостью планировщика.
- **ТЗ:** §17.12, §3.8 (ClientAsset, ServiceInterval).

#### C-29. Мои адреса
- **Назначение:** сохранённые адреса с деталями доступа.
- **Кто видит:** B2C.
- **Точки входа:** C-30; C-10.
- **Данные:** список адресов: улица/дом/квартира, подъезд, этаж, домофон, лифт, комментарий.
- **Элементы и действия:** добавить/редактировать/удалить; пометка «основной».
- **Состояния:** пусто/загрузка/ошибка.
- **Переходы:** выбор адреса из C-10.
- **Крайние случаи:** адрес вне зоны покрытия — сохраняется, но при создании заявки срабатывает правило C-10.
- **ТЗ:** §6.1, §17.4.

#### C-30. Профиль и настройки
- **Назначение:** данные аккаунта, язык, согласия, контексты, выход.
- **Кто видит:** все роли.
- **Точки входа:** таббар.
- **Данные:** ФИО, телефон (логин), язык, активный контекст, версия приложения.
- **Элементы и действия:** смена языка (рус/узб — меняет и язык SMS/push/документов, ТЗ §14); «Сменить контекст» → C-05; управление согласиями (маркетинговый чекбокс — отписка в один тап, ТЗ §17.12); «Мои адреса» → C-29; «Мои жалобы» → C-23; «Позвонить в поддержку»; «Сменить номер» — только через поддержку с верификацией личности (ТЗ §14), в UI — инструкция и звонок; «Выйти».
- **Состояния:** стандартные.
- **Переходы:** см. выше.
- **Крайние случаи:** PIN/биометрия настраиваются здесь для утверждающих ролей (требуется для утверждений выше порога, ТЗ §5.2).
- **ТЗ:** §6.1, §14, §5.2, §17.12.

### 3.4. Режим «Сотрудник точки»

#### C-31. Главный экран сотрудника точки
- **Назначение:** максимально простой хаб «фармацевт не должен думать» (ТЗ §6.2).
- **Кто видит:** сотрудник точки; руководитель точки (как базовый слой).
- **Точки входа:** вход/контекст.
- **Данные:** название точки; свои заявки со статусами и ETA мастера (усечённая карточка заявки: **без смет и денег** — настройка организации «показывать/нет», ТЗ §6.2); код приёмки для активной заявки.
- **Элементы и действия:** большая кнопка **«Сообщить о поломке»** → C-32; карточка «Что делать при аварии» → C-33; заявка → усечённый C-14 (статус, мастер, ETA, без сумм); кнопка «Код приёмки» → C-34; ссылка **«Мои баллы»** с бейджем баланса → C-49 (только при включённой в договоре программе поощрения, ТЗ §17.14); «Пожаловаться» → C-23.
- **Состояния:** скелетоны; пусто — акцент на кнопке; офлайн — кеш + баннер.
- **Переходы:** см. выше.
- **Крайние случаи:** заявка ушла «На утверждение» (смета выше лимита) — сотрудник видит статус «ждёт утверждения» без суммы; апсейл мастера сотруднику не показывается и не может быть им принят (ТЗ §4.6 п.3).
- **ТЗ:** §6.2, §2.2, §4.6.

#### C-32. «Сообщить о поломке» (упрощённое создание)
- **Назначение:** создание заявки от имени точки за минимум шагов.
- **Кто видит:** сотрудник точки, руководитель точки.
- **Точки входа:** C-31.
- **Данные:** точка (предзаполнена, адрес из паспорта точки), шаги на одном экране.
- **Элементы и действия:** **фото (обязательно предложено**, для B2B желательно — ТЗ §4.1); описание; категория (можно «не знаю»); для категорий с признаком «требует общих зон» — тот же чек-лист доступа, что и в B2C (C-11): «Нужно ли отключение стояка?»/«Нужен ли доступ к подвалу/крыше/щитовой?» с полем **«Доступ подтверждён на {дата/время}»** (ТЗ §4.1); срочность: «обычная» / «аварийная» **с подсказкой, что такое авария** (для аварийной фото не обязательны) / **«Срочно»** (платная приоритетность — ближайший освободившийся мастер, наценка к работам; доступна и для плановых, не аварийных заявок точки, те же условия, что в B2C C-10, ТЗ §17.3); кнопка «Отправить».
- **Состояния:** отправка/ошибка (черновик сохраняется); офлайн — блок с баннером.
- **Переходы:** успех → C-31 с карточкой новой заявки. Если смета ≤ лимита заявки точки и месячный лимит не исчерпан — авто-старт без утверждения; иначе — «На утверждении» (ТЗ §5.1).
- **Крайние случаи:** детект дублей по точке/категории за 24 ч — «похожая заявка уже есть»; аварийная — минует оценку, назначается ближайшему мастеру, руководству уходит push + звонок (ТЗ §4.3); анти-дробление (> N авто-стартов за 48 ч) отрабатывает на бэкенде — сотрудник видит «заявка на проверке у диспетчера» (ТЗ §5.1).
- **ТЗ:** §6.2, §4.1, §4.3, §5.1.

#### C-33. Инструкция при аварии
- **Назначение:** «что делать до приезда мастера» — перекрыть кран, обесточить.
- **Кто видит:** сотрудник точки, руководитель точки.
- **Точки входа:** C-31; автоматически показывается после создания аварийной заявки.
- **Данные:** пошаговая инструкция по категориям аварий с **картинкой из паспорта объекта, где кран/щиток** (заполняется при первом осмотре, ТЗ §6.2, §3.2).
- **Элементы и действия:** шаги с фото; «Позвонить диспетчеру».
- **Состояния:** паспорт объекта не заполнен — общая инструкция без фото; кешируется для офлайна (авария — тот случай, когда сеть может пропасть).
- **Переходы:** → C-31.
- **Крайние случаи:** нет.
- **ТЗ:** §6.2, §3.2.

#### C-34. Код приёмки
- **Назначение:** подтверждение приёмки работы на месте по единому механизму приёмки: сотрудник получает одноразовый 4-значный код приёмки push/SMS-уведомлением (код также отображён в приложении) и либо называет его мастеру устно, либо подтверждает приёмку в приложении без озвучивания кода (ТЗ §7.1 шаг 5).
- **Кто видит:** сотрудник точки, руководитель точки.
- **Точки входа:** C-31 (кнопка на карточке заявки в статусе «Выполнена» у мастера); push «Подтвердите приёмку работ».
- **Данные:** крупный одноразовый 4-значный код по конкретной заявке; фото «после» для беглой проверки (без сумм).
- **Элементы и действия:** отображение кода; «Обновить код»; **«Подтвердить приёмку в приложении»** (альтернатива устному коду — засчитывается наравне, тот же принцип действует и для B2C, см. C-19); «Не принимаю работу» → комментарий диспетчеру.
- **Состояния:** загрузка; офлайн — последний полученный код из кеша.
- **Переходы:** после ввода кода мастером или тапа «Подтвердить приёмку в приложении» карточка обновляется до «Выполнена».
- **Крайние случаи:** сотрудник недоступен (смена кончилась, телефон сел) или код не доставлен — диспетчер подтверждает приёмку вручную без кода (по фото общего плана от мастера, с отметкой в системе, ТЗ §7.1); режимный объект «фото запрещено» — код приёмки + подпись представителя обязательны вместо фото (ТЗ §4.1).
- **ТЗ:** §7.1 шаг 5, §4.1, §6.2.

#### C-49. Мои баллы и ваучеры
- **Назначение:** личный счёт программы поощрения персонала точек: баллы за закрытые и оплаченные заявки, созданные сотрудником (% от суммы работ без материалов, 1 балл = 1 сум), и ваучеры супермаркета (стартовый партнёр — Корзинка), автоматически выдаваемые из закупленного компанией пула при достижении порога конвертации (ТЗ §17.14).
- **Кто видит:** сотрудник точки — при включённой в договоре организации программе поощрения (согласие руководства организации); руководители — только если включены админом точечно.
- **Точки входа:** пункт «Мои баллы» в профиле/меню контекста сотрудника (C-31); push «Ваучер ждёт вас» (deep-link).
- **Данные:** баланс баллов; прогресс до следующего ваучера (порог конвертации — параметр); история начислений: заявка → сумма баллов (глобальный процент 1%, персональный override — задаётся в админке; месячный потолок начислений — параметр; сторно при споре/возврате/отмене отображаются в истории); начисления привязаны к **заявителю** заявки (applicant_user_id) — в т.ч. по телефонным заявкам, где диспетчер привязал сотрудника по номеру телефона; авто-заявки и заявки, созданные руководителями за сотрудников, баллов не дают (ТЗ §17.14); список ваучеров: номинал, QR-код, срок действия, статус (активен/погашен/истёк).
- **Элементы и действия:** тап по ваучеру — разворот QR на весь экран с автоподнятием яркости (для сканирования на кассе супермаркета при оплате; ваучер дублируется SMS); ссылка «Правила программы».
- **Состояния:** программа не включена для организации — экран скрыт (пункт в C-31 не показывается); пусто — «Баллов пока нет — сообщайте о поломках через приложение»; загрузка/ошибка — retry; офлайн — кешированные ваучеры доступны, QR работает без сети.
- **Переходы:** → C-31; из истории начислений — карточка заявки (усечённая, без денег заявки).
- **Крайние случаи:** ваучер истёк — помечен статусом «истёк», баллы не возвращаются (параметр); сторно после конвертации уже выданный ваучер не отзывает — баланс уходит в минус: отрицательный баланс отображается и гасится будущими начислениями (ТЗ §17.14); организация отключила программу — баллы остаются конвертируемыми ещё 60 дней, затем сгорают; за 7 дней до сгорания сотруднику уходит уведомление «Баллы сгорят через 7 дней» (ТЗ §17.14).
- **ТЗ:** §17.14.

### 3.5. Режим «Руководитель точки»

#### C-35. Лента заявок точки
- **Назначение:** все заявки точки со сметами и деньгами (в отличие от сотрудника).
- **Кто видит:** руководитель точки.
- **Точки входа:** вход/контекст; таббар «Заявки».
- **Данные:** заявки точки: статус, категория, смета, мастер, окно; бейджи «ждёт утверждения»; фильтры по статусу/периоду.
- **Элементы и действия:** тап → карточка заявки (полный C-14 с суммами) или C-36, если ждёт утверждения; «Сообщить о поломке» (C-32) доступна и руководителю.
- **Состояния:** скелетоны/пусто/ошибка/офлайн-кеш.
- **Переходы:** → C-36, C-14, C-32.
- **Крайние случаи:** заявки со сметой выше порога руководителя точки — видны со статусом «у руководителя организации».
- **ТЗ:** §6.3.

#### C-36. Утверждение сметы / доп-сметы
- **Назначение:** санкция на работы: первичные сметы, доп-сметы, вынужденные доп-работы, апсейлы, восстановление после аварии.
- **Кто видит:** руководитель точки (до своего порога), руководитель организации (до своего), владелец (только второе утверждение при двойной схеме, фаза 2 — ТЗ §5.2, §6.5).
- **Точки входа:** push «Смета требует утверждения» (deep-link); C-35; C-41; эскалационные push/SMS (T+24/48, ТЗ §5.3).
- **Данные:** фото, позиции, сумма, точка, мастер; тип: обычная смета / доп-смета (сумма превышения) / **вынужденная** (красный флаг, фото проблемы, варианты минимум/полный, таймеры 30 мин / 2 ч) / **апсейл** (пометка «рекомендация мастера», для B2B никогда не автостартует — ТЗ §4.6); для критичного дефекта — красный флаг + дублирующий звонок диспетчера.
- **Элементы и действия:** **«Утвердить»** (для вынужденной — выбор варианта минимум/полный); **«Отклонить»** (для вынужденной — предупреждение о консервации и что позиция станет дефектом техдолга с готовой оценкой, ТЗ §4.6 п.5); **«Вопрос диспетчеру»** (звонок); для апсейла — «Отложить» → техдолг точки. Каждое решение — в аудит (кто, когда, сумма, устройство).
- **Состояния:** загрузка; ошибка отправки решения — retry; **сумма выше порога повторной аутентификации (по умолч. 5 000 000) — запрос PIN/биометрии** перед фиксацией (защита от SIM-swap, ТЗ §5.2).
- **Переходы:** решение → C-35/C-41; смета выше порога роли — экран read-only «передано на уровень выше».
- **Крайние случаи:** молчание: T+24 повторный push+SMS, T+48 эскалация уровнем выше + звонок, T+72 авто-отмена «не согласовано» (критичные дефекты не отменяются — ежедневное напоминание); для доп-смет на объекте — короткие таймеры 30 мин / 2 ч, авто-отмены нет: мастер завершает согласованную часть (ТЗ §5.3); **молчание по вынужденной доп-работе B2B**: SMS-напоминание уходит утверждающему сразу по истечении таймера 30 мин, при отсутствии решения к 2 ч — автоэскалация следующему по иерархии утверждающему (рук. точки → рук. организации → при включённой двойной схеме — владелец) вместе со звонком диспетчера; статус заявки на это время остаётся «Ожидает решения по вынужденной доп-работе», исходная согласованная часть работ продолжается без остановки; авто-отказ по молчанию для вынужденных доп-работ не применяется (в отличие от T+72 у обычных доп-смет) — решение обязательно явное (ТЗ §5.3, §4.6); двойное утверждение: после первого утверждения статус «ждёт второго утверждения владельцем».
- **ТЗ:** §5.1–5.3, §4.6, §6.3, §6.4.

#### C-37. Техдолг точки
- **Назначение:** реестр дефектов точки: что найдено, отклонено, отложено — и сколько это стоит.
- **Кто видит:** руководитель точки.
- **Точки входа:** таббар; ежемесячный дайджест-push «Техдолг точки X: 4,2 млн, из них критичного 1,1 млн» (ТЗ §10).
- **Данные:** дефекты: фото, описание, категория, приоритет (критичный/высокий/средний/низкий), оценка устранения и срок её актуальности (30 дней, потом переоценка), статус (новый/на утверждении/утверждён/отложен/отклонён/устранён); сумма техдолга, разбивка по приоритетам, подсветка дефектов 60+ дней.
- **Элементы и действия:** карточка дефекта; «Утвердить» (порождает заявку в статусе «Утверждена», в пределах порога роли) / «Отложить до даты» / «Отклонить» (остаётся в архиве с пометкой — юридическая защита «мы предупреждали», ТЗ §10).
- **Состояния:** пусто — «Дефектов нет»; загрузка/ошибка.
- **Переходы:** утверждённый дефект → заявка в C-35.
- **Крайние случаи:** MVP — дефекты простым списком без модуля техдолга (фаза 2 — полный модуль, ТЗ §15); заявки из осмотра всегда требуют утверждения, даже в пределах лимита (анти-навязывание, ТЗ §5.1).
- **ТЗ:** §10, §3.5, §5.1, §6.3, §15.

#### C-38. Лимиты точки
- **Назначение:** прозрачность авто-старта: сколько израсходовано; плюс базовые данные профиля точки — график доступа и контакт ТСЖ, нужные для планирования обслуживания на объектах с ограниченным доступом.
- **Кто видит:** руководитель точки.
- **Точки входа:** таббар/блок на главном.
- **Данные:** лимит на заявку; месячный лимит: индикатор «израсходовано 640 000 из 1 500 000 авто-лимита» (ТЗ §6.3); счётчики месяца; **график доступа точки** (рабочие часы, когда возможен допуск на объект); **контакт ТСЖ/УК** (ФИО, телефон) — используются диспетчером при планировании плановых осмотров и работ, требующих согласования доступа (ТЗ §4.1, §17.3).
- **Элементы и действия:** просмотр (изменение лимитов — только руководитель организации, C-45); редактирование графика доступа и контакта ТСЖ/УК (руководитель точки); при исчерпании лимита — предупреждение «до конца месяца все заявки идут на утверждение» (ТЗ §5.1).
- **Состояния:** загрузка/ошибка.
- **Переходы:** —
- **Крайние случаи:** график доступа/контакт ТСЖ не заполнены — чек-лист доступа (C-11/C-32) всё равно запрашивает подтверждение на каждую заявку.
- **ТЗ:** §6.3, §3.2, §5.1, §4.1, §17.3.

#### C-39. Отчёты точки
- **Назначение:** месячный отчёт точки (PDF).
- **Кто видит:** руководитель точки.
- **Точки входа:** таббар.
- **Данные:** список отчётов по месяцам: заявки/аварийные/осмотры, суммы работ и материалов, списано с абонентки, сверхлимит, динамика; раздел «Техдолг» (ТЗ §9.2).
- **Элементы и действия:** «Скачать PDF»; «Поделиться».
- **Состояния:** генерация/загрузка/ошибка; пусто — «Отчёт появится после первого месяца».
- **Переходы:** — 
- **Крайние случаи:** реестр заявок в PDF содержит QR-ссылки на акты.
- **ТЗ:** §6.3, §9.2.

### 3.6. Режим «Руководитель организации»

#### C-40. Дашборд организации (светофор)
- **Назначение:** состояние всех точек одним взглядом.
- **Кто видит:** руководитель организации.
- **Точки входа:** вход/контекст.
- **Данные:** плитки точек со светофором: **зелёная** — всё ок; **жёлтая** — заявки в работе; **красная** — авария или висит утверждение (ТЗ §6.4); сводка: ожидают утверждения (N), остаток абонентки, техдолг.
- **Элементы и действия:** тап по точке → лента её заявок (C-35 в разрезе точки); плитка «Центр утверждений» с бейджем → C-41; переходы в C-43, C-44, C-45, C-46, C-47.
- **Состояния:** скелетоны; ошибка/офлайн — кеш + баннер; организация «приостановлена» (неоплата абонентки к 10-му) — красный баннер «Обслуживание приостановлено, доступны только аварийные заявки» (ТЗ §8.3).
- **Переходы:** см. выше.
- **Крайние случаи:** авария на точке — красная плитка + push + звонок диспетчера контактному лицу (ТЗ §4.3, §11).
- **ТЗ:** §6.4, §8.3.

#### C-41. Центр утверждений
- **Назначение:** единая лента всего, что ждёт решения: сметы, доп-сметы, вынужденные, апсейлы, пакеты дефектов.
- **Кто видит:** руководитель организации.
- **Точки входа:** C-40; push; **бейдж на иконке приложения** (ТЗ §6.4).
- **Данные:** карточки с типом, точкой, суммой, возрастом ожидания; **сортировка по срочности**: вынужденные с красным флагом и критичные дефекты сверху; индикаторы таймеров эскалации.
- **Элементы и действия:** тап → C-36 (смета/доп-смета/апсейл) или C-42 (пакет дефектов); свайп-действия «Утвердить»/«Отклонить» для типовых смет (с подтверждением; выше порога повторной аутентификации — только через C-36 с PIN/биометрией).
- **Состояния:** пусто — «Всё решено»; загрузка/ошибка/офлайн-кеш (решения офлайн не принимаются).
- **Переходы:** → C-36, C-42.
- **Крайние случаи:** сверхпороговое двойное утверждение — карточка показывает статус цепочки «вы утвердили, ждёт владельца».
- **ТЗ:** §6.4, §5.1–5.3.

#### C-42. Пакетное утверждение дефектов (фаза 2)
- **Назначение:** разбор результатов осмотра одним экраном: «Осмотр {точка}: найдено N дефектов на {сумма}» (ТЗ §5.4).
- **Кто видит:** руководитель организации.
- **Точки входа:** push после осмотра; C-41; C-43.
- **Данные:** список дефектов: фото, цена, приоритет; итого по выбранным.
- **Элементы и действия:** чекбоксы (по умолчанию критичные отмечены); **«Утвердить выбранные»** — каждый становится заявкой в статусе «Утверждена», планирует диспетчер; **«Отложить до даты»** (дата-пикер); **«Отклонить»** (с причиной; остаются в архиве с пометкой); тап по дефекту — детальная карточка.
- **Состояния:** загрузка/ошибка; частичная отправка — идемпотентный ретрай.
- **Переходы:** → C-41/C-43.
- **Крайние случаи:** сумма выбранных выше порога роли — двойное утверждение/эскалация по §5.2; критичный дефект — красный флаг + дублирующий звонок диспетчера (ТЗ §5.1); эскалация молчания по §5.3, критичные не авто-отменяются; **в MVP (пока этого экрана нет)** пакетный push после осмотра — только уведомление текстом («N дефектов на {сумма}»), каждый дефект утверждается по отдельности через C-36/C-41, а сводка по ним видна простым списком в C-37 «Техдолг точки» (ТЗ §5.4, §15).
- **ТЗ:** §5.4, §5.1–5.3, §6.4, §15 (фаза 2).

#### C-43. Техдолг организации (фаза 2)
- **Назначение:** сумма техдолга по всем точкам, приоритеты, тренд.
- **Кто видит:** руководитель организации.
- **Точки входа:** C-40; ежемесячный дайджест-push.
- **Данные:** общая сумма, разбивка по точкам и приоритетам, тренд («в прошлом месяце 6,1 млн → сейчас 4,2 млн», ТЗ §6.4); старение 60+ дней; источники: осмотры, отклонённые вынужденные, отложенные апсейлы (ТЗ §10).
- **Элементы и действия:** тап по точке → список дефектов (C-37 в разрезе точки); кнопка «Утвердить пакетом» → C-42.
- **Состояния:** пусто/загрузка/ошибка.
- **Переходы:** → C-42, C-37.
- **Крайние случаи:** дефект с истёкшей оценкой (30 дней) — пометка «требует переоценки», утверждение недоступно до переоценки.
- **ТЗ:** §10, §6.4, §3.5.

#### C-44. Финансы организации
- **Назначение:** абонентка, сверхлимит, СФ, акт сверки, динамика.
- **Кто видит:** руководитель организации.
- **Точки входа:** C-40.
- **Данные:** остаток абонентки + **прогноз «хватит до ~24 числа»**; сверхлимит текущего месяца; список СФ (период, сумма, статус: draft/отправлена/оплачена/просрочена) с PDF; помесячная динамика расходов по точкам (ТЗ §6.4); резерв плановых осмотров (списываются первоочерёдно, ТЗ §8.3); блок **«Договор»**: срок (годовой / месячный с авто-продлением), дата продления, режим цен **«зафиксированы по релизу прайса №N до {дата продления}»** — руководитель видит главный торговый аргумент годовой заморозки цен (ТЗ §3.7, §18 п.17).
- **Элементы и действия:** «Скачать СФ (PDF)»; **«Акт сверки за период»** — PDF одной кнопкой (ТЗ §8.9); фильтры по периоду/точке.
- **Состояния:** загрузка/ошибка; пусто — до первого начисления.
- **Переходы:** СФ → просмотр PDF; месячный отчёт-приложение к СФ → C-47.
- **Крайние случаи:** неоплата абонентки — баннеры дунинга (T+3/T+7), к 10-му — приостановка (ТЗ §8.3, §8.9); пени, если включены в договоре, — отдельной строкой СФ; частичное покрытие абонентки — сверхлимит рассчитан по формуле §8.2 (UI показывает готовые суммы); при уведомлении о смене цен при продлении договора — доступен авто-отчёт **«что изменилось в ваших ценах»** и опция **«не продлевать»** (для месячного договора; отказ = расторжение с даты окончания срока, ТЗ §3.7).
- **ТЗ:** §6.4, §8.3, §8.9, §3.7, §18 п.17.

#### C-45. Лимиты и пользователи
- **Назначение:** управление лимитами точек и пользователями.
- **Кто видит:** руководитель организации.
- **Точки входа:** C-40.
- **Данные:** по каждой точке: лимит на заявку, месячный лимит, израсходовано; пользователи точек с ролями.
- **Элементы и действия:** изменение лимитов (в пределах, разрешённых договором; каждое изменение — в аудит, ТЗ §3.8 AuditLog); **«Пригласить пользователя»** — по номеру телефона (SMS-приглашение, ТЗ §6.4, §17.2), выбор роли (сотрудник/руководитель точки) и точки; деактивация пользователя; настройка «показывать ли сотрудникам сметы и деньги» (ТЗ §6.2).
- **Состояния:** загрузка/ошибка; отправка приглашения — подтверждение.
- **Переходы:** — 
- **Крайние случаи:** пороги утверждения задаются в договоре и меняются только админом платформы — в UI показываются read-only (ТЗ §5.2).
- **ТЗ:** §6.4, §5.2, §6.2, §17.2.

#### C-46. График осмотров (фаза 2; в MVP осмотры создаёт диспетчер)
- **Назначение:** просмотр и согласование графика плановых осмотров точек.
- **Кто видит:** руководитель организации.
- **Точки входа:** C-40.
- **Данные:** график по точкам (InspectionSchedule): периодичность, ближайшие даты; история осмотров с отчётами (чек-лист, дефекты — ТЗ §9.3).
- **Элементы и действия:** запрос переноса осмотра; просмотр отчёта по осмотру; переход в пакет дефектов → C-42.
- **Состояния:** пусто/загрузка/ошибка.
- **Переходы:** → C-42.
- **Крайние случаи:** осмотры — фоновый демпфер планировщика: двигаются в пределах недели автоматически (ТЗ §17.3); при приостановке организации осмотры замораживаются (ТЗ §8.3).
- **ТЗ:** §6.4, §3.8, §8.3, §9.3, §17.3.

#### C-47. Отчёты организации
- **Назначение:** месячный сводный PDF по организации и по каждой точке — главная продающая ценность B2B (ТЗ §9.2).
- **Кто видит:** руководитель организации.
- **Точки входа:** C-40; push «СФ выставлена» (отчёт — приложение к СФ).
- **Данные:** отчёты по месяцам: сводка, реестр заявок с QR на акты, раздел «Техдолг» (устранено/добавлено/остаток).
- **Элементы и действия:** выбор месяца и разреза (организация/точка); «Скачать PDF»; «Поделиться».
- **Состояния:** генерация/ошибка/пусто.
- **Переходы:** —
- **Крайние случаи:** двуязычные шаблоны — язык документов из настроек организации (ТЗ §14).
- **ТЗ:** §6.4, §9.2, §14.

### 3.7. Режим «Владелец»

#### C-48. Дашборд владельца (фаза 2)
- **Назначение:** «только наблюдение»: вся картина без операционных кнопок (ТЗ §6.5).
- **Кто видит:** владелец организации.
- **Точки входа:** вход/контекст; push второго утверждения.
- **Данные:** настраивается в договоре: светофор точек, суммы, техдолг, отчёты — read-only версии C-40/C-43/C-44/C-47.
- **Элементы и действия:** просмотр без кнопок действий. **Единственное исключение:** карточки «Требуется второе утверждение» (сверхпороговые сметы при двойном утверждении) → C-36 в режиме второго утверждения с PIN/биометрией (ТЗ §5.2, §6.5).
- **Состояния:** загрузка/ошибка/офлайн-кеш.
- **Переходы:** → C-36 (только второе утверждение), просмотр отчётов.
- **Крайние случаи:** двойное утверждение выключено в договоре — режим полностью read-only.
- **ТЗ:** §6.5, §5.2, §15 (фаза 2).

### 3.8. Веб-карточка заявки (телефонные клиенты, без приложения)

Общее: открывается по SMS-ссылке с **одноразовым подписанным токеном с ограниченным сроком жизни**; действия по ссылке журналируются как подтверждения клиента; чужую заявку перебором URL не открыть (ТЗ §12 п.5). Без установки и регистрации. Язык — из профиля клиента (рус/узб). Адаптивная mobile-first вёрстка.

#### W-01. Статус заявки
- **Назначение:** «где мой мастер» для клиента без приложения.
- **Кто видит:** клиент телефонного канала по SMS-ссылке.
- **Точки входа:** SMS «Мастер назначен: {имя}, окно {T}. Подробнее: {ссылка}»; SMS «Мастер выехал, будет ~{T}».
- **Данные:** статус-трекер; карточка мастера (фото, имя, рейтинг); окно/ETA; состав заявки с вилкой цены; телефон диспетчера; при наличии рекомендации мастера (апсейл) — карточка на этом же экране: фото, позиции с ценами, комментарий мастера, пометка «Это рекомендация — отказ не влияет на текущую работу» (тот же принцип, что в C-17).
- **Элементы и действия:** «Позвонить диспетчеру» (tel:); переключатель языка; при апсейле — кнопки **«Принять»**/**«Отклонить»**/**«Отложить»** прямо на карточке рекомендации (решение журналируется как подтверждение клиента, ТЗ §4.6, §12); рядом с карточкой мастера — ссылка «Проверить мастера» → публичная страница верификации (L-07, PRD-06, ТЗ §17.15); после первой закрытой заявки — один раз ссылка «В приложении удобнее: история, гарантия, запись в два тапа» (без спама, параметр — ТЗ §12 п.7).
- **Состояния:** загрузка; ошибка сети — retry; токен истёк/использован → W-05.
- **Переходы:** смета ждёт подтверждения → W-02; заявка выполнена → W-03; апсейл принимается/отклоняется/откладывается без перехода на отдельный экран.
- **Крайние случаи:** кто не открывает ссылку — ключевые события дублируются SMS-текстом (назначен + окно; выехал + ETA; акт готов), оплата наличными/QR с экрана мастера, оценка — QC-звонком (ТЗ §12 п.5, §17.11).
- **ТЗ:** §12, §11.

#### W-02. Смета — «Согласен»
- **Назначение:** юридически значимое подтверждение сметы без приложения.
- **Кто видит:** телефонный клиент.
- **Точки входа:** SMS/переход из W-01 при событии «Подтвердите стоимость».
- **Данные:** позиции, сумма, фото; по позициям с запчастями — выбранный ценовой уровень («эконом»/«стандарт»/«премиум») и цена конкретной запчасти (тот же принцип, что в приложении, C-15); для вынужденной доп-работы — фото проблемы и варианты минимум/полный.
- **Элементы и действия:** кнопка **«Согласен»** — журналируется как подтверждение клиента (аудит); «Отказываюсь» (оплачивается только выезд); «Позвонить диспетчеру».
- **Состояния:** загрузка/ошибка; токен истёк → W-05 (устное согласие может зафиксировать диспетчер с пометкой «озвучено по телефону» — ТЗ §12 п.4).
- **Переходы:** → W-01.
- **Крайние случаи:** повторное нажатие «Согласен» идемпотентно.
- **ТЗ:** §12, §4.1, §4.6.

#### W-03. Акт + оплата
- **Назначение:** итог работ и онлайн-оплата.
- **Кто видит:** телефонный клиент.
- **Точки входа:** SMS «Работа выполнена, акт: {ссылка}»; напоминания оплаты.
- **Данные:** фото до/после, работы, материалы, итог; акт (онлайн-версия, PDF по кнопке); гарантийный срок.
- **Элементы и действия:** «Оплатить» — Payme/Click/Uzum-checkout; после успешной оплаты — экран **чаевых** (те же пресеты, что в приложении, C-20): пресеты сумм + своя сумма, «целиком мастеру», кнопка «Без чаевых» (доступно и телефонному клиенту, ТЗ §7.1, §18 №11); «Скачать акт (PDF)»; «Позвонить диспетчеру».
- **Состояния:** ожидание callback провайдера; неуспех — повтор; уже оплачено (наличные/QR мастеру) — блок оплаты скрыт, показан канал оплаты.
- **Переходы:** оплата → чаевые (опционально) → W-04.
- **Крайние случаи:** неоплата — дунинг B2C: push/SMS T+24/T+72, блок новых заявок (ТЗ §8.9).
- **ТЗ:** §12, §9.1, §8.9.

#### W-04. Оценка
- **Назначение:** оценка 1–5 без приложения.
- **Кто видит:** телефонный клиент.
- **Точки входа:** после оплаты в W-03; SMS-приглашение.
- **Данные:** мастер, заявка.
- **Элементы и действия:** 5 звёзд + комментарий; «Отправить».
- **Состояния:** отправка/ошибка; окно 72 ч истекло — «спасибо, окно оценки закрыто».
- **Переходы:** финальный экран «Спасибо» + одноразовая ссылка на приложение.
- **Крайние случаи:** оценка 1–2 → тикет диспетчеру (как в приложении); не оценил — попадает в выборку QC-прозвона (ТЗ §17.11).
- **ТЗ:** §12, §17.11.

#### W-05. Ссылка недействительна / истекла
- **Назначение:** безопасный тупик по истёкшему/использованному токену.
- **Кто видит:** телефонный клиент.
- **Точки входа:** любой W-экран с невалидным токеном.
- **Данные:** нейтральное сообщение без данных заявки.
- **Элементы и действия:** «Позвонить диспетчеру» (диспетчер вышлет свежую ссылку); ссылка на приложение.
- **Состояния:** статический.
- **Переходы:** —
- **Крайние случаи:** перебор URL не раскрывает существование заявки (одинаковый ответ на «нет заявки» и «нет прав»).
- **ТЗ:** §12 п.5.

### 3.N. Экраны контура «Дом» (M7, DEV-15)

Раздел появляется целиком в M7. Для жителя неподключённого объекта ни один из экранов ниже не показывается — приложение работает ровно как в v2.25.

#### C-51. Мой дом
- **Назначение:** сделать приложение нужным жителю чаще, чем раз в полгода, и дать управляющей компании канал, которого у неё нет.
- **Кто видит:** житель помещения в объекте со статусом `active`.
- **Точки входа:** вкладка/раздел главного экрана при наличии контекста «Житель»; deep-link из push об отключении; QR с наклейки в подъезде через L-10.
- **Данные:** `Building` (название, аварийный и диспетчерский телефоны), лента `BuildingAnnouncement`, ближайшие `ResourceShutdown`, свои `BuildingObservation`.
- **Элементы и действия:** **крупная кнопка «Аварийная служба дома»** (звонок на `emergency_phone`) первым блоком; лента объявлений УК; блок «Ближайшие отключения» с датой, ресурсом и зоной; «Сообщить о проблеме в доме» → C-52; «Отключения и работы» → C-53; «Пропуск гостю» → C-54; контакты УК.
- **Состояния:** пусто — «В доме сейчас всё спокойно»; объект в `degraded` — честная плашка «Управляющая компания временно не подтверждает доступ, заявки принимаются в обычном порядке»; офлайн — кеш с меткой давности.
- **Переходы:** → C-52, C-53, C-54, C-14, tel:.
- **Крайние случаи:** житель нескольких помещений (квартира + паркинг + офис) — переключатель объекта в шапке; смена управляющей компании — раздел не пропадает, меняются название и контакты, история жителя сохраняется (DEV-15 §12 п.4); арендатор видит раздел полностью, но заявки по общему имуществу подаёт с пометкой роли.
- **ТЗ:** §11, §14 · DEV-15 §10.3.

#### C-52. Сообщить о проблеме в доме (заявка в УК)
- **Назначение:** дать жителю канал по общему имуществу — течёт в подъезде, не горит лампа, сломан домофон, грязь у мусорных площадок. **Для жителя бесплатно**, в биллинг платформы не попадает.
- **Кто видит:** житель подключённого объекта.
- **Точки входа:** C-51; C-07 при выборе категории, помеченной как общее имущество (мягкое перенаправление «это зона ответственности УК — передадим им»).
- **Данные:** создаёт `BuildingObservation` с `source = resident`.
- **Элементы и действия:** фото с камеры (обязательно ≥1); выбор категории плиткой из справочника A-44; где именно (подъезд/этаж или «во дворе»); комментарий текстом или голосом — необязателен. **Не более трёх шагов.**
- **Состояния:** отправка; офлайн — в очередь; дубль по зоне за 14 дней — предложение «здесь уже есть обращение, присоединиться?».
- **Переходы:** → экран статуса обращения (в C-51).
- **Крайние случаи:** **аварийная ситуация** (льёт, искрит, запах газа) — категория с меткой `emergency`: экран немедленно предлагает **позвонить в аварийную службу**, а не ждать обработки, и параллельно создаёт обращение с автодозвоном оператору (DEV-15 §7.5 п.4). Жителю прямо написано: «За устранение отвечает {название УК}» — платформа общее имущество своими мастерами не чинит. Устранение последствий **в вашей квартире** (откачка, сушка, ремонт отделки) — обычная платная заявка, кнопка доступна тут же.
- **ТЗ:** §4.3, §11 · DEV-15 §7.5, §7.7.7.

#### C-53. Отключения и работы в доме
- **Назначение:** заменить бумажное объявление на подъезде.
- **Данные:** `ResourceShutdown` по помещениям жителя — плановые, идущие и история.
- **Элементы и действия:** календарь и список: ресурс, окно, зона, причина; статус «запланировано / идёт / восстановлено»; напоминание пушем за 2 ч (подписка включена по умолчанию, отключаемая).
- **Состояния:** пусто — «Отключений не запланировано». Превышение планового окна — карточка обновляется новым прогнозом, а не остаётся с истёкшим временем.
- **Крайние случаи:** отключение, созданное задним числом, показывается с фактическим временем без ложного «предупреждали заранее»; житель без приложения получает то же самое SMS (PRD-05 §6.3 п.8).
- **ТЗ:** §11 · DEV-15 §5.

#### C-54. Пропуск гостю или своему подрядчику
- **Назначение:** самая частая бытовая нужда жителя закрытого ЖК или БЦ — и лучший повод установить приложение.
- **Элементы и действия:** имя гостя, дата и окно, тип (гость / мой подрядчик / доставка), автомобиль и номер — опционально; кнопка «Выписать пропуск» → QR и числовой код, которыми можно поделиться любым мессенджером.
- **Крайние случаи:** правила объекта могут требовать подтверждения УК — тогда пропуск создаётся в статусе ожидания с честным сроком. **Свой подрядчик жителя** для работ, затрагивающих общее имущество, требует наряда-допуска на общих основаниях — запрет не вводится, но процедура обычная, без ускорения (DEV-15 §12 п.1). Лимит активных пропусков в сутки — параметр объекта, защита от превращения квартиры в проходной двор.
- **ТЗ:** §14, §17.15 · DEV-15 §6.

#### C-55. Голосования и опросы дома
- **Назначение:** канал УК для сбора мнений.
- **Фаза:** **Pro, фаза 2.** В M7 не разрабатывается; ID зарезервирован.

#### C-56. Согласование доступа в моё помещение
- **Назначение:** обратная сторона наряда-допуска, о которой легко забыть: чтобы починить стояк, часто нужно попасть **в чужую квартиру**. Сегодня альтернатива — стучать в дверь.
- **Кто видит:** житель, чьё помещение попало в `affected_unit_ids` наряда.
- **Точки входа:** push «Соседу снизу нужен доступ к стояку в вашей квартире».
- **Данные:** наряд, инициатор (заявка соседа или работа УК), запрошенное окно, кто придёт (имя и фото мастера, ссылка на L-07).
- **Элементы и действия:** **[Подтвердить окно]** · **[Предложить другое время]** · **[Отказать]** с причиной. После подтверждения — карточка с временем и данными мастера.
- **Крайние случаи:** молчание — эскалация к диспетчеру и оператору, авто-согласия за жителя **не бывает никогда** (доступ в частное помещение); авария — доступ запрашивается, но локализация не ждёт согласия (ТЗ §4.3); житель в отъезде — вариант «дам ключ соседу/консьержу» с фиксацией в наряде.
- **ТЗ:** §4.1, §4.3, §17.5 · DEV-15 §4.

#### C-57. Простой режим
- **Назначение:** дать пожилым жителям работающий канал вместо отдельного SMS-контура. **Режим внутри приложения, не вторая сборка** (решение владельца, DEV-15 §10.3.1).
- **Кто видит:** любой житель, включивший режим сам или получивший его от члена семьи.
- **Точки входа:** переключатель в C-30 «Профиль»; включение членом семьи с его аккаунта — приложение обычно ставит взрослый ребёнок.
- **Элементы и действия:** **не более трёх действий на экране**. (1) Крупная кнопка **«Вызвать мастера»** → прямой звонок на общий номер; заявку оформляет диспетчер через D-08. (2) **«Аварийная служба дома»** → звонок на `emergency_phone`. (3) «Мои заявки» — крупный список, **статус словами**, без цветовых кодов и иконок.
- **Чего в режиме нет:** промо и акций, баллов и ваучеров, чаевых, апсейлов, рекомендаций мастера, онлайн-оплаты, лент. Только тапы — без свайпов и длинных нажатий. Типографика и контраст — DEV-06 (раздел простого режима).
- **Состояния:** офлайн — телефонные кнопки работают всегда, они не требуют сети.
- **Крайние случаи:** режим **не предлагается автоматически по возрасту** — это оскорбительно и повышает отток; выход из режима — там же, где вход, без пароля; уведомления в простом режиме приходят и пушем, и SMS (у таких жителей приложение часто выгружено из памяти).
- **ТЗ:** §11, §12 · DEV-15 §10.3.1.

## 6. Нефункциональные требования приложения

- **Платформы:** Flutter, iOS + Android, единая кодовая база с приложением «Мастер» не требуется (два отдельных приложения — ТЗ §14).
- **Языки:** русский + узбекский (латиница) с первого релиза; переключение в профиле; язык всех исходящих коммуникаций (push/SMS/документы/веб-карточка) — из профиля пользователя; все шаблоны двуязычные (ТЗ §14).
- **Офлайн-поведение клиента:** в отличие от приложения «Мастер», полный офлайн не требуется. Обязательный минимум: кеш последнего состояния главного экрана, активной заявки и истории с баннером «Нет соединения»; инструкция при аварии (C-33) кешируется; создание заявок, утверждения, оплаты и любые юридически значимые действия офлайн недоступны и явно блокируются (санкции — только онлайн, аудит требует серверной фиксации); черновик создаваемой заявки переживает потерю сети и убийство процесса; автоповтор отправки при восстановлении сети без дублей (идемпотентные запросы).
- **Часовой пояс и валюта:** отображение Asia/Tashkent (UTC+5); суммы в сумах без копеек, разряды пробелами, округление до 100 сум по единому правилу (ТЗ §8.1, §14).
- **Фото:** сжатие на клиенте до ~1600px/≈500КБ, EXIF-очистка; загрузка с прогрессом и поштучным ретраем; просмотр по signed URL только участникам заявки (ТЗ §14).
- **Безопасность:** JWT с ротацией; каждая роль проверяется на API (клиентская сборка UI — не защита); PIN/биометрия для утверждений выше порога (§5.2); телефон мастера клиенту — только кнопкой звонка; персданные хранятся на серверах в РУз (ЗРУ-547 — серверное требование, влияет на эндпоинты).
- **Доступность:** динамические размеры шрифта ОС; контраст WCAG AA для статусов и светофора (не только цвет — иконки/подписи на плитках дашборда); TalkBack/VoiceOver-метки для всех кнопок действий (особенно «Утвердить»/«Отказаться» — юридически значимые); минимальная область тапа 44×44 pt; крупные кнопки в аварийном сценарии.
- **Push:** FCM; бейдж непрочитанных утверждений на иконке (ТЗ §6.4); при отсутствии FCM-токена критичные события дублируются SMS (ТЗ §11); deep-links (universal links / app links) для всех событий таблицы §5.
- **Обновления:** force update по минимальной версии; feature flags для поэтапного включения (техдолг, пакетные утверждения, «Моя техника», Uzum — фаза 2); версионирование API (ТЗ §14).
- **Производительность:** холодный старт ≤ 3 с на средних устройствах (в Ташкенте распространены бюджетные Android); список окон слотов — ответ планировщика ≤ 2 с; работа на Android без Google-сервисов (деградация: карты, пуши → SMS).
- **Мониторинг:** сбор ошибок (Sentry или аналог); телеметрия обязательна (ТЗ §17.17 п.11): воронка создания заявки по шагам визарда, клики по недоступным окнам (упущенный спрос — ТЗ §17.3, §13), источники создания, платежи, оценки — полный каталог аналитических событий в DEV-08 §5.
- **Веб-карточка:** SSR/лёгкий SPA ≤ 200КБ первичной загрузки (открывается по мобильной сети с дешёвых телефонов); одноразовые подписанные токены с ограниченным сроком жизни; одинаковый ответ на невалидный токен и отсутствующую заявку; журналирование действий как подтверждений клиента (ТЗ §12).
