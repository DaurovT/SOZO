# PRD-03: Веб-панель «Диспетчерская» USTAPRO

**Версия:** 1.0 · **Дата:** 19.07.2026 · **Источник истины:** ТЗ USTAPRO v2.25 (разделы 2.2, 3.4, 4, 5.3, 7.3, 8.4, 11, 12, 17.3, 17.5, 17.6a, 17.10, 17.11)
**Платформа:** веб (desktop-first, Chrome/Edge, минимальная ширина 1440 px). Язык интерфейса: русский.

---

## 1. Обзор

Диспетчерская — операционный центр платформы. Диспетчер — узкое горлышко системы (ТЗ 17.3): все заявки, назначения, модерация фото, споры, жалобы и голосовые контакты проходят через панель. Панель обязана делать состояние операционного дня полностью наблюдаемым и управляемым: «ничего не живёт в голове диспетчера» — всё в очередях, таймерах и журналах.

### 1.1. Роли панели

| Роль | Скоуп | Ключевые отличия |
|---|---|---|
| **Зонный диспетчер** | 1–2 закреплённые зоны (районы Ташкента), норматив 1 диспетчер на 50–70 мастеров (ТЗ 17.3) | Панель по умолчанию отфильтрована его зонами; ведёт заявки, ленты, очереди своих зон |
| **Старший смены (старший диспетчер)** | Все зоны города | Видит всю картину; полная пересборка лент при массовом инциденте; эскалированные споры, апелляции мастеров и жалобы руководителей организаций; распределение зон по диспетчерам смены |

Роль — свойство аккаунта (ТЗ 2.2); один пользователь может быть старшим в одной смене и зонным в другой. Матрица прав — раздел 6 этого PRD.

### 1.2. Зонное шардирование

Город разбит на зоны (справочник зон, ТЗ 17.4). Диспетчерская шардируется по зонам (ТЗ 17.3): каждый экран панели имеет глобальный **зонный фильтр** (мультиселект), по умолчанию = зоны текущего диспетчера. Старший смены по умолчанию видит «Все зоны». Кросс-зонные события (аварии, замены, перекидка мастера между зонами) подсвечиваются обеим сторонам. MVP — зонный фильтр как представление; полноценное шардирование диспетчеров — фаза 2 (ТЗ 17.3, этапность).

### 1.3. Режим 24/7 и передача смены

Платформа принимает заявки круглосуточно (ТЗ 17.6a). Ночь (22:00–07:00, параметры): минимум 1 диспетчер ночной смены, ночные зонные дежурные мастера, ночной коэффициент к работам. Ночью плановые B2C-окна не бронируются (кроме B2B-точек с ночным графиком доступа); наценка «Срочно» ночью не применяется — действует только ночной коэффициент (наценки взаимоисключающие, применяется наибольшая). Очередь «Позвонить» ночью обслуживает только операционные звонки (QC/B2B-ритм/дунинг — дневное окно 9:00–20:00, ТЗ 17.11).

**Передача смены (handover, ТЗ 12):** незакрытые инциденты, ожидания утверждений, VIP-контроли, активные протоколы замены и открытые задачи переходят следующей смене через handover-журнал с **явной отметкой приёма** каждого пункта. Смена не считается сданной, пока все пункты не приняты (экран D-17).

## 3. Экраны

### 3.1. D-01. Дашборд смены

**Назначение.** Первый экран смены: за 30 секунд понять, где горит. Агрегатор всех очередей и таймеров панели.

**Данные.** Счётчики по зонам фильтра: новые неназначенные (с возрастом старейшей), «Требуется замена» (активные протоколы + таймеры), очередь проверки фото/чеков, очередь «Позвонить» (просроченные SLA отдельно), жалобы (в работе / просрочка SLA), споры открытые, «Заблокировано третьей стороной» (с датой попытки сегодня), лист ожидания, ожидания утверждений B2B (по таймерам 5.3), заявки с риском срыва окна (из прогноза 17.3), непринятые пункты handover, апелляции мастеров (открытые). Метрики смены: время «Новая → Назначена» (текущее среднее), доля заявок в окне сегодня.

**Элементы и действия.** Каждый счётчик — кликабельная плитка → соответствующий экран с предустановленным фильтром. Лента live-алертов справа (см. раздел 5). Кнопка «Принять смену» при непринятом handover (блокирующий баннер). Кнопка «Режим инцидента» доступна зонному (для своей зоны) и старшему смены; старшему смены — дополнительно разбивка по зонам/диспетчерам.

**Состояния.** Норма (все SLA зелёные) / внимание (жёлтые таймеры) / горит (красные: просроченный SLA жалобы, замена > 15 мин, авария без назначения). Пустое состояние ночной смены: только операционные очереди, несрочные скрыты с пометкой «дневное окно с 9:00».

**Переходы.** → любой экран очереди; → D-06 по клику на заявку в алерте; → D-17 из баннера handover.

**Крайние случаи.** Обрыв соединения — баннер «нет связи, данные на {время}», автопереподключение; расхождение зонного фильтра с зонами смены (диспетчера переназначили) — предложение сбросить фильтр.

**Ссылки на ТЗ:** 12, 17.3 (KPI, тепловая карта), 17.10, 17.11, 11.

### 3.2. D-02. Kanban-доска заявок

**Назначение.** Оперативный обзор всех заявок по статусам жизненного цикла; главный рабочий экран распределения.

**Данные.** Колонки = статусы 4.1: Новая, Оценена, На утверждении, Утверждена, Назначена, Мастер выехал, В работе, Доп-согласование, Выполнена, Проверена, Ожидает оплаты. Терминальные (Закрыта, Отменена) — в архивном представлении. Карточка-тайл: номер, тип (B2C/B2B/аварийная/осмотр/гарантийная/из осмотра), категория, адрес + зона, окно, мастер, сумма сметы, возраст в статусе, флаги (аварийная — красная рамка; «Требуется замена»; срочная; гео-флаг; «выполнена частично»; многодневная — индикатор числа дней; пауза: технологический перерыв / ожидание материалов / заблокировано).

**Элементы и действия.** Фильтры: зона (глобальный), тип, категория, мастер, флаг, поиск. Заявки с флагом «Требуется замена» — красные, вверху доски (ТЗ 17.3). Drag карточки между колонками запрещён (переходы — только через действия карточки D-06, статусная машина на API отклоняет переходы вне графа, ТЗ 4.1). Клик → D-06 (боковая панель-preview + открытие полной карточки). Быстрые действия из тайла: назначить (для Утверждена/Оценена), позвонить, перехватить авто-назначение аварийной (ТЗ 4.3).

**Состояния.** Live-обновление (websocket): новая заявка появляется с подсветкой + звук (раздел 5). Сортировка в колонке — по приоритету очереди 17.3 (аварийные → B2B в окне → гарантийные → продолжения этапных → срочные → FIFO), затем по возрасту.

**Переходы.** → D-06; → D-15 (переназначение) из контекстного меню; → D-12 по красной карточке.

**Крайние случаи.** Дубли: тайл с меткой «похожая заявка есть» (проверка 24 ч по точке/адресу+категории, ТЗ 4.1) — действие «Слить как дубль» (причина отмены «дубль»). Анти-дробление B2B: заявка с флагом «> N авто-стартов за 48 ч» требует ручной проверки до запуска (ТЗ 5.1). Аварийная, авто-назначенная системой, показывается уже в «Назначена» с меткой «авто» — диспетчер может перехватить.

**Ссылки на ТЗ:** 12, 4.1–4.3, 5.1 (анти-дробление), 17.3 (приоритеты).

### 3.3. D-03. Карта города

**Назначение.** Пространственная картина: где мастера, где заявки, где кластеры проблем.

**Данные.** Слои: (1) мастера — последняя гео при активной заявке (ТЗ 12), цвет по состоянию (едет / на объекте / свободен / дежурный), иконка авто у автомобильных; (2) заявки — пины по статусам, аварийные красные; (3) границы зон; (4) инцидент-кластеры (при включённом режиме D-13) — окружности с числом заявок; (5) слой «риск»: заявки со срывом окна.

**Элементы и действия.** Клик по мастеру: мини-карточка (имя, текущая заявка, расчётное завершение, следующая) → «Открыть ленту» (D-05), «Позвонить». Клик по заявке: preview → D-06. Лассо-выделение заявок кластера → «Создать инцидент» (зонный или старший, → D-13). Фильтр зон применяется, но аварии соседних зон видны полупрозрачно (кросс-зонные аварии разрешены, ТЗ 17.3).

**Состояния.** Гео мастера обновляется только при активной заявке; мастер без активной заявки — на базе последней точки со стилем «нет трека». Устаревшая гео (> 15 мин) — серый маркер.

**Переходы.** → D-05, D-06, D-13.

**Крайние случаи.** После «Выехал» гео не приближается к адресу 15+ мин — мягкий флаг на маркере + алерт (триггер протокола замены, ТЗ 17.3). Фото/гео вне радиуса ±300 м от адреса — заявка получает гео-флаг (мягкая проверка, не блок, ТЗ 4.1). Мастер в подвале без связи — маркер «оффлайн» без тревоги (штатно, ТЗ 7.2).

**Ссылки на ТЗ:** 12, 17.3 (детект протокола замены), 4.1 (гео-проверка), 7.2.

### 3.4. D-04. Тепловая карта дня

**Назначение.** Прогнозная загрузка: увидеть срывы окон до того, как они случились, и перебалансировать.

**Данные.** Матрица «мастер × часы дня» по зоне: заполненность слотов (30-минутная сетка, ТЗ 17.3), цвет = загрузка; **красная подсветка** заявок с риском срыва (прогноз завершения предыдущей работы позже начала следующей); строка сводной загрузки зоны по часам; маркеры аварийного резерва ёмкости (X% часа не бронируется под плановые); отдельные строки: очередь срочных, лист ожидания.

**Элементы и действия.** Клик по красной ячейке → варианты перебалансировки, предложенные системой: переназначить свободному, сдвинуть с извинением (проактивный push), обменять заявки между мастерами. Принятие предложения выполняет соответствующую атомарную операцию D-05. Кнопка «Закрыть окна сегодня» (авто при перегрузе: спрос > ёмкость — окна «сегодня» закрываются, клики клиентов считаются упущенным спросом, ТЗ 17.3). Переключатель дня (сегодня / завтра — черновики D−1).

**Состояния.** Пересчёт прогнозов по событиям (кнопка мастера «Задерживаюсь +30/60», ранний финиш, отмена). MVP — упрощённо: сводка загрузки и ручная очередь с подсказкой «кто освободится раньше»; авто-пересчёт ETA, полная тепловая карта и предложения перебалансировки — фаза 2 (ТЗ 17.3, этапность).

**Переходы.** → D-05 (строка мастера), → D-18 (строки срочных/листа ожидания), → D-06.

**Крайние случаи.** «Задерживаюсь» выбивает следующую заявку за окно → алерт с вариантами (ТЗ 17.3); аварийная вытесняет плановую → диспетчер видит конфликт и переносит плановую с извинением и push (ТЗ 17.3); освободившийся слот — авто-предложение по приоритетам: срочные → лист ожидания (push «появилось окно») → подтягивание гибких из хвоста.

**Ссылки на ТЗ:** 12, 17.3 (планировщик, аварийный резерв, перегруз, освободившийся слот).

### 3.5. D-05. Ленты мастеров

**Назначение.** Лента = ячейка сетки «мастер × день»: упорядоченный маршрут дня. Здесь диспетчер правит планы руками.

**Данные.** По каждому мастеру зоны: последовательность заявок с окнами, дорожными буферами (матрица езды зона→зона + запас 20%, параметр), якорные метки (жёсткие окна клиентов, графики доступа B2B, «Заблокировано» с подтверждённым временем доступа — якорь), гибкие (осмотры, лист ожидания), сессии этапных работ, метка «план дня ≤ 80% смены» с индикатором превышения. Метрики здоровья сетки в шапке: churn лент, дыры, средний пробег, доля интрадей-вставок, доля заявок в окно (ТЗ 17.3).

**Элементы и действия.** Drag-and-drop, ограниченный **четырьмя атомарными операциями** (ТЗ 17.3, анти-каша №2): (1) вставить заявку в дыру ленты; (2) сдвинуть хвост ленты; (3) обменять две заявки между мастерами; (4) заменить мастера (запускает протокол D-12). Каждая операция автоматически рассылает пуши всем затронутым (мастерам и клиентам). **Правило заморозки:** ближайшие 2 часа каждой ленты закрыты для автоматики и визуально «заморожены»; диспетчер может править вручную — с явным подтверждением «трогаете горячую зону» (ТЗ 17.3, анти-каша №1). Кнопка «Полная пересборка» — только старший смены, только при массовом инциденте. Утренний режим «волновой сборки»: список аномалий авто-черновиков D−1, диспетчер за 15 минут просматривает и подтверждает ленты (правит, а не собирает).

**Состояния.** Черновик (D−1, вечер) / подтверждена (утро) / live (интрадей — только события). Парные заявки — сдвоенный блок «ведущий+помощник» в двух лентах с линией связи; экипаж дня (фаза 2) — общая лента двух мастеров. Заявки, требующие оборудование/авто, — только в ленты мастеров с выданным оборудованием и признаком «авто» (транспортный фильтр, ТЗ 17.3, 17.9).

**Переходы.** → D-06, → D-12 (операция «заменить мастера»), → D-04.

**Крайние случаи.** Drop, ломающий подтверждённую бронь другого клиента, — блок с объяснением («обещания святы», ТЗ 17.3: подтверждённые брони ради срочной не ломаются); нарушение допустимого окна этапа этапной работы — предупреждение с вариантами из инварианта 4.1 (перенос всей цепочки / сверхурочный слот с согласия мастера / передача с разделом доли); вставка в ленту дежурного — предупреждение (дежурному плановые не бронируются; с середины тихого дня — можно срочные и лист ожидания рядом с зоной, ТЗ 17.3).

**Ссылки на ТЗ:** 12, 17.3 (рабочая сетка, три горизонта, заморозка, атомарные операции, дежурный резерв, парные работы, транспортный фильтр), 17.9.

### 3.6. D-06. Карточка заявки

**Назначение.** Полное досье заявки — всё из Order (ТЗ 3.4) плюс действия диспетчера.

**Данные (вкладки).**
- **Сводка:** номер, тип, срочность, источник (приложение/телефон/бот), клиент или точка (с лимитами и остатком месячного лимита для B2B), создатель, категория, описание, фото клиента (до 5), желаемое время, назначенное окно, мастер + история переназначений, связанные заявки, скидка/промокод, канал списания, статус передачи лицензиату-субподрядчику (для лицензируемых категорий, если применимо).
- **Статус и журнал:** текущий статус, журнал переходов (кто, когда, откуда/куда), таймеры эскалаций 5.3, возраст в статусе, индикатор многодневной работы.
- **Смета:** первичная (для B2C — вилка «от–до»), утверждённая, доп-сметы [{сумма, тип: вынужденная/апсейл, статус, кто утвердил, когда}], позиции с копией цен на момент заявки, позиция «Минимальный заказ», зачёт диагностики, событие «смета подтверждена на месте» (B2C).
- **Фото:** «до» / «в процессе» / «после», серверный таймштамп + геометка каждого, флаги «без гео», «зафиксировано офлайн», гео-флаг ±300 м; для режимных объектов — код приёмки + подпись представителя вместо фото (ТЗ 4.1).
- **Материалы:** расходники сумки (по фикс-каталогу, без чеков, с проверкой нормативов расхода — превышение = флаг, ТЗ 8.4.1), запчасти с чеками/накладными; **сверка накладной партнёрского магазина с позициями сметы** (расхождение — разбор, ТЗ 8.4.4); фото-доказательство замены для дорогих запчастей (старая / новая в упаковке / установлена, ТЗ 8.4.3); выбор ценовой категории клиента (эконом/стандарт/премиум) в аудите.
- **Аудит:** все значимые действия (утверждения — кто/когда/сумма/устройство, устные согласования «озвучено по телефону», ручные подъёмы приоритета с причиной).
- **Оплата/итог:** работы, материалы, способ, статус биллинга; долг аккаунта B2C.

**Элементы и действия.** Звонок клиенту/мастеру (MVP — показ номера, фаза 2 — клик-ту-колл с записью, ТЗ 12); перевод статусов, доступных диспетчеру (Оценена; Проверена/возврат — через D-07; Ожидает оплаты — санкция «отпустить без оплаты» с причиной, ТЗ 4.1 п.11); отмена с причиной из справочника (последствия по матрице 4.4 показываются до подтверждения: ложный вызов, оплата факта, компенсации мастеру); фиксация устного согласования от имени клиента с пометкой «озвучено по телефону» → аудит; открытие спора; переназначение / раздел заявки (→ D-15); передача лицензиату-субподрядчику для лицензируемых категорий (газ, лифты, ТЗ 17.8): выбор партнёра из справочника лицензиатов, статус передачи (предложено → принято лицензиатом → в работе → выполнено/отказано), комментарий условий передачи — в аудит; дробление на связанные заявки (разные специальности — ТЗ 4.5); слияние дубля; пауза «Ожидание материалов» с датой повторного визита; подтверждение фактически выполненной части при остановке работ клиентом (мастер фиксирует, диспетчер подтверждает, ТЗ 4.4); квалификация вины по гарантийной переделке (мастер/материал/эксплуатация — влияет на удержания 0/50/100%, ТЗ 4.2); решение «кто платит фикс помощника» при непарной позиции (клиент — никогда; компания / доля ведущего, ТЗ 17.3); подтверждение закупки сверх лимита 500 000 по фото ценника (ТЗ 8.4.3).

**Состояния.** Read-only для терминальных статусов (кроме открытия спора в окне 72 ч и гарантийной заявки-ссылки). Индикатор «не синхронизировано» при офлайн-конфликте мастера (ТЗ 7.2).

**Переходы.** → D-07 (модерация), D-11 (спор), D-15, D-16 (если заблокирована), D-08 (карточка клиента), связанные и исходные заявки.

**Крайние случаи.** «Клиент недоступен» от мастера (фото двери + гео) → авто-задача прозвона 15 мин в D-09, затем отмена с ложным вызовом (ТЗ 4.4); «Прервать: небезопасно» от мастера → решение диспетчера, отмена без штрафа мастеру, кандидат в чёрный список (ТЗ 17.5); заявка вне зоны покрытия не создаётся — лид-лист «ждут покрытия» (ТЗ 17.4); телефон клиента мастеру виден только со статуса «Назначена» до «Закрыта» (ТЗ 17.5) — диспетчер видит всегда; лицензиат-субподрядчик отказался от переданной заявки — возврат в очередь назначения с флагом «нужен лицензиат», диспетчер выбирает другого партнёра или эскалирует (ТЗ 17.8).

**Ссылки на ТЗ:** 3.4, 4.1–4.6, 8.4, 12, 17.5, 17.8.

### 3.7. D-07. Очередь проверки фото/чеков

**Назначение.** Модерация перехода «Выполнена» → «Проверена»: фото до/после, чеки, материалы (ТЗ 4.1 п.10, 12).

**Данные.** Очередь заявок в «Выполнена» (FIFO с приоритетом: B2B, споро-рисковые, мастера на испытательном — их пакеты проверяются на 100%, ТЗ 7.4). Панель сравнения фото «до/после» рядом, чеки/накладные, позиции материалов против сметы, флаги: «без гео», гео-флаг, превышение норматива расходников, расхождение накладной со сметой, офлайн-фиксация, итоговая сумма ≠ утверждённой, «принято без кода» (мастер закрыл заявку без кода подтверждения клиента — no-code fallback, приёмка подтверждена диспетчером вручную), «согласовано офлайн» (смета подтверждена подписью клиента пальцем без сети — ТЗ 17.17 п.7).

**Элементы и действия.** «Принять» → статус «Проверена» (для B2B и наличных B2C — сразу к закрытию, «Ожидает оплаты» пропускается, ТЗ 4.1); «Вернуть с комментарием» → возврат в «В работе» с обязательным комментарием (влияет на компоненту рейтинга «качество фиксации», ТЗ 7.4). Хоткеи (A — принять, R — вернуть) для конвейерной работы. Фильтр очереди по флагам, включая «принято без кода» и «согласовано офлайн», — отдельное представление для точечной проверки таких заявок; «согласовано офлайн» проверяется выборочно аналогично «принято без кода» — при выборочной проверке диспетчер прозванивает клиента и подтверждает, что смета действительно согласовывалась (ТЗ 17.17 п.7). Метрика времени модерации — в KPI (D-19).

**Состояния.** Пустая очередь; заявка «выполнена частично» (консервация после отказа от вынужденных работ) — проверка фото проблемы и записи «клиент предупреждён об опасности» (ТЗ 4.6); режимный объект — проверка кода приёмки и подписи вместо фото; заявка «принято без кода» — приоритетная проверка (наравне с испытательными).

**Переходы.** → D-06 (полная карточка), → D-11 (если оплата уже принята на месте и недочёты не закрываются доработкой — спор, ТЗ 4.1 п.10).

**Крайние случаи.** Возврат не отменяет уже принятую оплату — только доработка или спор (ТЗ 4.1 п.10); многодневная/этапная: промежуточные сессии дают фото «в процессе» + отметку этапа/консервацию объекта — модерация финальная на последней сессии; фото, досланные офлайн-синком после «Выполнена», дозаполняют пакет — карточка обновляется в очереди; «принято без кода» без комментария диспетчера, кто и как подтвердил приёмку, — заявка не может быть переведена в «Проверена»; осмотр с пометкой «без представителя» — попадает в очередь выборочной проверки (аналогично «принято без кода»): диспетчер прозванивает точку для подтверждения визита мастера (ТЗ 9.3).

**Ссылки на ТЗ:** 4.1 (п. 9–10), 4.6, 7.2, 7.4, 8.4, 9.3, 12.

### 3.8. D-08. Создание заявки по телефону

**Назначение.** Обязательный сценарий (половина B2C звонит, приложение им не нужно, ТЗ 12): создать заявку, согласовать окно и назначить мастера, не вешая трубку.

**Данные.** Автопоиск клиента по номеру: существующий — карточка с историей заявок и паспортом техники (ClientAsset) сразу на экране; новый — форма 30 секунд (имя, адрес → определение зоны). **Адресный блок с картой:** ввод адреса с подсказками геокодера + мини-карта с пином, который диспетчер двигает прямо во время разговора («ориентир — школа №12» → пин на дом рядом); зона и дорожный буфер определяются по координате пина, не по тексту адреса. Живой планировщик: реально доступные окна по зоне+skill (ТЗ 17.3 — «никогда не обещаем то, под что нет ёмкости»). Справочник позиций прайса с вилками цен B2C; вилки цен — из активного релиза прайса (для организаций с договором — из релиза договора); заявка фиксирует свой релиз при создании (ТЗ 3.7). Входящий по **выделенному номеру лендингов** (параметр) → заявка автоматически метится «источник: лендинг-звонок» — атрибуция без колл-трекинга (ТЗ 17.15).

**Элементы и действия.** Пошаговый флоу (ТЗ 12): (1) карточка клиента; (2) заполнение заявки голосом клиента: категория, описание, позиции с озвучиванием вилки; (3) **живой подбор окна:** «могу сегодня 16:00–18:00 или завтра с утра» — выбор клиента → бронь встаёт в ленту, мастер назначается сразу; диспетчер озвучивает имя мастера и окно; (4) фиксация устных согласований от имени клиента с пометкой «озвучено по телефону» (аудит); (5) отправка SMS со ссылкой на веб-карточку заявки (одноразовый подписанный токен). Опции в флоу: тариф «Срочно» (+30%, правило честности — авто-снятие через 3 ч, ТЗ 17.3) или бесплатный лист ожидания с честным прогнозным интервалом; чек-лист внешних зависимостей для категорий с общими зонами («нужно отключение стояка?» + поле «доступ подтверждён на {дата/время}», ТЗ 4.1); флаг «аварийная» → ветка 4.3 (авто-назначение ближайшему, локализация без утверждения); предупреждение о дубле (24 ч). Если при автопоиске выявлен сотрудник B2B-точки с включённой программой баллов — диспетчер привязывает его к заявке как **заявителя** (applicant_user_id): баллы по телефонным заявкам начисляются заявителю (ТЗ 17.14).

**Состояния.** MVP — обычные номера и ручной ввод; фаза 2 — автоподстановка звонящего, клик-ту-колл, запись (ТЗ 12). Геокодер не нашёл адрес (частные сектора, новые массивы) — пин ставится вручную по ориентиру + обязательный комментарий для мастера; пин вне зон покрытия — заявка не создаётся, телефон и адрес уходят в лид-лист «ждут покрытия» (ТЗ 17.4). Клиент с непогашенным долгом — блок создания до онлайн-оплаты долга (параметр: блокировать/предупреждать); исключение — аварийная: одновременная оплата долга или санкция диспетчера (ТЗ 4.4).

**Переходы.** → D-06 (созданная заявка), → D-18 (в лист ожидания), → D-09 (пропущенный входящий → задача «перезвонить за 10 минут», ТЗ 12 п.6).

**Крайние случаи.** Адрес вне зоны покрытия → лид-лист «ждут покрытия», вежливый отказ (ТЗ 17.4); лицензируемая категория (газ, лифты) — заявка создаётся и передаётся лицензиату-субподрядчику (см. D-06, статус передачи); прямое назначение штатного мастера недоступно до получения платформой соответствующих лицензий (ТЗ 17.8); «не знаю, что сломалось» — первичная смета = «Выезд/диагностика», объём оформит мастер доп-сметой на месте (штатный сценарий, ТЗ 4.1); нет ёмкости в желаемое окно — честно предложить завтра, при отказе — задача D-09 (триггер «нет ёмкости», SLA 30 мин, продажа ожидания/срочного тарифа, ТЗ 17.11); перевод в приложение — одна SMS после первой закрытой заявки, без спама (ТЗ 12 п.7).

**Ссылки на ТЗ:** 12 (телефонный флоу целиком), 11 (профиль «SMS + веб-ссылка»), 17.3, 17.4, 4.1, 4.3, 4.4, 17.8, 17.14, 3.7, 17.15.

### 3.9. D-09. Очередь «Позвонить»

**Назначение.** Единая очередь всех голосовых контактов: каждый триггер = задача-звонок с приоритетом, SLA и скриптом; исходы — в ContactLog. «Ничего не держится в памяти диспетчера» (ТЗ 17.11).

**Данные.** Задачи с полями: триггер, заявка/клиент, приоритет, SLA-таймер (цвет по остатку), скрипт (текст, MVP), исходы предыдущих попыток. **Приоритеты (ТЗ 17.11):** операционные по активным заявкам (аварии, критический дефект по итогам осмотра, замены, «клиент недоступен», доп-сметы) → эскалации утверждений и дунинг → QC-прозвоны → B2B-ритм. Группы триггеров и SLA:
- *До работ:* **лид с лендинга B2C** (форма «Оставить заявку», L-02 — перезвон за 10 мин, тот же SLA, что пропущенный звонок; UTM лида наследуется создаваемой заявкой, ТЗ 17.15); заявка непонятна (15 мин); внешняя зависимость не подтверждена (2 ч); нет ёмкости в окно (30 мин); подтверждение накануне дорогой/этапной работы (до 20:00 D−1) — в чек-лист звонка входит задача «уточнить детали адреса (квартира/подъезд/домофон), если клиент не заполнил C-50» с полем ввода деталей диспетчером — зафиксированные детали снимают у мастера пометку «детали не указаны» и баннер у клиента (ТЗ 17.17 п.1).
- *Во время:* сдвиг окна > 1 ч или повторный (сразу); замена не решена за 15 мин (сразу); «клиент недоступен» (15 мин прозвона); вынужденная доп-смета без ответа 2 ч; авария B2B (автозвонок контактному лицу); молчание утверждающего T+48; критический дефект, выявленный при осмотре (риск безопасности — сразу, максимальный приоритет: предупредить клиента, зафиксировать «клиент предупреждён об опасности», предложить срочный тариф/ближайшее окно, ТЗ 4.6).
- *После (QC):* выборка N% закрытых (старт 10%, 24–48 ч, скрипт: качество, чистота, поведение, «порекомендуете?»); обязательный QC — первая заявка нового B2C, мастера на испытательном, чек > порога, доп-смета выросла > 50% (24–48 ч); оценка 1–2 (2 ч, живой разбор); выборка N% отменённых (48 ч, анти-сговор «мимо кассы», ТЗ 12); гарантийное обращение (4 ч); дунинг B2C T+30.
- *B2B-ритм:* выборка абонентки < 50% два месяца; сверхлимит > 30% два месяца (апсейл договора); за 30 дней до конца договора (звонок к продлению + авто-отчёт); ежемесячный контакт топ-N организаций.

**Элементы и действия.** «Взять задачу» → карточка звонка: скрипт, контекст заявки, кнопки исхода: дозвонился/нет, результат (структурированный по типу триггера), следующий шаг (перезвонить в {время} / создать жалобу / создать спор / закрыть). Каждый исход — запись ContactLog. Недозвон — авто-перепостановка с интервалом (параметр). QC с негативом → конвертация в жалобу/спор по процедуре (ТЗ 17.11).

**Состояния.** Ночная смена: видны только операционные; несрочные (QC, B2B-ритм, дунинг) — скрыты до дневного окна 9:00–20:00 (параметр). Просрочка SLA — красная строка + алерт.

**Переходы.** → D-06, D-08 (входящий/перезвон превращается в заявку), D-10 (создать жалобу), D-11 (создать спор).

**Крайние случаи.** «Клиент недоступен»: не дозвонились за 15 мин → отмена с ложным вызовом из карточки задачи (ТЗ 4.4); контрольный прозвон отменённой выявил «сделали мимо кассы» → эскалация старшему + разбор мастера; конфликт очереди (звонков больше, чем диспетчеров) — строгая сортировка по приоритетам, KPI фиксирует пропуски выборки QC.

**Ссылки на ТЗ:** 17.11 (весь раздел), 12 (пропущенные, контрольные прозвоны), 4.4, 5.3, 8.9.

### 3.10. D-10. Очередь жалоб

**Назначение.** Support-контур Complaint (ТЗ 17.10): жалобы шире споров — хамство, грязь, опоздание, курение, работа диспетчера, глюки приложения.

**Данные.** Complaint: тип (качество / поведение мастера / сроки / деньги → конвертируется в спор / сервис и диспетчер / приложение / другое), связь с заявкой (опциональна), кто подал, статус (новая → в работе → решена → закрыта), ответственный, резолюция, корневая причина (фаза 2). SLA-таймеры: первый ответ ≤ 2 ч в окне 8:00–22:00 (ночная жалоба — таймер с 8:00), резолюция ≤ 24 ч, сложные ≤ 72 ч (параметры, производственный календарь).

**Элементы и действия.** Взять в работу; резолюция **обязана ссылаться на метод из плейбука** (справочник, ТЗ 17.10): извинение + VIP-контроль следующей заявки; переделка (гарантийная механика 4.2); частичный/полный возврат (через спор с проводками → D-11); замена закреплённого мастера точки; B2B — звонок руководству + официальный ответ письмом. Тип «деньги» — кнопка «Конвертировать в спор». Закрытие — подтверждение клиента или таймаут 72 ч.

**Состояния.** Просрочка SLA → эскалация админу (авто); жалоба руководителя организации → **сразу старшему диспетчеру** (ТЗ 17.10, 11); повторная жалоба того же клиента по той же причине → немедленная эскалация (фаза 2); 3+ подтверждённых жалобы на мастера за 30 дней → авто-разбор (фаза 2).

**Переходы.** → D-06, D-11 (конвертация), D-09 (звонок клиенту по жалобе).

**Крайние случаи.** Жалоба без заявки (на приложение, на диспетчера) — полный цикл без Order; жалоба «мастер навязывал» (анти-давление апсейла) — сигнал в профиль мастера (ТЗ 4.6); подтверждённая жалоба на поведение/качество = событие уровня «оценка 1» в рейтинге — **после резолюции**, не в момент подачи; неподтверждённые на рейтинг не влияют (ТЗ 17.10).

**Ссылки на ТЗ:** 17.10 (весь), 4.2, 4.6, 11, 12.

### 3.11. D-11. Споры

**Назначение.** Спор — про деньги конкретной заявки (ТЗ 4.2): карточка, материалы, резолюция, возвраты.

**Данные.** Карточка спора: инициатор (клиент — кнопка «Оспорить» в окне 72 ч после «Выполнена», или диспетчер), причина (включая отдельную «приехал не тот мастер»), материалы заявки (фото до/после, чеки, аудит, ContactLog), сумма, статус, блокировка начисления доли мастеру до резолюции.

**Элементы и действия.** Резолюции: `в пользу клиента` (переделка/возврат) / `в пользу мастера` / `компромисс` (частичный возврат) — с обязательным комментарием в аудит. Возвраты: онлайн-оплаты — через refund-API провайдера (Payme/Click/Uzum) со сторнирующей проводкой; наличные мастеру — возврат делает **компания** переводом клиенту (не мастер из кармана), проводка + при вине мастера удержание с его баланса (ТЗ 4.2). Назначение гарантийной переделки (новая заявка типа «гарантийная» со ссылкой). Кнопка «Эскалировать».

**Состояния.** **Авто-эскалация старшему/админу:** спор на сумму выше порога (параметр) и спор по заявке, которую вёл тот же диспетчер, — «диспетчер не судит собственные заявки» (ТЗ 4.2, 12); такие споры для зонного диспетчера read-only.

**Переходы.** → D-06, гарантийная заявка, D-09 (звонок сторонам).

**Крайние случаи.** «Приехал не тот мастер» (лицо ≠ фото карточки) — грубое нарушение, вплоть до блокировки; оценки по спорам, решённым в пользу мастера, исключаются из его рейтинга (ТЗ 7.4); остановка работ клиентом — спорные случаи оплаты факта решает резолюция диспетчера (ТЗ 4.4); ущерб третьим лицам (затопили соседей) — не спор, а процедура резервного фонда 17.7: выезд старшего, акт, резолюция админа.

**Ссылки на ТЗ:** 4.2, 4.4, 8.7 (refund-API), 12, 17.7.

### 3.12. D-12. Требуется замена (протокол быстрой замены)

**Назначение.** Мастер исчез или отказался — новый мастер за 15 минут (ТЗ 17.3).

**Данные.** Активные протоколы: заявка (красная, дублируется вверху D-02), триггер детекта (не нажал «Выехал» за 30 мин до окна → авто-пинг → нет реакции 10 мин; явный отказ «Не могу поехать»; гео не приближается 15+ мин — мягкий флаг), таймер протокола (цель 15 мин), список кандидатов по порядку сборки: дежурный резерв → свободные рядом с нужным skill → расчётное завершение в ближайшие 30 мин → снять с гибкой заявки (планового осмотра), статус бродкаст-оффера.

**Элементы и действия.** Автозапуск протокола системой (диспетчер подключается вторым); экспресс-оффер **бродкастом всем кандидатам сразу, 120 сек, первый принявший забирает** (параллельный, не последовательный — ТЗ 17.3); клиенту немедленный авто-push «Мастер заменён, к вам едет {имя}, будет к {время}» или честный сдвиг окна — «молчание запрещено». Через 15 мин без принятия — задача «позвонить клиенту» (D-09, сразу): два варианта — сдвиг на сегодня позже или перенос на завтра с приоритетным первым окном и VIP-контролем. Пост-обработка: квалификация причины исчезнувшего (уважительная — без санкций, отметка; невыход без причины — удар по дисциплине + счётчик: 2-й за 90 дней — снятие с линии и разбор, 3-й — блокировка; невыход с ущербом — денежное удержание; явный отказ заранее — мягче тихого исчезновения).

**Состояния.** Детект → оффер → принят / не принят за 15 мин → решено звонком. Аварийная заявка в протоколе — максимальный приоритет + звук.

**Переходы.** → D-06, D-09, D-05 (перекидка снятой гибкой заявки).

**Крайние случаи.** Кандидатов нет вообще (ночь, дальняя зона) — сразу звонок клиенту, не дожидаясь 15 мин; замена в этапной работе — через «раздел заявки» (все сессии — один мастер, ТЗ 4.1); мастер «нашёлся» после запуска — оффер отменяется, если ещё не принят, иначе замена доводится.

**Ссылки на ТЗ:** 17.3 (протокол замены, детект, санкции), 4.4 (строка «мастер не вышел»), 4.5.

### 3.13. D-13. Режим массового инцидента

**Назначение.** Авария сети/отключение: > N заявок одной категории из одного района за час (ТЗ 17.3) — управлять кластером, а не сотней заявок поштучно.

**Данные.** Детект-баннер «возможен массовый инцидент: {категория}, {район}, {N} заявок/час»; карта кластера (из D-03); список заявок кластера с приоритизацией внутри; статус оповещений.

**Элементы и действия.** «Включить инцидент» (**зонный или старший смены** — инцидент может обнаружить и включить любой дежурный диспетчер): заявки группируются по кластеру; шаблонное оповещение клиентам «в вашем районе массовое отключение, мастера направлены» (конструктор на базе шаблона); приоритизация внутри кластера (уязвимые/аварийные первыми); направление мастеров пакетом; при инциденте старшему доступна полная пересборка лент затронутой зоны (единственное исключение из запрета глобальной пересборки, ТЗ 17.3). Новые заявки, попадающие в сигнатуру кластера, присоединяются автоматически с тем же оповещением. «Закрыть инцидент» — финальное оповещение, возврат к обычной диспетчеризации.

**Состояния.** Нет инцидента / детект (предложение) / активен (глобальный индикатор в шапке всех экранов) / закрыт (отчёт: заявок, время реакции, закрыто).

**Переходы.** → D-03 (кластер на карте), D-05 (пересборка), D-02 (фильтр «инцидент»).

**Крайние случаи.** Два одновременных инцидента в разных зонах — независимые кластеры; ложный детект (совпадение) — отклонение предложения с причиной; инцидент ночью — ночные дежурные + подъём дежурного резерва, эскалация админу при нехватке ёмкости.

**Ссылки на ТЗ:** 17.3 (режим массового инцидента, запрет пересборки), 12.

### 3.14. D-14. Расписание мастеров

**Назначение.** График доступности — фундамент планировщика: рабочие дни/часы, отпуска, больничные, дежурства.

**Данные.** Календарь «мастер × дни недели/месяца»: смены, отпуска/больничные (запросы из приложения мастера — на подтверждение диспетчеру, ТЗ 17.3), недельный график дежурств («скорая помощь» — один дежурный в день на ротации, в идеале универсал сантехника+электрика), ночные дежурные (17.6a), skill-теги и зоны мастера, признак «свой авто», выданное оборудование (фильтры распределения).

**Элементы и действия.** Подтвердить/отклонить запрос отпуска (учитывается авто-распределением); **составить график дежурств на неделю** (ротация; валидация: дежурному не бронируются плановые; гарантированный минимум за смену дежурства начисляется проводкой независимо от выездов, ТЗ 8.6); назначить ночных дежурных; закрепить мастера за зонами на день (1–2 смежные); снятие с линии/возврат (лимит наличных, разборы — статус виден, управление у админа).

**Состояния.** MVP — базовый календарь мастера и нормо-часы; полные графики/отпуска и слоты — фаза 2 (ТЗ 15). Конфликт «отпуск поверх забронированных заявок» — список заявок на переназначение (→ D-15).

**Переходы.** → D-05 (лента мастера), D-15.

**Крайние случаи.** Дежурство без минималки невозможно сохранить (валидация — «без минималки дежурство — наказание», ТЗ 17.3); увольнение/блокировка мастера (офбординг, ТЗ 8.6) — все активные заявки в очередь переназначения; неполный набор инструмента — временное снятие skill-тега, мастер не получает соответствующие заявки (ТЗ 8.4.1) — индикатор в календаре.

**Ссылки на ТЗ:** 17.3 (график, дежурный резерв), 17.6a, 8.6, 8.4.1, 12.

### 3.15. D-15. Переназначение и «раздел заявки» (модал из D-06)

**Назначение.** Смена мастера на статусах 5–8 и справедливое деление доли при частично сделанной работе (ТЗ 4.5).

**Данные.** Текущий мастер, статус, выполненная часть (фиксирует мастер, при остановке работ), кандидаты (skill + зона + слоты), история переназначений заявки.

**Элементы и действия.** Переназначить с **обязательной причиной** из справочника: заболел / не успевает / нет навыка / отказ клиента от мастера. Если работа частично сделана — интерфейс «раздел заявки»: слайдер/поля «% первому, % второму» с предпросмотром сумм долей каждого; всё с аудитом. Пуши затронутым — автоматически. Дробление на связанные заявки для разных специальностей (поле «связанные заявки»).

**Состояния.** Доступно только на статусах 5–8 (Назначена / Выехал / В работе / Доп-согласование); вне диапазона — кнопка скрыта. Раздел доли активен только при отметке частичного выполнения.

**Переходы.** ← D-06, D-12 (замена по протоколу — тот же механизм назначения), D-14 (конфликт отпуска).

**Крайние случаи.** Этапная работа: передача продолжения другому мастеру — только через раздел доли, параметр «передача с разделом» по умолчанию выключен (ТЗ 4.1); парная заявка: переназначение ведущего ≠ помощника (роли и доли раздельны, ТЗ 17.3); спорный процент раздела — фиксируется резолюцией диспетчера в аудит.

**Ссылки на ТЗ:** 4.5, 4.1 (этапные), 17.3 (парные), 12.

### 3.16. D-16. Заблокировано третьей стороной

**Назначение.** Список заявок в паузе «Заблокировано» (нет доступа к подвалу/стояку/крыше/щитовой, ТСЖ/УК): контроль дат следующих попыток и дозвона (ТЗ 4.1).

**Данные.** Заявки со статусом паузы: причина из справочника, фото (закрытая дверь), время следующей попытки (если известно — заявка уже якорем в ленте), возраст блокировки, таймеры: задача «дозвониться до ТСЖ» (без даты), эскалация 48 ч, решение с клиентом на 7-й день. Сортировка: попытка сегодня → без даты по возрасту.

**Элементы и действия.** Указать/изменить подтверждённое время попытки → заявка автоматически встаёт якорной в ленту на это время, пуши клиенту и мастеру; создать задачу-звонок ТСЖ/клиенту (D-09, триггер «внешняя зависимость», SLA 2 ч); на 7-й день — «Решить с клиентом»: перенос или закрытие с оплатой факта (деньги — по матрице 4.4: зависимость всплыла на месте — повторный выезд клиент не платит, компенсация мастеру от компании; клиент подтверждал доступ, но не обеспечил — «повторный выезд» в счёт клиента; B2B в подтверждённое окно графика не пустили — «холостой выезд» строкой в СФ).

**Состояния.** С датой (якорь в ленте) / без даты (задача дозвона) / эскалирована (48 ч) / на решении (7 дней).

**Переходы.** → D-06, D-09, D-05 (якорь в ленте).

**Крайние случаи.** Профилактика на входе: чек-лист общих зон при создании заявки (D-08) должен предотвращать большинство таких пауз (ТЗ 4.1); дата попытки от ТСЖ сместилась — перестановка якоря с каскадом пушей; блокировка этапной работы посреди цепочки — пересчёт допустимых окон следующих этапов с алертом.

**Ссылки на ТЗ:** 4.1 («Заблокировано третьей стороной»), 4.4 (три строки «нет доступа»), 17.11.

### 3.17. D-17. Handover смены

**Назначение.** Передача смены в 24/7 без потерь: «ничего не живёт в голове ушедшего диспетчера» (ТЗ 12).

**Данные.** Автособираемый журнал незакрытого на момент передачи: активные протоколы замены; открытые инциденты; ожидания утверждений с таймерами 5.3 (следующая контрольная точка ночью/утром); VIP-контроли; заявки «Заблокировано» с попыткой в ближайшую смену; просроченные/горящие задачи D-09; открытые споры и жалобы с дедлайном SLA в смену приёмника; заявки «Ожидает оплаты» с таймерами напоминаний; свободный комментарий сдающего по каждому пункту и по смене.

**Элементы и действия.** Сдающий: проверяет автосписок, дополняет комментарии, жмёт «Сдать смену». Принимающий: проходит по пунктам, каждый — **явная отметка приёма** (чекбокс с фиксацией кто/когда в аудит); «Принять смену» активна только при 100% отмеченных пунктов. Несогласие с пунктом — комментарий, пункт остаётся видимым старшему.

**Состояния.** Смена не сдана (баннер на D-01 у обеих сторон) / сдана-не принята / принята. История handover-журналов доступна старшему и админу.

**Переходы.** → каждый пункт открывает свой экран (D-06/09/10/11/12/13/16).

**Крайние случаи.** Приёмник не вышел — эскалация старшему/админу, сдающий не бросает пост по регламенту (процессное правило, фиксируется в журнале); события, случившиеся между «Сдать» и «Принять», автоматически дополняют журнал; ночная смена из 1 диспетчера принимает все зоны — журнал агрегируется по всем зонам города.

**Ссылки на ТЗ:** 12 (передача смены), 17.6a, 5.3.

### 3.18. D-18. Лист ожидания и срочные

**Назначение.** Управление очередью за свободной ёмкостью: платные срочные и бесплатный лист ожидания (ТЗ 17.3).

**Данные.** Две очереди: **Срочные** (тариф «Срочно», +30% к работам, параметр) — таймер правила честности: не начали за X ч (по умолч. 3) → наценка снимается автоматически, клиенту push «не успели — срочность не тарифицируем», доля мастера от базовой; **Лист ожидания** — FIFO, честный прогнозный интервал («ориентировочно 15:30–17:30»). Подсказка «кто освободится раньше» (MVP — ручное ведение очереди с этой подсказкой, ТЗ 17.3).

**Элементы и действия.** При освобождении слота (отмена, ранний финиш) система предлагает по приоритетам: срочные → лист ожидания (авто-push «появилось окно сегодня 16:00, подтвердить?») → подтягивание гибких из хвоста ленты — диспетчер видит и подтверждает/правит. Ручной подъём приоритета — **только с причиной в аудит** (ТЗ 17.3). Перевод из листа ожидания в «Срочно» и обратно (по звонку клиента). Аварийный резерв: срочные получают доступ сразу, лист ожидания — за 2 ч до начала часа резерва.

**Состояния.** Порядок доступа к слотам строго по приоритетам 17.3: аварийные → B2B в договорном окне → гарантийные → продолжения этапных → срочные → B2C с бронью (FIFO) → лист ожидания (FIFO) → плановые осмотры (фоновый демпфер, двигаются в пределах недели).

**Переходы.** → D-06, D-04, D-09 (триггер «нет ёмкости», продажа ожидания/срочного).

**Крайние случаи.** Срочная B2B вне аварий — списание с абонентки: базовая × срочность × подписной коэффициент, санкция по матрице лимитов (ТЗ 17.3); ночью «Срочно» не применяется — только ночной коэффициент (ТЗ 17.6a); денежных компенсаций за сдвиги нет — валюта извинений: приоритетный слот, VIP-контроль, проактивная связь (ТЗ 17.3).

**Ссылки на ТЗ:** 17.3 (тариф «Срочно», лист ожидания, приоритеты очереди, аварийный резерв), 17.6a.

### 3.19. D-19. KPI-виджет диспетчера

**Назначение.** Личные и сменные метрики: «диспетчер — узкое горлышко, его метрики должны быть видны» (ТЗ 17.3). Полный дашборд — у админа; в панели — виджет самоконтроля.

**Данные.** Время «Новая → Назначена»; время модерации фото; доля заявок с нарушенным окном; время резолюции споров; SLA жалоб (входит в KPI, ТЗ 17.10); по матрице контактов: доля выполненных QC-прозвонов из выборки, время реакции по каждому триггеру, конверсия «звонок к продлению → продление» (ТЗ 17.11). Метрики здоровья сетки зоны: churn лент, дыры, пробег, доля интрадей-вставок, доля в окно.

**Элементы и действия.** Периоды: смена / день / неделя; сравнение с целевыми (параметры); своя зона vs средняя по сменам (старшему — разрез по диспетчерам).

**Состояния.** Фаза 2 (ТЗ 15). Деградация метрики за порог — жёлтая/красная подсветка.

**Переходы.** → соответствующие очереди (клик по метрике — список «нарушителей»).

**Крайние случаи.** Малые выборки (ночная смена) — подавление статистики с пометкой «мало данных»; растущий churn лент — ранний симптом «каши», алерт старшему (ТЗ 17.3).

**Ссылки на ТЗ:** 17.3 (KPI диспетчерской, метрики сетки), 17.10, 17.11, 13.

### 3.20. D-20. Апелляции мастеров

**Назначение.** Формальное оспаривание мастером решения диспетчерской (штраф к рейтингу, спорная отмена, дисциплинарное взыскание) — очередь рассмотрения и резолюции, по аналогии со спорами (D-11), но по линии «диспетчерская ↔ мастер», а не «диспетчерская ↔ клиент».

**Кто видит.** Зонный диспетчер — апелляции по своей зоне, кроме апелляций на собственные решения (конфликт интересов, см. D-11); старший смены — все зоны, включая эскалированные и апелляции на решения зонного диспетчера.

**Точки входа.** Бейдж/плитка на D-01 («апелляции мастеров»); из карточки мастера — история апелляций; уведомление о новой апелляции.

**Данные.** Карточка апелляции: мастер, предмет (штраф/пересчёт рейтинга, оспариваемая отмена, дисциплинарное взыскание, снятие с линии), связанное решение (ссылка на заявку D-06 / спор D-11 / протокол замены D-12), обоснование мастера (текст + вложения), кто и когда принял оспариваемое решение, статус (новая → на рассмотрении → удовлетворена / отклонена / частично удовлетворена), SLA рассмотрения (параметр), резолюция с обязательным комментарием в аудит.

**Элементы и действия.** «Взять в рассмотрение»; запросить у мастера дополнительные пояснения; резолюция: удовлетворить (отменяет штраф/восстанавливает рейтинг/снимает взыскание с авто-пересчётом последствий), отклонить (с обоснованием), частично удовлетворить — во всех случаях обязательный комментарий в аудит.

**Состояния.** Апелляция на решение, принятое тем же зонным диспетчером, — read-only для него, автоматически эскалируется старшему («диспетчер не пересматривает собственные решения», по аналогии с ТЗ 4.2); просрочка SLA — эскалация админу.

**Переходы.** → D-06 (связанная заявка), → D-11 (связанный спор), → D-12 (связанный протокол замены/санкция за невыход).

**Крайние случаи.** Повторная апелляция по тому же вопросу без новых фактов — авто-отклонение с пометкой; апелляция на окончательную блокировку мастера — панель формирует рекомендацию, финальное решение у админа (ТЗ 8.6).

**Ссылки на ТЗ:** 7.4 (рейтинг), 17.3 (санкции за невыход), 4.2 (конфликт интересов, по аналогии со спорами), 8.6, 12.

## 5. Уведомления и алерты панели

Каналы панели: live-лента алертов (D-01), бейджи счётчиков на рейке, звуковые сигналы, браузерные нотификации (при свёрнутой вкладке). Все — поверх серверной матрицы уведомлений (ТЗ 11); события «Заявка создана» и «Жалоба от руководителя организации» адресованы панели напрямую.

| Событие | Сигнал | Кому |
|---|---|---|
| Аварийная заявка создана / авария на точке B2B | Звук (высокий приоритет) + красный алерт + автозвонок контактному лицу | Зонный + старший |
| Критический дефект по итогам осмотра | Звук + красный алерт + задача D-09 максимального приоритета | Зонный |
| Заявка создана (обычная) | Бейдж + строка ленты (панель + push, ТЗ 11) | Зонный |
| Протокол замены запущен / не решён за 15 мин | Звук + красная карточка вверх доски / повторный звук | Зонный; эскалация старшему |
| Мастер «Задерживаюсь +30/60», срыв следующего окна | Алерт с вариантами перебалансировки | Зонный |
| Гео-флаги: не приближается 15+ мин; фото вне ±300 м | Мягкий флаг (жёлтый), без звука | Зонный |
| SLA-таймеры D-09: 80% срока / просрочка | Жёлтый / красный + звук на просрочке операционных | Зонный |
| Жалоба: первый ответ < 30 мин до SLA / просрочка | Жёлтый / красный + эскалация админу | Ответственный; админ |
| Жалоба руководителя организации | Push + панель, SLA-таймер (ТЗ 11) | Старший смены |
| Спор эскалирован (порог/конфликт интересов) | Бейдж + алерт | Старший/админ |
| Эскалации утверждений (T+48 — «позвонить») | Задача в D-09 + бейдж | Зонный |
| Вынужденная доп-смета без ответа 2 ч | Красный флаг + задача звонка | Зонный |
| Детект массового инцидента (> N заявок/час) | Баннер-предложение + звук | Старший |
| «Клиент недоступен» от мастера | Задача прозвона 15 мин + таймер | Зонный |
| Handover не принят | Блокирующий баннер D-01 | Обе смены; старший |
| «Заблокировано» — эскалация 48 ч / 7 дней | Бейдж + задача | Зонный |
| Правило честности «Срочно» (3 ч) | Инфо-алерт «наценка снята автоматически» | Зонный |
| Лимит наличных мастера превышен → снятие с линии | Алерт (дублирует push мастеру и админу, ТЗ 8.5, 11) | Зонный |

Правила: звук — только для событий, требующих реакции в минуты (аварии, замены, просрочка операционных SLA); всё остальное — бейджи и лента. Ночная смена наследует те же правила, несрочные категории не сигналят до 9:00. Каждый алерт кликабелен и ведёт в контекст. Алерты не сбрасываются «прочтением» — только устранением причины или явным «взять в работу».

## 6. Права: зонный диспетчер vs старший смены

| Действие | Зонный | Старший |
|---|---|---|
| Заявки, назначения, ленты, модерация, отмены — в своих зонах | Да | Да, во всех зонах |
| Просмотр чужих зон | Read-only (аварии соседних зон — видимы) | Да |
| 4 атомарные операции интрадей | Да (свои зоны) | Да |
| Ручная правка замороженной зоны ленты (2 ч) | Да, с подтверждением | Да |
| **Полная пересборка лент** | Нет | **Да — только при массовом инциденте** (ТЗ 17.3) |
| Включение/закрытие режима инцидента | Да (любой зонный может обнаружить и включить) | Да |
| Споры: резолюции и refund | Да, кроме эскалированных | Да, включая: **сумма выше порога** и **споры по заявкам, которые вёл сам диспетчер** (ТЗ 4.2) |
