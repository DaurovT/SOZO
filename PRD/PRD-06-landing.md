# PRD-06: Публичные лендинги и лид-контур USTAPRO

**Версия:** 1.1 · **Дата:** 30.07.2026 · **Источник истины:** ТЗ USTAPRO v2.25 (разделы 17.15, 17.1, 17.2, 12, 17.11, 3.7, 14, 15, 18)
**Платформа:** публичный веб (mobile-first — основной трафик из таргета мобильный; desktop-адаптация обязательна). Языки: русский + узбекский (латиница) с переключателем; служебные страницы — минимум оба языка.

---

## 1. Обзор

Приложения не продают сами себя (ТЗ 17.15): лендинги — верх воронки для таргетированной рекламы и SEO. Три аудитории — три лендинга на общем домене в едином стиле: клиент B2C, организация B2B, кандидат-мастер. Плюс публичная страница верификации мастера по QR с бейджа и служебные страницы (оферта, политика персданных, контакты).

Ключевой принцип: **лендинг не живёт сам по себе — каждая форма порождает лид в операционном контуре системы** с задачей и SLA. Форма B2C — лид-задача в очередь «Позвонить» диспетчерской (D-09, PRD-03) с SLA перезвона 10 минут; форма B2B — лид в реестре B2B-лидов + задача менеджеру; анкета мастера — кандидат в воронке онбординга мастеров (A-12, PRD-04). Лид ни при каком сценарии не остаётся «письмом на почту».

### 1.1. Цели и метрики

**Целевые события конверсии** (передаются в аналитику и пиксели рекламных площадок, ТЗ 17.15):

| Событие | Где возникает | Что означает |
|---|---|---|
| `lead.created` | сабмит любой формы лендинга (после SMS-подтверждения) | лид создан в системе |
| `order.created_from_lead` | диспетчер создал заявку из лид-задачи (D-08/D-09) | лид B2C сконвертирован в заявку |
| `app.install` | переход по deep link / smart banner с последующей регистрацией | установка приложения с лендинга |
| `contract.signed_from_lead` | договор организации, чей лид пришёл с L-04 | лид B2B сконвертирован в договор |
| `master.candidate_created` | анкета с L-06 попала в воронку онбординга | кандидат-мастер создан |
| `master.activated_from_landing` | кандидат с лендинга дошёл до статуса «активен» | конверсия воронки найма |

**Сквозная аналитика:** UTM-метки источника сохраняются в лиде и наследуются производными сущностями (заявка / договор / кандидат) — окупаемость каждой рекламной кампании видна до заявки, LTV и подписанного договора (раздел 4.2). Дашборды конверсии — в админке (PRD-04): воронка лидов B2C/B2B, конверсия воронки онбординга мастеров.

**Операционные метрики лендингов:** конверсия визит → лид по каждому лендингу; доля лидов, прозвоненных в SLA; конверсия лид → заявка / лид → договор / анкета → активен; LCP < 2.5 s на мобильном (раздел 5.2); доля узбекоязычных сессий (сигнал для контента).

### 1.2. Что лендинги НЕ делают

- Не создают заявку напрямую (нет онлайн-записи в окно с лендинга) — заявку создаёт диспетчер в разговоре по телефонному флоу (ТЗ 12): окно согласуется голосом по живому планировщику. Онлайн-путь «сам выбрал окно» — только через приложение.
- Не показывают точные цены — только «от» по активному релизу прайса (ТЗ 3.7); точная смета — после осмотра/оценки.
- Не содержат личных кабинетов (личный кабинет B2B-лида — фаза 3).

## 3. Экраны

### 3.1. L-01. Лендинг B2C

**Назначение.** Продать клиенту-физлицу первый контакт: убедить в четырёх УТП и довести до одного из двух конверсионных путей — форма заявки без приложения (L-02) или установка приложения (ТЗ 17.15).

**Кто видит.** Аноним из таргета/SEO/офлайн-рекламы; авторизации нет.

**Точки входа.** Рекламные кампании (UTM), органический поиск, прямой заход на домен, QR с офлайн-носителей, ссылка в SMS-коммуникациях.

**Данные.** Категории услуг с ценами «от» — по публичному API из **активного релиза прайса** (минимальная цена позиций категории по базовому B2C-прайсу; кеш с инвалидацией по событию активации релиза — раздел 5.1); тексты и медиа — статический контент (рус/узб); отзывы — статические (MVP), авто-подтягивание оценок из системы — фаза 2.

**Элементы и действия.**
- **Hero-блок:** заголовок с УТП — мастер приезжает в согласованное окно; цена известна до начала работ; фотофиксация до/после; гарантия на работы. Первичный CTA «Оставить заявку» (→ L-02), вторичный — кнопки приложений.
- **Категории услуг:** плитки (сантехника, электрика и т.д. — состав из прайса) с ценой «от {X} сум»; клик → L-02 с предвыбранной категорией. Категории, закрытые в прайсе (лицензируемые до договора с лицензиатом, ТЗ 17.8), не показываются.
- **«Как это работает» — 4 шага:** заявка → согласуем окно и цену → мастер в окне, фото до/после → акт, гарантия, оплата как удобно.
- **Отзывы:** карусель.
- **Аварийный блок «Прорвало? Звоните сейчас»:** крупный номер tel:-линком (клик = звонок в диспетчерскую, дальше телефонный флоу ТЗ 12); на мобильном — липкая кнопка звонка. Пометка «работаем 24/7».
- **Кнопки приложений:** App Store / Google Play deep link + smart banner (iOS Smart App Banner, Android intent) с пробросом UTM в install-атрибуцию.
- **Переключатель рус/узб** — в шапке; выбор запоминается (cookie) и передаётся в лид.

**Состояния.** Загрузка цен: скелетоны плиток; API цен недоступен/кеш пуст — плитки без цен (текст «уточним по телефону»), лендинг работоспособен без API. Пустых и офлайн-состояний как таковых нет (публичная статика).

**Переходы.** → L-02 (CTA, плитка категории), → сторы (кнопки), tel: (аварийный блок), → L-03/L-05 (шапка), → L-08 (подвал).

**Крайние случаи.** Релиз прайса активирован в момент сессии — пользователь мог видеть старую цену «от»: допустимо, «от» не оферта (дисклеймер мелким текстом «точная стоимость — после оценки»); заход с UTM — метки кладутся в cookie первого касания и живут до сабмита формы (раздел 4.2).

**Ссылки на ТЗ:** 17.15, 3.7 (релиз прайса), 12 (телефонный канал), 14 (языки), 17.8 (закрытые категории).

### 3.2. L-02. Форма заявки B2C

**Назначение.** Конверсия клиента без приложения: минимальная форма → лид-задача диспетчерской, перезвон в 10 минут, дальше — телефонный флоу с веб-карточкой заявки (ТЗ 12).

**Кто видит.** Аноним; отдельный URL + секция L-01.

**Точки входа.** CTA и плитки категорий L-01, прямой таргет на URL формы, ссылка из SMS/рекламы.

**Данные.** Поля: телефон (обязательно, маска +998), категория (селект из активного прайса; предзаполняется из плитки L-01), описание проблемы (текст, обязательное короткое), фото (опционально, до N шт., сжатие на клиенте — как правило ТЗ 14); язык формы; UTM из cookie; согласие на обработку персданных.

**Элементы и действия.**
1. Заполнение полей; чекбокс **согласия на обработку персональных данных (ЗРУ-547) — обязателен**, ссылка на политику (L-08); без отметки сабмит недоступен.
2. Сабмит шаг 1 → отправка SMS-кода на номер (антиспам-подтверждение владения номером); поле ввода кода, повторная отправка по таймеру (параметр, по умолч. 60 сек).
3. Код верен → создаётся лид (тип B2C) с UTM и языком → **лид-задача в очередь «Позвонить» диспетчерской (D-09) с приоритетом и SLA перезвона 10 минут** — та же механика, что пропущенный входящий (ТЗ 12 п.6, 17.11).
4. Экран успеха: **«Спасибо! Перезвоним в течение 10 минут»** + аварийная приписка «не терпит — звоните прямо сейчас» (tel:) + кнопки приложений («в приложении удобнее: статус, история, запись в два тапа»).

**Состояния.** Отправка (блокировка повторного сабмита, идемпотентность по номер+время); ошибка SMS-шлюза — «не смогли отправить код, позвоните нам» (tel:); ошибка API — данные формы сохраняются локально, повтор без перезаполнения.

**Переходы.** → экран успеха; tel:; → сторы.

**Крайние случаи.**
- **Дубль:** по номеру уже есть активная заявка или непрозвоненный лид < 24 ч — новая лид-задача не плодится; существующая задача получает пометку «повторное обращение» и подъём приоритета; клиенту — тот же экран успеха (дубль — проблема операционная, не клиентская).
- **Номер в блок-листе** (долг B2C блокирует новые заявки, ТЗ 16): лид создаётся с флагом «блок-лист/долг» — диспетчер при звонке следует скрипту работы с долгом; форма клиенту отказ не показывает (долг не разглашается публично).
- **Адрес/район вне зоны покрытия** (выясняется на прозвоне): исход лид-задачи «вне покрытия» → лид попадает в **лид-лист «ждут покрытия»** — при открытии зоны список прозванивается кампанией (задачи в очередь «Позвонить»).
- Rate limit по IP/номеру превышен (раздел 4.4) — мягкая ошибка «слишком много попыток, позвоните нам» (tel:).
- SMS-код не приходит (проблемы оператора) — после 2 неудачных повторов показать tel: как основной путь.

**Ссылки на ТЗ:** 17.15, 12 (п.5–6, веб-карточка, перевод в приложение), 17.11 (очередь «Позвонить», SLA), 14 (ЗРУ-547).

### 3.3. L-03. Лендинг B2B

**Назначение.** Продать организации (сеть аптек, ресторанов, офисов) идею одного договора на обслуживание всех точек; довести до калькулятора/формы КП (L-04).

**Кто видит.** Аноним — ЛПР организации (владелец, директор, АХО) из таргета/SEO/прямых продаж.

**Точки входа.** Рекламные B2B-кампании (UTM), ссылка из шапки L-01, прямые ссылки менеджеров по продажам, SEO.

**Данные.** Статический контент рус/узб; демо-скрины отчётов — статичные изображения из демо-организации (ТЗ 17.6); логотипы/кейсы клиентов — **плейсхолдеры до набора реальных** (блок скрыт флагом, включается контент-правкой).

**Элементы и действия.**
- **Блок болей:** свой штатный завхоз/АХО дорог и не масштабируется; разовые подрядчики без контроля, фото и гарантий; «когда потекло на товар — уже поздно».
- **Оффер:** один договор на все точки; **SLA прибытия по авариям — днём ≤ 60 минут, ночью ≤ 120 минут** (параметры договора, ТЗ 18-п.2); фотоотчёты по каждой работе; абонентка — предсказуемый бюджет, работы списываются по факту; техдолг точек и плановые осмотры (дефекты видны до того, как стали аварией); **программа мотивации персонала точек — опция договора** (баллы и ваучеры сотрудникам за своевременные обращения, ТЗ 17.14, с согласия руководства).
- **Демо-скрины:** месячный отчёт, акт с фото до/после, онлайн-баланс абонентки.
- **Логотипы/кейсы:** плейсхолдер-блок.
- **CTA «Рассчитать абонентку»** (первичный, дублируется по секциям) → L-04; вторичный — телефон отдела продаж (tel:).

**Состояния.** Полностью статический; деградаций нет.

**Переходы.** → L-04, tel:, → L-08, → L-01/L-05 (шапка).

**Крайние случаи.** Заход по ссылке менеджера с ref-меткой продавца — метка сохраняется в UTM-наборе лида (атрибуция продаж). До подписания договора с лицензиатом упоминаний газа/лифтов в оффере нет (ТЗ 17.8).

**Ссылки на ТЗ:** 17.15, 17.2 (воронка B2B), 17.14 (программа баллов — опция), 18-п.2 (SLA аварий), 17.6 (демо-организация).

### 3.4. L-04. Калькулятор абонентки + форма КП B2B

**Назначение.** Дать ЛПР порядок цифр без звонка (снятие барьера) и сконвертировать в лид с задачей менеджеру.

**Кто видит.** Аноним; отдельный URL + секция L-03.

**Точки входа.** CTA L-03, прямой таргет на калькулятор.

**Данные.** **Упрощённый калькулятор** (ТЗ 17.15): входы — число точек (степпер) и тип объекта (селект: аптека, ресторан, офис, магазин… — справочник типов из калькулятора 17.2); выход — **ориентировочная вилка абонентки в месяц**, посчитанная по базовым ставкам калькулятора абонентки (сум/м² по типу объекта × типовая площадь типа, коэффициенты из админки, ТЗ 17.2) × число точек, с округлением до «красивой» вилки. Ставки — по публичному API (тот же контур кеша, что цены «от», раздел 5.1). Полный калькулятор (паспорт объекта: м², санузлы, кондиционеры, щитки) — инструмент продавца в админке (PRD-04), на лендинге не показывается.

**Элементы и действия.**
- Калькулятор: живой пересчёт вилки при изменении входов; **дисклеймер обязателен: «Ориентировочно. Точный расчёт — в коммерческом предложении после аудита объекта»** (первичный аудит платный с зачётом — ТЗ 18-п.8; на лендинге не педалируется, озвучивает менеджер).
- Форма «Получить КП»: название компании, число точек (предзаполняется из калькулятора), имя контакта, телефон (обязателен), email (опционально); чекбокс согласия ЗРУ-547 (обязателен).
- Сабмит → SMS-подтверждение номера (как L-02) → **лид (тип B2B) в реестре B2B-лидов** (сущность «лид» единая с воронкой 17.2) с UTM, параметрами калькулятора (тип объекта, число точек, показанная вилка — контекст для менеджера) → **задача менеджеру «позвонить лиду» с SLA (параметр,** по умолч. 4 рабочих часа в дневное окно — единый источник PRD-04 §5 (№114) и табл. 4.1; лид ночью — задача на утро).
- Экран успеха: «Спасибо, менеджер свяжется с вами {SLA-текст}» + телефон отдела продаж.

**Состояния.** API ставок недоступен — калькулятор скрывается, форма КП работает (текст «рассчитаем и пришлём КП»); отправка/ошибки — как L-02.

**Переходы.** → экран успеха, tel:.

**Крайние случаи.** Дубль по телефону/компании с открытым лидом — задача не дублируется, существующий лид получает пометку «повторное обращение» + новые параметры калькулятора; менеджер видит историю касаний. Число точек > порога (параметр, «крупная сеть») — флаг лида «крупный», отдельный приоритет задачи. Email указан невалидно — мягкая валидация (поле опционально).

**Ссылки на ТЗ:** 17.15, 17.2 (ставки, лид, воронка), 17.11 (задачи со SLA), 14 (ЗРУ-547).

### 3.5. L-05. Лендинг «Мастерам»

**Назначение.** Верх воронки найма: набор исполнителей — такой же конвейер, как набор клиентов; масштабирование до 300 мастеров без потока кандидатов невозможно (ТЗ 17.15). Довести кандидата до анкеты L-06.

**Кто видит.** Аноним — действующие мастера рынка (частники, сотрудники сервисов) из таргета/SEO/реферальных ссылок мастеров.

**Точки входа.** Рекламные кампании найма (UTM), реферальные ссылки мастеров (с ref-кодом рекомендателя — ТЗ 17.1), шапка домена.

**Данные.** Статический контент рус/узб; параметры калькулятора заработка (средний чек, доля) — конфигурируемые значения контента (обновляются вручную, не из прайс-API — маркетинговые, не договорные).

**Элементы и действия.**
- **Условия:** доля от каждого заказа (стартовая доля грейда — из 7.4; формулировка «до 57% на грейде „Золото“» — ТЗ 18-п.9); **выплаты еженедельно**; график выбираешь сам (+ дежурства с гарантированной минималкой); обучение и стандарты за счёт компании; поток заявок без поиска клиентов; материалы в долг компании через партнёрские магазины (фаза 2 — упоминание после включения).
- **Калькулятор «сколько заработаешь»:** входы — заявок в день (слайдер), средний чек (слайдер с дефолтом по категории), выход — оценка месяца: заявок × чек × доля × рабочие дни; дисклеймер «оценка, не оферта».
- **Требования:** свой инструмент (обязательный список по skill-тегам — ТЗ 17.6b), подтверждаемый опыт (практический экзамен по чек-листу категории), ответственность (фото до/после — норма работы); транспорт — плюс.
- **Как попасть:** 4 шага — анкета → собеседование и проверка навыков → обучение с мини-экзаменом → первые заявки (испытательный период).
- **Реферальный блок:** «работаешь у нас — приведи мастера, получи бонус после 20 закрытых заявок приведённого» (ТЗ 17.1).
- **CTA «Заполнить анкету»** → L-06 (ref-код из URL пробрасывается).

**Состояния.** Статический; деградаций нет.

**Переходы.** → L-06, → L-08, шапка.

**Крайние случаи.** Заход по реферальной ссылке — ref-код кладётся в cookie вместе с UTM и доживает до сабмита анкеты. Цифры калькулятора расходятся с реальными долями прайса — контентная ответственность маркетинга; в анкете и договоре фигурируют только реальные условия.

**Ссылки на ТЗ:** 17.15, 17.1 (воронка, реферальная программа, комплект новичка), 7.4 (грейды, доли), 17.3 (дежурства, минималка).

### 3.6. L-06. Анкета кандидата-мастера

**Назначение.** Первый шаг воронки онбординга мастеров: анкета с лендинга → кандидат в админке (A-12) со статусом «анкета с лендинга».

**Кто видит.** Аноним; отдельный URL + переход с L-05.

**Точки входа.** CTA L-05, прямой таргет, реферальные ссылки.

**Данные.** Поля: имя (обязательно), телефон (обязательно, SMS-подтверждение), skill-категории (мультиселект из справочника категорий: сантехника, электрика, …), опыт (селект: < 1 года / 1–3 / 3–5 / 5+), транспорт (нет / авто / мото), город и районы работы (мультиселект зон, ТЗ 17.4); **реферальный код мастера-рекомендателя** — авто-подставляется из ref/utm-параметра ссылки (поле видно и редактируемо: «есть код от нашего мастера?»); согласие ЗРУ-547 (обязателен).

**Элементы и действия.**
1. Заполнение → SMS-код → подтверждение номера (антиспам, как L-02).
2. Сабмит → **кандидат создаётся в воронке онбординга мастеров (A-12, PRD-04) со статусом «анкета» и меткой источника «анкета с лендинга»** + UTM + ref-код рекомендателя (для начисления реферального бонуса после 20 закрытых заявок приведённого — ТЗ 17.1; бонус проводкой, контур PRD-04/05).
3. Экран успеха: **«Спасибо! Анкета принята — пригласим на собеседование»** + что дальше (проверка документов, собеседование, обучение) + контакт для вопросов.

**Состояния.** Отправка/ошибки — как L-02; сохранение черновика локально при ошибке сети.

**Переходы.** → экран успеха.

**Крайние случаи.** Дубль номера: кандидат с этим номером уже в воронке — анкета не дублируется, существующая карточка получает пометку «повторная анкета» (рекрутёр видит); номер принадлежит **действующему мастеру** — анкета не создаётся, экран «вы уже работаете с нами» (защита от самореферала). Ref-код не существует/мастер рекомендателя заблокирован — анкета создаётся без реферальной привязки, флаг «код не распознан» в карточке. Выбранные районы вне текущих зон покрытия — анкета принимается (найм опережает покрытие), пометка рекрутёру.

**Ссылки на ТЗ:** 17.15, 17.1 (воронка, статусы, реферальная программа), 17.4 (зоны), 14 (ЗРУ-547).

### 3.7. L-07. Публичная страница верификации мастера

**Назначение.** Клиент сканирует QR с бейджа мастера у двери — и видит подтверждение, что человек действительно от компании (ТЗ 17.1, 17.15; анти-риск «приехал не тот мастер»).

**Кто видит.** Аноним по уникальному URL вида `/m/{verification_code}` (код с бейджа; неперебираемый).

**Точки входа.** QR-код с бейджа мастера (бейджи — фаза 2; страница и коды — MVP, чтобы контур верификации был готов к печати бейджей); ссылка из веб-карточки заявки (W-xx, PRD-01) — «проверить мастера».

**Данные.** Фото мастера (то же, что видит клиент в заявке), имя, skill-теги, **статус: «Действует» (зелёным) / «НЕДЕЙСТВИТЕЛЕН» (красным, крупно)**, грейд и рейтинг (после запуска авто-рейтинга — фаза 2; до того — грейд вручную из админки). **Без телефона, адреса и любых персональных контактов** (ТЗ 17.15) — мастер копирует базу клиентов, а не наоборот.

**Элементы и действия.** Статичная карточка; кнопка «Что-то не так? Позвоните нам» (tel: диспетчерской). Индексация запрещена (noindex) — страница только по прямому коду.

**Состояния.** Действует / недействителен; загрузка — скелетон.

**Переходы.** tel:; логотип → L-01.

**Крайние случаи.**
- **Отозванный бейдж** (мастер уволен/заблокирован, бейдж не возвращён): статус «НЕДЕЙСТВИТЕЛЕН» красным с текстом «этот человек не представляет компанию — не открывайте, позвоните нам» + tel:. Отзыв — событием из админки (блокировка мастера мгновенно инвалидирует код).
- **Несуществующий/битый код:** та же страница «НЕДЕЙСТВИТЕЛЕН» без данных мастера (не раскрывать, существует ли код) + tel:.
- Перевыпуск бейджа — новый код, старый отзывается.

**Ссылки на ТЗ:** 17.15, 17.1 (бейдж с QR — фаза 2), 13/A-11 (управление бейджами в админке), 16 (риск «приехал не тот мастер»).

### 3.9. L-09. Лендинг для эксплуатирующих организаций (M7)

**Назначение.** Довести руководителя службы эксплуатации до **самостоятельного подключения объекта на Free**, а не до звонка менеджера. Продажа Pro — вторичный путь. Если для согласования допусков нужно пройти менеджера, КП и подписание, никто не подключится и чокпоинт не образуется.

**Кто видит.** Аноним: управляющий БЦ, руководитель УК/ТСЖ, начальник техотдела сети, директор FM-компании.

**Точки входа.** Таргет и SEO по эксплуатационным запросам; ссылка из L-10 «Публичная страница объекта»; прямые ссылки менеджеров; QR в письмах.

**Данные.** Статический контент рус/узб; ставки для калькулятора — по публичному API (тот же контур кеша, что L-04); демо-скрины кабинета — из демо-объекта (ТЗ 17.6).

**Элементы и действия.**
- **Четыре оффера, переключаемые табами** по типу: **БЦ** — «SLA перед арендаторами, подтверждённый фотографиями»; **свой техотдел** — «ваши мастера, ваши правила, наш инструмент»; **УК/ТСЖ** — «жители видят, что вы работаете»; **FM** — «доказательство выполнения заказчику».
- **Блок «Мы не забираем вашу работу»** — прямой ответ на главное возражение начальника службы: право первой руки, свои мастера в системе, заявки по общему имуществу только вашей службе. Без этого блока лендинг не работает: решение принимает тот, кто боится за свой отдел.
- **Калькулятор дохода, а не расхода.** Входы: число помещений и тип объекта. Выход: **оценка сервисного сбора в месяц** — «ваш объект может приносить ~{X} сум в месяц, при этом Free стоит 0». Единственный лендинг в пакете, показывающий заработок, а не цену. Дисклеймер об ориентировочности обязателен.
- **Сопоставление с ценой Pro.** Под результатом калькулятора — вторая строка: «Pro стоит 3 000 000 сум в месяц за объект». Это делает оффер проверяемым в уме: если расчётный сервисный сбор сопоставим с ценой подписки, разговор о Pro начинается сам. Если сильно меньше — честно оставляем человека на Free, он вернётся с ростом объёма.
- **CTA первичный:** «Подключить объект бесплатно» → self-serve регистрация (§3.10). **CTA вторичный:** «Получить КП на Pro» → лид типа `operator` в реестр A-37 с задачей менеджеру (механика L-04 без изменений).
- Блок «Что бесплатно навсегда»: согласование допусков, заявки жителей по общему имуществу, оповещения, пропуска, право первой руки, получение сервисного сбора. Честный перечень Pro-функций отдельно.

**Состояния.** API ставок недоступен — калькулятор скрывается, форма подключения работает.

**Переходы.** → self-serve подключение, → форма КП, → L-10, tel:.

**Крайние случаи.** Заявка на объект, уже подключённый другим оператором, — форма принимает, но обещает разбор, а не подключение (конфликт заявителей, DEV-15 §10.9.3). Оператор без документов — путь «сначала посмотреть демо», подключение остаётся доступным позже.

**Ссылки на ТЗ:** 17.15, 17.2 · DEV-15 §9.2, §10.7, §10.9. **Фаза:** M7.

### 3.10. Self-serve подключение объекта (флоу, не экран)

1. Регистрация по телефону + OTP (существующая механика) → выбор типа организации.
2. Поиск объекта по адресу (`/buildings/resolve`) или создание нового.
3. Загрузка документа-основания, контактные данные, акцепт оферты **в интерфейсе** — без бумажного договора и без менеджера.
4. Объект переходит в `claimed`, кабинет открывается в **демо-режиме на сид-данных** (ТЗ 17.6): человек видит продукт в первые пять минут, а не надпись «ожидайте».
5. Модерация A-39 → `verified` → настройка объекта U-13 → `active`.

**Крайние случаи.** Демо-данные не порождают проводок и не видны жителям. Отказ в верификации — с причиной и возможностью донести документы. Молчание заявителя дольше N дней — заявка архивируется, объект возвращается в `unmanaged`.

### 3.11. L-10. Публичная страница объекта (M7)

**Назначение.** Витрина подключённого объекта и **ростовой цикл**: житель неподключённого дома видит, чего лишён, и создаёт давление на свою УК. Давление снизу дешевле холодных звонков.

**Кто видит.** Аноним; ссылка с наклейки в подъезде, из поиска, из приложения.

**Данные.** Публичный минимум по `Building`: название, кто управляет, аварийный телефон, ближайшие плановые отключения. **Персональные данные жителей и заявки не публикуются никогда.**

**Элементы и действия.**
- **Первым экраном — крупная кнопка звонка** на общий номер. Это главное назначение страницы для человека, пришедшего по QR с наклейки: он хочет вызвать мастера, а не читать.
- Аварийный телефон УК; ближайшие отключения; ссылки на приложение.
- Для **неподключённого** объекта — кнопка **«Моего дома здесь нет»**: адрес и телефон копятся в реестре A-39 как спрос; при накоплении N обращений менеджер получает задачу «в этом доме {N} жителей ждут подключения» и готовый аргумент в разговоре с их УК.

**Состояния.** Подключённый объект — полная страница; неподключённый — короткая с кнопкой сбора спроса; объект в `degraded` — без обещаний по срокам.

**Крайние случаи.** noindex для страниц неподключённых объектов (чтобы не плодить мусор в поиске); rate limit на сбор обращений по IP; наклейка ведёт на страницу конкретного объекта через неперебираемый код в URL.

**Ссылки на ТЗ:** 17.15 · DEV-15 §10.7, §10.3.1. **Фаза:** M7.

### 3.12. W-06. Согласование наряда-допуска по ссылке (M7)

**Назначение.** Дать согласующему — консьержу, главному инженеру — возможность согласовать доступ **в один тап, без установки приложения и без регистрации**. Критично для Free-контура: требовать освоения веб-кабинета ради двух нажатий в день бессмысленно, и без этой страницы бесплатный тариф не взлетит.

**Кто видит.** Держатель одноразового подписанного токена из SMS.

**Точки входа.** SMS «{Мастер} просит доступ к {зона} на {окно}. Согласовать: {ссылка}».

**Данные.** Наряд: зона и её критичность, окно, мастер (имя, фото, ссылка на страницу верификации L-07), заявка (категория, помещение — без персональных данных клиента, ТЗ 17.5), сколько помещений затронет отключение.

**Элементы и действия.** Три крупные кнопки: **[Согласовать]** · **[Предложить другое время]** (дата-пикер) · **[Отклонить]** (причина из списка). Подтверждение решения на экране + SMS-квитанция.

**Состояния.** Ссылка использована — «Решение уже принято: {решение} в {время}». Истекла — «Срок ссылки истёк, наряд согласован автоматически / ожидает решения в кабинете». Наряд отменён — соответствующий текст.

**Переходы.** → L-07 (проверить мастера), → предложение установить кабинет (ненавязчиво, после решения).

**Крайние случаи.** Токен одноразовый, неперебираемый, noindex, rate limit — та же механика, что W-01…W-05. **Критичная зона** — плашка «Авто-согласия не будет, наряд ждёт вашего решения». Пересланная ссылка работает у любого получателя — это осознанный компромисс ради скорости; ответственность несёт назначивший согласующего оператор, каждое решение пишется в аудит с номером телефона получателя SMS.

**Ссылки на ТЗ:** 12, 14, 17.5, 17.15 · DEV-15 §10.7. **Фаза:** M7.

### 3.8. L-08. Служебные страницы

**Назначение.** Юридический минимум и контакты. MVP — статические страницы.

**Кто видит.** Аноним; ссылки из подвала всех лендингов и из чекбоксов согласия форм.

**Точки входа.** Подвал, чекбоксы форм (политика), сторы (требуют privacy policy URL).

**Данные / состав.**
- **Публичная оферта** — текст от юриста (открытая зависимость пакета, PRD-00); версия и дата редакции на странице.
- **Политика обработки персональных данных** — соответствие ЗРУ-547 (хранение персданных граждан РУз на территории Узбекистана — ТЗ 14); на неё ссылаются все чекбоксы согласия.
- **Контакты:** телефон (tel:), адрес офиса, реквизиты юрлица, часы работы («24/7 приём заявок»).

**Элементы и действия.** Статический текст рус/узб; печатная версия.

**Состояния.** Статика.

**Переходы.** Возврат на лендинги.

**Крайние случаи.** Тексты не готовы к запуску форм — формы не запускаются без опубликованной политики (юридический блокер, PRD-00 «Открытые зависимости»). Обновление редакции оферты/политики — новая версия с датой; старые версии архивируются (append-only, как аудит).

**Ссылки на ТЗ:** 17.15 (согласие ЗРУ-547), 14 (персданные), PRD-00 (зависимости: юрист).

## 4. Лид-контур

### 4.1. Маршрутизация лидов: источник → лид → задача → SLA

| Источник | Куда падает лид | Порождаемая задача | SLA | Исходы |
|---|---|---|---|---|
| Форма B2C (L-02) | Лид B2C (телефон, категория, описание, фото, UTM, язык) | Лид-задача в очередь «Позвонить» диспетчерской (D-09), механика пропущенного звонка (ТЗ 12 п.6) | **Перезвон 10 минут** (параметр; просрочка — алерт старшему смены) | заявка создана (D-08) / вне покрытия → лид-лист «ждут покрытия» / недозвон (ретраи по регламенту 17.11) / отказ с причиной |
| Форма КП B2B (L-04) | Лид B2B в реестре лидов (A-37, PRD-04; компания, точки, контакт, параметры калькулятора, UTM) | Задача «позвонить лиду» — **админу** (роли «менеджер продаж» в MVP нет, ТЗ 17.15; выделенная роль — фаза 2) | **Параметр** (по умолч. 4 рабочих часа, дневное окно) | демо → аудит → КП → договор (воронка 17.2) / отказ с причиной / «думает» с датой следующего касания |
| Анкета мастера (L-06) | Кандидат в воронке онбординга (A-12), статус «анкета», метка «анкета с лендинга», ref-код | Задача рекрутёру по регламенту воронки | Регламент онбординга (параметр) | проверка → обучение → активен / отклонён (ТЗ 17.1) |
| Аварийный tel:-звонок (L-01) | Телефонный флоу напрямую (ТЗ 12) — лид-сущность не создаётся, создаётся заявка | — (живой звонок) | — | заявка / пропущенный → задача «перезвонить за 10 минут» |

Правила контура: лид не может «потеряться» — у каждого лида либо открытая задача, либо терминальный исход с причиной; все касания фиксируются (ContactLog, ТЗ 17.11); лид-лист «ждут покрытия» — именованный сегмент реестра лидов, при открытии зоны — кампания прозвона.

### 4.2. UTM и сквозная атрибуция

- При первом заходе на домен UTM-параметры (`utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, + `ref` мастера, + ref-метка продавца) сохраняются в first-touch cookie (срок — параметр, по умолч. 90 дней).
- При сабмите любой формы UTM-набор пишется **в лид** (поля сущности, не свалка в комментарии).
- Наследование: заявка, созданная из лид-задачи, наследует UTM лида; договор организации — UTM её лида; кандидат — UTM анкеты. Дальше стандартная аналитика системы связывает кампанию с выручкой заявок, LTV клиента и абоненткой договора — **сквозная окупаемость каждой кампании** (ТЗ 17.15).
- Отчёты по атрибуции — админ-дашборд (PRD-04): лиды/заявки/выручка в разрезе source/medium/campaign.

### 4.3. Пиксели и события конверсии

Пиксели рекламных площадок: Meta Pixel, Google Tag, Яндекс.Метрика (набор — параметр конфигурации, управляется через контейнер тегов). События из таблицы 1.1 отправляются: клиентские (`лид создан`, клики CTA, `установка` через install-атрибуцию сторов) — с лендинга; серверные (`заявка создана`, `договор подписан`) — server-side по Conversions API площадок (фаза 2; MVP — минимум `lead.created` клиентски). Согласие на куки/трекинг — по требованиям площадок; персданные в пиксели не передаются (только хеш номера там, где площадка требует, — вопрос юристу).

### 4.4. Антиспам

Три эшелона на всех формах (ТЗ 17.15):
1. **Honeypot** — скрытое поле; заполнено ботом → тихий отказ (форма «успешна», лид не создаётся, инцидент в лог).
2. **Rate limit** по IP и по номеру телефона (параметры: N сабмитов/час с IP, M SMS-кодов/сутки на номер); превышение — мягкая ошибка с tel:.
3. **SMS-подтверждение номера** — обязательное для всех трёх форм: лид без подтверждённого номера не создаётся и задач не порождает (диспетчерская не тратит SLA на фейки).

Дополнительно: серверная валидация всех полей (клиентская — только UX); блок-лист номеров-спамеров (админка); CAPTCHA — резервный рубеж, включается флагом только при атаке (по умолчанию выключена — трение убивает конверсию).

## 5. Интеграции и нефункциональные требования

### 5.1. API цен «от» и ставок калькулятора

- Публичный read-only эндпоинт: категории + минимальная цена «от» по **активному релизу прайса** (базовый B2C-прайс, ТЗ 3.7) и базовые ставки калькулятора абонентки по типам объектов (ТЗ 17.2). Никаких полных прайсов наружу — только агрегаты.
- **Кеш:** ответ кешируется (CDN/Redis); **инвалидация — по событию `pricelist.release_activated`** (событийная шина PRD-05): активация релиза сбрасывает кеш, лендинг показывает новые «от» без деплоя. TTL-страховка на случай пропуска события (параметр, по умолч. 1 час).
- Деградация: API недоступен — лендинг живёт без цен (см. L-01/L-04); формы от API не зависят.

### 5.2. Производительность и доставка

- **Статика/SSR:** лендинги — статическая генерация или SSR с кешем; никакого тяжёлого SPA. Формы — прогрессивные (работают при медленном JS).
- **Скорость: LCP < 2.5 s на мобильном** в 4G-профиле — таргет-трафик мобильный; бюджет страницы (параметр, ориентир ≤ 500 КБ критического пути), изображения — современные форматы, lazy-load ниже первого экрана.
- Доступность форм с дешёвых Android-устройств (основной парк Ташкента).

### 5.3. Языки и SEO

- **Рус/узб (латиница)** — полный контент обеих локалей с первого релиза (ТЗ 14); переключатель в шапке; hreflang; язык пишется в лид и наследуется коммуникациями (SMS клиенту — на языке лида).
- **SEO-базис (MVP):** мета-теги, Open Graph, sitemap.xml, robots.txt, семантическая разметка, ЧПУ-адреса. **Полная SEO-структура — по категориям услуг и районам города (страницы «сантехник в Юнусабаде») — фаза 2** (ТЗ 17.15).
- L-07 — noindex (раздел 3.7).

### 5.4. Аналитика и наблюдаемость

- Веб-аналитика: GA4 и/или Яндекс.Метрика (набор — параметр); события из 1.1; цели на сабмиты форм.
- Мониторинг (общий контур PRD-05): доступность лендингов и API цен, доля ошибок SMS-подтверждения, алерт «лиды перестали создаваться» (тишина форм N часов в дневное время — параметр).
- Все конфигурируемые значения этого PRD (SLA задач B2B-лидов, тайминги SMS-кодов, rate limit, TTL кеша, срок cookie, пиксели) — в сводной таблице параметров PRD-04.

## 7. Фазы

**MVP (входит в скоуп фазы 1 по ТЗ 15):** все три лендинга со статическим контентом рус/узб; формы L-02/L-04/L-06 с SMS-подтверждением, согласием ЗРУ-547 и антиспамом; лид-контур с задачами и SLA (перезвон B2C 10 мин, B2B — параметр); лид-лист «ждут покрытия»; UTM в лиде с наследованием; клиентские пиксели и событие `lead.created`; API цен «от» с кешем и событийной инвалидацией; страница верификации L-07; служебные страницы L-08; SEO-базис; LCP < 2.5 s.

**Фаза 2:** SEO-структура по категориям услуг и районам (генерируемые посадочные); A/B-тесты; блог/справочник цен; отзывы из системы (авто-подтягивание оценок закрытых заявок с модерацией); server-side события конверсии (заявка/договор); печать бейджей с QR (контур L-07 уже готов); отчёт атрибуции кампаний в админ-дашборде расширенный.

**Фаза 3:** личный кабинет B2B-лида (статус КП, документы, переписка); онлайн-подписание договора (ЭДО-контур); API-выдача контента лендингов под доп. каналы (Telegram-бот B2C — ТЗ 15).
