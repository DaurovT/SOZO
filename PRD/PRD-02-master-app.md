# PRD-02. Мобильное приложение «Мастер» — платформа USTAPRO

Версия: 1.1 · Дата: 30.07.2026 · Источник истины: ТЗ USTAPRO v2.25 (вкл. UX-решения продакт-аудита, раздел 17.17) · Платформа: Flutter (Android приоритет, iOS), языки рус/узб (латиница), офлайн-режим обязателен.

---

## 1. Обзор

### 1.1. Назначение
Рабочий инструмент исполнителя: приём офферов, конвейер выполнения заявки строго по шагам (фото-цикл, смета, доп-работы, материалы, приёмка, оплата), кошелёк с прозрачностью до копейки, дежурства, парные работы, оборудование, онбординг кандидата. Приложение — единственный канал фиксации работ: «сделал мимо приложения — сделал за свой счёт» (ТЗ 4.6 п.4).

### 1.2. Роли внутри приложения
| Роль | Описание | Отличия интерфейса |
|---|---|---|
| Кандидат на онбординге | Статус `анкета`/`проверка`/`обучение` (ТЗ 17.1) | Доступны только экраны онбординга M-02…M-05; лент и заявок нет |
| Мастер | Активный исполнитель, самозанятый/ГПХ (ТЗ 2.2) | Полный функционал |
| Мастер-ведущий (парная заявка) | Отвечает за смету, фото-цикл, приёмку (ТЗ 17.3 «Парные работы») | Карточка заявки полная + блок «Помощник» |
| Помощник (парная заявка) | Физическая помощь, фикс/меньшая доля за сессию | Упрощённая карточка M-33: без конвейера, смет и фото-цикла |
| Дежурный | Мастер в дежурной смене (ТЗ 17.3) | Индикатор «Ты дежурный сегодня», минималка смены в кошельке, плановые не бронируются |

Роль — свойство аккаунта; помощник и дежурный — контекстные роли поверх роли «мастер».

### 1.3. Принципы (несущие ограничения)
1. **Конвейер строго по шагам** (ТЗ 7.1): Выехал → Приступить+фото «до» → работа/смета → фото «после» → приёмка → оплата. Пропуск шага невозможен ни в UI, ни на API (критерий приёмки MVP №1).
2. **Фото только с камеры** (ТЗ 7.1 шаг 2, 16): без доступа к галерее; сжатие до ~1600px/500КБ, EXIF-очистка, серверный таймштамп, гео в метаданных записи (допускается null с флагом «без гео» — подвал).
3. **Офлайн-first** (ТЗ 7.2, 14): приложение полностью функционально без сети; каждая операция получает клиентский UUID; синк идемпотентен; каждый экран этого PRD обязан описывать офлайн-состояние.
4. **Ни одна работа без санкции** (ТЗ 4.6): доп-работы и апсейл — только через утверждение в системе.
5. **Мастер не завершает визит без оплаты B2C** (ТЗ 7.1 шаг 6); исключения: санкция диспетчера, промежуточные этапные сессии.
6. **Прозрачность денег** (ТЗ 8.6): мастер видит каждую копейку с расшифровкой — это удержание мастеров.
7. **Минимум данных клиента** (ТЗ 17.5): имя, адрес, подъезд; телефон только со статуса «Назначена» до «Закрыта», звонок кнопкой, номер не копируется.
8. **Честность вознаграждается**: ранний отказ («Не могу поехать») мягче тихого невыхода; «Задерживаюсь» — честный сдвиг вместо срыва окна (ТЗ 17.3).

## 3. Спецификации экранов

### M-01. Вход (телефон + OTP)
- **Назначение:** аутентификация по номеру телефона + OTP-SMS (ТЗ 14 «Аутентификация»).
- **Точки входа:** первый запуск; разлогин; протухший refresh-токен.
- **Данные:** телефон; OTP; выбор языка (рус/узб) — до входа; версия приложения (force update).
- **Элементы и действия:** переключатель языка; поле телефона (+998, маска); [Получить код] → SMS; поле OTP (авто-подстановка из SMS); [Войти]; таймер повторной отправки (60 с); [Отправить снова].
- **Состояния:** загрузка (отправка/проверка кода); ошибка «неверный код» (3 попытки → новый код); «слишком много запросов»; аккаунт заблокирован → экран «Обратитесь к диспетчеру» с телефоном; версия ниже минимальной → блокирующий экран «Обновите приложение» (ТЗ 14). **ОФЛАЙН:** вход невозможен — экран «Нет сети. Для входа нужен интернет»; если сессия уже была (JWT в secure storage) — приложение открывается офлайн без повторного OTP.
- **Переходы:** кандидат → M-02/M-05 (по статусу онбординга); активный мастер → M-06.
- **Крайние случаи:** смена номера — только через диспетчера с верификацией личности (ТЗ 14); передача аккаунта запрещена (спор «приехал не тот мастер»).
- **ТЗ:** 14, 2.2, 17.1.

### M-02. Онбординг: анкета кандидата
- **Назначение:** первый шаг воронки `анкета` (ТЗ 17.1).
- **Точки входа:** M-01 при отсутствии профиля мастера; ссылка из рефералки (M-41), с зашитым кодом рекомендателя.
- **Данные:** телефон (из входа), ФИО, skill-теги (мультивыбор из справочника: сантехника, электрика, кондиционеры/фреон, сварка, малярка, слаботочка…), опыт (лет, описание), фото лица (только камера — это фото увидит клиент в карточке мастера), зоны выезда (районы Ташкента), транспорт (свой авто с инструментом / без авто), налоговый статус (самозанятый / ГПХ), реферальный код (опц.).
- **Элементы и действия:** пошаговая форма с прогресс-баром; [Сфотографироваться]; [Отправить анкету].
- **Состояния:** валидация полей; загрузка отправки; ошибка сети — черновик анкеты сохраняется локально, [Повторить]. **ОФЛАЙН:** заполнение и сохранение черновика работают; отправка встаёт в очередь синка, баннер «Анкета отправится при появлении сети».
- **Переходы:** → M-03; сразу после отправки анкеты открываются учебные модули и тренажёр конвейера M-04 (ТЗ 17.17 п.9).
- **Крайние случаи:** повторная анкета после отклонения — допускается через N дней (параметр); заявленные skill-теги — только заявка, подтверждение через экзамен (ТЗ 17.1: «самопровозглашённых навыков нет»).
- **ТЗ:** 17.1, 3.3.

### M-03. Онбординг: документы
- **Назначение:** шаг `проверка` — загрузка документов для верификации.
- **Точки входа:** после M-02; push «Догрузите документы» при возврате на доработку.
- **Данные:** фото паспорта (разворот + прописка), подтверждение статуса самозанятого (справка/скрин из Soliq) или данные для ГПХ, фото инструмента по чек-листу ToolChecklist выбранных skill-тегов (ТЗ 8.4.1: комплектность проверяется при онбординге).
- **Элементы и действия:** карточки документов со статусами (не загружен / на проверке / принят / отклонён с комментарием); [Снять] (камера); чек-лист инструмента по каждому skill-тегу с фото набора; [Отправить на проверку].
- **Состояния:** частично загружено; возврат с комментариями проверяющего; **ОФЛАЙН:** съёмка и постановка в очередь работают, отправка при сети.
- **Переходы:** → M-05 (ожидание проверки) → после одобрения и собеседования → M-04.
- **Крайние случаи:** неполный набор инструмента — skill-тег не активируется (мастер не получит заявки, требующие этого инструмента, ТЗ 8.4.1); статус самозанятого перепроверяется периодически (ТЗ 8.6).
- **ТЗ:** 17.1, 8.4.1, 8.6.

### M-04. Онбординг: обучение + мини-экзамен
- **Назначение:** шаг `обучение` — стандарты платформы + мини-экзамен прямо в приложении (ТЗ 17.1).
- **Точки входа:** **учебные модули и тренажёр конвейера доступны сразу после отправки анкеты** (M-02/M-05) — кандидат не остывает 1–2 дня (ТЗ 17.17 п.9); **экзамен открывается после собеседования** (перевод в статус `обучение`; собеседование и практическая проверка — офлайн, отмечает админ).
- **Данные:** учебные модули (фото-фиксация, общение с клиентом, стандарты сервиса: бахилы, коврик под инструмент, уборка; работа в приложении — тренажёр конвейера); вопросы экзамена; проходной балл (параметр).
- **Элементы и действия:** список модулей с прогрессом; просмотр контента (текст/видео); [Начать экзамен] (заблокирована до собеседования с пояснением); вопросы с вариантами; результат; [Пересдать] (лимит попыток — параметр).
- **Состояния:** экзамен не сдан (разбор ошибок по темам); сдан → ожидание подписания договора и активации. **ОФЛАЙН:** скачанные модули доступны; экзамен требует сети (анти-читинг), баннер «Экзамен доступен онлайн».
- **Переходы:** сдан + договор подписан → админ активирует → M-06 с бейджем «Испытательный период: N/20 заявок».
- **Крайние случаи:** новый skill-тег действующему мастеру — тот же экзаменационный флоу с записью в аудит (ТЗ 17.1); на испытательном 100% фото-пакетов идут на модерацию (ТЗ 7.4).
- **ТЗ:** 17.1, 7.4.

### M-05. Онбординг: статус кандидата
- **Назначение:** хаб ожидания между шагами воронки `анкета` → `проверка` → `обучение` → `активен`/`отклонён`.
- **Точки входа:** вход кандидата; push о смене статуса.
- **Данные:** текущий статус, следующее действие («ждём проверку документов», «приходите на собеседование {дата, адрес}»), комментарии отказов, комплект новичка (форма, бейдж, стартовый набор расходников — за счёт компании или удержанием из первых выплат, параметр; ТЗ 17.1).
- **Элементы и действия:** статус-трекер воронки; [Учиться сейчас] → M-04 (модули и тренажёр доступны с момента отправки анкеты; экзамен — после собеседования, ТЗ 17.17 п.9); [Связаться с нами]; при возврате на доработку — переход к M-02/M-03.
- **Состояния:** отклонён (причина, возможность повторной подачи через N дней). **ОФЛАЙН:** показывает последний закешированный статус с меткой давности.
- **Переходы:** активация → M-06.
- **ТЗ:** 17.1.

### M-06. «Сегодня» — лента дня (главный экран)
- **Назначение:** маршрут сегодняшнего дня, управление сменой, вход во все разделы.
- **Точки входа:** запуск приложения; пуши по изменению ленты; нижняя навигация (Сегодня / Заявки / Кошелёк / Профиль).
- **Данные:** тумблер «На линии / Не работаю»; **строка дня у тумблера** — «Сегодня: +420 000 сум · 3 заявки» (заработок дня, тап → M-34 с чипом «Сегодня»; ТЗ 17.17 п.10); индикатор «Ты дежурный сегодня» + сумма минималки смены (дневная ~200 000 / ночная ~250 000, параметры; ТЗ 17.3, 18.4) и **прогресс минималки** в плашке дежурства — «набрано {X} из 250 000»; упорядоченная лента заявок дня: время окна, адрес, категория, статус, расчётная длительность (нормо-часы), дорожный буфер; счётчик несинхронизированного; бейдж испытательного периода; для этапных — метка «Сессия i из N»; для парных — метка роли (ведущий/помощник).
- **Элементы и действия:** тумблер смены (на линии → участвует в авто-распределении, ТЗ 7.1); тап по заявке → M-11 (или M-33 для роли помощника); [Карта] → M-08; таб «Завтра» → M-07; pull-to-refresh; иконка синка → M-42.
- **Состояния:** загрузка; пусто «Заявок нет — вы на линии, офферы придут пушем» / «Вы не на линии»; ошибка сети. **ОФЛАЙН:** лента из локальной БД, баннер «Офлайн — данные на {время}»; тумблер смены офлайн недоступен (переключение требует сервера — авто-распределение), показывается последнее известное положение с замком; изменения ленты не приходят — предупреждение «маршрут мог измениться».
- **Переходы:** M-07, M-08, M-09 (модально поверх), M-11, M-33, M-34, M-39, M-42.
- **Крайние случаи:** дежурному плановые не бронируются — лента почти пустая, плашка «Дежурство: аварийные и замены; с середины смены — срочные рядом с зоной» (ТЗ 17.3); лимит наличного долга превышен → мастер автоматически снят с линии, тумблер заблокирован с причиной и кнопкой [Внести через Payme] → M-35 (ТЗ 8.5); изменение ленты диспетчером → push + подсветка изменённых карточек; ближайшие 2 часа ленты заморожены для автоматики (ТЗ 17.3) — визуально «замок» на ближайшем отрезке.
- **ТЗ:** 7.1, 17.3, 8.5.

### M-07. Лента «Завтра»
- **Назначение:** завтрашний маршрут виден с вечера — мастер утром сразу едет (ТЗ 17.3 «Волновая сборка»).

### M-09. Входящий оффер (60 секунд)
- **Назначение:** принятие/отказ от заявки авто-распределения (ТЗ 7.1, 7.3).
- **Точки входа:** push «Новая заявка» → полноэкранный оффер (heads-up, поверх всего, со звуком).
- **Данные:** категория и состав работ; адрес (без подъезда/квартиры до принятия) + расстояние; окно времени; **сумма его доли** (не полная цена; настройка админа: показывать долю или полную цену; для B2C-вилки — расчёт от текущей оценки с пометкой «финальная доля — от подтверждённой на месте суммы»); фото клиента при создании заявки; бейджи: «Аварийная», «Срочно +30%» (доля с наценкой — мастеру выгодно, ТЗ 17.3), «Ночная», «Парная: ведущий», «Этапная: N сессий», «Требует оборудование: {название}»; таймер обратного отсчёта 60 сек.
- **Элементы и действия:** [Принять] — заявка встаёт в ленту, клиенту push; [Отказаться] — обязательный выбор причины (занят / далеко / нет материала / другое); таймер истёк = молчание → оффер уходит следующему (ТЗ 7.3); **режим вождения** (детект по датчикам/Activity Recognition): оффер озвучивается TTS (категория, район, доля), ответ — кнопкой гарнитуры (принять/отклонить) либо авто-отложение оффера на 3 мин; молчание в режиме вождения **не учитывается** в дисциплине офферов (ТЗ 17.17 п.8).
- **Состояния:** оффер отозван (принял другой / отменён) — «Заявка уже недоступна»; **ОФЛАЙН:** офферы не приходят (мастер без сети фактически невидим для распределения); если сеть пропала при открытом оффере — [Принять] недоступна, подпись «нет сети»; после восстановления сети — сводка «Пока вы были офлайн: N офферов» (информационно, без санкций); **батарея <10 %** — режим деградации: отключаются live-карта и расчёт ETA, камера и офлайн-очередь продолжают работать.
- **Переходы:** принял → M-06 (лента обновлена) или сразу M-11.
- **Крайние случаи:** два отказа подряд без причины — понижение приоритета в распределении (ТЗ 7.1); отказы с уважительной причиной, подтверждённой диспетчером, исключаются из знаменателя дисциплины офферов (ТЗ 7.4); аварийные офферы — ближайшему свободному, минуя очередь, визуально красные.
- **ТЗ:** 7.1, 7.3, 7.4, 17.3, 17.17.

### M-10. Экспресс-оффер замены (120 секунд, бродкаст)
- **Назначение:** протокол быстрой замены исчезнувшего мастера — «новый мастер за 15 минут» (ТЗ 17.3).
- **Точки входа:** push-бродкаст кандидатам по уровням, с расширением на следующий уровень при отсутствии отклика (общий таймер 120 сек): 1) дежурный по зоне; 2) свободные мастера рядом; 3) мастера, завершающие текущую заявку в ближайшие 30 мин; 4) при отсутствии отклика — расширенный бродкаст на соседние зоны / сверхурочный слот с согласия мастера (доплата); если и это не сработало — алерт диспетчеру на ручное назначение.
- **Данные:** как M-09 + плашка «Срочная замена» + время «клиент ждёт с {время}»; таймер 120 сек; правило «первый принявший забирает».
- **Элементы и действия:** [Принять] (гонка — сервер отдаёт первому, остальным «уже забрали»); [Пропустить] без причины и без штрафа (бродкаст ≠ персональный оффер).
- **Состояния:** «Заявку забрал другой мастер»; **ОФЛАЙН:** не приходит.
- **Переходы:** принял → M-11 (заявка с флагом замены; клиенту авто-push «Мастер заменён, едет {имя}»).
- **Крайние случаи:** мини-оффер «Нужен помощник» (M-26) использует этот же механизм с текстом «подсобить ~2 ч, фикс + дорога».
- **ТЗ:** 17.3 «Протокол быстрой замены».

### M-11. Карточка заявки — рабочий конвейер
- **Назначение:** центральный экран выполнения; степпер строго по шагам (ТЗ 7.1).
- **Точки входа:** M-06/M-07/M-08; push по заявке; deep-link `sozo-master://order/{id}`.
- **Данные:** номер `Z-2026-…`, тип (B2C/B2B/гарантийная/из осмотра/осмотр), срочность, адрес + подъезд/этаж/домофон + наличие лифта; **состояние блока адреса «детали не указаны»** (клиент не заполнил C-50) — жёлтая пометка «уточните у клиента/диспетчера», снимается при заполнении клиентом или фиксации деталей диспетчером; имя клиента (минимум данных, ТЗ 17.5), окно, состав работ с ценами и **долей мастера**, статус, степпер шагов: Выехал → Приступить (фото «до») → Работа/Смета → Материалы → Техника → Фото «после» → Приёмка → Оплата; для осмотра — чек-лист вместо фото-цикла; для гарантийной — ссылка на исходную заявку, смета клиенту = 0; примечания диспетчера; чек-лист доступа к общим зонам («доступ подтверждён на {дата/время}», ТЗ 4.1); **для B2B — блок «Доступ на объект»**: график доступа точки (дни/часы работы), контакт ТСЖ/охраны/ответственного лица, известные ограничения доступа (пропускной режим, шлагбаум, техническое окно) — подтягивается из профиля точки (LocationProfile, ТЗ 5.1); индикатор «не синхронизировано» (ТЗ 7.2).
- **Элементы и действия:** активная кнопка текущего шага (остальные заблокированы с пояснением); **состояние «В пути» — прямо на карточке** (объединено с M-12, v2.25): [Выехал] → клиенту push с ETA и карточкой мастера, ETA по карте на карточке; чипы [Задерживаюсь +30] / [+60] (каскадный пересчёт очереди, алерт диспетчеру при выбивании окна); [На месте — приступить] сразу открывает камеру фото «до» (M-13); гео-приближение ±300 м к адресу даёт авто-подсказку «Вы на месте?» с той же кнопкой; **плашка-таймлайн доп-согласования** (объединено с M-18, v2.25): после отправки доп-сметы на карточке — таймлайн «Отправлено → повтор 30 мин → звонок диспетчера 2 ч», баннер «можно выполнять согласованную часть», результат пушем; [Позвонить клиенту] (кнопкой, без отображения номера — доступно со статуса «Назначена» до «Закрыта», ТЗ 17.5); [Позвонить диспетчеру]; меню «⋮»: «Не могу поехать» (до выезда, M-32), «Клиент недоступен» (на месте, M-30), «Нет доступа: третья сторона» (M-14), «Прервать: небезопасно» (M-31), «Нужен помощник» (M-26), «Рекомендовать» (M-20); при активном помощнике — блок «Помощник: {имя}, статус: выехал/на месте/работает» с кнопкой **[Подтвердить: помощь завершена]**, доступной ведущему после того как помощник отметил «На месте» (M-33) — саму отметку ставит только ведущий; до этого подтверждения финальная приёмка (M-28) недоступна, если помощь фактически привлекалась; для многодневной **простой** работы без технологических пауз (обычная большая работа на 2+ смены, не путать с этапной M-25) — [Продолжение завтра]: обязательное фото «в процессе» + консервация рабочего места на ночь; конвейер возобновляется на следующий день с той же точки без повторного фото «до».
- **Состояния:** по статусам заявки; возврат от модерации диспетчера («Вернуть с комментарием», ТЗ 12) — красная плашка с комментарием и требуемым исправлением; пауза «Ожидание материалов» / «Технологический перерыв» / «Продолжение завтра» (многодневная простая работа) / «Заблокировано» — плашка с датой возобновления. **ОФЛАЙН:** весь конвейер работает; действия пишутся в очередь; плашка «Офлайн — действия сохранены, отправим при сети»; на карточке значок «не синхронизировано».
- **Переходы:** M-12…M-31 по шагам и веткам.
- **Крайние случаи:** гео-проверка ±300 м при «Приступить» — мягкая: несовпадение → флаг диспетчеру, не блок (ТЗ 4.1 ст.7); заявка переназначена — карточка блокируется «Заявка передана другому мастеру»; режимный объект («фото запрещено») — шаги фото заменены на код+подпись (M-28); осмотр — вместо фото до/после чек-лист по шаблону типа объекта, найденные дефекты (фото обязательно, категория, описание); перед завершением осмотра — обязательный шаг **«Представитель точки»**: выбор из списка сотрудников точки или ручной ввод ФИО+должности; подтверждение присутствия кодом приёмки (единый механизм M-28) ИЛИ подписью пальцем на экране (механизм режимных объектов); кнопка [Представитель отсутствовал] — требует фото точки доступа, ставит флаг диспетчеру на выборочную проверку, отчёт помечается «без представителя»; работает офлайн (подпись и данные — в очередь синка); без этого шага переход осмотра в «Выполнена» заблокирован (ТЗ 4.1, 9.3).
- **ТЗ:** 7.1, 4.1, 17.5, 3.7, 5.1.

### M-12. В пути: «Выехал» + «Задерживаюсь +30/60» (объединён, v2.25)
- **Статус:** отдельного экрана нет — всё нижеописанное живёт **состоянием карточки M-11** (ТЗ 17.17: конвейер ~40 тапов сокращается слиянием экранов). ID сохранён для ссылок; поведение и офлайн-правила действуют без изменений.
- **Назначение:** старт визита, честное управление сдвигами (ТЗ 7.1 шаг 1, 17.3).
- **Точки входа:** M-11, шаг 1; напоминание-пуш за 30 мин до окна (недожатие «Выехал» → авто-пинг → протокол замены, ТЗ 17.3).
- **Данные:** адрес, окно, ETA (расчёт по карте); статус «клиенту отправлен ETA».
- **Элементы и действия:** [Выехал] → статус «Мастер выехал», клиенту push с ETA и карточкой мастера; [Маршрут] → навигатор; [Задерживаюсь +30] / [+60] — доступна с момента «Выехал» и в любой момент работы: сдвигает план, каскадный пересчёт очереди мастера; если сдвиг выбивает следующую заявку за окно — алерт диспетчеру (переназначить/предложить клиенту сдвиг) (ТЗ 17.3); [На месте — Приступить] → сразу открывает камеру M-13; при гео-приближении ±300 м к адресу — авто-подсказка «Вы на месте?».
- **Состояния:** **ОФЛАЙН:** «Выехал» и «Задерживаюсь» пишутся в очередь с двойной меткой времени; ETA клиенту уйдёт при синке — предупреждение «клиент увидит выезд с задержкой».
- **Переходы:** M-13; M-30; M-14; M-31.
- **Крайние случаи:** после «Выехал» гео не приближается к адресу 15+ мин → мягкий флаг диспетчеру (звонок), не санкция (ТЗ 17.3); «Задерживаюсь» многократно — каждый раз пересчёт, повторный сдвиг окна клиента > 1 ч — звонок диспетчера поверх push (ТЗ 17.11).
- **ТЗ:** 7.1, 17.3, 17.11.

### M-13. Фото «до» (обязательный экран камеры)
- **Назначение:** гейт перехода «В работе» — мин. 1 фото «до» (ТЗ 4.1 ст.7, 7.1 шаг 2).
- **Точки входа:** [На месте — приступить] на карточке M-11 (состояние «В пути», бывш. M-12) — открывает камеру сразу; авто-подсказка «Вы на месте?» при гео ±300 м.
- **Данные:** видоискатель камеры (галерея недоступна); счётчик снимков; для каждого фото: клиентское время + монотонные часы, гео (или флаг «без гео»), клиентский UUID.
- **Элементы и действия:** [Снять] (до N фото); превью с удалением до отправки; [Готово — приступить к работе] (активна при ≥1 фото) → статус «В работе», фиксируется отметка «Приступить» (пунктуальность рейтинга считается по ней, ТЗ 7.4); рядом — [Нет доступа (третья сторона)] → M-14.
- **Состояния:** нет разрешения камеры — блокирующий запрос (без камеры работа невозможна); **ОФЛАЙН:** полный функционал; фото в локальной очереди, серверный таймштамп присвоится при синке, запись с флагом «зафиксировано офлайн» (ТЗ 7.2); гео нет (подвал) — фото принимается с флагом «без гео», конвейер не блокируется.
- **Переходы:** M-15 (смета) или продолжение работ на M-11.
- **Крайние случаи:** гео-несовпадение ±300 м — флаг диспетчеру, не блок; возобновление после паузы «Ожидание материалов» — повторное фото «до» не требуется (ТЗ 4.1); режимный объект — экран заменён кодом приёмки (M-28-вариант).
- **ТЗ:** 4.1, 7.1, 7.2, 14 (фото).

### M-14. «Нет доступа (третья сторона)»
- **Назначение:** фиксация блокировки работ третьей стороной: ТСЖ/УК, стояк, подвал, щитовая (ТЗ 4.1 «Заблокировано третьей стороной»).
- **Точки входа:** M-13 (не смог приступить); меню M-11 (блокировка вскрылась в процессе).
- **Данные:** причина из справочника (нет доступа к подвалу/стояку/крыше/щитовой; нужно отключение стояка; УК говорит «завтра»); фото (закрытая дверь) — обязательно; время следующей попытки, если известно.
- **Элементы и действия:** выбор причины; [Снять фото]; поле «следующая попытка {дата/время}» (опц.); [Отправить] → заявка в паузу «Заблокировано»; при подтверждённом времени — авто-якорь в ленту на это время, пуши клиенту и мастеру; без даты — задача диспетчеру «дозвониться до ТСЖ» (эскалация 48 ч, через 7 дней — решение с клиентом) (ТЗ 4.1).
- **Состояния:** **ОФЛАЙН:** полностью работает через очередь.
- **Переходы:** → M-06 (мастер свободен для других заявок).
- **Подключённый объект (M7, DEV-15 §10.4):** экран перестаёт быть тупиком. Если у мастера есть **действующий наряд-допуск**, а его не пускают, появляется отдельная причина **«Наряд есть, не пускают»**: заявка не уходит в паузу «Заблокировано», а порождает немедленную эскалацию дежурному оператора (push + SMS + автодозвон) с таймером и фиксацией нарушения в счётчик санкций объекта (DEV-15 §9.3). Мастер ждёт на месте до истечения таймера, затем решение принимает диспетчер. Пауза `blocked_third_party` для объектов в статусе `active` **не используется** — её место занимают статусы наряда `requested` и `rescheduled`.
- **Крайние случаи:** деньги — по ТЗ 4.4: зависимость, которую никто не мог знать → повторный выезд клиенту бесплатно, мастеру компенсация от компании (50% выезда, параметр); клиент подтверждал доступ, но не обеспечил → «повторный выезд» в счёт клиента, мастеру доля; B2B в подтверждённое окно не пустили → «холостой выезд» в СФ, мастеру 50% выезда. Мастеру расчёт показывается в кошельке с причиной.
- **ТЗ:** 4.1, 4.4.

### M-15. Уточнение сметы
- **Назначение:** превращение первичной оценки/диагностики в точную смету на месте (ТЗ 7.1 шаг 3; «половина B2C — диагностика», ТЗ 4.1).
- **Точки входа:** шаг конвейера после фото «до».
- **Данные:** текущие позиции — **по ценам релиза заявки** (`price_list_release_id`, зафиксирован при создании заявки; для заявок организаций — релиз договора), а не по текущему активному прайсу (ТЗ 3.7); поиск по прайсу (локальный кеш хранит несколько последних релизов, обновляется при синке; позиции подставляются из релиза заявки); калькулятор итога: работы + материалы, наценки (аварийная/ночная/срочная — одна наибольшая, ТЗ 3.7), минимальный чек (позиция «Минимальный заказ» видна до утверждения), доля мастера; утверждённая сумма и дельта.
- **Элементы и действия:** [+ Позиция] (поиск по названию, qty, ед. изм.); **ускорители сметы** (ТЗ 17.17 п.5) — над строкой поиска три блока, работающие без клавиатуры: **«Частые по категории заявки»** (топ-10 позиций релиза по статистике категории), **«Мои недавние»**, **«Наборы»** (пресеты-бандлы: «замена смесителя» = 3 позиции одним тапом; справочник наборов ведётся в админке); в меню — **«Скопировать смету из заявки той же категории»** (из прошлых заявок мастера); целевая метрика спеки: смета из 3 позиций — ≤ 5 тапов без клавиатуры; удаление/правка своих позиций до утверждения; итог обновляется живо; [Отправить на подтверждение]: B2C — клиенту push «Подтвердите стоимость {сумма}» (клиент решает со своего телефона — анти-подделка согласий; телефонный клиент — фиксирует диспетчер); B2B — если итог > утверждённого, авто-запуск доп-согласования → M-18; если ≤ утверждённого лимита — работа продолжается (для B2B доп-сметы в остатке лимита — параметр организации авто/вручную, ТЗ 5.1); отметка типа доп-работы: «Вынужденная» → M-17, «Рекомендация» → M-20; для этапных позиций — переход к плану сессий M-25.
- **Состояния:** ожидание подтверждения (M-18); отказ клиента от сметы после диагностики — оплачивается только выезд/диагностика (ТЗ 6.1); **ОФЛАЙН:** составление сметы работает на кеше прайса; отправка на подтверждение — в очередь, плашка «подтверждение уйдёт при сети» (работать по неподтверждённой смете нельзя — таймер согласования стартует с серверной доставки); **офлайн-подтверждение сметы** (ТЗ 17.17 п.7, закрывает дедлок «подвал без сети у обоих»): при отсутствии сети клиент подтверждает смету **подписью пальцем на экране мастера + фото**; пакет уходит в очередь синка с флагом «согласовано офлайн» и попадает в выборочную модерацию — зеркало механизма «принято без кода» (M-28).
- **Переходы:** M-16 (дорогая запчасть), M-17, M-18 (плашка-таймлайн на M-11), M-20, M-25.
- **Крайние случаи:** диагностика с отложенным выполнением — клиент платит только диагностику, при выполнении в 30 дней она зачитывается (ТЗ 3.7); позиция снята/изменена в новом релизе прайса — заявка продолжает работать по своему релизу (`price_list_release_id`); смета валидируется сервером против релиза заявки, позиция «не из релиза» отклоняется при синке (ТЗ 3.7); смета > утверждённой не даёт завершить заявку (гейт «итоговая сумма = утверждённой или утверждена доп-смета», ТЗ 4.1 ст.9).
- **ТЗ:** 7.1, 4.1, 3.7, 5.1, 6.1, 17.17.

### M-16. Вилка запчастей эконом/стандарт/премиум
- **Назначение:** выбор ценовой категории запчасти клиентом для позиций дороже порога (по умолч. 200 000; ТЗ 8.4.3).
- **Точки входа:** M-15/M-21 при добавлении запчасти дороже порога.
- **Данные:** три варианта из SparePartCatalog (ориентировочные цены) или фото ценников в магазине; описание отличий.
- **Элементы и действия:** [Из каталога] / [Сфотографировать ценники]; [Отправить клиенту] — выбор клиента фиксируется как часть доп-сметы, в аудит; индикатор «клиент выбирает…»; результат выбора.
- **Состояния:** клиент молчит — эскалация по таймерам доп-смет (30 мин push+SMS, 2 ч звонок диспетчера, ТЗ 5.3); **ОФЛАЙН:** формирование и фото работают, отправка в очереди.
- **Переходы:** назад в M-15/M-21 с выбранной позицией.
- **ТЗ:** 8.4.3, 5.3.

### M-17. Вынужденная доп-работа
- **Назначение:** оформление работ, без которых исходную не завершить (ТЗ 4.6). Не смешивается с апсейлом ни в интерфейсе, ни в правилах.
- **Точки входа:** M-15, тип «Вынужденная — без неё не завершить».
- **Данные:** фото проблемы (обязательно, камера); позиции — добавляются **по ценам релиза заявки** (`price_list_release_id`; для заявок организаций — релиз договора), а не по текущему активному прайсу; доп-смета валидируется сервером против релиза заявки (ТЗ 3.7); где осмысленно — **два варианта**: минимальный (безопасная времянка/частичный ремонт) и полный (замена целиком); суммы и доля мастера по каждому.
- **Элементы и действия:** [Снять фото проблемы]; конструктор вариантов «Минимальный» / «Полный»; [Отправить]: B2C — push клиенту с фото и вариантами (решает со своего телефона, даже стоя рядом); B2B — красный флаг утверждающему, короткие таймеры (30 мин повтор + SMS, 2 ч звонок диспетчера, ТЗ 5.3) → M-18.
- **Состояния:** согласие → доп-смета утверждена, работа по выбранному варианту; отказ или молчание (B2C — клиент не отвечает на push, B2B — не утверждено по таймерам) → M-19 Консервация — молчание по вынужденной работе **всегда** эскалируется по таймерам и требует явного закрытия статуса (в отличие от апсейла M-20, где молчание клиента ничего не эскалирует и ни на что не влияет); **ОФЛАЙН:** оформление полностью, отправка в очереди (таймеры стартуют от серверной доставки).
- **Переходы:** M-18, M-19.
- **Крайние случаи:** B2B: отклонённая/неутверждённая вынужденная работа автоматически становится дефектом в техдолге точки с готовой оценкой и фото (ТЗ 4.6 п.5) — мастеру уведомление «сохранено в техдолг»; доля мастера с принятых вынужденных — обычная, от базовой цены.
- **ТЗ:** 4.6, 5.1, 5.3, 3.7.

### M-18. Ожидание подтверждения доп-сметы (объединён, v2.25)
- **Статус:** отдельного экрана нет — представлен **плашкой-таймлайном на карточке M-11** (ТЗ 17.17). ID сохранён для ссылок; логика эскалаций и офлайн-правила действуют без изменений.
- **Назначение:** статус «Доп-согласование»: работа по согласованной части продолжается (ТЗ 4.1 ст.8).
- **Точки входа:** авто после отправки доп-сметы (M-15/M-16/M-17).
- **Данные:** что отправлено (позиции, фото, варианты), кому (клиент/утверждающий B2B), таймлайн эскалации (отправлено → повтор 30 мин → звонок диспетчера 2 ч), результат.
- **Элементы и действия:** баннер «Можно выполнять согласованную часть»; [Вернуться к работе] (экран не блокирует конвейер по утверждённым позициям); [Позвонить диспетчеру]; результат приходит пушем: «Утверждено {вариант}» / «Отклонено».
- **Состояния:** утверждено; отклонено → предложение консервации (M-19) при вынужденной; молчание — авто-отмена НЕ применяется: мастер завершает согласованную часть, несогласованные позиции снимаются (ТЗ 5.3); **ОФЛАЙН:** ответ не придёт без сети — плашка «результат появится при сети»; согласованную часть можно продолжать.
- **Переходы:** M-11, M-19.
- **ТЗ:** 4.1, 4.6, 5.3.

### M-19. Консервация
- **Назначение:** безопасное отключение/перекрытие при отказе от вынужденных работ (ТЗ 4.6 п.4): «клиент предупреждён об опасности, от работ отказался».
- **Точки входа:** отказ/молчание по вынужденной доп-смете (M-18).
- **Данные:** фиксированная позиция прайса «Консервация» (аналог аварийной локализации; в B2B списывается без утверждения как мера безопасности, ТЗ 5.1); фото выполненной консервации.
- **Элементы и действия:** [Выполнил консервацию] + фото; авто-формирование итога: выезд + фактически сделанное + консервация; заявка завершается с флагом «выполнена частично»; в акте — фото проблемы и запись об отказе (юридическая защита).
- **Состояния:** **ОФЛАЙН:** полностью работает.
- **Переходы:** → M-27 (фото «после» по сделанной части) → приёмка/оплата.
- **ТЗ:** 4.6, 5.1, 4.4.

### M-20. Апсейл «Рекомендовать»
- **Назначение:** рекомендация «заодно» при выполнимой исходной работе (ТЗ 4.6). Отдельная кнопка, НЕ доп-смета, не блокирует конвейер.
- **Точки входа:** меню M-11; M-15 (тип «Рекомендация»).
- **Данные:** фото, позиции, комментарий; статистика: конверсия и выручка рекомендаций мастера (мотивация, на рейтинг не влияет).
- **Элементы и действия:** [Снять фото]; [+ Позиция]; комментарий; [Отправить рекомендацию]: B2C — клиенту в приложение («Принять» → утверждённая доп-смета, мастер делает сейчас / «Отклонить» / «Отложить» → список рекомендаций в профиле клиента); B2B — всегда утверждающему по порогам, **никогда не автостартует**, сотрудник точки принять не может, «Отложить» → техдолг (ТЗ 4.6 п.3).
- **Состояния:** принято / отклонено / отложено — пуш мастеру; **ОФЛАЙН:** оформление работает, отправка в очереди.
- **Переходы:** принято → позиции добавляются в смету (M-15).
- **Крайние случаи:** работа по непринятому апсейлу (включая молчание клиента — простое отсутствие ответа) не оплачивается вообще (ТЗ 4.6 п.4); **в отличие от вынужденной доп-работы (M-17/M-18)**, молчание по апсейлу не запускает никакой эскалации, таймеров или консервации — рекомендация просто остаётся без ответа; анти-давление: отказ не влияет на завершение исходной работы; жалоба «навязывал» — причина спора; апсейл не влияет на рейтинг ни вверх, ни вниз (ТЗ 4.6 п.5). Завершение заявки не ждёт ответа на рекомендацию.
- **ТЗ:** 4.6, 5.1.

### M-21. Материалы заявки
- **Назначение:** фиксация запчастей и расходников (ТЗ 7.1 шаг 4, 8.4).
- **Точки входа:** шаг конвейера; доступен весь период «В работе».
- **Данные:** список материалов заявки: {название, кол-во, цена, фото чека, источник, флаг «возместить мастеру»}; каталог расходников ConsumableCatalog (фикс-цены, локальный кеш); согласованный бюджет материалов; лимит закупки без согласования 500 000/заявка (параметр).
- **Элементы и действия:** [+ Материал] → **выбор запчасти из SparePartCatalog** (поиск по каталогу — по умолчанию, а не свободный текст; ТЗ 17.17 п.5) с fallback «нет в каталоге — ввести вручную», кол-во, цена, **фото чека обязательно** (камера); тумблер «куплено из своих» → пометка «возместить мастеру»; [+ Расходник из каталога] → позиции по фикс-цене **без чека** (вся сумма расходников идёт мастеру, ТЗ 8.4.1); [Код закупки] → M-22 (фаза 2); [Список закупки клиенту] → M-23; для запчастей дороже порога — принудительный переход к вилке M-16 и чек-лист «доказательство замены»: фото старой детали, новой в упаковке, установленной; демонтированная деталь остаётся клиенту (ТЗ 8.4.3).
- **Состояния:** превышен лимит закупки → требуется фото ценника + подтверждение диспетчера (блокирующее); превышение норматива расходников на категорию → предупреждение «будет флаг диспетчеру» (ТЗ 8.4.1); **ОФЛАЙН:** всё работает — каталог из кеша, чеки в очередь фото.
- **Переходы:** M-16, M-22, M-23.
- **Крайние случаи:** неиспользованные материалы — возврат в магазин по чеку либо передача клиенту, если оплачены; в акте только фактический расход (ТЗ 8.4.3); гарантия на запчасть фиксируется в заявке отдельно от гарантии на работу; материалы, купленные до отмены заявки, оплачиваются клиентом по чекам (ТЗ 4.4).
- **ТЗ:** 8.4.1–8.4.3, 7.1, 17.17.

### M-22. «Код закупки» — QR партнёрского магазина (фаза 2)
- **Назначение:** закупка в долг компании без денег мастера (ТЗ 8.4.4).
- **Точки входа:** [Код закупки] на M-21.
- **Данные:** одноразовый код (QR + цифры), лимит = согласованный бюджет материалов заявки + 10%, срок жизни 4 часа, привязка к заявке; список партнёрских магазинов рядом (адреса, категории).
- **Элементы и действия:** [Сгенерировать код] → экран QR + цифровой код + таймер жизни; магазин проверяет код на веб-странице проверки и отпускает товар в долг компании; после закупки — [Зафиксировать накладную]: фото + позиции (обязательно; сверяется диспетчером со сметой при модерации).
- **Состояния:** код просрочен → [Сгенерировать новый]; лимит кода исчерпан; **ОФЛАЙН:** генерация кода требует сети (сервер выдаёт код) — плашка «нужна сеть»; ранее сгенерированный код и накладная фиксируются офлайн.
- **Переходы:** → M-21 (позиции накладной в материалы; клиенту — по накладной без наценки).
- **Крайние случаи:** превышение лимита кода магазином — риск магазина (в договоре); расхождение накладной со сметой — разбор с магазином и мастером (ТЗ 8.4.4).
- **ТЗ:** 8.4.4, 3.6 (PurchaseCode).

### M-23. Список закупки клиенту
- **Назначение:** схема «клиент покупает сам» (ТЗ 8.4.3 п.3).
- **Точки входа:** [Список закупки клиенту] на M-21.
- **Данные:** позиции списка (название, кол-во, ориентир цены), дата повторного визита.
- **Элементы и действия:** конструктор списка; [Отправить клиенту] → заявка в паузу «Ожидание материалов» с датой повторного визита (ТЗ 4.1); заявка уходит из активного шага, мастер свободен.
- **Состояния:** **ОФЛАЙН:** работает через очередь.
- **Переходы:** → M-06; при возобновлении — конвейер продолжается без повторного фото «до» (ТЗ 4.1).
- **ТЗ:** 8.4.3, 4.1.

### M-24. Фиксация техники клиента (шильдик)
- **Назначение:** пополнение паспорта техники ClientAsset — «сервисный след» (ТЗ 17.12, 7.1 шаг 3a).
- **Точки входа:** шаг конвейера «Техника» (перед завершением); можно из M-11 в любой момент «В работе».
- **Данные:** тип (кондиционер/котёл/бойлер/стиральная машина/смеситель…), бренд, модель, год; **фото шильдика обязательно** (OCR — фаза 3, пока поля руками); **условный гейт** (ТЗ 17.17 п.6): обязательная фиксация техники — только для категорий с оборудованием (признак позиции прайса: котлы, кондиционеры, бойлеры, крупная техника); для остальных категорий шаг закрывается чипом **«Техники нет»** одним тапом — мусорные записи «Смеситель, -, -» хуже отсутствия записи; **бренд/модель необязательны при снятом фото шильдика** — дозаполнит модерация/OCR; привязка выполненных позиций к единице техники; ранее зафиксированные единицы этого клиента/точки (выбор существующей вместо дубля).
- **Элементы и действия:** [Выбрать существующую] / [+ Новая единица]; чип [Техники нет] (для категорий без признака оборудования); [Снять шильдик]; поля (бренд/модель — опциональны при фото шильдика); [Сохранить].
- **Состояния:** шильдик нечитаем/отсутствует — чекбокс «шильдик отсутствует» + фото общего вида; **ОФЛАЙН:** полностью работает.
- **Переходы:** → M-27.
- **Крайние случаи:** заполненность паспорта техники учитывается в компоненте «качество фиксации» рейтинга (ТЗ 7.4, 17.12); повторные заявки по напоминаниям уходят закреплённому мастеру — мотивация заполнять аккуратно (ТЗ 17.12).
- **ТЗ:** 17.12, 7.1, 7.4, 17.17.

### M-25. Этапные сессии
- **Назначение:** работы с технологическими перерывами: план сессий, завершение этапа, бронирование следующих (ТЗ 4.1 «Этапная работа», 17.3). Не путать с простой многодневной работой без технологических ограничений (просто не уместилась в одну смену) — та закрывается на карточке заявки (M-11) паузой «Продолжение завтра», без плана сессий и брони слотов.
- **Точки входа:** карточка этапной заявки (M-11); M-15 при добавлении этапной позиции по итогам диагностики.
- **Данные:** план этапов из прайса: [{этап, нормо-часы, пауза после: окно [мин; макс]}] (пример: стяжка — «не раньше 24 ч, не позже 7 дней»); статус каждой сессии (заброн./выполнена); индикатор «Сессия i из N».
- **Элементы и действия:** **бронирование следующих сессий на экране мастера при утверждении сметы** (сценарий «работа выяснилась на месте»): система предлагает клиенту слоты следующих сессий из реальной ленты, клиент подтверждает их вместе со сметой (ТЗ 4.1); **инвариант: этап 1 не начинается, пока не подтверждены слоты всех следующих этапов** — кнопка старта заблокирована с пояснением «не начинай красить, если некому приехать домазать»; если слотов нет — планировщик предлагает: перенести всю работу / сверхурочный слот с согласия мастера / передача другому мастеру с разделом доли (параметр, по умолч. выкл.); [Этап N завершён] в конце каждой сессии → обязательное фото «в процессе» + отметка этапа; заявка в паузу «Технологический перерыв» — **мастер свободен, пауза не занимает ленту**.
- **Состояния:** пауза с датой следующей сессии; **ОФЛАЙН:** завершение этапа с фото — офлайн; бронирование слотов требует сети (живая лента) — плашка «подтверждение слотов при сети».
- **Переходы:** финальная сессия → M-27 → M-28 → M-29 (оплата B2C — на последней сессии; промежуточные сессии — единственное исключение из «не уходить без оплаты», ТЗ 4.1).
- **Крайние случаи:** все сессии — один мастер; замена — через «раздел заявки» диспетчером (ТЗ 4.5); отмена посередине — оплата фактически выполненных этапов (ТЗ 4.4); продолжения начатых работ стоят высоко в приоритетах очереди (уровень 4, ТЗ 17.3); цена — за работу целиком, выезды сессий отдельно не тарифицируются.
- **ТЗ:** 4.1, 3.7, 17.3, 4.4, 4.5.

### M-26. «Нужен помощник»
- **Назначение:** вызов второго человека, когда вскрылось, что одному физически нельзя (ТЗ 17.3 «Парные работы»).
- **Точки входа:** меню M-11 при статусе «В работе».
- **Данные:** оценка времени помощи (~ч), фикс помощника (параметр), адрес.
- **Элементы и действия:** [Отправить мини-оффер] → бродкаст ближайшим свободным и дежурному: «подсобить ~2 ч, фикс + дорога», первый принявший едет (механика M-10); статус поиска; результат (имя, ETA помощника).
- **Состояния:** никого нет → работа переносится на ближайший парный слот (механика инварианта этапных работ) — согласование переноса с клиентом через диспетчера; **ОФЛАЙН:** недоступно (бродкаст требует сервера) — плашка «нужна сеть, позвоните диспетчеру».
- **Переходы:** → M-11 (блок «Помощник: {имя}»).
- **Крайние случаи:** кто платит фикс, если позиция не была парной: клиент — никогда; скрытые условия — расход компании; ведущий недооценил очевидное — из доли ведущего (решает диспетчер, в аудит) (ТЗ 17.3). **Фаза 2 (заметка на будущее):** при устойчиво высокой доле парных заявок у мастера/в зоне (по статистике) система может перейти в режим «Экипаж дня» — стабильная пара/бригада на весь день вместо разового мини-оффера на каждую парную заявку; в MVP не реализовано.
- **ТЗ:** 17.3, 4.5.

### M-27. Фото «после»
- **Назначение:** гейт «Выполнена»: мин. 1 фото «после» (ТЗ 4.1 ст.9; критерий приёмки №1 — контроль на API).
- **Точки входа:** [Завершить] на M-11.
- **Данные:** камера; подсказка «тот же ракурс, что „до“» с миниатюрой фото «до» (ТЗ 7.1 шаг 5); чек-гейты перед выходом: все материалы внесены с чеками; итоговая сумма = утверждённой или утверждена доп-смета; техника зафиксирована **или отмечен чип «Техники нет»** — гейт обязателен только для категорий с оборудованием (M-24, ТЗ 17.17 п.6).
- **Элементы и действия:** [Снять]; [Готово] → сразу M-28 — отдельный итоговый под-экран упразднён (объединён, v2.25): итог работ/материалов/доли показывается на экране приёмки M-28.
- **Состояния:** незакрытые гейты — список блокеров со ссылками на шаги; **ОФЛАЙН:** полностью работает.
- **Переходы:** M-28; B2C с онлайн-оплатой в приложении — сразу M-29 (код приёмки не запрашивается, см. M-28).
- **Крайние случаи:** режимный объект — фото запрещено, вместо экрана — приёмка кодом + подписью (M-28); осмотр — вместо фото «после» заполненный чек-лист + обязательный шаг «Представитель точки» (код/подпись либо «отсутствовал» + фото точки доступа — M-11, ТЗ 9.3).
- **ТЗ:** 4.1, 7.1, 15 (критерии приёмки).

### M-28. Приёмка
- **Назначение:** подтверждение принятия работы на месте единым способом — одноразовым кодом подтверждения, одинаковым для B2C и B2B (ТЗ 7.1 шаг 5).
- **Точки входа:** после M-27. **Ветка «онлайн-оплата в приложении» (B2C):** если клиент выбирает онлайн-оплату в приложении, **код приёмки не запрашивается** — приёмка фиксируется автоматически вебхуком успешного платежа (ТЗ 17.17 п.3); флоу мастера: M-27 → M-29 (оплата), экран кода M-28 показывается только для наличных, телефонного канала и B2B (сотрудник точки).
- **Данные:** итог работ/материалов; единое поле одноразового 4-значного кода подтверждения — код получает клиент (B2C) или сотрудник точки (B2B) пушем на свой телефон (SMS-дубль при недоступности пуша) и называет его мастеру; мастер вводит этот же код независимо от типа заявки.
- **Элементы и действия:** поле ввода кода подтверждения (единая механика для B2C и B2B); **дополнительно для B2C** — подпись клиента пальцем на экране (опциональное усиление, не замена кода); **fallback** [Принято без кода] (клиент/сотрудник недоступен: не называет код, телефон сел, смена кончилась) → обязательное фото результата с общим планом помещения → флаг диспетчеру на ручное подтверждение (документированный запасной путь без кода); **режимный объект:** тот же код подтверждения + подпись представителя на экране мастера, в акте отметка «фотофиксация запрещена режимом объекта» (ТЗ 4.1).
- **Состояния:** неверный код (3 попытки → предложение fallback); **ОФЛАЙН:** ввод кода и «Принято без кода» работают офлайн (запись в очередь); сама проверка/валидация кода по закешированному значению не производится — код валидируется при синке с пометкой «принят офлайн» (конфликт — флаг диспетчеру).
- **Переходы:** B2C → M-29 Оплата; B2B → «Выполнена», → M-06 (списание с абонентки/СФ — без участия мастера).
- **Крайние случаи:** диспетчер возвращает пакет с модерации → заявка назад «В работе» с комментарием (ТЗ 4.1 ст.10); если оплата уже принята — возврат её не отменяет.
- **ТЗ:** 7.1, 4.1.

### M-29. Оплата (B2C)
- **Назначение:** сбор оплаты до ухода мастера — «исключение, а не норма — уйти без оплаты» (ТЗ 4.1 ст.11, 7.1 шаг 6, 8.5).
- **Точки входа:** после приёмки B2C; финальная сессия этапной работы.
- **Данные:** сумма к оплате; способы: QR провайдера (Payme/Click/Uzum) на экране мастера; push клиенту со ссылкой на оплату; наличные. Статус платежа в реальном времени.
- **Элементы и действия:** [Показать QR]; [Отправить ссылку клиенту]; [Принял наличные {сумма}] → подтверждение → вся сумма становится долгом мастера перед компанией (ТЗ 8.5), обновляется индикатор долга; после оплаты и оценки — экран чаевых у клиента (целиком мастеру, мимо долей, отдельной проводкой; в MVP — решение владельца); [Не могу получить оплату] → звонок диспетчеру; уход без оплаты — только с санкции диспетчера, заявка в «Ожидает оплаты».
- **Состояния:** ожидание платежа (поллинг/пуш); платёж не прошёл; **ОФЛАЙН:** онлайн-оплата невозможна — доступны «Принял наличные» (офлайн, в очередь) и памятка «QR клиента может сработать по его сети»; санкция диспетчера требует связи (звонок).
- **Переходы:** → «Выполнена» → M-06; кошелёк обновляется после закрытия.
- **Крайние случаи:** долг мастера по наличным ≥ лимита 2 000 000 (параметр) → предупреждение и требование внести через Payme, при превышении — автоснятие с линии (ТЗ 8.5) → M-35; чаевые не смешиваются с суммой заявки.
- **ТЗ:** 7.1, 8.5, 4.1, 3.7.

### M-30. «Клиент недоступен»
- **Назначение:** фиксация «не открыл / не пустил» (ТЗ 4.4).
- **Точки входа:** меню M-11, мастер на месте.
- **Данные:** фото двери/фасада (обязательно) + гео; время прибытия.
- **Элементы и действия:** [Снять фото] → [Отправить] → диспетчер прозванивает 15 мин (ТЗ 17.11) → отмена с «ложным вызовом» (клиенту 50 000 по умолчанию; мастеру компенсация 50% выезда, ТЗ 4.4); статус ожидания решения диспетчера; [Позвонить клиенту] кнопкой.
- **Состояния:** диспетчер дозвонился — заявка продолжается (пуш мастеру «клиент откроет через 5 мин»); **ОФЛАЙН:** фиксация в очередь; прозвон диспетчера не запустится до синка — рекомендация позвонить диспетчеру голосом.
- **Переходы:** отмена → M-06; продолжение → M-13.
- **ТЗ:** 4.4, 17.11.

### M-31. «Прервать: небезопасно»
- **Назначение:** защита мастера от неадеквата/угроз (ТЗ 17.5).
- **Точки входа:** меню M-11 на любом шаге.
- **Данные:** фото и/или комментарий (что происходит).
- **Элементы и действия:** [Прервать и уйти] — немедленно, без блокировок конвейером; материалы уходят диспетчеру, он решает: отмена без штрафа мастеру; подтверждённый неадекват → B2C-аккаунт в чёрный список.
- **Состояния:** **ОФЛАЙН:** работает полностью (безопасность не может зависеть от сети), синк потом.
- **Переходы:** → M-06.
- **ТЗ:** 17.5.

### M-32. «Не могу поехать»
- **Назначение:** честный ранний отказ от принятой заявки — караётся мягче тихого невыхода (ТЗ 7.1, 17.3).
- **Точки входа:** карточка принятой заявки (M-11 до «Выехал»), лента завтра (M-07).
- **Данные:** причина обязательна (заболел / форс-мажор / не успеваю / другое + комментарий).
- **Элементы и действия:** [Подтвердить отказ] → протокол замены запускается немедленно (ТЗ 17.3): заявка — красная на доске диспетчера, бродкаст кандидатам; заявка исчезает из ленты мастера.
- **Состояния:** **ОФЛАЙН:** критично — отказ должен дойти быстро; офлайн ставится в очередь + экран настоятельно предлагает [Позвонить диспетчеру].
- **Переходы:** → M-06.
- **Крайние случаи:** уважительная причина (подтверждает диспетчер) — без санкций, отметка в профиле; без причины — удар по дисциплине рейтинга + счётчик невыходов (2-й за 90 дней — снятие с линии и разбор, 3-й — блокировка); невыход с ущербом — денежное удержание (ТЗ 17.3, 7.4).
- **ТЗ:** 17.3, 7.1, 7.4.

### M-33. Карточка помощника (упрощённая)
- **Назначение:** участие в парной заявке в роли помощника — без конвейера, смет и фото-цикла (всё это на ведущем; ТЗ 17.3).
- **Точки входа:** принятый оффер парной заявки (роль «помощник») или мини-оффер «Нужен помощник»; лента M-06.
- **Данные:** адрес, время, имя и телефон ведущего (кнопкой), фикс за сессию (или меньшая доля — параметр), описание («поднять бойлер на 4 этаж, лифта нет»).
- **Элементы и действия:** [Выехал]; [На месте]; после этого статус — «Ожидает подтверждения ведущего»: саму отметку «Помощь завершена» ставит ведущий на своей карточке (M-11, блок «Помощник»), помощник её только ожидает; [Позвонить ведущему]; [Не могу поехать] → M-32 (санкции невыхода — обычные).
- **Состояния:** **ОФЛАЙН:** отметки в очередь.
- **Переходы:** завершение → M-06; фикс — в кошелёк после закрытия заявки ведущим.
- **Крайние случаи:** помощь на рейтинг не влияет; исключение — невыход на принятый оффер (ТЗ 17.3); помощником может быть кандидат на испытательном/младший грейд (подработка и обучение).
- **ТЗ:** 17.3, 4.5.

### M-34. Кошелёк
- **Назначение:** полная прозрачность денег мастера (ТЗ 7.1 «Кошелёк», 8.5, 8.6).
- **Точки входа:** нижняя навигация; push «Выплата проведена»; переходы из M-29.
- **Данные:** «Заработано за период» с детализацией по заявкам (доля за работы отдельно от **возмещений** материалов — возмещения не доход и не облагаются налогом, ТЗ 8.6); расходники сумки (возмещение + микромаржа); удержания с причинами (гарантийная переделка по вине 0/50/100%, регресс ущерба частями ≤30% выплаты, невыход с ущербом); принятые наличные (долг перед компанией) + прогресс-бар к лимиту 2 000 000; гарантированный минимум дежурства — отдельной строкой за смену дежурства (ТЗ 8.6); **возмещение ГСМ** (только мастера со своим авто): строка «Возмещение ГСМ: {N} км × {ставка} = {сумма}» с расшифровкой по сменам — считаются переезды по карте между выполненными заявками ленты, путь дом↔заявки не считается (ТЗ 8.6); чаевые; реферальные бонусы; формула «к выплате = начисления − удержания − наличные»; отрицательный итог = «к внесению через Payme»; история выплат (ведомости, даты, суммы, статус); для ГПХ — строки удержаний НДФЛ/соцналог; для самозанятых — брутто; начисления считаются от релиза каждой заявки: по старым заявкам — старые цены, по новым — новые (ТЗ 3.7).
- **Элементы и действия:** периоды (неделя — параметр) + **чип «Сегодня»** — дневная лента проводок текущего дня: ответ «сколько сегодня» за 5 секунд (ТЗ 17.17 п.10; сюда же ведёт тап по строке дня на M-06); тап по строке → расшифровка до заявки/проводки; [Внести наличные] → M-35; [Апелляция] на удержание → тикет диспетчеру (решение в аудит, ТЗ 7.4).
- **Состояния:** пусто (новый мастер); **ОФЛАЙН:** кеш с меткой «данные на {время}»; принятые офлайн наличные видны сразу с пометкой «не синхронизировано».
- **Переходы:** M-35.
- **Крайние случаи:** офбординг — заморозка выплат, акт сверки, финальная выплата/взыскание (ТЗ 8.6) — отображается статусом «Выплаты заморожены: сверка»; споры блокируют начисление доли до резолюции (ТЗ 4.2) — строка «доля заблокирована спором».
- **ТЗ:** 7.1, 8.5, 8.6, 4.2, 17.3, 17.17.

### M-35. Внесение наличных через Payme
- **Назначение:** погашение наличного долга мастера (ТЗ 8.5).
- **Точки входа:** M-34; блокировка тумблера на M-06 при превышении лимита; push «Лимит наличных превышен».
- **Данные:** текущий долг; сумма к внесению (по умолчанию — до нуля или до безопасного уровня); реквизиты/deep-link Payme на счёт компании.
- **Элементы и действия:** ввод суммы; [Оплатить через Payme] → приложение/веб Payme; статус зачисления (вебхук провайдера, идемпотентно, ТЗ 8.8); после зачисления — авто-возврат на линию, если снятие было по лимиту.
- **Состояния:** платёж в обработке; не прошёл; **ОФЛАЙН:** недоступно (онлайн-платёж), экран-заглушка.
- **Переходы:** → M-34; → M-06.
- **ТЗ:** 8.5, 8.8.

### M-36. Сумка / MasterStock (фаза 2)
- **Назначение:** количественный учёт расходников мастера (ТЗ 8.4.2). В MVP экрана нет — расходники добавляются в заявку из каталога без учёта остатков.
- **Точки входа:** профиль; push «Остаток ниже норматива».
- **Данные:** остатки по позициям (кол-во, себестоимость), нормативы min/max по skill-тегу, индикатор «ниже норматива», история пополнений.
- **Элементы и действия:** [Пополнить чеком] — фото чека + позиции → зачисление в сумку по себестоимости, мастеру возмещение; пополнение со склада компании — фаза 3; списание в заявку (из M-21) уменьшает остаток автоматически.
- **Состояния:** **ОФЛАЙН:** остатки из кеша; пополнения в очередь.
- **Переходы:** M-21.
- **ТЗ:** 8.4.2.

### M-37. Оборудование компании («Моё оборудование»)
- **Назначение:** учёт выданного мастеру парка компании: прочистные машины, течеискатели, тепловизор, сварка ПП и т.п. (ТЗ 17.9).
- **Точки входа:** профиль; push «Вам назначена выдача оборудования» / «ТО оборудования».
- **Данные:** список выданных единиц: инвентарный номер, категория, фото состояния, дата выдачи, статус (`выдано мастеру`/`в ремонте`); акты выдачи/возврата (архив).
- **Элементы и действия:** тап → карточка единицы с актами; [Принять выдачу] / [Оформить возврат] → M-38; правило распределения: заявки, требующие оборудование, планировщик отдаёт только мастерам с выданным оборудованием и транспортом (ТЗ 17.9, 17.3 «Транспортный фильтр») — плашка-пояснение.
- **Состояния:** пусто «Оборудование не выдано»; **ОФЛАЙН:** кеш; акты — офлайн через очередь.
- **Переходы:** M-38.
- **Крайние случаи:** статус «в ремонте» исключает зависящие заявки из ленты мастера; утеря/поломка по вине — разбор, удержание 0/50/100% остаточной стоимости частями ≤30% выплаты (ТЗ 17.9) — отражается в кошельке.
- **ТЗ:** 17.9, 17.3.

### M-38. Акт выдачи/возврата оборудования
- **Назначение:** материальная ответственность прямо в приложении (ТЗ 17.9).
- **Точки входа:** M-37; инициирует админ/склад.
- **Данные:** единица оборудования, тип акта (выдача/возврат), фото состояния **со всех сторон** (мин. N ракурсов, камера), код подтверждения мастера.
- **Элементы и действия:** пошагово: фото со всех сторон → сверка комплектности → [Подтвердить кодом] (мастер вводит код — аналог подписи); акт фиксируется, PDF в архиве.
- **Состояния:** расхождение состояния при возврате — комментарий + разбор; **ОФЛАЙН:** съёмка и заполнение офлайн; подтверждение кодом — при сети (код одноразовый серверный).
- **Переходы:** → M-37.
- **ТЗ:** 17.9.

### M-39. Профиль
- **Назначение:** рейтинг, грейды, навыки, зоны, статистика (ТЗ 7.1 «Профиль», 7.4).
- **Точки входа:** нижняя навигация; периодический push «Подтвердите комплектность инструмента» (раз в месяц/квартал, параметр).
- **Данные:** рейтинг 0–100 (пересчёт еженедельно, окно 56 дней) с разбивкой по компонентам и формулами (ТЗ 7.4): пунктуальность 25% = доля «Приступить» в окне ×100; оценки клиентов 30% = средняя ×20 (байесовское сглаживание к 4.5 при <10 оценок); качество фиксации 15% = доля фото-пакетов, принятых с первой попытки ×100 (включая заполненность паспорта техники); отсутствие переделок 20% = 100 − 25×(переделки по вине); дисциплина офферов 10% = доля принятых ×100 (уважительные отказы исключены из знаменателя). Грейд: Бронза <70 / Серебро 70–85 / Золото >85 и ≥100 закрытых (доля 57% вместо 55%, с запуска авто-рейтинга ф.2); стартовый рейтинг 60, испытательный «N из 20 заявок»; апсейл-статистика (конверсия рекомендаций, выручка — на рейтинг не влияет); skill-теги (+ статус «снят временно: неполный инструмент», ТЗ 8.4.1); зоны выезда; транспорт; предпочтительный напарник; счётчик невыходов; язык интерфейса; выход.
- **Элементы и действия:** [Запросить новый skill-тег] → экзаменационный флоу (M-04); [Апелляция] на оценку/санкцию → тикет диспетчеру (ТЗ 7.4 «Гигиена оценок»); **периодическая проверка инструмента** (по пушу или вручную из профиля) → чек-лист ToolChecklist по каждому активному skill-тегу → [Подтверждаю, всё на месте] / [Не хватает: {позиция}] (снимает skill-тег до восстановления — та же логика, что при онбординге, ТЗ 8.4.1); переходы: M-40, M-41, M-37, M-36, M-42.
- **Состояния:** MVP: рейтинг выставлен диспетчером вручную, подпись «рейтинг устанавливается диспетчером; авто-расчёт — скоро» (ТЗ 7.4); **ОФЛАЙН:** кеш.
- **Крайние случаи:** рейтинг <40 — плашка «назначен разбор с диспетчером»; <25 — блокировка (экран блокировки при входе); санкции только приоритетом, денежных штрафов за рейтинг нет (ТЗ 7.4).
- **ТЗ:** 7.1, 7.4, 8.4.1.

### M-40. График и отпуска
- **Назначение:** рабочие дни/часы, запрос отпуска/больничного (ТЗ 17.3: «мастер запрашивает в приложении, диспетчер подтверждает»).
- **Точки входа:** профиль.
- **Данные:** календарь месяца: смены, дежурства (из недельной ротации), отпуска (одобренные/на рассмотрении), праздничный режим (производственный календарь УЗ).
- **Элементы и действия:** [Запросить отпуск] — диапазон дат + тип (отпуск/больничный) + комментарий → диспетчеру; статус запроса; просмотр графика дежурств.
- **Состояния:** запрос отклонён с причиной; **ОФЛАЙН:** просмотр из кеша, запрос в очередь.
- **Переходы:** —.
- **Крайние случаи:** одобренный отпуск исключает мастера из авто-распределения (календарь доступности, ТЗ 17.3); MVP — базовый календарь, полноценные графики/отпуска — фаза 2 (ТЗ 15).
- **ТЗ:** 17.3, 3.3, 15.

### M-41. Реферальная программа «Приведи мастера»
- **Назначение:** бонус рекомендателю после 20 закрытых заявок приведённого (ТЗ 17.1, решение владельца — включена).
- **Точки входа:** профиль.
- **Данные:** персональная ссылка/код; список приведённых: имя, статус онбординга, прогресс «N из 20 закрытых заявок», статус бонуса (ожидает/начислен — проводкой на баланс).
- **Элементы и действия:** [Поделиться ссылкой] (share sheet); история начислений → кошелёк.
- **Состояния:** пусто; **ОФЛАЙН:** кеш, шаринг работает (ссылка локально известна).
- **ТЗ:** 17.1, 8.6.

### M-42. Синк-центр офлайна
- **Назначение:** видимость очереди несинхронизированного — доверие к офлайн-режиму (ТЗ 7.2).
- **Точки входа:** иконка синка на M-06 (бейдж с числом операций); из плашки «не синхронизировано» на карточках.
- **Данные:** очередь операций: тип (статус/фото/материал/подпись/наличные…), заявка, клиентское время фиксации, размер (для фото), статус (в очереди / отправляется / ошибка / конфликт); суммарный объём к отправке; время последнего успешного синка.
- **Элементы и действия:** [Синхронизировать сейчас]; повтор упавших; просмотр деталей конфликта (конфликт версий решается по серверному времени, ТЗ 7.2) — итог сервера + что было локально; фото передаются с приоритетом статусов (сначала лёгкие операции, потом медиа).
- **Состояния:** всё синхронизировано (зелёное); идёт отправка; ошибки с ретраями (экспоненциальный backoff); **ОФЛАЙН:** сам экран и есть офлайн-состояние — «ждём сеть», очередь видна.
- **Переходы:** тап по операции → соответствующая заявка.
- **Крайние случаи:** повторная отправка не создаёт дублей (UUID, идемпотентность — критерий приёмки MVP №5); записи офлайна несут двойные метки: время устройства + монотонные часы, при синке сервер добавляет своё время получения и флаг «зафиксировано офлайн» — обе метки хранятся для споров (ТЗ 7.2); метрика очереди синка мониторится на сервере (ТЗ 14).
- **ТЗ:** 7.2, 14, 15.

### 3.N. Экраны контура «Дом» (M7/M8, DEV-15)

#### M-43. Наряд-допуск
- **Назначение:** дать мастеру всё, что нужно для входа в общие зоны, и зафиксировать вскрытие и восстановление.
- **Точки входа:** блок «Допуск» в карточке M-11; карточка ленты M-06 при наличии наряда.
- **Данные:** тип зон и флаг критичности, согласованное окно, кто встречает (эскорт), телефон дежурного оператора, зона влияния (сколько помещений), требуется ли отключение ресурса.
- **Элементы и действия:** карточка наряда; **[Открыл зону]** — обязательное фото до вскрытия (камера-only) → статус `opened`; **[Закрыл зону]** — фото после восстановления + подтверждение «ресурс включён» → `closed`; кнопка звонка дежурному.
- **Состояния. ОФЛАЙН — да, полностью:** наряд приезжает в устройство **вместе с заявкой** при попадании в ленту; «Открыл»/«Закрыл» и фото уходят в очередь. **Правило старта офлайн (критично):** если на момент последней синхронизации наряд был `approved` или `scheduled` — открывать можно; если `requested` или `rescheduled` — экран блокирует с текстом «Допуск не согласован, нужна сеть».
- **Переходы:** → M-11 (после `opened` снимается блокировка «Приступить»), M-44, M-45.
- **Крайние случаи:** вскрытие вне согласованного окна — только санкцией диспетчера с причиной в аудит; **критичная зона** — плашка с требуемой квалификацией; **два мастера офлайн на одной зоне** — конфликт разрешается на сервере при синке по монотонным часам, проигравший получает 409 и уходит в разбор диспетчера (D-22); аварийная заявка — наряд создаётся системой сразу открытым, экран показывает «Аварийное вскрытие, УК уведомлена».
- **ТЗ:** 4.1, 4.3, 7.2 · DEV-10 §7, DEV-15 §4.

#### M-44. Пропуск в здание
- **Назначение:** пройти охрану без звонков и объяснений.
- **Данные:** `VisitPass` — QR, резервный числовой код, окно валидности, правила объекта.
- **Элементы и действия:** крупный QR; **резервный числовой код** под ним; блок правил: где вход, есть ли грузовой лифт, где парковка, часы шумных работ, нужен ли эскорт.
- **Состояния. ОФЛАЙН — да:** QR рендерится из закешированного подписанного токена.
- **Крайние случаи:** **у охраны нет сети** — сверка по резервному коду звонком дежурному; парная заявка — **пропуск у каждого участника отдельно**, помощник без своего пропуска не пройдёт; блокировка мастера аннулирует пропуск мгновенно, экран показывает «Пропуск отозван».
- **ТЗ:** 17.5, 17.15 · DEV-15 §6.

#### M-45. Отключение ресурса
- **Назначение:** юридически значимая фиксация факта отключения и включения.
- **Элементы и действия:** карточка отключения (ресурс, зона, плановое окно); **[Отключил]** и **[Включил]** — каждая с фото и таймштампом; индикатор «затронуто {N} помещений».
- **Состояния. ОФЛАЙН — да (очередь).** **Важно:** оповещение соседей о **факте** отключения уйдёт только после синхронизации; о **плановом окне** жителей предупреждает сервер заранее и независимо от мастера (DEV-15 §5).
- **Крайние случаи:** превышение планового окна — приложение напоминает и предлагает отправить новый прогноз; попытка закрыть заявку с невключённым ресурсом блокируется гейтом `complete`.
- **ТЗ:** 4.1, 7.2 · DEV-15 §5.

#### M-46. Моя выработка
- **Назначение:** замена кошелька для работы **в смене оператора**: там мастер на окладе, долей нет.
- **Элементы и действия:** часы в смене, закрытые заявки, SLA-показатели, выполнение регламентов. Денежные суммы отсутствуют.
- **Крайние случаи:** мастер, работающий и на оператора, и на платформу, видит **оба** экрана: M-34 «Кошелёк» — по своим свободным сменам, M-46 — по сменам оператора. Разделение по владельцу смены, а не по «типу мастера» (DEV-15 §7.8.3).
- **Фаза:** M8.

#### M-47. Плановое ТО на объекте
- **Назначение:** регламентное обслуживание оборудования здания по чек-листу.
- **Элементы и действия:** карточка оборудования (модель, серийный номер, история), чек-лист регламента, отметки и фото по пунктам, замечания одной кнопкой.
- **Состояния. ОФЛАЙН — да:** чек-лист кешируется целиком, отметки в очередь.
- **Крайние случаи:** ТО не закрывается без отметок всех обязательных пунктов; лицензируемое оборудование (газ, лифты) мастеру платформы не назначается вовсе (ТЗ 17.8).
- **Фаза:** M8.

#### M-48. Обход: маршрут и чек-лист зон
- **Назначение:** режим для инженера и руководителя службы оператора — обход объекта ногами с фиксацией замечаний.
- **Кто видит:** пользователь с ролью инженера или руководителя службы; вместо ленты заявок получает вкладку «Обход».
- **Элементы и действия:** маршрут по зонам из чек-листа A-26, прогресс, кнопка «Замечание» на каждой зоне, завершение обхода с итогом.
- **Состояния. ОФЛАЙН — да, полностью:** чек-лист и список открытых замечаний кешируются; всё уходит в очередь.
- **Фаза:** M8.

#### M-49. Замечание — быстрая фиксация
- **Назначение:** зафиксировать грязь, поломку, нарушение. **Требование к экрану жёсткое: не более трёх тапов и 15 секунд.**
- **Элементы и действия:** фото с камеры → плитка категории (справочник A-44) → отправлено. Зона подставляется по гео и текущему пункту чек-листа, серьёзность по умолчанию «содержание», комментарий надиктовывается голосом и необязателен. Всё остальное дозаполняется в кабинете U-16.
- **Крайние случаи:** дубликат по зоне за 14 дней — предложение присоединиться к существующему; серьёзность `emergency` — создаётся заявка автоматически, минуя решение.
- **Фаза:** M8.

#### M-50. Мои замечания
- **Элементы и действия:** свои замечания со статусами, просроченные, устранённые с фото. **ОФЛАЙН — да (кеш).**
- **Фаза:** M8.

### 6.2. Очередь синхронизации
- Каждая операция — запись очереди: `{client_uuid, order_id, тип, payload, device_time, monotonic_time, гео|null}`.
- **Идемпотентность:** client_uuid — ключ дедупликации на сервере; повторная отправка не создаёт дублей и не меняет состояние (ТЗ 7.2, критерий №5).
- **Двойные метки времени:** время устройства + монотонные часы при фиксации; при синке сервер присваивает время получения; запись помечается «зафиксировано офлайн»; обе метки хранятся — материал для споров (ТЗ 7.2).
- **Порядок:** операции заявки отправляются строго в порядке фиксации (конвейер зависим); лёгкие операции — раньше медиа; фото — фоновой загрузкой с ретраями (backoff), возобновление с места обрыва.
- **Фото без гео:** гео недоступно (подвал) → фото с флагом «без гео», конвейер не блокируется (ТЗ 7.2, 14).
- **Конфликты:** версия на сервере новее (заявка переназначена/отменена, смета изменена диспетчером) → разрешение по серверному времени; локальные операции по неактуальной заявке помечаются «конфликт», видны в M-42, спорные — флаг диспетчеру (например, офлайн-код приёмки, не совпавший при валидации).
- **Индикация:** бейдж числа несинхронизированных операций на M-06; значок «не синхронизировано» на карточке заявки (ТЗ 7.2); синк-центр M-42 — полный список и ручной ретрай.
- **Мониторинг:** серверная метрика глубины очередей синка мастеров с алертами (ТЗ 14).
- **Хранение:** очередь и медиа переживают перезапуск приложения и перезагрузку устройства; шифрование локального хранилища; очистка — только после подтверждения сервера.
