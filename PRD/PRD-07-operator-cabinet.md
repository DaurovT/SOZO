# PRD-07. Кабинет эксплуатирующей организации (оператора)

**Статус:** рабочая спецификация для сборки M7/M8. · **Источники истины:** ТЗ USTAPRO v2.25, DEV-15 «Контур „Дом“» v0.9 (решения владельца приняты), DEV-02 §4, DEV-10 §7, DEV-07 §2.1 и §8. · **Платформа:** React SPA `apps/operator-web`. · **Языки:** рус/узб.
**Правило чтения:** бизнес-логика и графы — в DEV-15 и DEV-10; здесь — экраны, права, состояния и поведение. При расхождении верить ТЗ, затем DEV-15.

**Терминология.** «Оператор» в этом документе — **эксплуатирующая организация** (`operator_org_id`): УК, ТСЖ, служба эксплуатации бизнес-центра, техотдел сети, FM-подрядчик. Это не «тенант платформы» из DEV-07 §6 — см. там разъяснение двух осей изоляции.

---

## 1. Кто пользуется и что покупает

| `tenant_kind` | Кто | Главная боль | Что продаёт кабинет |
|---|---|---|---|
| `hoa` | УК / ТСЖ жилого комплекса | Жалобы жителей, аварии, отчётность правлению | Портал жителя + доказательство работы |
| `bc` | Служба эксплуатации бизнес-центра | SLA перед арендаторами = штрафы по договору | Контроль SLA до срыва |
| `inhouse` | Техотдел сети (рестораны, аптеки, банки, отели) | Разбросанные объекты, невидимая загрузка своих | Управление собственной службой |
| `fm` | FM-подрядчик на чужих объектах | Доказательство выполнения заказчику | Отчётность и мультиклиентность |

Все четыре типа поддерживаются с первого релиза (решение владельца, DEV-15 §3.1).

## 2. Роли и права

| Роль | Что видит и может |
|---|---|
| **Согласующий доступ** | Только наряды-допуски своих объектов: согласовать / отклонить / предложить окно. Намеренно узкая роль — выдаётся консьержу или главному инженеру. **Может вообще не заходить в кабинет** и работать через W-06 по SMS |
| **Диспетчер оператора** | Заявки своих объектов, назначение своих мастеров, отключения, объявления, замечания |
| **Инженер / бригадир** | + техдолг, плановое ТО, паспорт здания, обходы |
| **Руководитель службы** | Всё по своим объектам + SLA-политики, настройки, отчёты |
| **Администратор оператора** | + пользователи, тариф, договор подключения, портфель объектов |

**Инвариант (DEV-07 §8):** ни один пользователь оператора не видит данных другого оператора и не видит заявок вне закреплённых за ним объектов — включая прямые запросы к API. Обеспечивается RLS, а не фильтрацией в интерфейсе. Роли выдаются **на объект или на весь портфель**.

**Мультиобъектность обязательна с первого релиза.** Переключатель объекта в шапке + сводный дашборд по портфелю. Оператор с пятьюдесятью объектами — норма, а не исключение (DEV-15 §10.9.5).

## 3. Общие правила интерфейса

1. **Тарифные ограничения видны, а не спрятаны.** Pro-функции на Free показываются заблокированными с объяснением ценности, а не отсутствуют. Ограничение проверяется **и на API** — не только в UI.
2. **Демо-режим до верификации.** Пока заявка на подключение объекта на модерации, кабинет работает на сид-данных демо-объекта (механика ТЗ 17.6). Демо-данные не порождают проводок и не видны жителям.
3. **Ни одна функция кабинета не является предусловием базового цикла заявки.** Объект в `degraded` продолжает обслуживаться — теряются гарантии, а не сервис.
4. Все суммы — тийины, отображение по правилам DEV-06. Все настраиваемые значения — из A-05.
5. Каждое значимое действие пишет в append-only аудит: кто, что, когда, IP.

## 5. Спецификации экранов

### U-02. Очередь нарядов-допусков

**Назначение.** Ядро бесплатного контура и точка, ради которой оператор вообще заходит в кабинет: согласовать доступ мастера в общие зоны объекта.

**Кто видит.** Согласующий, диспетчер, инженер, руководитель службы, администратор.

**Точки входа.** Стартовый экран для роли «согласующий»; push и SMS о новом наряде; виджет U-01; ссылка W-06 (для тех, кто в кабинет не заходит).

**Данные.** `AccessPermit` со связанной заявкой: тип зоны и флаг критичности, требуется ли отключение ресурса, зона влияния (сколько помещений затронуто), запрошенное окно, мастер (имя, фото, статус верификации, ссылка на L-07), SLA-таймер, признак аварийности.

**Элементы и действия.**
- Список с сортировкой по остатку SLA; просроченные вверху и красным; критичные зоны отдельным фильтром и меткой.
- Карточка наряда: **[Согласовать]** · **[Предложить другое окно]** · **[Отклонить]** (причина из справочника обязательна).
- **Таймер бесплатного отзыва:** «отзыв бесплатен ещё {чч:мм}» — после порога 2 ч холостой выезд выставляется оператору (DEV-15 §11.5). Показывается на согласованных нарядах.
- Плашка для критичных зон: «Авто-согласие не применяется — наряд ждёт вашего решения».
- Плашка для обычных зон при приближении SLA: «Через {чч:мм} наряд будет согласован автоматически» — честно, до того как это случится.
- Массовое согласование однотипных нарядов одного мастера на день — одним действием (частый случай планового обхода стояков).

**Состояния.** Пусто — «Нет нарядов на согласование»; загрузка; ошибка API с сохранением решения локально до повтора.

**Переходы.** → карточка заявки (read-only, только свои объекты) → U-10 журнал доступа → L-07 верификация мастера.

**Крайние случаи.**
- Наряд согласован автоматически по молчанию — остаётся в списке с меткой «согласовано автоматически {время}», отменить нельзя, можно отозвать (с порогом оплаты).
- Мастер заблокирован платформой после согласования — наряд `cancelled`, уведомление, пропуск аннулирован.
- Аварийное вскрытие без согласования (DEV-15 §4.5) — приходит как событие первого приоритета с фото и временем, кнопок согласования нет: работа уже идёт.
- Согласующий уволился — наряды перекидываются на резервного; отсутствие резервного не даёт объекту статус `active`.

**Ссылки.** DEV-15 §4, §9.3, §11.5 · DEV-10 §7. **Фаза:** M7.

### U-04. Право первой руки

**Назначение.** Дать собственной службе шанс взять частную заявку жителя раньше платформы. Экран, который делает предложение неугрожающим для отдела эксплуатации.

**Кто видит.** Диспетчер оператора, руководитель службы.

**Точки входа.** Push о новой заявке в окне первой руки; виджет U-01.

**Данные.** Заявка: категория, описание, фото жителя, помещение, предпочтительное окно, оценочная вилка; таймер окна (30 мин рабочее / 10 мин нерабочее, параметры U-13).

**Элементы и действия.** **[Взять своими]** — назначить мастера из своих (Pro) или зарезервировать под ручное назначение (Free). **[Отпустить]** — причина из справочника: нет компетенции / нет свободных / не наш профиль / вне часов. Таймер обратного отсчёта крупно.

**Состояния.** Пусто — «Новых заявок нет». Истёкший таймер — карточка уезжает в архив с меткой «ушла в общий пул».

**Крайние случаи.** Заявка по **общему имуществу** сюда не попадает — она всегда и только своей службе, без таймера и без перелива (DEV-15 §7.5, решение владельца). Категория из списка «всегда наружу» не показывается вовсе. Аварийная — оффер уходит своим и в пул платформы параллельно.

**Ссылки.** DEV-15 §7.5, §11.9 · PRD-05 §3. **Фаза:** M7.

### U-13. Настройки объекта

**Назначение.** Единственное место, где объект превращается из `verified` в `active`.

**Кто видит.** Руководитель службы, администратор оператора.

**Данные.** `Building`: часы работ и часы шумных работ, правила пропуска и парковки, наличие грузового лифта, правила вывоза мусора, `internal_buffer_min`, аварийный и диспетчерский телефоны, окна первой руки, категории «всегда наружу» и «только свои», согласующие и резерв, ставка сервисного сбора (read-only, из договора).

**Элементы и действия.** Форма по блокам с чек-листом готовности к `active`: назначен согласующий ✓, назначен резервный ✓, указан круглосуточный аварийный телефон ✓, заполнен реестр помещений ✓. Кнопка **[Активировать объект]** неактивна, пока чек-лист не полон, — с объяснением, чего не хватает. SLA-политики — блок Pro.

**Крайние случаи.** Снятие последнего согласующего при активном объекте — запрещено с объяснением. Изменение часов шумных работ не двигает уже согласованные наряды. Смена аварийного телефона требует подтверждения звонком.

**Ссылки.** DEV-15 §9.3, §11.4.8. **Фаза:** M7 (SLA-блок — M8).

### U-01. Дашборд объекта и портфеля

**Назначение.** Ответ на вопрос «что горит прямо сейчас» за пять секунд.

**Кто видит.** Все роли оператора, состав виджетов — по правам и тарифу.

**Данные.** Агрегаты по выбранному объекту или по всему портфелю.

**Элементы и действия.**
- **Free:** наряды на согласовании и просроченные; активные аварии; идущие и ближайшие отключения; заявки по общему имуществу с просрочкой; новые замечания; счётчик обращений «моего дома здесь нет» с L-10.
- **Pro:** SLA-светофор (жёлтый на 80% дедлайна, красный при нарушении), загрузка своих мастеров, просроченное ТО, техдолг суммой, доля перелива наружу, rework за 30 дней.
- Переключатель «объект / весь портфель»; в режиме портфеля — таблица объектов со светофором.

**Состояния.** Демо-режим — баннер «Данные демонстрационные, объект на проверке». `degraded` — красная плашка с причиной и сроком исправления.

**Ссылки.** DEV-15 §7.6, §9.3. **Фаза:** M7 (Free-виджеты), M8 (Pro).

### U-06. Реестр помещений и жителей

**Назначение.** Основа всего: без реестра помещений не работают ни зона влияния отключений, ни адресный матчинг, ни тарификация.

**Данные.** `Unit`, `UnitResident`.

**Элементы и действия.** Импорт из Excel по шаблону (механика A-04) с отчётом об ошибках и дублях; ручное добавление; привязка жителя по номеру телефона; роль собственник / арендатор / член семьи; способ верификации проживания (оператором / документом / краудсорсом). Стояки помещения — обязательное поле для домов с водоснабжением, иначе зона влияния отключения не считается.

**Крайние случаи.** Житель без приложения — заводится, получает SMS-приглашение. Помещение без жителей — норма (пустующее). Арендатор ограничен в правах по общему имуществу. Смена собственника — старая связка закрывается `valid_until`, история заявок остаётся у помещения, персональные данные — у жителя (DEV-15 §12 п.4).

**Фаза:** M7.

### U-03. Заявки по общему имуществу

**Назначение.** Рабочая очередь службы эксплуатации по её прямым обязанностям.

**Данные.** Заявки с `order_scope = common_area` по объектам оператора, включая порождённые из замечаний жителей (C-52).

**Элементы и действия.** Список со статусами и сроками, назначение своего мастера (Pro) или отметка о работе вне системы (Free), связь с замечанием-источником, счётчик просроченных.

**Крайние случаи — главное.** Такая заявка **никогда** не уходит в общий пул платформы: ни по SLA-просрочке, ни при деградации объекта, ни в аварии (решение владельца, DEV-15 §7.5). Если компетенции нет, оператор размещает заказ у платформы **явно**, как B2B-заказчик по договорному контуру ТЗ 5.1–5.4 — это осознанная закупка со сметой и утверждением, а не молчаливый перелив. В интерфейсе жителя при этом честно написано, кто отвечает за срок.

**Фаза:** M7.

### U-07. Отключения и объявления

**Назначение.** Заменить бумажное объявление на подъезде и сделать приложение жителя нужным самому оператору.

**Данные.** `ResourceShutdown`, `BuildingAnnouncement`.

**Элементы и действия.** Создание отключения: ресурс, зона (дом / подъезд / стояк / список помещений), окно, причина. **Предпросмотр охвата:** «затронуто 87 помещений, 143 жителя с приложением, 21 без» — до отправки, а не после. Календарь отключений с конфликтами. Объявления с выбором аудитории. Pro: SMS-канал, сегменты, шаблоны.

**Состояния.** Конфликт стояка — блокирующая ошибка с указанием пересекающегося отключения (инвариант DEV-02 §4.4 п.9).

**Крайние случаи.** Плановое отключение позже чем за 24 ч до начала — создаётся, но помечается «создано с нарушением срока» и падает в индикатор объекта. Аварийное — публикуется немедленно. Превышение планового окна — авто-уведомление жителям с новым прогнозом, а не тишина.

**Фаза:** M7 (push), M8 (SMS и сегменты).

### U-10. Журнал доступа и пропусков

**Назначение.** Кто, когда и в какую зону заходил. Для `bc` — самостоятельная ценность: доказательство перед арендатором и службой безопасности.

**Данные.** `VisitPass`, `AccessPermit` с отметками вскрытия и закрытия.

**Элементы и действия.** Хронология входов и выходов, фильтры по мастеру, зоне, дате; фото вскрытия и восстановления; выгрузка за период. Аннулированные пропуска — с причиной.

**Фаза:** M7.

### U-16. Замечания и обходы

**Назначение.** Собрать в одном месте всё, что «не заявка»: грязь во дворе, разбитый плафон, подтёк в подвале, машина на газоне. Источники — обход руководителя (M-48…M-50), заявка жителя (C-52), находка мастера на заявке, жалоба.

**Данные.** `BuildingObservation` + справочник категорий A-44.

**Элементы и действия.**
- Очередь с фильтрами по категории, серьёзности, зоне, источнику и возрасту.
- **Карта объекта** — открытые замечания точками по зонам: видно, где скапливается.
- Маршрутизация одним действием: задача сотруднику / дефект в техдолг / заявка на выезд / претензия подрядчику / только журнал.
- **Приёмка с фото:** замечание закрывается исключительно снимком устранения (инвариант DEV-02 §4.4 п.13) — перенос продуктового принципа №2 ТЗ на содержание объекта.
- Pro: регулярные обходы по чек-листам A-26, отчёт «обход выполнен: N зон, M замечаний, K устранено» с фотографиями.

**Крайние случаи.** Дубликаты от нескольких обходящих — предложение присоединиться к существующему замечанию по зоне за последние 14 дней (параметр). Замечание с `severity = emergency` создаёт заявку автоматически, минуя решение. Замечание жителя — житель видит статус и фото устранения; это тот эффект доверия к УК, который она сама себе организовать не может.

**Ссылки.** DEV-15 §7.7. **Фаза:** M7 (очередь и маршрутизация), M8 (регулярные обходы и отчёт).

### U-11. Финансы: нетто-расчёт

**Назначение.** Показать оператору, что он зарабатывает, а не только платит. Главный аргумент апгрейда на Pro.

**Данные.** `OperatorSettlement` за период.

**Элементы и действия.** **Одна нетто-сумма месяца** с детализацией по строкам: подписка + холостые выезды + претензии по ущербу − начисленный сервисный сбор. Отрицательный нетто — выплата оператору, положительный — счёт. История по месяцам, выгрузка. Детализация сбора по заявкам с суммами и процентом.

**Крайние случаи.** Сбор не начисляется на общее имущество и на заявки, выполненные собственной службой (DEV-15 §8.2) — в детализации это видно строкой «выполнено вашей службой, сбор не начисляется», чтобы не выглядело ошибкой. Сторно сбора при возврате клиенту — пропорционально, отдельной строкой. Неоплата подписки → деградация Pro→Free, **но приём заявок жителей не останавливается**: жители не сторона договора.

**Ссылки.** DEV-15 §8.2, §11.5. **Фаза:** M7.

---

### U-14. Пользователи и роли

**Назначение.** Раздать доступы своим людям без участия платформы.

**Элементы и действия.** Приглашение по номеру телефона → SMS со ссылкой → вход по OTP (существующая механика). Роль на конкретный объект или на весь портфель. Назначение согласующих и резервных, отметка дежурного. Отзыв доступа — немедленная инвалидация контекста.

**Крайние случаи.** Согласующему кабинет не обязателен — он работает по W-06; в списке он помечен «работает по SMS-ссылке». Снятие последнего согласующего активного объекта запрещено.

**Фаза:** M7.

---

### U-15. Подписка и тариф

**Элементы и действия.** Текущий тариф, число тарифицируемых помещений, витрина Pro с перечнем функций и их ценностью, счета и история платежей, кнопка запроса КП.

**Наполнение.** Две модели, между которыми оператор выбирает (ТЗ §19.3 п.2): **«Подписка»** — 3 000 000 сум за объект в месяц (параметр 138), плоская ставка независимо от числа помещений, свои мастера в системе, сервисный сбор не начисляется; **«Доступ»** — бесплатно, сервисный сбор 5% с частных заявок жителей, управление своими мастерами недоступно.

**Экран обязан показывать выбор честно:** при переходе на подписку — предупреждение «вы перестанете получать 5% с заявок жителей», с расчётом по фактическим данным прошлого месяца. Скрывать эту потерю нельзя: оператор обнаружит её в первом же расчёте и решит, что его обманули. В карточке подписки — перечень объектов на Pro и сумма; при портфеле показывается разбивка по объектам, потому что оператор может держать часть объектов на Free, а часть на Pro.

**Крайние случаи.** Тариф применяется **к объекту, а не к организации**: оператор с пятью объектами вправе перевести на Pro только два, и это нормальный сценарий, а не ошибка. Free без ограничений по числу объектов (решение владельца) — витрина Pro не давит счётчиками и не блокирует объекты. Изменение цены в A-05 не затрагивает действующие подписки до конца оплаченного периода.

**Фаза:** M7.

### U-05. Свои мастера (Pro)

**Назначение.** Управление собственной выездной службой — ядро подписки.

**Данные.** `MasterAffiliation`, `Shift`, ленты.

**Элементы и действия.** Реестр своих мастеров, заведение оператором (экзамен платформы — на его усмотрение, решение владельца), skill-теги, себестоимость нормо-часа, допуск к объектам. Смены с указанием, что это **смена данного оператора**. Ленты дня, назначение, загрузка.

**Крайние случаи — мультиаффилиация (DEV-15 §7.8).** Мастер может работать на несколько операторов и одновременно быть свободным мастером платформы. Поэтому:
- **Лента единая.** Оператор видит свои заявки полностью, чужое время — **обезличенными блоками «занят»**, без указания у кого и по какой заявке.
- **Смены разных работодателей не пересекаются** — попытка поставить смену на занятое время отклоняется 409 `ShiftOverlap` без раскрытия второго работодателя.
- Заявки оператора ставятся только в его смену; в чужой смене мастер для него недоступен, даже если аффилирован.
- Авария вне своей смены — оффер уходит с пометкой и требует отметки «отпускаю» от диспетчера текущей смены.
- Суммарная нагрузка по всем работодателям ограничена (по умолчанию 60 ч/нед) — превышение блокирует постановку смены.

**Качество без экзамена (DEV-15 §7.1.1).** Оценки и жалобы по мастеру оператора ведутся отдельной веткой и не попадают в общий рейтинг платформы. При N подтверждённых жалобах платформа приостанавливает доступ этого мастера **к частным заявкам жителей**; работы по общему имуществу не затрагиваются — это внутреннее дело оператора.

**Фаза:** M8.

---

### U-08. Паспорт здания и оборудование (Pro)

**Элементы и действия.** Зоны и стояки, `BuildingEquipment` (лифты, насосы, ИТП, вентиляция, пожарные системы) с моделью, серийным номером, датой ввода и регламентом ТО. История обслуживания по единице оборудования. Ключи от зон — выдача и возврат по существующей механике `EquipmentIssuance` (акты M-38).

**Крайние случаи.** Оборудование лицензируемых категорий (газ, лифты) заводится и обслуживается, но **наряды на него мастерам платформы не выдаются никогда** (ТЗ 17.8, DEV-15 §7.1.2) — работы выполняет служба оператора или лицензиат.

**Фаза:** M8.

---

### U-09. Техдолг объекта (Pro)

**Элементы и действия.** Реестр дефектов с серьёзностью, оценочной стоимостью, сроком и ответственным; решение «в план / отложен / отклонён» с причиной; свод суммой и по срочности; связь с замечанием-источником; экспорт в отчёт.

**Крайние случаи.** **Отклонённый дефект не удаляется** — остаётся в аудите с формулировкой отказа и датой. Это юридическая защита оператора перед правлением и надзором («мы предупреждали {дата}»), механика уже заложена в ТЗ §14. Аварийный дефект создаёт заявку автоматически, минуя решение.

**Фаза:** M8.

---

### U-12. Отчёты (Pro)

**Элементы и действия.** Готовые формы: **правлению** (заявки, сроки, техдолг, обходы, отключения), **собственнику здания** (SLA, стоимость эксплуатации на м², техдолг), **арендаторам** (SLA по их помещениям, история обращений). Экспорт PDF и таблицей, период произвольный, брендирование логотипом оператора.

**Крайние случаи.** Отчёты содержат **только операционные и обезличенные данные**; персональные данные жителей в выгрузки не попадают ни при каких настройках — это техническое ограничение, а не политика (DEV-15 §12 п.4).

**Фаза:** M8.

## 7. Критерии приёмки кабинета

1. Пользователь оператора А прямым запросом к API по id оператора Б получает пусто **на уровне БД**, при отключённом скоупинге в коде.
2. Согласующий обрабатывает наряд не более чем в два действия — из кабинета или по SMS-ссылке W-06 без установки приложения.
3. Наряд в критичную зону не согласуется автоматически ни при каких обстоятельствах.
4. Заявка по общему имуществу не уходит в пул мастеров платформы ни при каком сценарии, включая аварию и деградацию объекта.
5. Объект не переводится в `active` без согласующего, резервного и круглосуточного аварийного телефона.
6. Оператор с 50 объектами переключается между ними и видит сводный светофор портфеля.
7. Замечание не закрывается без фотографии устранения.
8. Активация Pro при незаполненной цене за помещение отклоняется.
9. Неоплата подписки понижает тариф, но не останавливает приём заявок жителей.
10. В выгрузках U-12 отсутствуют персональные данные жителей.
11. Смена, пересекающаяся со сменой другого работодателя того же мастера, отклоняется без раскрытия работодателя.
12. Free-оператор не ограничен по числу объектов.
