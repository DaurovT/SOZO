# SOZO (USTAPRO) — платформа технического сервиса

Ташкент. Клиент вызывает мастера, мастер выполняет работу, диспетчер и админ
управляют потоком. Три контура: **B2C** (частные клиенты), **B2B** (сети —
аптеки, офисы, магазины) с лимитами, утверждениями сметы и актами осмотра, и
**«Дом»** (ТЗ §19) — управляющие компании и службы эксплуатации как клиенты
подписки, наряды-допуски в общие зоны, портал жителя.

> **Новой сессии Claude или новому разработчику:** начните с
> **[docs/HANDOVER.md](docs/HANDOVER.md)** — там состояние, ловушки и
> договорённости. Этот файл про то, как запустить и выложить.

## Быстрый старт

Нужны **Node 22 LTS** и **Flutter 3.44+**. Базы данных не нужны.

```bash
cd sozo
npm install && npm run build     # contracts → kernel → api
npm run api                      # http://localhost:3000/v1
```

Веб-панели:

```bash
npm run admin                                  # http://localhost:5173
cd apps/dispatcher-web && npm run dev          # http://localhost:5174
npm run operator                               # http://localhost:5176/operator/
```

Мобильные приложения — адрес сервера задаётся при сборке:

```bash
cd apps/client-app
flutter run --dart-define=SOZO_API=http://<IP-компьютера>:3000
```

На телефоне `localhost` не работает: нужен адрес компьютера в той же сети.
Если адрес сменился, а приложение уже установлено — менять его можно прямо в нём:
на экране ошибки есть **«Изменить адрес сервера»**.

### Вход

Код подтверждения в dev-режиме — **`00000`** для любого номера.
Демо-аккаунты перечислены в [docs/HANDOVER.md](docs/HANDOVER.md#4-демо-аккаунты);
главный — `+998900000000` (админ + все роли B2B + заявки B2C).

Предсказуемый код — свойство **журнального** отправителя, а не заглушка в
коде входа: сообщение никуда не уходит, и скрывать нечего. Как только
`SMS_PROVIDER=eskiz`, код становится случайным пятизначным, живёт три минуты,
сгорает после пяти неверных попыток, а между отправками на один номер минута
паузы и не больше пяти кодов в час.

```bash
sudo deploy/enable-sms.sh robot@sozo.uz 'пароль из кабинета Eskiz'
```

Скрипт вписывает ключи, перезапускает сервис, **проверяет отправку живой
SMS** и только после подтверждения выключает вход по dev-коду. Порядок именно
такой: выключить dev-код раньше проверки значит закрыть вход всем.

## Данные

Состояние целиком лежит в **одном файле**: `sozo/apps/api/data/state.json`
(~5 МБ). Путь переопределяется переменной `STATE_FILE`.

**Этого файла нет в репозитории** — каталог `data/` закрыт в `sozo/.gitignore`
намеренно, как dev-хранилище. Из этого следует:

- **Репозиторий не является бэкапом данных.** Единственная копия живёт на той
  машине, где сервер работал. Бэкап — отдельная задача: копия этого файла по cron.
- На свежем клоне поднимутся только константы из конструкторов сервисов: админ,
  бухгалтер, диспетчер, две демо-организации, релиз прайса №1. Заявок,
  адресов и истории не будет.
- Полная демо-картина — через `POST /v1/app/demo/seed` под диспетчером
  (`+998900000002`, код `00000`). Повторный вызов копий не плодит.

Postgres, Redis и MinIO в `sozo/infra/docker-compose.yml` — заготовка на
будущее, **в рантайме не используются**.

## Проверки

```bash
# Ядро — юнит-тесты (сервер не нужен)
cd sozo && npm test              # 57 тестов: деньги, графы заявок и нарядов-допусков

# База — миграции и инварианты на PGlite (WASM), сервер не нужен
cd sozo && npm run db:check      # 13 проверок: RLS, CHECK-и

# База — на настоящем сервере в Docker. Нужно ради инварианта п.9:
# в PGlite нет btree_gist, и EXCLUDE на стояки там просто пропускается
cd sozo && npm run db:up         # поднять PostgreSQL 16
npm run db:generate              # клиент Prisma (после правки schema.prisma)
npm run db:migrate:pg            # три миграции по порядку
npm run db:check:pg              # 6 проверок «один стояк — одно отключение»
npm run db:check:rls             # 10 проверок: контекст RLS и настоящая
                                 # изоляция — чужие строки не видны и не
                                 # записываются. Идёт ролью sozo_app: под
                                 # владельцем-суперпользователем RLS не
                                 # действует вовсе (см. DEV-19)

# API — сквозные прогоны. Сервер поднимать не нужно: раннер стартует его сам
cd sozo/apps/api
npm run test:e2e                 # все девять наборов, 618 проверок
                                 # если PostgreSQL поднят, раннер заводит
                                 # одноразовую базу на прогон и сносит её после
npm run test:e2e -- home-contour # один набор
E2E_KEEP_DB=1 npm run test:e2e   # оставить базу прогона и заглянуть в неё:
                                 # зелёный прогон не доказывает, что записи
                                 # действительно легли в PostgreSQL

# Flutter
cd sozo/apps/client-app && flutter analyze && flutter test    # 97 тестов
cd sozo/apps/master-app && flutter analyze && flutter test    # 75 тестов
```

**Про e2e и данные.** Раньше прогоны опирались на dev-состояние
(`sozo/apps/api/data/state.json`), которого нет в репозитории — оно закрыто в
`.gitignore` намеренно. Это давало два тихих провала: `b2b-access-e2e` на свежем
клоне выдавал 9 из 24, а любой набор, запущенный вторым разом подряд, валился
на накопленных данных (подписка начислена дважды, наряды остались с прошлого
раза). Оба закрыты: `test/run-e2e.mjs` поднимает API на одноразовом состоянии во
временной папке, а `b2b-access-e2e` заводит свои фикстуры сам. Прогон повторяем.

Запускать наборы вручную против рабочего сервера по-прежнему можно
(`node test/home-contour-e2e.mjs [url]`), но состояние он засорит.

Тесты клиента проверяют не только «экран построился», но и что он **виден и
помещается** на 390×844 — переполнение по ширине иначе всплывает только на
телефоне.

## Языки

Десять: русский (основа), узбекский, английский, турецкий, таджикский,
арабский, французский, немецкий, китайский, корейский. Переключаются
мгновенно, без перезапуска. Арабский разворачивает раскладку справа налево.

Половина текста приходит с сервера — названия категорий, статусы, уведомления.
Поэтому приложение обязано слать заголовок `Accept-Language`, а сервер держит
свои словари в `apps/api/src/common/locale-*.ts`. Ключ там — сама русская
строка.

**Приложение «Клиент» несёт в сборке только ru/uz/en.** Это языки Ташкента, и
первый экран обязан открыться на своём языке без сети. Остальные семь весят
вместе вдвое больше и нужны единицам, поэтому лежат на сервере и приезжают по
`GET /v1/public/app-locale/:code` при выборе языка — один раз, дальше из кеша
устройства. Подробности — в [apps/client-app/README.md](sozo/apps/client-app/README.md#языки).

**Лендинг держит язык в адресе,** а не в localStorage: иначе не работает
hreflang и пересланная ссылка открывается не на том языке. Русский остался в
корне — на `/order` и `/b/:code` ведут наклейки в подъездах и QR-коды
мастеров. Подробности — в [apps/landing/README.md](sozo/apps/landing/README.md#языки).

Две сверки, и нужны обе: `node tools/check-dicts.mjs` отвечает, все ли ключи
на месте, `node tools/check-translations.mjs` — что в них написано. Вторая
появилась не зря: первый проход перевода назвал «точку» (объект бизнеса)
«баллом» в восьми языках, а «сум» — арифметической суммой в шести.

Подробности и правило «что нельзя класть в общий словарь» —
в [docs/HANDOVER.md](docs/HANDOVER.md#7-языки).

## Выкладка на сервер

### Перенос на VPS: что взять с собой

**`git clone` переносит код, но не данные.** Состояние живёт в одном файле
`sozo/apps/api/data/state.json`, а каталог `data/` закрыт в `.gitignore`
намеренно. На свежем клоне поднимутся только константы из конструкторов
сервисов: админ, бухгалтер, диспетчер, две демо-организации, релиз прайса №1 —
ни заявок, ни адресов, ни истории.

Поэтому файл копируется отдельно, руками, до первого запуска на сервере:

```bash
# с машины разработки
scp sozo/apps/api/data/state.json user@vps:/var/lib/sozo/state.json
```

и сервер запускается с `STATE_FILE=/var/lib/sozo/state.json`. Путь вне каталога
приложения выбран сознательно: `git pull` и пересборка тогда не могут задеть
данные.

Если данные не нужны — не копируйте, но знайте, что демо-картина собирается
`POST /v1/app/demo/seed` под диспетчером (`+998900000002`, код `00000`), а
заявки и история не восстановятся ниоткуда.

**Что ещё не переносится через git:** `node_modules` (ставится `npm ci`),
сборки `dist/` и `build/`, и сами Flutter-артефакты — их пересобирают на месте
с боевым адресом (см. пункт 9 ниже).

**Docker на VPS есть — и это снимает главный блокер проекта.** Заготовка
`sozo/infra/docker-compose.yml` (Postgres, Redis, MinIO) до сих пор не
использовалась в рантайме только потому, что на машине разработки Docker не
поднят. Схема на 37 моделей, миграции RLS и инвариантов написаны и проверены
на PGlite — переход на настоящий Postgres перестаёт быть теоретическим.

### Порты

Открыть в файрволе ровно три:

| Порт | Откуда | Зачем |
|---|---|---|
| 443/TCP | отовсюду | Единственный публичный порт приложения |
| 80/TCP | отовсюду | Выпуск сертификата Let's Encrypt и редирект на HTTPS |
| 22/TCP | **только свой IP** | SSH |

**Не открывать:** `3000` (API стоит за nginx на `127.0.0.1`), `5432`, `6379`,
`9000`, `9001` (не используются, а появятся — только на localhost), `5173`–`5176`
(это dev-серверы Vite: админка, диспетчерская, лендинг, кабинет оператора —
в проде их нет).

Вебхуки Payme и Click придут на 443 — отдельного порта не нужно, но нужен
публичный домен с валидным сертификатом.

### Порядок

1. DNS заранее: `api.`, `admin.`, `dispatch.`, корень — все на один IP.
   Записи должны разойтись до выпуска сертификата.
2. Ubuntu 24.04 LTS, минимум 2 vCPU / 4 ГБ. На 1 ГБ сборка падает по памяти
   (`tsc` + `vite build`); либо больше памяти, либо собирать локально и
   отгружать готовый `dist`.
3. **Статический IP.** С динамическим адрес слетает при перезапуске машины, и
   мобильные сборки перестают достукиваться.
4. Node 22 LTS, nginx, certbot. Swap 2 ГБ, `ufw`, `unattended-upgrades`.
5. `npm ci && npm run build` в `sozo/`.
6. systemd-юнит для API: `PORT=3000`, `STATE_FILE=/var/lib/sozo/state.json`,
   `NODE_ENV=production`, `JWT_SECRET=<длинная случайная строка>`,
   `Restart=always`.
7. nginx: `api.домен` → `127.0.0.1:3000`; `admin.` и `dispatch.` — статика из
   `dist`. Затем certbot на все поддомены.
8. **Cron-бэкап `state.json`.**
9. Пересобрать приложения на боевой адрес:
   `--dart-define=SOZO_API=https://api.домен`,
   веб — `VITE_API_URL=https://api.домен/v1`.

### Блокеры публичного адреса — закрыты

Платформа выложена на `sozo.uz`, три блокера сняты до открытия адреса:

1. **`JWT_SECRET`** — при `NODE_ENV=production` сервер отказывается стартовать
   с дефолтным ключом. Боевой ключ лежит в `/etc/sozo/sozo.env`, не в репозитории.
2. **CORS** — белый список из `CORS_ORIGINS` вместо `origin: true`. В проде без
   списка кросс-доменные запросы запрещены совсем.
3. **Код `00000`** — за флагом `ALLOW_DEV_OTP`, при `NODE_ENV=production`
   работает только с ним.

**Третий закрыт не до конца, и это осознанно.** Флаг сейчас включён: SMS-провайдера
нет, и без dev-кода войти будет нечем. То есть на публичном адресе по-прежнему
можно войти под любым известным номером, включая `+998900000000` с ролью `admin`.
Снимать флаг — вместе с подключением Eskiz или Playmobile, не раньше. Пока
демо открыто, это принятый риск, а не забытая дыра: при старте в проде сервер
пишет об этом предупреждение в журнал.

### Про размещение

У Azure нет региона в Узбекистане; ближайший по задержке — UAE North (Дубай),
~40–60 мс до Ташкента, европейские дают 80–120 мс. При этом в `DEV-04` записано
«прод — два сервера в ЦОД РУз», а в Узбекистане действует требование о
локализации персональных данных граждан. Для демо и пилота вопросов не возникнет,
но перед боевыми данными это стоит сверить с юристом — переезжать с живой базой
дороже.

## Контур «Дом»: что сделано и что осталось

Управляющие компании и службы эксплуатации как клиенты подписки. Концепция —
**ТЗ §19**, детальная спецификация — **DEV-15**, экраны кабинета — **PRD-07**,
граф наряда-допуска — **DEV-10 §7**, трекер переделки — **DEV-16**.

### Две модели монетизации (не путать)

| | **Подписка** — БЦ, свои техотделы, FM | **Доступ** — ЖК с УК |
|---|---|---|
| Платит | 3 000 000 сум за объект в месяц | ничего |
| Свои мастера в системе | да | нет |
| Заявка мастеру платформы | достаётся платформе целиком | платформа делит с мастером, **5% уходит УК** |
| Сервисный сбор оператору | нет | 5% с частных заявок жителей |

Модели взаимоисключающи: подписчик сбора не получает. Правило живёт в одной
точке — `BuildingsService.effectiveServiceFeeBps()`.

### Сделано

**Спецификации.** ТЗ доведено до v2.26 (раздел 19), новые DEV-15…DEV-18 и PRD-07,
обновлены все существующие PRD и DEV: экраны, параметры 124–139, таймеры 55–64.

**Бэкенд — полностью.** Пять модулей (`buildings`, `access`, `subscriptions`,
`sla`, `operator-api`, ~2 900 строк) плюс интеграции в `orders` и `billing`:

- наряд-допуск с графом DEV-10 §7 и гейтами: заявку нельзя начать без открытого
  наряда, закрыть — с невключённым ресурсом;
- запрет лицензируемых зон мастерам платформы (ТЗ 17.8) и авто-согласие
  молчанием с абсолютным исключением для критичных зон;
- отключения ресурсов с зоной влияния по стоякам и запретом двух бригад на одном;
- замечания и обходы с дедупликацией и закрытием только по фото устранения;
- право первой руки, сервисный сбор, нетто-расчёт с оператором;
- развилка жителя: «в моей квартире» / «в доме» и выбор исполнителя.

**База.** Схема (37 моделей), миграции RLS и инвариантов. Проверяются
командой `npm run db:check` на настоящем PostgreSQL в WASM — сервер не нужен.

**Тесты.** 57 юнит-тестов ядра, **392 e2e** в шести наборах, 13 проверок БД,
**97 + 75** тестов мобильных. Прогон повторяем: раннер поднимает API на
одноразовом состоянии.

Три проверки стерегут ошибки, которые не видит ни анализатор, ни дымовой
прогон, потому что экран при них строится и падает только на действии:

- **ключи словаря** — незнакомый ключ `t()` возвращает как есть, и на экране
  появляется `walk.zavershitObhod` вместо текста, а прогон зелёный: кириллицы
  в такой строке нет;
- **иконки справочника A-44** обязаны существовать в `assets/icons` — иначе
  плитка быстрой фиксации пустая ровно там, где счёт идёт на секунды;
- **именованные маршруты** запрещены, пока в `MaterialApp` нет `routes` или
  `onGenerateRoute`: `pushNamed` на несуществующий маршрут роняет приложение.

**Кабинет оператора** собран по порядку DEV-15 §14: дашборд, наряды, первая рука, настройки объекта, помещения и жители, отключения, замечания и обходы, журнал доступа, финансы. Заглушек не осталось; D-21 в
диспетчерской; макеты восьми экранов в `design-home/`.

**A-39 — модерация подключений.** Заявка на объект не даёт прав: она встаёт
в очередь, и выше `claimed` объект поднимается только решением человека. Два
заявителя на один дом **замораживают друг друга** — платформа не арбитр в споре
хозяйствующих субъектов. Главный сигнал верификации работает на данных, которые
старше заявки: контакт ТСЖ/УК из паспортов точек A-09, внесённый мастерами при
первых осмотрах, — подделать его задним числом нельзя.

**Приложение мастера: M-43…M-45.** Наряд-допуск, пропуск с QR и резервным кодом,
отметки отключения ресурса. Офлайн-контракт соблюдён: наряд приезжает в устройство
вместе с заявкой, действия уходят в очередь, а гейт старта решается по кешу —
если наряд не согласован, экран называет причину словами, а не гасит кнопку молча.

**W-06 — согласование по SMS-ссылке.** Страница `/p/{код}` отдаётся сервером,
без JS и без регистрации: консьерж открывает ссылку из SMS и решает в один тап.
Короткие отзываемые коды вместо JWT — SMS кириллицей вмещает 70 символов.
Это снимает главный блокер Free-тарифа: требовать освоения кабинета ради двух
нажатий в день бессмысленно, а на согласованиях этого человека держится весь
контур доступа.

**Админка — A-39…A-43.** Очередь модерации с сигналами сверки и баннером
конкурирующей заявки, реестр операторов с долей просрочки за 30 дней, справочник
зон с разделением критичных и лицензируемых, биллинг подписок с разбором
взаимозачёта — на экране видно, какая из двух моделей применена к объекту.

**Лендинг — L-09, L-10.** Страница для эксплуатирующих организаций: четыре
сегмента, калькулятор **дохода** (единственный в пакете — остальные считают
расход) и форма подключения. Публичная карточка дома по QR с наклейки в
подъезде: первым экраном кнопка звонка, аварийный телефон, ближайшие отключения,
а для неподключённого дома — сбор спроса. Неподключённый и несуществующий объект
отвечают одинаково: иначе перебором кодов составляется реестр наших домов.

**A-44 — категории замечаний.** Категория перестала быть свободной строкой:
серьёзность и предлагаемый маршрут подставляются из справочника, указанные на
месте важнее умолчаний. Аварийная категория создаёт заявку сама — всегда как
общее имущество, то есть только службе оператора.

**Справочник зон сведён к одному источнику.** Знание о зонах жило в четырёх
местах, и подписи уже разъехались: в SMS консьерж читал «вентиляционная
камера», инженер в кабинете видел «камера дымоудаления». Полноту покрытия
стережёт компилятор.

**Мастер: M-48…M-50.** Режим «Обход» — маршрут с чек-листом, фиксация
замечания в три тапа, «Мои замечания». Офлайн-первый целиком: дедупликация
работает в подвале, потому что открытые замечания приезжают вместе с
маршрутом, а не запрашиваются в момент съёмки.

**Мастер: M-14 «наряд есть, не пускают».** Единственная причина отказа в
доступе, которая не ставит паузу. Пауза означает «ждём, пока договорятся», но
договариваться поздно: согласование получено, окно допуска идёт, а второй раз
согласовывать — ещё сутки. Вместо паузы эскалация дежурному объекта с
таймером, заявка остаётся за мастером.

**Справочники сведены к одному источнику.** Подписи зон жили в пяти местах,
подписи ресурсов — в четырёх, и они уже разъехались: мастер видел
«Вентиляционная камера», а консьерж в SMS по тому же наряду — «Камера
дымоудаления»; жителю приходило «Отопление», мастеру в наряде — «отопление».
Полноту покрытия зон стережёт компилятор: уберите зону из справочника, и
сборка упадёт с её именем. Браузерные приложения справочники не импортируют,
а получают по сети — пакет контрактов собирается в CommonJS под API, а Vite
не трансформирует CJS вне `node_modules`.

**Прогоны e2e больше не зависят от машины разработчика.** Раньше второй запуск
подряд валился на накопленных данных (подписка начислена дважды, наряды
остались с прошлого раза), а `b2b-access` на свежем клоне давал 9 из 24.
Теперь `npm run test:e2e` поднимает API на одноразовом состоянии во временной
папке, а фикстуры набор заводит сам.

### Переезд на PostgreSQL: где мы

**Каркас готов.** Prisma 6 подключена, `PrismaService.withContext` открывает
транзакцию и ставит контекст RLS, e2e-раннер поднимает одноразовую базу на
прогон и сносит после. Приложение работает и **без** `DATABASE_URL`: пока
модули на файле, база необязательна, и шаг миграции не обрушит работающий
сервер. Проверки: `npm run db:check:rls`, `npm run db:check:pg`.

**Перенесены все тридцать модулей.** Первые одиннадцать потребовали каждый
своей формы — их разбор ниже; оставшиеся девятнадцать легли на общее зеркало
`PgMirror`, потому что к тому моменту стало видно, чем эти формы различаются
(DEV-19 §6):

| Модуль | Форма | Почему так |
|---|---|---|
| `audit` | репозиторий с двумя реализациями | append-only; писателей 159, читателей мало |
| `parameters` | кеш с записью насквозь | читаются синхронно из глубины расчётов |
| `identity` | репозиторий + отображение справочников | перечни ролей в базе и коде не совпадают |
| `pricing` | набор в памяти, запись насквозь | активный релиз неизменяем по инварианту схемы |
| `crm` | набор в памяти, запись насквозь | оправдано единственным писателем, не неизменяемостью |
| `masters` | то же | карточку читают синхронно из лент и распределения |
| `buildings` | то же, но запись без задержки | на объект ссылается заявка внешним ключом |
| `orders` | рабочий набор + запись насквозь | заявку читают и меняют из шести модулей синхронно |
| `access` | то же, запись без задержки | на наряд ссылается запрос доступа внешним ключом |
| `billing` | **только дописывание** | журнал проводок append-only: правка задним числом запрещена (ТЗ 8.1) |
| `scheduling` | полная перезапись трёх коллекций | брони снимают и смены убирают — записи исчезают, а не только появляются |

**Ограничение обеих кеширующих форм:** со вторым экземпляром приложения кеши
`pricing` и `crm` обязаны уйти — правки одного процесса не увидит другой.
Пока прод один процесс (systemd, монолит DEV-07), это верно; при
горизонтальном масштабировании переписывать придётся до, а не после.

#### Два вывода, которые определяют оставшийся объём

**1. Схема расходится с кодом в каждом модуле.** Её писали по DEV-02 раньше,
чем сервисы обрели окончательный вид. Каждый перенос начинается с миграции,
а не с кода — закладывать в оценку надо это, а не объём портируемого кода.

Чтобы не удивляться этому по одному модулю, расхождения считаются командой:

```bash
cd sozo && npm run schema:drift
```

Отчёт сравнивает поля записей в коде с колонками схемы, с поправкой на
известные переименования. Расхождение закрыто целиком: **ноль полей** —
миграции m8…m22. Последними закрылись наряд-допуск и пропуска (m21), а для
запроса доступа в чужое помещение и памяти офлайн-синка таблиц не было вовсе
(m22) — обе сущности появились позже схемы.

У заявки расхождение закрыто миграциями m12…m14: было 30 полей из 58, стало 0.

**Как поделено у заявки.** Решение принято по правилу самого DEV-02: деньги,
время, ключи и всё, по чему ищут или что ограничивают — колонки; структурные
снимки (приёмка, детали доступа, платёж, выбранное окно) — jsonb. На jsonb не
наложить CHECK и не построить внятный индекс, поэтому граница проходит именно
здесь. Заодно два правила переехали из кода в базу: деньги не бывают
отрицательными, запчасть без чека не принимается.

**2. Причина 75 падений была в коде, и оператор оказался не тем, чем его
считали.** При включении `PrismaOrderRepository` падал контур «Дом», и виной
был `operator_org_id`: в схеме внешний ключ на `organization` типа uuid, а код
передаёт короткий код — `uk1`, `bc1`. Запись сваливалась на разборе uuid.

Первым делом чинился код, а не схема: оператор по DEV-15 **является
организацией** с ролью `operator`, а `uk1` выглядел упрощением из тестов.
Теперь контур «Дом» заводит оператора настоящим контрагентом CRM
(`crm.ensureOperator`, миграция m17 добавила организации бизнес-код,
уникальный в пределах арендатора) — иначе оператору нельзя ни выставить счёт,
ни посчитать нетто-расчёт.

Но код при этом остался кодом. Он стоит в адресах кабинета
(`/operator/uk1/finance`), в карточке объекта и в собранных приложениях —
это часть интерфейса, а не внутренний ключ. Поэтому m18 меняет тип колонок на
`text` и вместе с ними функцию контекста RLS: политики сравнивают операторов,
и типы по обе стороны сравнения обязаны совпадать. Пятнадцать политик
снимаются и возвращаются тем же кодом, что в m7 — PostgreSQL не даёт менять
тип колонки, от которой зависит политика. Целостность держит уникальный
индекс `(tenant_id, code)`, а не внешний ключ.

Первая попытка сделать это наспех сломала все пятнадцать политик; база была
пересоздана из миграций и проверена — `db:check:rls` и `db:check:pg` зелёные.

**3. Заявка переехала: 489 проверок из 489 зелёные на PostgreSQL.**
`PrismaOrderRepository` включён в `orders.module.ts` и выбирается, когда задан
`DATABASE_URL`. Путь от 75 падений до нуля:

| Что нашлось | Чем закрыто |
|---|---|
| оператор не был контрагентом CRM | `ensureOperator` + m17 (код организации) |
| `operator_org_id` — uuid против кода | m18 (тип `text`, функция RLS, 15 политик) |
| ИНН пустой у всех операторов, а он уникален | m19 — частичный уникальный индекс `WHERE inn <> ''` |
| в перечне `OrderType` не было аварийной | m20 — заявка по аварии не записывалась вовсе |
| ответ обгонял создание заявки по замечанию | `EventBus.publishAndWait` |

Последнее — не про хранилище, а про то, что оно вскрыло. Аварийное замечание
становится заявкой в подписчике шины, и ответ на фиксацию замечания его не
ждал. На файле подписчик успевал в том же тике, и связка всегда была на
месте; с PostgreSQL каждый его шаг ходит в базу, и клиент получал замечание
ещё не связанным. Публикация события теперь ожидается — но по-прежнему
**после** сохранения самого замечания, поэтому сбой маршрутизации не может
его потерять.

Проверено не только тестами: заявка, созданная одним процессом, читается
вторым процессом с **пустым** каталогом состояния — то есть из базы, а не из
`state.json`.

Попутно выяснилось, почему объекты пишутся без задержки, в отличие от
остальных модулей: отложенная на полсекунды запись создавала гонку — заявка,
созданная сразу после объекта, упиралась во внешний ключ на строку, которой
в базе ещё нет.

**4. Зелёные тесты не доказывают, что в базу что-то попало.** Репозитории
пишут насквозь и ловят ошибку записи, чтобы не ронять запрос: снимок в памяти
уже сделан, и потерять ответ клиенту хуже. Плата — прогон остаётся зелёным,
даже если в базу не попало ничего: всё читается из памяти того же процесса.

Ровно это и случилось с нарядами-допусками: 244 проверки прошли, а строк в
базе было ноль. Причина — выдуманные идентификаторы заявок в тестах
(`o-1`, `p-c56`): графу наряда всё равно, чей идентификатор в ссылке, а базе
нет — наряд ссылается на заявку внешним ключом. Тесты исправлены на настоящие
заявки, а прогон теперь **падает**, если в логе сервера была неудачная
запись, даже когда все проверки прошли.

Отсюда правило: каждый перенос заканчивается не тестами, а артефактом —
строками в базе и вторым процессом с **пустым** каталогом состояния, который
их читает.

**5. Ядро нельзя переносить поштучно.** `pricing.active()` зовут синхронно из
шести мест, у `crm` 61 внешний вызов — и все из глубины обработки запроса.
Сделать их асинхронными значит одновременно тронуть заявки, планировщик и
клиентские контроллеры. Кешировать, как параметры, нельзя: устаревшая цена
или лимит в заявке хуже медленного запроса.

Поэтому `pricing`, `crm`, `orders`, `scheduling` и `billing` переносятся
**одним блоком**, и это не осторожность, а единственный возможный порядок.
Три уже перенесённых модуля — ровно те, которые можно было двигать по
одному: аудит пишется и почти не читается, параметры кешируемы по природе,
identity зовут только из контроллеров.

#### Что осталось

Порядок первых переносов задавали внешние ключи заявки: `buildings` и
`masters` обязаны были попасть в базу раньше, иначе создание заявки падало на
`order_building_id_fkey`. Этот блок закрыт целиком — одиннадцать модулей,
двадцать четыре миграции, расхождение схемы с кодом ноль.

Осталось девятнадцать разделов состояния, и это не «остаток портирования», а
работа другого рода: **своих таблиц у них нет вовсе**. Качество, промо,
лояльность, резервный фонд, склад, реестры, лиды, аналитика, офферы,
онбординг, рейтинг и ресурсы мастера, веб-карточка, поле (акты и дефекты),
планировщик уведомлений. Их перенос начинается с проектирования двух десятков
сущностей — это работа уровня DEV-02, а не портирование. Исключения, где
модели есть и перенос будет обычным: `sla` (`SlaPolicy`) и `subscriptions`
(`OperatorSubscription`, `SubscriptionAccount`).

**Прод пока на файле — но переключение готово.** `DATABASE_URL` в
`/etc/sozo/sozo.env` не задан. Переключение делается одним скриптом
`deploy/switch-to-postgres.sh`, и порядок в нём не украшение: сервис
останавливается **до** снятия снимка, иначе он допишет файл посреди чтения;
приёмка идёт **до** переключения, а не после, чтобы расхождение было видно,
пока откат стоит одну строку в конфиге.

Репетиция на копии прода нашла три вещи, которых не было видно из кода:

1. **Приложение на пустой базе засевает демо.** Мастера, организации и
   стартовый прайс пишутся в базу при первом старте — на проде они смешались
   бы с настоящими контрагентами, и отличить их потом можно было бы только
   руками. Посев выключается `SOZO_NO_SEED=1`, и инструмент переноса ставит
   эту переменную сам, а не полагается на память запускающего.
2. **Хранилище состояния переписывает снимок.** Первый же прогон инструмента
   уничтожил копию: модули, работающие на базе, в state.json больше не
   пишутся, и файл ужался с пяти мегабайт до двухсот килобайт. Инструмент
   теперь работает на временной копии, а исходный снимок не трогает.
3. **Файл разрешал то, чего не разрешает схема.** На проде оказались семь
   тестовых организаций с одним ИНН — в базе он уникален, это налоговый
   номер. Инструмент называет такие конфликты **все сразу и до первой
   записи**, а не падает на второй строке, оставив половину данных внутри.

Перенос отрепетирован полностью: 199 заявок из 211 (двенадцать ссылались на
пропущенные тестовые точки), 11 801 запись аудита, 29 учётных записей с
ролями, 66 проводок, 28 смен. Приёмка `import-verify` поднимает два сервера
на одних данных — на файле и на базе — и сверяет ответы: заявки поимённо,
статусы, суммы, остатки по счётам плана, роли, параметры, прайс.

#### Изоляция арендаторов работала только на бумаге

Проектирование оставшихся таблиц началось с вопроса «где ставить политики
RLS у новых» и закончилось тремя находками в уже существующей схеме. Разбор
целиком — в [docs/DEV-19-schema.md](docs/DEV-19-schema.md), здесь короткая
выжимка, потому что это важнее самих новых таблиц.

**1. Политики стояли на пятнадцати таблицах из ста пятнадцати.** RLS завела
`m7` под контур «Дом». У заявки, пользователя, проводки, организации политик
не было вовсе — при том, что и README, и DEV-02 называют RLS механизмом
изоляции. Вреда не было: арендатор один. Но второй появляется одним `INSERT`,
и хватятся изоляции не тогда, когда он появится, а когда первый увидит чужие
заявки.

**2. Приложение ходило в базу суперпользователем — и это главное.**
`ENABLE ROW LEVEL SECURITY` не действует на владельца таблицы, а `FORCE` не
действует на суперпользователя. Роль `sozo` была и владельцем, и
суперпользователем. То есть изоляция была написана, объявлена в документации
и **не работала ни секунды**, включая те пятнадцать таблиц.

Увидеть это можно было только попыткой прочитать чужую строку. Прежняя
проверка `db:check:rls` проверяла лишь, что контекст живёт внутри транзакции,
— а это зелено и при полном отсутствии политик. Теперь она пишет строки от
двух арендаторов и убеждается, что каждый видит только своё.

**3. Политики требовали контекста, которого приложение не заполняет.** Как
только RLS заработала, посыпались отказы: правила `m7` требуют платформенной
роли или совпадения оператора, а `operatorOrgId` в `main.ts` всегда `null`.
Правило исправлено, а не отключено: арендатор проверяется всегда, оператор —
когда он в контексте назван.

Итог: 115 таблиц, 115 политик, отдельная роль `sozo_app` без суперпользователя
и без `BYPASSRLS`. Прогон e2e идёт под ней — то есть проверяет систему с
работающей изоляцией, а не схему без неё.

### Известные расхождения

- Все тридцать разделов состояния работают на PostgreSQL, когда задан
  `DATABASE_URL`, и на `state.json`, когда не задан. На проде он пока не задан
  — переключение делается скриптом с приёмкой, см. ниже.
- На экране C-51 «Мой дом» **убрана карточка «Что можно»**. Она вела на
  маршруты `/building/report`, `/building/shutdowns` и `/building/pass`,
  которых не существует, и нажатие роняло приложение: во всём остальном
  приложении экраны открываются через `MaterialPageRoute`, таблицы маршрутов
  в `MaterialApp` нет вовсе. Кнопка, которая падает, хуже отсутствующей, а
  заглушку «скоро» этот продукт не ставит. Ближайшие отключения житель и так
  видит выше на том же экране; карточка вернётся вместе с C-52…C-54 и их
  эндпоинтами (`POST` замечания от жителя и выпуск гостевого пропуска — их на
  сервере пока нет).
- Макетов новых экранов нет ни для одного приложения, кроме восьми в
  `design-home/`; дизайн обязан опережать разработку на спринт.
- Один web-разработчик на четыре панели: кабинет — критический путь.
